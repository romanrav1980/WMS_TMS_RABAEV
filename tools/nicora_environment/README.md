# NS00: исполнимое задание подготовки стенда

Автор — Codex. Назначенный независимый проверяющий — Claude Code; его проверка ещё не состоялась. Владелец принимает результат. Основание — NS00 редакции 57, сценарии NS00-TC01–TC03. Постоянные NK-ID назначает NS01.

## Контракт и границы

Модуль: `tools/nicora_environment`, operational tooling платформы; не импортируется API. Вход — неизменённый `execution/fixtures/base.json`, проверенная структура Oracle, закреплённые зависимости. Выход — паспорт, provenance manifest, реальные Oracle/API/UI evidence. Единственный исполнитель seed/reset — локальный CLI, одна Oracle-транзакция на весь набор; внешних вызовов внутри неё нет. Роль запуска — оператор выделенного dev-стенда, подключение RABAEV в ORCL/orcl. Новые схемы и DDL не нужны.

Разрешённые изменения: launcher overrides/strict ports; зависимость httpx и Windows/Python 3.13 lock; scripts подготовки/запуска; tools/nicora_environment; db/fixtures/nicora_ns00; tests/tooling; focused wiki и статусы NS00. API-бизнес-правила и legacy SQL определения не меняются. Перед Oracle-записью фиксируется hash-манифест текущих файлов. GitHub не используется.

## Данные и ожидаемый результат

Ядро DS-BASE материализуется в девяти существующих таблицах: один отдельный тестовый склад 9807, три ячейки, пять SKU, два клиента, одно тестовое входящее основание, две паллеты/остатка и три заказа/строки. Всего 22 строки. Имена DS-BASE-B1/B2, даты партии из base.json; дополнительно зафиксирован исходный запас 50+50 коробок D10, 24 штуки/коробка = 2400 штук. Заказы 40/30/30 коробок соответствуют 960/720/720 штукам. Это ввод начального состояния теста, не приемка товара без SAP.

Паллетные UID внутренние: SSCC не подменяется ими. Грузовое место HU1 из JSON остаётся моделью смешанного состава, не объявляется одной строкой монопаллеты. Клиенты неактивны, заказы DRAFT, ячейки закрыты для внешних операций. Тестовый признак RELEASED — изолированное начальное условие, не результат рабочего контроля качества.

NS00 материализует только основу для диагностики среды. Машины, смешанная загрузка, ставки, HU-состав, режим приёмки магазина, мягкий резерв, будущие профили маркировки и остальные business settings в base/track_trace сохраняются декларативными; их фактическое отображение и исполнение — NS02–NS04 и профильные спринты. Успех NS00 не подтверждает эти функции.

## Проверки до исполнения

TC01: новая venv без system-site-packages, все пакеты из version/hash lock; новый node_modules через npm ci по двум lockfile; typecheck/build; реальные HTTP 200 API/ARM/TSD и /db/ping. Existing RABAEV проходит шесть SQL verification профилей. Разрушительный from-zero Oracle reinstall выделен как незавершённая часть доказательства, не выполняется поверх существующих данных и не заменяется deploy smoke.

TC02: seed, повтор seed без второго эффекта, reset с удалением только явных ключей, повторное создание точно того же набора; cleanup до нуля и reseed. До/после сравниваются SHA256 всех строк активного внешнего запаса и связанных паллет, плюс остальных строк затронутых справочников/заказов/ячеек/входящих оснований. Старые паллеты без остатка не читаются целиком; DML ограничен явными owned UID, активных trigger нет. SQL trace и ограничения выборок сохраняются. Ключи без provenance или изменённые строки не принимаются автоматически. Ссылки извне блокируют reset.

TC03: PATCH действующего API меняет только параметры тестового SKU DS-BASE-D10, факт читается через API и прямо Oracle. Завершаются процессы API/ARM/TSD, подтверждается отсутствие listener, root bat запускают новые PID из подготовленных зависимостей. После restart тот же факт и 2400 штук остаются в Oracle/API. Это перезапуск приложений, не crash/recovery сервера Oracle.

Условия остановки: другой target, collision/потеря provenance, активный неизвестный trigger, внешняя ссылка, несовпадение hash вне fixture, отказ DB/API/build. Авторские проверки и независимая приёмка различаются. Итог сохраняется с фактическими статусами; полный NS00 не закрывается при непроверенной установке Oracle с нуля.
