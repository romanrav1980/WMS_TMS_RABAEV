# Перенос и запуск SNS «График поставок»

## Что нужно

Python 3.9 или новее со стандартным модулем sqlite3. Дополнительные пакеты для сервера не нужны. Скопируйте папку проекта целиком, в том числе `site`, `data`, `server.py`, `start_sns.bat` и файл базы `runtime/schedule.sqlite3`, если нужно перенести сохранённые предложения. Исходные выгрузки SAP не нужны для просмотра уже подготовленных данных. Они остаются конфиденциальными.

База содержит рекомендации пользователей; при переносе проекта без неё сервер создаст пустую базу. Предложения, которые ещё остались только в прежнем браузере, сначала импортируйте, открыв окно графика на прежнем адресе приложения. Перенос localStorage между разными компьютерами или адресами сайта автоматически не выполняется.

## Запуск на Windows

В папке проекта выполните `start_sns.bat` и откройте `http://127.0.0.1:4179/site/`. Сервер работает, пока открыто его окно. Для настройки можно передать параметры в командной строке:

```bat
start_sns.bat --host 127.0.0.1 --port 4180 --db "D:\SNS-data\schedule.sqlite3"
```

Либо без BAT: `python server.py --host 127.0.0.1 --port 4180 --db "D:\SNS-data\schedule.sqlite3"`. Аналогичные настройки доступны через переменные окружения `SNS_HOST`, `SNS_PORT`, `SNS_DB`; параметры командной строки имеют приоритет. Путь базы должен находиться на локальном диске машины сервера, доступном для записи пользователю процесса. Не размещайте рабочую SQLite-базу на сетевой папке.

Для доступа с других компьютеров в доверенной сети можно запустить `python server.py --host 0.0.0.0 --port 4179` и использовать `http://АДРЕС-СЕРВЕРА:4179/site/`; доступность зависит от правил сетевого экрана. В приложении нет входа, ролей, шифрования и разрешения конфликтов одновременного редактирования. Такой доступ подходит только для контролируемой сети; для полноценной многопользовательской эксплуатации нужны отдельные меры доступа и защита от конфликтов.

## Резервная копия и восстановление

Используйте штатный SQLite backup, в том числе пока приложение работает:

```bat
python server.py --backup "D:\SNS-backup\schedule-2026-11-09.sqlite3"
```

Если база расположена отдельно, добавьте `--db "D:\SNS-data\schedule.sqlite3"`. Команда не перезаписывает существующий файл. Для восстановления остановите сервер, сохраните текущую базу отдельно, скопируйте выбранную резервную копию на путь базы и снова запустите сервер. Храните копии с учётом конфиденциальности клиентских данных.

## Перенос базы через интерфейс

В окне «График клиентов» обеих цепей кнопка «Выгрузить все данные XML» скачивает один файл `sns-project-*.xml`. Он включает рекомендации и настройки, все JSON из `data`, исходные Excel и каталоги источников из корня, файлы папок «Данные» и «Протоколы совещаний». Файлы программы, журналы разработки, исторические отчёты, старые резервные копии и временные lock-файлы Office не включаются.

Кнопка «Загрузить все данные XML» после подтверждения заменяет весь рабочий набор. Проверяются версия, обязательные таблицы, размер, JSON, SHA-256 и допустимые имена. Файлы хранятся в таблице SQLite `project_files`; программа читает импортированные таблицы из базы, а следующая выгрузка включает весь импортированный набор исходников. Данные не распаковываются по произвольным путям. Замена файлов, рекомендаций и настроек проходит в одной транзакции. Ошибка откатывает изменения. Перед импортом создаётся SQLite backup в `runtime/backups`; успешный импорт перезагружает страницу, чтобы не оставить старые таблицы в памяти браузера.

Формат XML v2: `sns_project`, внутри `sns_schedule` v1 и `files/file` с именем, размером, SHA-256 и zlib-base64 содержимым. Ограничения: XML до 768 МиБ, один файл до 192 МиБ, суммарные распакованные данные до 640 МиБ. XML v1 по-прежнему принимается и заменяет только рекомендации и настройки; таблицы и исходники остаются прежними. Код: `project_xml.py`, `database_xml.py`, API `/api/database.xml`.

## Проверка сборки 10.11.2026

Готовый установщик — 229851136 байт (около 230 МБ); SHA-256 в `installer/SNS-Setup.sha256.txt`. В составе 35 файлов данных/источников общим объёмом 353312406 байт и 19 рекомендаций из базы работающей установленной копии. Чистая установка и переустановка с изменённой контрольной настройкой прошли: настройка сохранилась, резервная копия создана. Текущая пользовательская база после обновления сравнена с исходной — рекомендации и настройки совпали.

`tools/test_project_transfer.py` проверил полный XML round-trip и повторный round-trip, SHA-256 всех 35 файлов, целостность SQLite, откат при обрезанном XML, неверной контрольной сумме, пути, кодировке и DTD, а также совместимость XML v1. `tools/test_installed_project.py` запущен именно на Python из установленного пакета: GET/POST XML прошли по HTTP, 35 файлов и 19 рекомендаций восстановлены; таблицы после импорта побайтово совпали. Результаты: `reports/project-transfer-check.json`, `reports/installed-project-check.json`.

HTTP-выгрузка полного XML около 294 МБ заняла 22,66 с, импорт — 16,54 с. Локальные GET таблицы операций 6,53 МБ до импорта: 617,2 / 115,6 / 79,8 мс; после импорта: 55,0 / 68,8 / 49,6 мс. Три последовательных запроса в каждом случае, loopback, файловый кеш ОС не очищался, первая выборка включает прогрев. Это не измерение WMS/Oracle и не доказательство ускорения. Открытие графика в браузере — 3,46 с на обычном экране и 3,07 с при ширине 390 px; кнопки доступны. Единственный console error — отсутствующий favicon, ошибок приложения не было.

Решение по SQL: чтение импортированного файла ограничено точным ключом `project_files.name` (PRIMARY KEY); полный обход выполняется только для явной выгрузки. Новые индексы не нужны. SQLite-соединения явно закрываются после запросов, чтобы не удерживать файлы при восстановлении/обновлении. Длительные XML операции обусловлены объёмом исходников и сжатием; они показывают состояние выполнения и не участвуют в обычной загрузке календаря.
