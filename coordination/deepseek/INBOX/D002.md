## Подтверждённые проблемы

В handleSolve ветка job_id после done читает metrics, игнорирует ответ, затем выбирает первый план из истории. Это может показать чужой расчёт. metrics не обязан возвращать массив routes. cancelled продолжает тот же путь поиска истории. EventSource использует относительный URL при отдельном API_BASE и не передаёт Basic Authorization. Ошибки чтения результата скрыты catch best effort. При применении используется текущий filterDate, который может отличаться от даты рассчитанного плана.

## Реализация

1. Прочитай фактические transport routes и контракт jobs. Поддерживай только реально существующие ответы. Прямой VrpPlan показывай из ответа запроса. Для job_id используй точный результат этой задачи через существующий endpoint/stream; не подбирай последний план истории. Если сервер не предоставляет результат — сохрани job_id, покажи честную ошибку и передай Codex точный недостающий контракт.
2. Для потока используй существующий способ аутентификации приложения и правильный API_BASE; не передавай пароль в URL. Закрывай поток и таймер при отмене, смене контекста и размонтировании. Устаревший ответ не заменяет новый расчёт.
3. cancelled не загружает другой план и не показывает успех. Ошибка JSON/соединения выводится сотруднику с доступным следующим действием. Убери пользовательский текст про backend 500/CORS/порт 8088.
4. Зафиксируй дату и параметры принятого расчёта. Применяй план с ними; смена фильтра не меняет payload применения. Не разрешай применение без маршрутов/plan_id или повторное параллельное нажатие.
5. Не меняй payload при повторе неопределённого применения. Используй имеющийся контракт повторного apply по plan_id; не обещай успешный повтор без ответа сервера. Сохрани ручное редактирование маршрутов, если оно поддерживается текущим контрактом.
6. Вынеси добавленную логику из большой функции в небольшой feature-модуль при необходимости; не раздувай архитектурный baseline. Не добавляй зависимости.

## Приёмка по коду; прогоны позже

UI показывает результат своего расчёта; отмена не выбирает план истории; дата применения совпадает с датой расчёта; поток/таймер не остаются после ухода; ошибки не маскируются; пустой план неприменим. RESULT содержит изменённые файлы, ограничения API и список отложенных проверок. Автотесты, Oracle и браузерные прогоны сейчас не запускать.
