# RESULT C0121 — передача CASE между комплектовщиками (UI)

Исполнитель: Claude Code, 16.10.2026 (ночь). Multi-store не делался. C0119/C0120 не запускались. Backend, Oracle, loading/finance/KPI, admin-auth.js, admin-nav.js и React-админку не трогал. Commit/push, субагенты и бизнес-POST не использовались.

## Что сделано

1. **Форма вместо prompt.**
   - Новый `case-handoff-dialog.js`: доступный модальный `<dialog>` в стиле ARM. Esc и «×» закрывают форму, фокус встаёт на первое поле, а во время отправки закрыть её нельзя.
   - Вверху живая карточка текущего исполнителя: исполнитель, ресурс, сессия, техника, паллета, версия содержимого, склад, отобранные строки.
   - Поля формы:
     - «ID ресурса нового комплектовщика»;
     - «ID активной сессии» с явной подписью, что список сессий экран не получает и номер проверит сервер;
     - «ID техники» — необязательно;
     - «Идентификатор паллеты» — любой идентификатор, не только SSCC; обязателен, если на паллете есть отобранный товар;
     - «Причина»;
     - флажок «Паллета физически передана».
   - Enter сканера в поле паллеты переводит фокус к следующему полю, а не отправляет форму.
   - У каждого поля и кнопки есть `title` и `data-help-id` (`case.handoff.*`), рядом ссылка на статическую справку `/help/case-handoff.html`.
   - Перед созданием команды карточка перечитывается. Если исполнитель, сессия или версия изменились, команда не создаётся.
2. **Журнал команды (`case-handoff.js`, переписан на общем `wmsCommandIntent`).**
   - Тело с `offline_event_id` `HANDOFF:<uuid>` и `expected_*` из перечитанной карточки сохраняется до отправки и потом не меняется. Повтор отправляет то же тело с тем же ключом.
   - Рядом хранится отметка доставки `:delivery`.
   - Отказ 403/404/409 на первой отправке считается доказанным исходом: запрос снимается.
   - После неизвестного исхода (потерян ответ, 5xx) отказ 403/409 запрос не снимает. Экран перечитывает карточку:
     - если задание уже у целевого ресурса и сессии, передача засчитывается как доказанная;
     - иначе запрос остаётся, и снять его можно только явным действием: «Снять сохранённый запрос…», флажок проверки, затем «Снять в архив». Запрос переносится в `:resolved:<uuid>`, без молчаливого удаления.
   - Ответ 400/422 — отказ проверки полей, детерминированный, поэтому запрос снимается.
   - При 401 запрос остаётся.
   - Повреждённая запись не затирается: новая передача по заданию заблокирована, доступно только «Сохранить в архив» (`:damaged:<uuid>`).
   - Успех очищает только запрос этого задания.
3. **Старые и новые запросы разделены.**
   - Новые запросы хранятся под ключом `retailcase.caseHandoff:<api>:<user>:<task>`.
   - Старые (legacy, `case.handoff:<api>:<user>:<task>`) не мигрируются и не удаляются. Форма показывает их отдельно с пометкой «Запрос из прежней версии экрана — исход неизвестен» и разбирает раньше новых.
   - Для legacy исход всегда считается неизвестным: повтор тем же телом, 403/409 запрос не удаляет, снятие только явным действием в архив.
   - Прежний код удалял сохранённые запросы при 400/403/404/409/422, поэтому уцелеть могли только записи после 5xx, тайм-аута или неотправки.
4. **Гейты CASE ARM.**
   - Плоский гейт страницы `data-required-permission="case_pick_view"` заменён на `case-access.js`. Экран открывается по плоскому `case_pick_view` или по действующему (ACTIVE) назначению области из `/api/access/me`.
   - При доступе по области показывается плашка «Доступ по назначению области: …». Если доступа нет, данные не загружаются. Если проверка недоступна (5xx или сеть), появляется кнопка «Повторить проверку».
   - Повтор сохранённых решений по недостачам больше не отсекается только плоским `case_pick_short_approve` — решает сервер.
   - Ответ 401/403/404 при загрузке списка очищает прежние строки. Ответ 401/403/404 на карточку в форме показывает отказ без карточки и без формы.
5. **Возврат в контекст.** Выбранное задание хранится в адресе (`task_id`), поэтому перезагрузка и возврат открывают то же задание. Прочие параметры адреса, в том числе склад, сохраняются. После передачи список перечитывается с тем же выбранным заданием.
6. **Справка.** Новая статическая `docs/help/public/case-handoff.html` с разделами `#open`, `#fields`, `#retry`, `#refusal`, `#resolve`, `#access`. Адрес `/help/case-handoff.html` отвечает 200.

## Ограничения и что передать root

- **Вход в админку.** Сам вход по-прежнему требует плоского `PRAVO_ADMIN_LOGIN` (серверный `/api/admin/auth/login`). Пользователь только с назначением по области без этого флага в ARM не войдёт — это вне UI.
- **Навигация.** Ссылку «Комплектация» в `admin-nav.js` показывает плоское право `case_pick_view`, поэтому пользователь с доступом по области откроет экран только по прямой ссылке. Предлагаю root добавить аналогичную проверку назначений; файл не мой, я его не трогал.
- **Список сессий.** API не отдаёт список чужих активных сессий, поэтому ID ресурса и сессии вводятся вручную с подписью. Автовыбора нет.
- **Серверная проверка не повторялась.** Ответ 200 для реальной передачи не проверялся на живом сервере по этому заданию (запрет бизнес-команд). Доказательство исхода после неизвестного ответа опирается на поля `assigned_resource_id` и `resource_session_id` карточки.
- **Чужая проблема на странице.** Кнопка «Повторить сохранённые решения по недостачам», которую добавляет `case-pick-management.js` в начало `main`, наезжает на заголовок страницы. Это было до C0121, я её не правил.
- **Мобильный вид страницы.** Сама страница на 390 px прокручивается горизонтально из-за глобального `body{min-width:1280px}` в общем `styles.css`. Форма передачи от этого не зависит и помещается в экран.
