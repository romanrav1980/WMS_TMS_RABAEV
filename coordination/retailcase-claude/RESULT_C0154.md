# RESULT C-0154 — полный маршрут и решение о дополнительном заезде T09 (Claude)

Статус: **кандидат готов, native NOT_APPLIED.** Checkpoints `693406f8` + ревизия по замечаниям Codex (см. «Ревизия»). T09 целиком не закрыт (границы ниже).

## Источник правила
`wiki-raw/tradecase_source_review_20261021/program.txt`, раздел 12 «Добавление получателя вне основного маршрута»: до предельного времени основной доставки остаётся 30 мин; заезд с обслуживанием 15 мин → **предложить на согласование и показать изменение времени и пробега**; после подтверждения — заказ SAP и новая точка; 45 мин → **отклонить**; при запрете новых точек **не предлагать**. Реализовано как правило «заезд укладывается в остаток» — остаток берётся из пересчёта штатным калькулятором, 15/30/45 нигде не зашиты.

## Полный расчёт (пункт 1)
Писатели всех входов `RRL_TT_ROUTE_SCHEDULE.calculate` уже есть на экране рейса: депо — «Настроить исходные данные маршрута» (warehouse-depots); **момент выезда/конец ресурса** — оценка длительности там же (`route-inputs` → `RRL_TT_ROUTE_API.apply_input` → `RRL_TT_OPERATION_PLAN_API.generate`, создаёт DRIVE/DRIVE_BACK; проверено по live-источнику); плечи — «Обновить дорожные плечи» (root); норма разгрузки/строгость/окна — карточка адреса (root). Новое: в «Плане маршрута» под статусом — **«Что сделать»** по каждой недостающей причине со ссылкой на существующее действие (live-проверено на рейсе 33665). Второй ТМС/норматив не добавлялся. Реальные рейсы сегодня: 33665/33660 — нет депо, выезда, плеч, правил точки; 33564 — нет депо и плеч. Полного реального маршрута нет: дорожные провайдеры недоступны (внешний сбой root).
**Находка:** на примере раздела 10 штатный калькулятор вставляет обязательный перерыв 15 мин после 120 мин непрерывного вождения (политика `REV55_ROUTE_V6_120_15_540`), поэтому магазин 12:55 (а не 12:40) и возврат 14:10 (а не 13:55). Политику не менял — решение за владельцем программы/root.

## Решение о заезде (пункты 2–3)
Новый пакет `RRL_TRADE_EXTRA_STOP_API` (миграция `db/migrations/2026-10-23_trade_extra_stop/`, общие пакеты не меняются):
- `evaluate` (READ ONLY): `RRL_TT_TIME_API.context` (права просмотра) → BEFORE `calculate`; для **каждой позиции вставки** AFTER-источник строят штатные `RRL_TT_ROUTE_SCHEDULE.material` + `RRL_STORE_WINDOW_RULES.material` + правило адреса из RRL_ADDR как в context; вердикт варианта FEASIBLE / VIOLATION (строгое окно, конец ресурса, лимит вождения) / UNKNOWN (любой недостающий вход). Решение: **PROPOSE** (лучшая выполнимая позиция, ранний возврат) / **REJECT** (все варианты полные и нарушают) / **UNKNOWN** (основной маршрут не подтверждён или для точки не хватает данных) / **FORBIDDEN** / ALREADY_ON_ROUTE. Отдаёт остаток до/после, сдвиг возврата, приезды/ожидания/опоздания по точкам, пробег по кэшу расстояний (иначе «нет данных»).
- `command`: APPROVE / DECLINE / SET_POLICY; `transport_dispatch_edit` по всем складам рейса до и после блокировки строки рейса; replay: рейс+автор+hash; **APPROVE заново пересчитывает в той же TX** и требует того же source_hash/версии контекста и PROPOSE с той же позицией; согласованное → `WAITING_SAP_ORDER` (заказ SAP не создаётся — SAP недоступен); журнал append-only; запрет новых точек — версионная настройка рейса.
- `decisions`: решения с признаком CURRENT / STALE_ROUTE_CHANGED (маршрут изменился → нужно новое решение).
Backend: `modules/transport/{contracts_extra_stop.py,infrastructure/extra_stop.py,api/extra_stop_routes.py}` (`GET/POST /api/transport/preflight/trips/{id}/extra-stops`, `GET …/decisions`), экспорт в `modules/transport/public.py`, `app/extra_stop_composition.py` + 2 строки в `app/main.py`. Frontend: `tradecase/ExtraStop.tsx` в карточке рейса (TripRoute), подсказки по причинам в `RoutePlan.tsx`, одна строка кода в `useRead.ts`, справка `public/help/tradecase-documents.html#route`.

## Ревизия по замечаниям Codex (перед RELEASE)
- Private PL/SQL helpers из SQL не вызываются; JSON `get_*`/`to_clob` внутри SQL отсутствуют (DML проверяется тестом; `result_text` вынесен в переменную).
- `evaluate_source` (PURE с контролируемыми плечами) — **private**; `evaluate`/`command` удаляют присланные `extra_rule`/`new_stops_forbidden` и подставляют правило адреса из RRL_ADDR и запрет из таблицы; плечи — только штатный material. Synthetic окна/плечи доступны лишь в read-only проверочном блоке.
- Стоимость (live, `material_cost_live.py`): вариант = 2 material + 1 calculate; 1 точка ≈14–17 мс, крупнейший реальный рейс 5977 (51 точка) ≈320 мс на вариант → полный перебор ≈17 с. Поэтому **все позиции перебираются только до 20 точек**; на длинном маршруте диспетчер указывает позицию (один вариант), иначе UNKNOWN «укажите позицию». Технический предел, не бизнес-норма. Тяжёлых фоновых чтений не запускалось.
- Перепроверено: pytest 11 PASS, PURE live (+ случай позиции 2 → ровно 1 вариант), реальные рейсы, UI 28/28, gate/encoding/tsc PASS.

## Ревизия 2 — обязательное ревью C0154 (checkpoint `7f15288c`)
1. **Access fence:** `command` берёт `RRL_ACCESS_REV` share до строки рейса (как остальные TRADECASE writers); права `transport_dispatch_edit` проверяются до и после обеих блокировок.
2. **Отпечаток предложения:** `proposal_fingerprint` = sha(базовый source_hash + полный AFTER-источник выбранного варианта, собранный штатными material: плечи с временем кэша и признаком свежести, правило и профиль окна добавленного адреса, операции рейса). Экран передаёт отпечаток показанного предложения; APPROVE отклоняет `EXTRA_STOP_PROPOSAL_CHANGED`, если он другой. Колонка `PROPOSAL_FINGERPRINT` обязательна для APPROVE (CHECK). Список решений: смена базы → STALE_ROUTE_CHANGED; для новейшего согласования каждого адреса (не более 5, один вариант) отпечаток пересчитывается → STALE_INPUTS_CHANGED; более ранние → «заменено». Live read-only: отпечаток стабилен при тех же входах и меняется при смене нормы добавленного адреса.
3. **Согласованные входы:** перед окончательной оценкой APPROVE вызывает штатный `RRL_TT_ROUTE_SCHEDULE.lock_material` на AFTER-источник (RRL_ADDR всех адресов, включая новый, и все плечи FOR UPDATE), затем оценивает ещё раз в той же TX — смешанные до/после невозможны. NULL позиции или отпечатка в APPROVE — явный отказ натива.
4. **Одно действующее согласование:** под блокировкой рейса — `EXTRA_STOP_ALREADY_APPROVED`, если последнее решение по адресу — согласование на той же базе и с тем же отпечатком; новое согласование возможно только при новом основании.
Проверки: pytest 13 PASS; PURE + evaluate_internal выполнены read-only блоком на живой БД (пример программы, реальные рейсы, отпечаток); UI 28/28 (APPROVE несёт отпечаток); gate/encoding/tsc PASS. `command`/`decisions` (новые таблицы, `lock_material` FOR UPDATE) в моей среде не компилировались — их проверяет root при apply.
