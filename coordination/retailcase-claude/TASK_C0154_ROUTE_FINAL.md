## Законченный результат
1. Устрани оставшиеся настоящие блокеры полного расчёта рейса с исходными окнами и нормами, используя существующие RRL_TT_TIME_API / RRL_TT_ROUTE_SCHEDULE / operation plan. Не создавай вторую ТМС. Проверь, как диспетчер задаёт отсутствующие плановые операции/момент выезда, и доведи существующий путь/экран, если писатель уже есть. Не заменять проверку времени выдуманными нормативами.
2. Реализуй решение о новом заезде из раздела12 программы (примеры15/45мин), с источником правил из самой программы. Сначала прочитай точный текст, не назначай15мин универсальным лимитом. Сравнение до/после должно использовать реальный полный маршрут/окна, свежие дорожные плечи и текущий состав. Неизвестные входы запрещают обещать выполнимость. Согласование — существующий native approval/журнал или узкое дополнение с правами/версией/source hash/operation_id; изменение маршрута после согласования требует нового решения.
3. Экран должен объяснять сотруднику причину, показывать изменившиеся точки/приезд/ожидание/опоздание/возврат и давать штатные действия без технических кодов вне раскрываемых сведений. Сохранить scope/скрытие владельцев, журнал неизвестного результата, подсказки и локальную справку. 390/1440.
4. Если нужен DDL — отдельная versioned миграция, свежие before SHA, rollback/verify; native apply только root после ревью. Модульные границы не расширять baseline, shared функции не раздувать. Модель вместимости/резервов не менять без подтверждённой необходимости T09.
