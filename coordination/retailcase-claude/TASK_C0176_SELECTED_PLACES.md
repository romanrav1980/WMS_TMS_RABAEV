# C0176 — снять выбранные физические места, сохранив сборку

C0175 RELEASE K0178 прочитан. Root проверяет и применяет твой комплект единиц заказа; не меняй эти файлы далее без сообщения. Тебе следующее крупное независимое задание по T08: рабочее выборочное снятие части мест одной сборки с рейса, с правами, повтором и понятным UI.

## Сценарий и факты

Root-набор210069361: приняты1100BOX/11000EA, основные200A+150A+250B и добивка60A отобраны660отдельными физическими коробами по10EA. Рейс33698 содержит четыре ST_NUMBER: P210069361101(200),102(150),103(250),104(60). Все60мест добивки в одномST_NUMBER. Нужно снять20мест добивки, оставить40того же заказа/получателя в этом рейсе и остальные20 в экспедиции с теми же адресами, кодами, собственником и резервом. Не делим паллету на разных получателей. Изменение stock/reserve не требуется для одного снятия; выезд потом проверит root.

Проверенные функции целиком снимают/переносят ST_NUMBER. Не переименовывай ST_NUMBER SQL ради теста. Вероятно достаточно выборочно снять фактические RRL_SBORKA_PALLETS.ID, оставив номер сборки; проверь, что чтения и LOAD/TRIP допускают смешанное назначение одного номера. Если это несовместимо, предъяви факты и минимальный вариант решения, не маскируй ошибку.

Существующий единый writer: FUNCTION RRL_TT_ADD_PALL(TT_ID int,ST_NUMBER1 varchar2). Root только что применил grouped-st-assignment9/9/9: одна сборка теперь до1000мест. RRL_TT_MEMBERSHIP_CTX_API accessible by(function RRL_TT_ADD_PALL), trigger запретит обход. Две прямые зависимости функции — RRL_TRANSPORT_PLAN_API BODY и RRL_ST_DEFER_API BODY. Сохрани границы1000/пачкуномеров200 и старые2аргумента.

## Возможное минимальное решение, проверить до реализации

Расширить общий writer необязательным третьим p_member_id default null: прежние2аргумента продолжают целую сборку, выбранное ID разрешено только для TT_ID=0 (снятие), discovery/snapshot фильтруются тем же ID. Старые блокировки TT→member, shipped/loaded/billing/snapshot и контекст неизменны. Новый native command снимает список до200ID одной сборки в одной транзакции через writer, хранит operation_id/actor/request_hash/result и проверяет ожидаемый состав. Это предложение, не требование добавлять избыточный каркас.

На сервере: действующий actor, актуальные warehouse transport_dispatch_edit и owner-operate для торговых мест, проверки до cached reply; целевой рейс/сборка/selectedIDs/current membership; запрет снятия LOADED/DEPARTED/выставленного счёта. Не снимать ещё один рейс при смене назначения. Точный повтор после неизвестного исхода — прежний результат, payload/actor конфликт — отказ, общий rollback без частичного снятия. Операция не меняет получателя, исходный заказ, UID, коды, остаток, резерв или адрес. Проверь две конкурирующие команды и отзыв прав.
