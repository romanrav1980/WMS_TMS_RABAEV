# RESULT C-0145 — T09: маршрут рейса и обеспеченность заказов

Обращение 3 из 3 (22.10). ACK K-0097, RELEASE K-0098. Это срез T09, а не весь T09: ограничения ниже.

## Что сделано

**Маршрут — источник существующий нативный:** `GET /api/transport/preflight/trips/{native_task_id}/route-context`. Он читается правами самого пользователя (`transport_dispatch_edit`); новых чтений в обход не добавлено.
- Номер рейса склада берётся из привязки (исполнение рейса). Нет привязки — «маршрут неизвестен», запрос не отправляется.
- Показываются точки в порядке `route_ordinal` текущего транспортного основания: адрес, окно доставки, документ.
- Прямо сказано, что это план, а не исполненный маршрут; что адрес склада отправления не настроен; что время в пути не рассчитано (`route_status NO_INPUT`, `route_duration_verified=false`).
- Карта без координат не строится.
- Сопоставление точки с получателем СНС/BLC источником не подтверждено, и экран это указывает.

**Обеспеченность — новый bounded READ ONLY read model:** `GET /api/tradecase/warehouses/{w}/trips/{trip}/coverage` (`integrations/infrastructure/trade_route.py`).
- Одна транзакция `set transaction read only`: один снимок Oracle, версии не смешиваются.
- `tradecase_view` склада; право на собственника строки — до любых агрегатов. Скрытые строки исключаются и не раскрываются числами: `unattributed_loads` при скрытой части не возвращается.

| Величина | Источник |
|---|---|
| Заказано | текущие TRIP/ORDER, базовые штуки (BOX × units_per_box) |
| Резерв сейчас, собрано, не обеспечено | нативный `RRL_STOCK_POOL_READ.line_snapshot_json(CUSTOMER_ORDER_ROW_ID)` по строке, привязанной через RRL_TRADE_ORDER_LINK/LINE (признак актуальной версии привязки) |
| Погружено, не выехало / выехало / передано получателю | RRL_TT_HU_LOAD_FACT привязанного рейса склада: CASE (`ROOT_CASE_TASK_ID` → RRL_CASE_PICK_LINE → RRL_PICK_PLAN_LINE → строка заказа) или целая паллета (`ROOT_UID` → RRL_PICK_TASK FULL_PALLET DONE); UNLOADED не считается |

- Погрузки, не отнесённые ни к одной строке, считаются отдельно.
- Неизвестное — `null`, а не 0:
  - строка не передана на склад;
  - ошибка нативного снимка по одной строке (`native_error`, остальные строки читаются);
  - рейс не привязан.
- Отменённый заказ показывается с отметкой, а не теряется.

## Ограничения / до полного T09

1. **Связь точки маршрута с получателем.** Точки нативного основания (адрес, документ ST) не связаны с получателем и заказом СНС/BLC подтверждённым ключом. Нужен контракт: например, `wms_customer_id` получателя → RRL_CUSTOMER_ADDRESS → адрес точки, либо явная ссылка ST → торговый заказ.
2. **Нет данных маршрута.** Адрес и координаты склада отправления не настроены, длительности плеч не подтверждены. Сценарии с окнами 11:00/11:55/12:40, возвратом 13:55, заездом вне маршрута (15/45 мин) и запретом новых точек не реализованы.
3. **Вложенный состав погрузки.** Погрузка контейнера со вложенными CASE учитывается как «не отнесённая к строке»; разбор `COMPOSITION_JSON` по узлам — следующий шаг.
4. **Единицы.** «Собрано» — по нативному снимку строки (pick-задания); поле CASE `PICKED_QTY` используется только для погрузки. Единицы этих полей приняты как базовые по существующему коду; Codex стоит сверить на dev.
5. **Не реализовано:** заказ SAP, сорт добивки, отправка в СКМ. Выкатить `/coverage` на :8088 (перезапуск сервера) и проверить живым HTTP; проверить пороги производительности на крупном рейсе (до 200 строк, 1 вызов снимка на строку).
6. **Wiki:** правки `wiki/index` / `wiki/log` и `wiki/components/tradecase_route_coverage_*` не делал — передаю Codex.
