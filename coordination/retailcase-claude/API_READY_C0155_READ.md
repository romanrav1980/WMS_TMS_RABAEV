## Готовый настоящий API

- `GET /api/warehouse-tasks?ware_id=<id>&assigned_to=<login>&limit=100` — прежняя scoped очередь, предел500; для UI/печати выбирай ограниченный набор, не весь склад.
- `GET /api/warehouse-tasks/{task_id}` — прежний scoped detail, содержит `task_signature` (64uppercaseHEX), `qty_exact`/`fact_qty_exact` (точные строки). Добавлены `from_warehouse_name`, `to_warehouse_name`, `assigned_to_name` в том же READ ONLY снимке; при пустом имени используй существующий идентификатор.
- `GET /api/warehouse-tasks/{task_id}/paper?expected_signature=<необязательно>` — новый READ ONLY снимок `{task,reference,barcode_svg,prepared_at}`. `task` — тот же detail. `reference` строго `WTASK:<task_id>:<64uppercaseHEX>`; `barcode_svg` — Code128 B по этому payload. Дополнительного номера/таблицы бумажных документов нет. Параметр `expected_signature` возвращает409 `PAPER_TASK_CHANGED`, если выбранная версия уже изменилась;403/404 скрывают недоступное задание. Подготовка бланка не назначает и не исполняет задание.

## Исполнение: готовый обычный путь и ограничения

`POST /api/warehouse-tasks/{task_id}/complete` уже принимает `WarehouseTaskStatusRequest`: обязательно передавай новый сохранённый `operation_id`, **подпись именно бумажного снимка** в `expected_task_signature`, `fact_qty` точной строкой, необходимые `scanned_pallet`, `scanned_from_cell`, `scanned_to_cell`, `scanned_to_slot_code`, `unit_keys`/`scan_draft_id`, существующие resource/session поля. Не отправляй весь объект task как тело команды. Квитанция `{status:"ok",result:{operation_id,task_id,...}}`; сохраняй исходное тело до ответа и точного повтора. Не подменять подпись бумажного снимка свежей при его устаревании.

Обычный `TASK_COMPLETE` проверяет ожидаемую подпись при compile, затем исходный снимок после блокировок. Подпись включает количество, паллету/ячейки, склады/слот, документ, статус, назначенного сотрудника и resource/session/equipment. Изменение/переназначение/отмена не должны тихо превращать старый лист в новое задание. Native допускает обычный complete из PLANNED/ASSIGNED/IN_PROGRESS; для выдачи сотруднику используй существующее назначение. Печать не должна вызывать START: это отдельный факт, а изменение статуса меняет подпись.

**Root ещё принимает ожидаемую подпись в HU_TASK_COMPLETE и в ветке CASE_CARRIER_MOVE через physical_task_id.** В них есть свои frozen-композиции и текущие права, но не объявляй новую бумажную сверку принятой до отдельного native readiness. Не создавай parallel ledger и не обходи generic complete ради этих веток. CASE picking имеет собственные контракты/версии/коды: сначала назови использованный текущий путь, не выдумывай один generic write на все виды задания.
