# C-0166 — маркированная инвентаризация: недостача и находка той же единицы, T11 (Claude)

Native-комплект **NOT_APPLIED**: применение, живые HTTP/Oracle/SQL-сценарии и cleanup выполняет root. T11 этим не закрывается. Реальный обмен с СКМ/SAP о недостаче и находке не выполняется.

## Источники и пробел (READ ONLY: USER_SOURCE, схема)
- **Недостача.** INVENTORY_COUNT delta<0 → `RRL_STOCK_UNIT_CORE.issue_free_units` → STOCK_STATUS='ISSUED'. Так же выглядит отгрузка; журнала «операция → единица» для инвентаризации не было.
- **Находка была невозможна:**
  - INVENTORY_COUNT delta>0 для маркированного артикула → `MARKED_INVENTORY_INCREASE_REQUIRES_CAPTURED_UNITS` (root подтвердил на ревизии 418: 20→21 отклонено);
  - INVENTORY_REGISTER_LOT → `ReceivingMarks`: «Unique unit code has already been received» (PK `RRL_WMS_RECEIPT_CODE`);
  - `resolve_count_codes`: скан найденного кода разрешался в ISSUED-единицу той же паллеты, затем «Scanned unit is no longer present».
- **Образец** — interware shortage/recovery (`RRL_INTERWARE_SHORTAGE_UNIT` и `RECOVERY_UNIT`). Запись единиц возможна только через UNIT_CORE: триггер `RRL_STOCK_UNIT_GUARD` и accessible-by `RRL_STOCK_CTX_API`. Границы подтверждены Codex (K-0151, K-0152).

## Решение — тот же писатель INVENTORY_COUNT, без второго writer и без новой единицы
- **Native** `db/migrations/2026-10-23_inventory_found_units/`:
  - журналы `RRL_INVENTORY_LOSS_UNIT` (единица, операция и ревизия недостачи, паллета, ячейка, UNIT_VERSION после выбытия) и `RRL_INVENTORY_FOUND_UNIT` (одно восстановление на один случай недостачи). Append-only; потеря, находка и новая потеря — отдельные случаи; две открытые недостачи одной единицы запрещены (`INVENTORY_LOSS_ALREADY_OPEN`);
  - `RRL_STOCK_INVENTORY_CMD`:
    - delta<0 → выбывшие ключи пишутся в журнал;
    - delta>0 с `found_unit_keys` → проверки, затем восстановление и запись находки. Проверки: тот же склад; operate текущего собственника каждого ключа через `RRL_TRADE_STOCK_GUARD.assert_owner` (отказ без trade-атрибутов, в том числе при остатке 0); недостача и находка одной паллеты — отдельно;
    - план блокирует UNIT-ключи найденных единиц;
    - в факт добавлены `lost_units` и `found_units`;
  - `RRL_STOCK_UNIT_CORE.restore_inventory_loss` пропускает только:
    - текущую операцию INVENTORY_COUNT в статусе IN_FLIGHT;
    - единицы этой паллеты и ячейки в статусе ISSUED, без резерва, с открытой недостачей и тем же UNIT_VERSION;
    - при сумме BASE_QTY, равной дельте, и при совпадении живого состава с остатком.
    Единица возвращается в AVAILABLE; ключ, код, собственник, МРЦ и годность не меняются.
  - Отгруженная или иначе выбывшая единица недостачи не имеет и остаётся ISSUED (`INVENTORY_FOUND_LOSS_REQUIRED`); изменённая после недостачи — `INVENTORY_FOUND_UNIT_CHANGED_SINCE_LOSS`.
- **Python:**
  - `resolve_count_codes(..., found)` направляет скан ISSUED-единицы с открытой недостачей в `found_unit_keys`; всё остальное отклоняется, как раньше. Полностью утерянная партия (остаток 0) тоже может вернуть найденные единицы. До apply — явный отказ «not installed», а не 500;
  - `InventoryObservations.count` добавляет `found_unit_keys` только в серверный `counts`. `requested_counts` (сравнение при повторе) и HTTP-контракт (`CountLine extra=forbid`) не менялись: старые команды повторяются байт в байт;
  - чтение партий: `lost_codes` — коды незакрытых недостач по партии (до 50) в той же READ ONLY транзакции после проверки собственника; до apply — пусто.
- **UI** `wiki-raw/wms_admin_ui_reference/inventory-count.{html,js}`:
  - у партии строка «Не найдены ранее (N): коды», в подсказке — как закрыть: отсканировать найденный код и увеличить количество;
  - итог проводки: «не найдено N ед.» и «найдено N ед., возвращены в остаток»;
  - справка: что нельзя вернуть и что недостачу и находку проводят отдельно;
  - повтор, 403 и неизвестный исход — прежний контракт.
- Изменён тест root `test_inventory_task_scoped_boundary.py` (освобождён): поддельный курсор отвечает на новый запрос, ожидается `lost_codes=[]`.

## Сценарий для root после apply
Root ведёт его своим `live_inventory_loss_found.py` на ревизии 418.
1. Недостача одной единицы: `lost_units=1`, строка в журнале недостач, единица ISSUED, атрибуты не изменились.
2. Повтор той же команды — одна операция.
3. Находка тем же кодом: `found_units=1`, единица AVAILABLE, тот же ключ, код, собственник, МРЦ и годность.
4. Повторная недостача той же единицы — новый случай.
5. Вся партия из 20 до нуля, затем восстановление при отозванном праве собственника → 403.
6. Чужой код или SHIPPED без недостачи → отказ.
7. Конфликт тела под прежним operation_id → 409.
8. Uncaptured 20→21 остаётся отклонённым.
9. Cleanup до 250/H0.

## Ограничения
- Единицы, выбывшие до apply, журнала не имеют и не восстанавливаются этим путём.

- Физический сканер и бумажный режим не проверялись.
