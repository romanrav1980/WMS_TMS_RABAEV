# C0163 — состав кодов частями, T02

Запрос25 зарегистрирован. Начни после исправлений C0161 и RELEASE C0162. Прочитай AGENTS/wiki/index и focused integration pages; используй nicora-api-integrations. Сначала ACK точных путей. Root принимает native/API/Oracle; ты готовишь цельный NOT_APPLIED комплект и backend/UI.

## Основание

Программа revision27, wiki-raw/tradecase_source_review_20261021/program.txt, раздел «Данные пришли не полностью или в неверном порядке»: задержанная/повторённая часть, раннее завершение, старая версия после исправленной; не считать весь состав переданным до сверки. Источник не задаёт реальный SAP wire-format: собственный additive API не объявлять промышленным SAP-протоколом.

Root прочитал contracts_tradecase.py: SUPPLY содержит полный список codes1..10000 и прежнюю версионную оболочку. Уже есть durable deferred messages/worker для отсутствующих справочников; не создавать второй движок доставки и второй товарный writer. Сначала проверь реальные receive/retry/package callers: возможно, часть механизма существует. Применяй первый работающий вариант по Ponytail/YAGNI.

## Результат

Добавь минимальную передачу входящего состава SUPPLY частями поверх действующего приёма полного документа. Записывай части и признак завершения долговечно; показывай конкретные недостающие части/несовпадение состава. Завершение до последней части не создаёт принятую SUPPLY/товар. Последняя часть после завершения передаёт тот же канонический документ ровно один раз через существующий приём, с восстановлением после потери ответа/перезапуска. Полные прежние сообщения сохраняют поведение.

Контракт частей явно связывает source/warehouse/document/version/transfer и последовательность/полноту. Выбери минимальные поля для проверки полноты и неизменности по текущим контрактам; не выдумывай внешний SAP формат. Конфликт тела прежнего идентификатора — отказ, точный повтор — прежняя квитанция; текущие права проверяются и для чтения/повторов. Поздняя старая часть не меняет результат новой версии. Ограничь части/общий состав существующим пределом10000. Не пиши коды физического прихода напрямую. Запиши, какие исходящие подтверждения состава/раннее закрытие сборки этим инкрементом ещё не покрываются.

Подготовь краткое решение в ACK, затем реализуй без вопроса владельцу. Если канонический receive фиксирует транзакцию отдельно, обеспечь durable recovery стабильным event_id/каноническим hash. Не держи транзакцию в ожидании внешней системы. Не добавляй универсальную платформу обмена.
