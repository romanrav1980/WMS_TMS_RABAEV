# C-0176 — снять выбранные физические места сборки с рейса

## Факты
- Действующие writer и функции снимают или переносят только целую сборку (ST_NUMBER).
- LOAD проверяет назначение каждой строки RRL_SBORKA_PALLETS своего места, а не всего номера, поэтому смешанное назначение одного ST_NUMBER с LOAD совместимо. TRANSPORT_CORE.validate_members считает только строки на рейсе.
- Свой фиксированный прогон (склад 243193085, рейс 33699, 4 места одной сборки) прочитал места и флаги через новое API.

## Сделано
- Native NOT_APPLIED `db/migrations/2026-10-27_tt_selected_places/` (README там же):
  - writer с необязательным ID места только для снятия;
  - команда RRL_TT_PLACE_REMOVAL_API (версия состава source_hash, права до квитанции под RRL_ACCESS_REV, повтор после блокировки рейса, журнал, конфликт на другом рейсе без частичного снятия);
  - откат при пустом журнале;
  - синтаксис чистый: только ожидаемые до apply семантические ошибки — нет таблицы, нет 3-аргументного writer, accessible-by.
- API (модуль transport):
  - `GET /api/transport/trips/{trip}/sts/{st}/places`;
  - `POST /api/transport/trips/{trip}/place-removals` (строгие целые ID, ≤200, уникальные);
  - для команды 403 и OPERATION_CONFLICT дают `outcome_confirmed=false` (прежний потерянный запрос мог выполниться), 503 — повтор того же operation_id.
- UI `admin/wms_admin_frontend/src/features/transport/TransportStPlaceRemoval.tsx` в панели «Паллеты СТ» обеих вкладок диспетчера:
  - список мест, выбор и количество, основание, подтверждение, help id на кнопках;
  - команда сохраняется до отправки и повторяется точно;
  - 403 очищает список, а команду сохраняет; конфликт операции не подтверждает отказ;
  - поздний ответ игнорируется.
  - Подключение без роста файла TransportDispatchPage (gate PASS).
