# C-0177 (T10) — двойное назначение сотрудника и техники при параллельном открытии сеанса

Источник: T10 BP15/18 — «двойное назначение сотрудника». Общие ворота, интервалы и визиты уже приняты (C0158, C0150, 23.10).
Сценарий: `POST /api/resources/sessions/login`, параллельные запросы. Проверка: ASGI in-process (текущий код) + реальный Oracle, свой отсутствующий склад.

| Случай | До (склад 242835552) | После (склад 242237740) |
|---|---|---|
| один оператор на два ресурса | 200 + 500 (ORA-00001) | 200 + 409 `OPERATOR_ALREADY_IN_SESSION` |
| два оператора на один ресурс | 200 + 500 | 200 + 409 `RESOURCE_ALREADY_IN_SESSION` |
| два оператора на одну технику | 200 + 500 | 200 + 409 `EQUIPMENT_ALREADY_IN_SESSION` |
| точный повтор одновременно | 500 + 200 | 200 + 200, один SESSION_ID 112 |
| повтор после потерянного ответа | 500 | 200, тот же SESSION_ID 112 |
| смена ричтрака, лимит 1, два водителя | 409 + 200 | 200 + 409 `REACH_SHIFT_DRIVER_CAPACITY_REACHED` |

Во всех случаях открыт ровно 1 сеанс. 409 возвращается с `outcome_confirmed: true`, частичных изменений нет.

Правка: `api/wms_api_server/app/modules/resources/infrastructure/session_lifecycle.py` (без native/миграции):
- проверка точного повтора идёт сразу после блокировки смены и до проверки лимита, иначе севший водитель получил бы отказ по лимиту;
- ORA-00001 от индексов U1/U2/U3 даёт 409 с кодом;
- одинаковый конкурирующий запрос возвращает сеанс победителя;
- прочие ошибки БД не маскируются.

Тесты:
- `tests/tradecase/test_session_competition.py`: 8 passed;
- живой прогон `tests/tradecase/live_session_competition.py {before|after}`;
- quality gate PASS, encoding PASS, architecture PASS (cycles 0);
- tests/tradecase: 372 passed, 1 error окружения (PermissionError на `%TEMP%\pytest-of-roma` в test_api_audit_concurrency — tmp_path, не связано).

Задержки:
- максимум HTTP login 614 мс (до правки 459 мс);
- это проигравший в гонке ждёт `FOR UPDATE` строки смены, пока победитель держит транзакцию; это ожидаемая сериализация, не медленный SQL;
- одиночные вызовы быстрее 400 мс.

Очистка: склады 242835552, 247107957 (отладочный прогон с ошибкой bind ORA-01745, исправлено), 245495666 (прогон с трассировкой) и 242237740. На каждом проверено read-only: 0 открытых сеансов, 0 активных ресурсов, 0 живых операторов TC03QA, объект доступа неактивен.

Остатки:
- Поломка ворот: писателя `DOCK_IS_BLOCKED` нет, это новый механизм, не реализован.
- Право `resource_session_manage` глобальное, без области склада: актор с правом может открыть сеанс на любом складе. Это не менялось и требует решения владельца.
- UI этот вызов напрямую не использует, проверки экрана нет.
