# C0117 — обзор восстановления недостач у старшего смены

Поручение владельца16.10: прочитать результат Claude и разделить следующую работу. C0116 RELEASE принят и интегрирован; его не переделывать. Новый пакет можно выполнять по текущим API, без ожидания межскладской CASE и SHIPPING_GROSS.

## Разделение

**Claude:** один законченный UI сценарий: старший смены выбирает склад, видит недостачи и этап восстановления, открывает связанную волну/существующий экран разбора, возвращается к контексту. Типизированный источник вместо `Record<string, unknown>`, компактный список/карточка в существующем стиле двойника. У директора сохранить честный обзор разрешённых складов, не выдавать его за один выбранный склад.

**Codex:** CASE-aware interWARE: перенос закрытой CASE внутри смешанной матрёшки с сохранением происхождения, ST/fulfillment, тары и однократного количества. Затем отдельный handover поддерева магазину. Серверные scope guards и оставшаяся матрица manager/driver/dispatcher/finance также у Codex. Backend/Oracle/apply, общие контракты и сквозная интеграция не переходят Claude.

## Готовый контракт и его ограничения

GET `/api/inventory/recovery-shorts?ware_id=<positive-id>&limit=50` — JSON array, максимум50 строк. Права `case_pick_view`, actor из RUSERS identity, native фильтр actualWARE до limit в READ ONLY снимке. Для сменного обзора всегда передавать выбранный склад; без выбора не запрашивать. Подробный источник: `app/modules/inventory/infrastructure/recovery_reads.py`, `RECOVERY_PROJECTION`; HTTP граница `api/recovery_routes.py`.

Важно: это **не** контракт из прежнего K-0063 во всех деталях. Нет `has_more`/cursor/total: показывать «показано N, выборка до50», при50 полнота неизвестна. Без `ware_id` сервер читает все разрешённые склады; не возвращает ошибку множественного склада. Неизвестный/недоступный склад сейчас403, не обещать404. Неверный параметр422. Даты naive, `time_status` нет. Не дописывать Z, не пересчитывать браузером пояс, не выдавать локальные часы за UTC/плановое окно. `remaining_seconds` — серверное относительное значение снимка, если показываешь, подписать его как таковое; не превращать в живой SLA/KPI. На данном шаге дорабатывать сервер для этих ограничений не требуется.

Поля строки (nullable значения обрабатывать явно):

- Числовые ID: `short_id`, `case_pick_task_id`, `case_pick_line_id`, `pick_wave_id`, `warehouse_id`; nullable `inventory_task_id`, `replenish_task_id`, `warehouse_task_id`.
- Строки состояния/контекста: `status`, `recovery_state`, `cell`, `article`, `picker`, `inventory_status`, `auditor`, `count_operation_id`, `replenish_status`, `wait_reason`, `recovery_last_error`; часть nullable.
- Десятичные количества **строками**: `short_quantity`, `restored_quantity`, `order_remaining_quantity`. Не суммировать разные SKU/единицы в общий объём, не считать коробками без основания.
- `age_seconds`, `remaining_seconds` — числа; `recovery_deadline_at`, `restored_at` — nullable legacy строки даты без подтверждённого пояса.

Неизвестный код состояния показать с пометкой, не трактовать как DONE. Пустой массив, источник ещё не прочитан и отказ доступа — разные состояния. При401/403/404 скрыть старые данные; смена склада/пользователя не должна показывать прошлую выборку. При5xx прежний снимок можно оставить только явно устаревшим, без вывода «проблем нет». Не вводить polling/автоматические товарные команды.
