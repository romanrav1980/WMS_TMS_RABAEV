## Что сделано в `page=tradecase`

### 1. Вкладка «Выкупы»

- **Список** с курсором (`after`) и флажком «только без ответа СКМ» (`pending_only`, хранится в адресе `tc_pending`).
- **Колонки:** основание и строка, товар, «собственник → новый», момент выкупа, коды «подтверждено / ожидает / отклонено», состояние.
- **Состояние без обещаний:** «ответ СКМ не получен» — не «отправлено».
- **Колонка «Разделение»** показывает «в карточке»: в списке `composition_checked=false`.
- **Карточка — всегда свежий DETAIL:**
  - коды запрошено / подтверждено / ожидает / отклонено;
  - «ответ ещё не получен; запрос в очереди склада не означает отправку провайдеру»;
  - «Разделение паллеты: нужно / не нужно / не проверено».
- **Коды выкупа** — таблица по курсору: паллета, адрес, ответ СКМ, причина, удержание.
- **После любой команды или повтора** открывается свежий DETAIL созданного выкупа.

### 2. Создание выкупа по финансовому основанию

Финансовое основание — это ORDER с `order_kind=BUYOUT`: вида BUYOUT в API нет, вкладка «Заказы» подписывает его «финансовое основание выкупа».

- **Строка:** в карточке документа выбирается строка.
- **Скан паллеты:** скан идентификатора паллеты (Enter или «Прочитать коды») читает **все** страницы `/stock?pallet_identifier=` по курсору.
- **Подходящие коды:** тот же товар, МРЦ и собственник-источник, `mark_state=VALID`. Набор — первые N по ключу из текущего запаса; ключи видны только в технических сведениях.
- **Итог перед отправкой:** число кодов, собственник → новый, паллета, адрес, основание и версия.
- **Ограничения выбора:**
  - только `BEFORE_PICK`; `AFTER_PICK`/`IN_TRANSIT` показаны как «пока недоступен»;
  - строки в коробах не поддерживаются;
  - финансовое основание не меняется, кнопки подтверждения от имени СКМ нет.

### 3. Вкладка «Разделение» (`POST /stock/sort`, подключено по API_READY_C0136)

- **Поля:** исходная паллета, исходная и целевая ячейки, профиль CRPT/TOBACCO (единственный в QA).
- **Сканы:** по Enter или «Добавить»; повтор отклоняется; есть «Убрать последний»; счётчик принятых сканов.
- **Явное подтверждение:** «Подтверждаю перенос N кодов с паллеты X в ячейку Y».
- **Результат — `response.uid`:** «внутренний идентификатор, не новая SSCC; регуляторная агрегация: ожидает подтверждения; этикетка не напечатана; следующий шаг — оформить этикетку и агрегацию отдельно».
- **После любого успеха форма очищается:** и после первой отправки, и после повтора.

### 4. Общий журнал команд и неизвестный исход

- **`intent.ts`** — общий журнал команд для bind, buyout и sort.
  - Ключ: API + пользователь + склад.
  - Тело и `operation_id` сохраняются **до** POST.
  - Повреждённая запись или недоступное хранилище блокируют отправку.
  - `bindIntent.ts` переведён на этот журнал, ключ и правила Codex (паллета ≤50, недоступный localStorage) сохранены.
- **`useCommand.ts`:**
  - синхронная блокировка двойного клика;
  - неизвестный исход (сеть/5xx) блокирует изменения, повтор — тем же телом;
  - подтверждённый 409/422/403 на первой отправке снимает команду с понятной причиной;
  - 403 после неизвестной отправки и `OPERATION_CONFLICT`/`OPERATION_CONTENT_CONFLICT` команду **сохраняют**: новая вместо неизвестной не создаётся.

## Ревью SQL `db/migrations/2026-10-19_tradecase_sorting/001–004` (только чтение)

1. **[Средне] Повтор зависит от изменяемого состояния.** `003_posting.sql:49` вызывает `assert_scope` до поиска сохранённой операции (`:82`).
   - Что проверяет `assert_scope` (`001:14-25`): ячейки этого склада, `RRL_TRADE_SITE.ENABLED=1`, право `tradecase_stock_sort` и `assert_owner` по **текущим** владельцам кодов.
   - Чем грозит: если после разделения выкуп подтвердит смену SNS→BLC, точный повтор той же операции оператором без права BLC получит 403. Выключенная площадка даст отказ вместо сохранённого результата. UI в этом случае честно держит команду, но разрешить её некем.
   - Рекомендация: при повторе проверять только автора и право, изменяемые проверки пропускать.
2. **[Средне] Пустота целевой ячейки не проверяется guard'ом.** `assert_selection` проверяет только зону (`001:44`). `execute_move` проверяет `CELL_NOT_EMPTY` лишь при `OTBOR=0 and IS_SYSTEM=0` (`002`, блок перед весовым лимитом). Если ячейки SORT/WAIT системные или отборочные, разделение уйдёт в непустую ячейку. Требование «target empty» стоит проверить явно в `assert_selection`.
3. **[Средне/производительность] Глобальная блокировка для всех внутренних перемещений.** `003_posting.sql:217` добавляет `INTERNAL_MOVE` в список видов, берущих глобальную блокировку таблицы доступа (`lock table RRL_ACCES…`). Это касается **всех** внутренних перемещений, а не только разделения: обычные перемещения выстраиваются в очередь с изменениями прав. Рекомендация: условие по `is_sort`.
4. **[Низко, защита в глубину] Флаг разделения берётся из запроса.** `is_sort` (`001:9-12`) доверяет `metadata.tradecase_sorting` из канонического запроса. По этому флагу снимаются право `INTERNAL_MOVE` и общий запрет частичного перемещения маркированного товара (`002:56-57`, `:112`). Сейчас флаг ставит только `trade_sort.py:63`; общих API, передающих клиентские metadata в INTERNAL_MOVE, я не нашёл. Будущий вызывающий код сможет включить эту ветку сам. Взамен действуют более строгие проверки `assert_selection`, поэтому риск низкий. Лучше отдельный `command_type` или флаг, который ставит только доверенный пакет.
5. **[Низко] Дубли ключей.** `assert_selection` считает строки `json_table` без `DISTINCT` (`001:36`). Дубли одинаково увеличивают `n` и `qty`, поэтому сам guard их не отвергает; отвергает API (`duplicate 422`). Рекомендация: `count(distinct)=expected`.
6. **[Порядок блокировок — замечаний нет].**
   - Проверки до блокировок рекомендательные (`003:49`).
   - После `acquire_resources` они повторяются (`003:221`), `assert_selection` вызывается внутри `execute_move`.
   - `compile` якорит `STOCK_ORIGIN_UID` клона (`002:36`), а триггер `004` проверяет удержание блокировок нового и исходного UID.
   - Чужие, зарезервированные, ожидающие и удержанные выкупом коды отсекаются условиями `CURRENT_UID`/`CURRENT_CELL`/`AVAILABLE`/`HARD_RESERVATION_ID is null`/`VALID`/`HOLD_ACTIVE` (`001:36-38`).
   - Однородность: `owner/SKU/МРЦ/срок`.
   - `004` разрешает клон только по действующему `IN_FLIGHT` INTERNAL_MOVE с флагом и точными происхождением, накладной, артикулом и количеством; при количестве больше 1 — отказ.
