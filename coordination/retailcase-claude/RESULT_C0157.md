# RESULT C-0157 — добивка товара общего пула (Claude). Checkpoint `d28e2e6a`, native NOT_APPLIED

## Как устроено сейчас (живые исходники, `src/`)
- Удержание подтверждённой добивки — HARD на точных единицах (`RRL_TRADE_TOPUP_CMD`). Подтверждение не трогает открытую потребность основных заказов: `protected_units` считает её через `RRL_STOCK_POOL_READ.line_snapshot_json`, в том числе для строк товаров общего пула.
- Планирование (`RRL_PICKING_API.create_plan`) пул не использует. Строка заказа добивки проецируется только на свои удержания (`hold_rid`, `hold_free`). Потребность берётся из `line_snapshot_json`.
- Общий пул: `RRL_STOCK_POOL_CMD.compile_command` распределяет SOFT (`POOL_WARE_ID`) по открытым строкам из `snapshot_json`. Запуск волны (`compile_wave_pool`) требует пуловое SOFT для каждой строки товара пула и списывает его.
- Двойное обещание возникает в двух местах:
  - в `snapshot_json` строка добивки просит полное количество: её HARD не привязан к строке плана;
  - на запуске волны строке нужна пуловая доля, хотя её обслуживает своё удержание.
  - Отсюда прежний явный отказ `TRADE_TOPUP_COMMON_POOL_UNSUPPORTED`.

## Кандидат `db/migrations/2026-10-23_trade_topup_common_pool/` (NOT_APPLIED)
Меняются только тела трёх пакетов; spec не меняются:
1. `RRL_STOCK_POOL_READ.snapshot_json`:
   - у строки добивки (`line_proposal>0`) потребность пула уменьшается на её ACTIVE-удержание;
   - у заблокированной (`-1`: отмена, расхождение условий или нет обновлённого рейса) потребность 0;
   - `line_snapshot_json` не тронут, поэтому `create_plan` по-прежнему планирует строку на своё удержание.
2. `RRL_STOCK_POOL_CMD.compile_wave_pool`: строка с `line_proposal>0` пропускается после объявления якоря `SOFT.POOL` и ключа строки. Её HARD забирает существующий `adopt_hold` (тот же RID при полном переносе; деление `move_coverage` с теми же единицами при частичном).
3. `RRL_TRADE_TOPUP_ADOPT.compile_wave`: вместо отказа для всех товаров пула — `TRADE_TOPUP_POOL_SHARE_RECALC_REQUIRED`, только если у строки добивки осталась активная пуловая доля (например, распределённая до установки). Ключ строки предложения сохраняется: запуск сериализован с подтверждением и отменой.
- Новых таблиц, второго учёта и второго writer нет. Резерв по-прежнему меняют `RRL_STOCK_RESERVE_CORE` и `RRL_STOCK_UNIT_CORE` внутри `RRL_STOCK_WAVE_LAUNCH_CMD`.
- Хэши before/after — в `manifest.json`. `000_preflight` сверяет before. `verify` сверяет after, INVALID и ошибки компиляции. `rollback` возвращает before-тела.

## Препятствие: частичный перенос
`adopt_hold` делит удержание, только если строка плана проецирует на паллету меньше удержанного. Для добивки:
- `line_proposal` требует, чтобы количество строки в штуках равнялось `APPROVED_BOXES*UNITS_PER_BOX`;
- удержание создаётся на эти же штуки (только EA, `BASE_QTY=1`);
- потребность в `create_plan` (`line_snapshot_json`) уменьшается лишь на HARD строки, отобранное, весовые отклонения и выбор веса. Весовые пути к EA-добивке неприменимы.
- План проецирует `least(остаток, hold_free)` по каждой удержанной паллете. Значит, каждое удержание переносится целиком: при нескольких паллетах — несколько полных переносов, при паллете, временно непригодной, — позже отдельным полным переносом.
- Чтобы получить частичный перенос, нужен новый бизнес-ввод (например, уменьшение количества строки SAP без отмены предложения). Сейчас такое изменение даёт `line_proposal=-1`. В источниках этого ввода нет. Успешный тест прямым DML не делался.
