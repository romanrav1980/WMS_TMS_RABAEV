## Основание и найденный запрет

Прочитай AGENTS.md/wiki/index.md и `wiki-raw/tradecase_source_review_20261021/program.txt`, строки145–159. Revision27 требует повторить добивку до погрузки, после закрытия основной сборки и при уже погруженной части основного груза. Основные заказы учитываются один раз; задания создаются только для дополнительного заказа. При начатой погрузке проверяются доступ по маршруту и отправление. Это исходный объём, не новый сценарий владельца.

Сейчас Python allocate/capacity_preview, native TOPUP_API.save и TOPUP_CMD.confirm запрещают весь случай через loading_started. READ.loading_started смешивает LOADED и DEPARTED. Просто удалить четыре запрета нельзя.

Root прочитал настоящие пакеты и таблицы; снимки в `runtime/test-evidence/tradecase/2026-10-23/T08/after-load-review/`. Файл RRL_STOCK_HU_LOAD_CMD.sql пуст: такого пакета нет, настоящий владелец RRL_STOCK_HU_LOAD_CORE. Не считай пустой export доказательством. Перед изменениями получи свежие исходники/SHA.

## Используй существующие механизмы

- Весь основной план уже включён в capacity_context.planned; `_confirmed` вычитает добивку, включённую в TRIP. Сохрани эту защиту от двойного учёта.
- Факты погрузки сохраняют вес, объём и замороженный COMPOSITION_JSON. Фактическая тара/габариты могут отличаться от теоретических коробов: нельзя прибавить полный план и весь погруженный груз повторно или молча игнорировать упаковку. Используй существующие подтверждённые сведения и явно откажи при недостаточных данных.
- `RRL_TRADE_TRANSPORT_CORE.bind_trip` уже допускает повторную привязку до DEPARTED и проверяет полный физический состав по заказам. Не собирай основной груз заново. Новая версия TRIP и новый SAP-заказ должны пройти штатные связи.
- `RRL_STOCK_LOAD_FLOOR.checked_trip/planning_counts` и transport loading_status/floor_read уже проверяют фактические паллетоместа и варианты профиля. Изучи их и используй существующую политику, не создавай второй планировщик укладки. Учти габариты/массу/места; не включай approval_available без всех нужных проверок.
- DEPART и LOAD сериализуются существующим row_key RRL_TRANSPORT_TASK. CONFIRM добивки должен участвовать в том же порядке блокировок, чтобы не подтвердить новый резерв после выезда. При SAVE изменение груза делает расчёт устаревшим; точный повтор подтверждённой операции возвращает исходную квитанцию до новой бизнес-проверки, но после текущих прав.
- Учитывай смену автомобиля, реальный native binding, изменения состава, маршрут и время отправления. Для отсутствующей геометрии/подтверждения возвращай конкретную причину; не выдавай оценку по одному свободному объёму за допуск к погрузке.

## Поставка

Цель — действительный рабочий путь дополнительного заказа при уже погруженном основном грузе, с сохранением его фактов и резервов. Отдельные модули/contracts/public вместо роста legacy-функций. Не менять POSTING_API, paper/CASE/count, yard/shift, исходники SAP; pool-файлы C0160 теперь принадлежат root для приёмки, изменения согласуй.

Передай отдельную NOT_APPLIED миграцию с актуальными before SHA/apply/rollback/verify/manifest, минимальным diff и checkpoint. Уже применённые комплекты не переписывать. Никаких fixture DML, новых приходов или складских команд: настоящий LOAD/добавление/отмену и количественные инварианты проверяет root после RELEASE. Старые actors/fixtures не возобновлять.

Нужны проверки: часть main LOADED считается один раз; дополнительный заказ получает только свои задания; UNLOAD/изменение факта требует пересчёта; DEPART блокирует новое подтверждение; точный повтор/конфликт/отзыв; неверная машина/неподтверждённые места/профиль; concurrent LOAD/DEPART/CONFIRM. Не объявляй синтетические сообщения реальными SAP/СКМ. UI со статической help-ссылкой, подсказками и восстановлением команды; общий dist согласовать. Отчёт и ограничения — reports/tradecase/2026-10-23/claude/C0161/. Gate/encoding, BACKEND_READY и RELEASE точных путей обязательны.
