# C0160 — действительное распределение торгового остатка в общем пуле

Зарегистрировано22-м до передачи. Начинай после RELEASE C0159. Root принимает двор/планы ворот и UI; ты исправляешь обнаруженный при настоящей приёмке исходный пробел T08. Сначала ACK путей. Не дублируй существующее распределение.

Доказательство root: `runtime/test-evidence/tradecase/2026-10-23/T08/common-pool-live.json`, `wiki/database/trade_topup_common_pool_20261023.md`. C0157 применён7/7/7; подтверждённая добивка40EA действительно передана волне618 с прежним HARD1985 и кодами. Но обычная привязанная строка3690/заказ2203 на20EA получила0. `snapshot_json` вызывает `RRL_STOCK_ELIGIBILITY.reason` без заказа, и торговый guard правильно возвращает `TRADE_ORDER_BINDING_REQUIRED`. Поэтому C0157 принят только как перенос собственного удержания при включённом пуле, не как полноценный торговый пул.

Данные этого прогона уже закрыты: документы отменены, волна/короб отменены, actor отключён, owner0, policy OTHER/inherited восстановлена, stock210564699=250/H0. Их не возобновлять и не создавать новые приходы. Ты работаешь READ ONLY с Oracle; root готовит следующие реальные fixtures после RELEASE.

Изучи текущие pool snapshot/command/plan/domain allocation, trade binding и все действующие ограничения источника/получателя: собственник, МРЦ, ОСГ, состояние маркировки, выкуп, коробные ограничения. Реализуй минимальное расширение существующего пула, чтобы обычные торговые строки получали обеспеченную SOFT-долю только из совместимых источников. Нельзя снимать guard отсутствующего заказа или объявлять весь запас SKU взаимозаменяемым между несовместимыми заказами. Один источник нельзя обещать двум долям сверх свободного количества; собственный HARD добивки нельзя обещать повторно. Обычные неторговые сценарии и их алгоритм сохраняются.

Нужны определённые результаты для двух разных owner/МРЦ или ограничений получателя при одном SKU, нехватки, отменённого/устаревшего binding, пересчёта после HARD и запуска волны. Покрой конкурентный пересчёт/запуск и сохранение прежней квитанции; текущие права не обходить. Если существующий контракт не позволяет безопасно распределить некоторые сочетания, верни конкретный отказ, не фиктивный положительный результат и не нулевую долю без объяснения.

Работай через существующий stock writer и модульные границы. Не менять stock POSTING_API, исходники SAP/SAP_INTEGRATION, paper/CASE/count/yard/shift файлы. Уже применённые миграции не переписывать. Новый native-кандидат NOT_APPLIED с актуальными before SHA, минимальным diff, apply/rollback/verify/manifest, offline и READ ONLY проверками. Python/UI можно менять только после ACK конкретных путей; согласование approval_available не включать. Общий dist не собирать.
