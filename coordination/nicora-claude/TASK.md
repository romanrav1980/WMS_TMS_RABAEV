## Задача A — NI07.2: понятный рабочий экран сверки дня
Результат: начальник смены выбирает склад и день, видит факты, незавершённые обязательства и внешние подтверждения, понимает причину каждой группы и куда перейти для решения.

### Твои файлы
- wiki-raw/wms_admin_ui_reference/day-reconciliation.html
- wiki-raw/wms_admin_ui_reference/day-reconciliation.js
- wiki-raw/wms_admin_ui_reference/day-reconciliation.css
- Новые модули day-reconciliation-* рядом: только для этой задачи.
Codex резервирует эти файлы за тобой до RELEASE.

В HTML изменяй только обзор сверки: фильтры drWare/drDay/drZone/drLoad, drMessage, drFacts, drTaskTimes, drBacklog, drStock, drErp, drRegulatory и новые контейнеры своего обзора. Страница также содержит перенос СТ, выбор рейса, ожидание товара, грузовую зону, подписи и сохранение решения. Сохрани их разметку, ID, обработчики и подключения скриптов. CSS новых компонентов ограничь контейнером обзора, чтобы не сломать эти соседние процессы.

### Сделай
1. Раздели отображение на понятные группы: факты выбранного дня; текущие незавершённые обязательства; остатки/резервы; ERP; государственные системы.
2. Покажи дату/часовой пояс, склад и время получения данных. Текущее состояние и факты за день должны быть явно различимы.
3. Для группы обязательств показывай описание, число, доступную причину и следующее действие. Ссылку на конкретный документ строй только из реального ID API. Если API возвращает агрегат — дай ссылку на соответствующий реестр и честно подпиши её.
4. Добавь быстрый поиск/фильтр по уже загруженным группам. Укажи границы данных, если выдача ограничена; фильтрацию клиента не выдавай за поиск по всей базе.
5. Доведи состояния загрузки, ошибки, пустых данных, неполных сведений, смены склада/даты. Устаревший ответ не должен перезаписывать новый выбор.
6. Сохрани различие «отправлено» и «подтверждено» для SAP и маркировки. Неизвестное состояние не отображай зелёным нулём.
7. Сделай читабельную адаптивную компоновку, видимый фокус и доступные подписи полей. Используй существующую визуальную систему.

### Используй готовое
GET /api/finance/day-reconciliation/warehouses/{ware_id}?business_date=YYYY-MM-DD&timezone_region=Asia/Tbilisi
Право transport_dispatch_view. Схему ответа читай из действующего modules/finance/infrastructure/day_reconciliation.py и связанных reconciliation_*; используй фактический ответ API, не выдумывай поля.

Не добавляй новую команду закрытия дня. На странице уже есть сохранение результата/подписи: их существующее поведение сохрани; отчёт сверки сам не закрывает день.

### Принять можно, когда
- Работает чтение существующего API; пользователь понимает группы и дальнейшие действия.
- Смена склада/дня не оставляет чужую или старую выдачу.
- ERP/государственный ACK показаны отдельно от локального факта.
- Соседние блоки переноса/ожидания/грузовой зоны не потеряли подключения и ID.
- Есть один показ результата desktop/mobile, адресные проверки ошибки и устаревшего ответа.
Это готовность назначенной части NI07.2; полный спринт не закрывать самостоятельно.

## Задача B — NI08.1: объяснимый прогноз складской нагрузки
Результат: руководитель получает существующий прогноз по факту исполнения, видит его исходные данные и ограничения.

### Твои файлы
- wiki-raw/wms_admin_ui_reference/warehouse-forecast.html
- wiki-raw/wms_admin_ui_reference/warehouse-forecast.js
- Новый warehouse-forecast.css и модули warehouse-forecast-* рядом.
Codex резервирует эти файлы за тобой до RELEASE.

### Сделай
1. Удобную форму склада, вида работы, истории, горизонта, минимального числа активных дней. Границы ввода должны соответствовать API.
2. Сводку: окно истории, включён ли неполный день, активные дни, пропуски проекции, время чтения.
3. Читаемую таблицу по артикулам: фактическое количество, единица, активные дни, прогноз горизонта, статус/объяснение. Не суммируй несовместимые единицы.
4. Объясни состояния NEEDS_PROJECTION, NO_SERIES, ADVISORY, INSUFFICIENT_HISTORY. Отсутствие данных не равно нулевой нагрузке.
5. Дай локальную сортировку/поиск и при необходимости простой график только по реальным числам ответа. Не изображай статистическую уверенность, которую API не вычисляет.
6. Сохрани отдельное явное обновление исполненной истории с существующими правами. Это меняет проекцию, поэтому не вызывай его автоматически при открытии или смене фильтра.
7. При смене пользователя/склада/входных параметров исключи показ устаревшего результата как текущего.

### Используй готовое
- POST /api/transport/warehouse-forecast/warehouses/{ware_id}/view — расчёт/чтение, transport_dispatch_view.
- POST /api/transport/warehouse-forecast/warehouses/{ware_id}/project?limit=100 — существующее обновление проекции, transport_dispatch_edit.
- contracts_forecast.py, api/forecast_routes.py, infrastructure/warehouse_forecast.py, domain/forecast_quantity.py — читать как источники.
Окно истории1..90, горизонт1..31, минимум активных дней1..90. Режимы CASE_DISPATCH/FULLPAL_DISPATCH/OUTBOUND_WORKLOAD. Сохраняй текущую серверную математику.

### Принять можно, когда
- Расчёт соответствует выбранным параметрам и фактическому API; ошибки и недостаток истории понятны.
- Пользователь видит основания рекомендации.
- Нет автоматических назначений, проводок или изменений рейсов.
- Есть показ законченного интерфейса и адресная проверка недостаточной истории/смены параметров.
Потребность в людях/технике/слотах нельзя вывести без нормативов производительности. Если таких данных в готовом контракте нет, передай точный CONTRACT_REQUEST; не делай выдуманную формулу. Эта часть полного NI08.1 остаётся отдельным остатком.
