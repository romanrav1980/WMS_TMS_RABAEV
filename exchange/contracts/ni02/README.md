# NI02 — нормализованный заказ магазина

[store-order.example.xml](store-order.example.xml) — предположение о контракте шлюза, не реальный SAP export и не название стандартного IDoc. Вход — WarehouseCustomerOrder version=1, UTF-8 ≤4MiB без DTD/entities, 1–1000 строк. Поля/ID сохраняют ведущие нули. LineNumber положительный integer и уникален; Quantity/TargetWeightKg положительны с максимум шестью знаками. Timestamp содержит UTC offset. Неизвестные/дублированные scalar fields отклоняются.

Sender/OrderNumber — неизменная business identity. Sender/MessageId — delivery identity. Повтор исходного MessageId должен содержать те же bytes. Новый MessageId допускается только с тем же исходным содержанием заказа; изменения уже переданного заказа запрещены требованиями. Это отличается от изменяемого заказа входящей поставки NI01.

CustomerCode/StoreCode/WarehouseId должны существовать в WMS. Регистрировать адрес из неполного заказа нельзя. Календарь/UTC offset/день-в-день настраиваются в WMS; пример +04:00 не навязывает этот offset всем складам. OperationalDate — дата начала работы, а не дата завершения ночной сборки. Основной shipment на следующий день; день-в-день только для настроенного источника. После 16:00 фактического серверного получения заказ ждёт решения логиста, исходные времена не переписываются.

Товары/pack ratios берутся из сохранённого ARTMAS того же Sender. Маркировка остаётся политикой WMS; в исходном заказе нет выдуманных уникальных марок/агрегаций. KG base при отсутствии отдельного TargetWeightKg использует quantity как целевой вес; для иной единицы вес не подменяется количеством.

Запуск `sap-store-orders.bat`, root `exchange/sap_store_orders`. HTTP-вход запасной: POST `/api/integrations/sap/store-orders`. Потребность сохраняется в действующих customer orders без изменения inventory. Транспортный handoff и ответ об отказе позднего заказа — следующий срез NI02, не имитируются импортом.
