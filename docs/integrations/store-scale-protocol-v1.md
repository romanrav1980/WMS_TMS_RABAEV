# Внешние весы: протокол шлюза v1

Владелец обмена — `integrations`, архива измерений и приёмки — `delivery`.
Задача: получить физический вес в приложении магазина одной понятной командой,
сохранить исходное измерение и восстановить результат после обрыва связи.
Вес из поля браузера, состояние «весы доступны» и архивная запись другого груза
не подтверждают текущую приёмку.

## Принятая архитектура: OPC 40200 → шлюз → HTTPS API

По последнему решению владельца единый стандарт оборудования на складе и в
магазине — **OPC UA for Weighing Technology (OPC 40200) v2.00**. Шлюз выступает
OPC UA клиентом, а с retailcase обменивается по описанному здесь HTTPS API v1.
Это два участка одного решения. Браузер магазина не подключается к COM/TCP весам.
Модели оборудования будут выбраны позже; gateway OPC adapter ещё предстоит
реализовать. SMA parser сохранён только для явно рассмотренной legacy совместимости,
а не как стандарт закупки. Общая архитектура и различие складских/магазинных DTO:
[шлюз склада и магазина](weighing-gateway-opc40200.md).

## Подключение оборудования

```text
весы ── OPC UA 40200 v2 ── локальный шлюз магазина/склада
                                                    │ HTTPS + identity шлюза
приложение магазина ── запрос измерения ────────────── API
                                                    │
                                             native архив Oracle
```

Принятый профиль оборудования —
[OPC UA for Weighing Technology, OPC 40200 v2.00 от 01.04.2025](https://reference.opcfoundation.org/specs/OPC-40200).
Это отраслевой стандарт представления весового оборудования; он не делает
произвольные RS-232 весы OPC UA совместимыми. Перед вводом конкретной модели
задаются endpoint, certificate trust, security policy, node identifiers,
engineering units, качество значения и его timestamp. Клиент OPC UA ещё не
реализован; отсутствующий драйвер нельзя обозначать как подключённые весы.

Для legacy оборудования реализован чистый разбор нормального KG/GROSS ответа
[SMA Standard Scale Communication Protocol, §3 и §5.1](https://www.scalemanufacturers.org/PDF/ScaleCommProtocol5199M1.pdf).
Кадр: LF, status, range, gross/net, motion, reserved, десять символов массы,
три символа единицы, CR; всего 20 байт. Профиль принимает только `G`, `kg `,
normal resolution и обычное/нулевое состояние. Перегрузка, ошибки нуля/тары,
NET, high resolution, неизвестные флаги, склеенные/обрезанные кадры отклоняются.
Признак motion сохраняется: движущееся показание не становится устойчивым.
Нормализация использует Decimal, без float, усреднения, округления и конверсии lb.

Парсер сам не открывает COM-порт. Паспорт установки должен содержать модель,
серийный номер, прошивку, протокол, COM/USB VID/PID или адрес TCP, baud rate,
data bits/parity/stop bits, flow control, timeout, метод фрейминга, контрольную
сумму для выбранного протокола, предел, дискретность, диапазоны и поверку.
Нельзя угадывать эти параметры. SMA профиль не добавляет выдуманную checksum.
Драйвер модели обязан отдельно проверить фактическое отсутствие preset tare;
получение `G` само по себе не доказывает всё состояние устройства.
Удалённые команды ZERO/TARE/CALIBRATE этот контракт не разрешает.

## Команда «Получить вес»

Магазинный request handshake реализован в delivery/native; подключение реального
OPC оборудования и складской общий request workflow — следующие инкременты.

1. Приёмщик выбирает весы, ставит груз и нажимает «Получить вес».
2. `POST /api/delivery/store-scales/requests` принимает только `request_id`,
   `device_id`, `load_operation_id`, `store_address`, `expected_composition_signature`.
   Массы и sample values в запросе браузера отсутствуют. Сервер проверяет текущего
   приёмщика, действующее устройство этого магазина, поставку и версию состава.
3. `GET /api/delivery/store-scales/gateway/requests?device_id=…` доступен только
   текущему выделенному sender этого устройства и отдаёт ограниченную очередь.
   Шлюз не выбирает произвольный магазин или другую поставку.
4. Шлюз получает реальную проверку пустой платформы/нуля, затем исходные samples
   физического груза, формирует неизменяемый пакет и сохраняет его локально до POST.
   `capture_id` **равен `request_id`**. Один новый замер — один новый запрос;
   сетевой повтор сохраняет прежние request/capture ID и исходное тело.
5. Шлюз отправляет пакет в существующий `/captures`. Native атомарно сохраняет
   неизменяемый архив. Серверный request status сопоставляет его с запросом,
   устройством, грузом и составом и возвращает capture_key; захват сам не
   подтверждает приёмку магазина.
6. Приложение читает `GET /requests/{request_id}` и показывает подтверждённый вес,
   время, устройство и результат проверки. Отдельные live этапы, отмена и достоверный
   статус «Весы не подключены» требуют запланированных heartbeat/OPC функций; при движении целевой OPC интерфейс покажет «Дождитесь устойчивого веса».

Согласованный запрос API имеет state `REQUESTED`; после архива — `CAPTURED`,
отдельно `EXPIRED` и `STALE`. Cancellation, MEASURING/FAILED и heartbeat
требуют нового согласованного серверного endpoint и сейчас не реализованы.
Heartbeat и промежуточные показания относятся только к диагностике и не подменяют
CAPTURED. Сервер допускает один активный запрос на устройство. Нынешняя outbox
lease защищает отправку; отдельный hardware claim для OPC collection ещё требуется.
Поздний пакет истёкшего запроса или изменённого
состава не предлагается как актуальное доказательство. Повтор CAPTURED возвращает
сохранённый результат. NOT_VISIBLE после таймаута не доказывает откат.

## Установленный gateway → API контракт

`POST /api/delivery/store-scales/captures`, `Content-Type: application/json`,
`X-Scale-Protocol-Version: 1.0`. Неизвестная major version отклоняется сервером;
при отсутствии заголовка сохраняется совместимость с существующим v1 клиентом.
Версия v1 зафиксирована отдельным контрактом/schema; в тело не добавляется
`protocol_version`, потому что текущая модель запрещает неизвестные поля.
Используется отдельная identity шлюза с `store_scale_ingest`, привязанная к
устройству; пароль приёмщика и GLOBAL_ADMIN не применяются для оборудования.
В production — HTTPS с проверкой сертификата; секреты не попадают в пакет/логи.

Точная [JSON Schema v1](store-scale-capture-v1.schema.json) сгенерирована из
существующей `ScalePacket` и проверяется тестом на расхождение с API.

```json
{
  "device_id": "STORE-17-SCALE-01",
  "capture_id": "50adb6f1-9e2b-4fea-bad6-de8089971965",
  "load_operation_id": "LOAD:example",
  "store_address": "Адрес из серверного запроса",
  "device_policy_version": 3,
  "calibration_ref": "CAL-2026-017",
  "unit": "KG",
  "basis": "GROSS",
  "preset_tare_kg": "0",
  "zero_confirmed": true,
  "zero_check_kg": "0",
  "zero_check_at": "2026-10-15T08:00:00.000000+00:00",
  "measured_at": "2026-10-15T08:00:05.000000+00:00",
  "samples": [
    {"offset_ms": 0, "gross_weight_kg": "10.00"},
    {"offset_ms": 500, "gross_weight_kg": "10.00"},
    {"offset_ms": 1000, "gross_weight_kg": "10.00"},
    {"offset_ms": 1500, "gross_weight_kg": "10.00"},
    {"offset_ms": 2000, "gross_weight_kg": "10.00"}
  ]
}
```

Пример содержит синтетические данные. Действующую policy/calibration и источник
груза предоставляет настройка/сервер, их нельзя копировать из примера.
Числа массы — decimal strings; UTC — шесть знаков микросекунд и `+00:00`.
Временные отметки устройства и шлюза должны иметь явно установленное происхождение;
нельзя выдавать локальное время без зоны за UTC. Offline старый пакет не получает
новое `measured_at`, чтобы пройти ограничение свежести.

Единственный authoritative валидатор — `RRL_SCALE_PACKET_READ` через существующий
`RRL_STORE_SCALE_API`: 5–25 исходных samples, окно не менее 2 секунд,
смещения до 10 секунд, текущие capacity/resolution/calibration, zero proof,
пределы и разброс. Окончательный вес — последний sample. Отдельный алгоритм
«стабильности» на шлюзе или в React не заменяет эти правила.

## Доставка и восстановление

`SqliteScaleOutbox` реализует локальный durable журнал: исходные UTF-8 bytes
сохраняются до отправки, device/capture identity неизменна, другое тело с прежним
ключом отклоняется. После сбоя процесса/потери ответа истёкшая аренда позволяет
повторить только исходные bytes. Два worker не получают одну действующую lease;
устаревший worker не может подтвердить новую аренду. ACK сохраняет ответ.
Локальный hash очереди не является серверным `capture_key`.

Реализованы `HttpScaleGateway`, `ScaleGatewayWorker` и утилита
`tools/store_scale_gateway.py`: HTTPS Basic, запрет redirect, bounded timeout/response,
проверка device/capture/load/store, вычисленного серверного capture_key,
source_sha256 от серверного canonical JSON, policy/calibration/measured_at
и Decimal массы последнего sample перед ACK,
backoff после network timeout/5xx. Неисправный ACK тоже оставляет исходный пакет
для повтора. 409/422 переводят локальную запись в SUSPENDED, без автоматического
нового capture_id. Утилита не является драйвером неизвестной модели весов. 401/403 требуют
восстановления identity, 409/422 — явной диагностики, без автоматической замены
capture_id/содержимого. Нельзя считать любой ответ 200 доказательством приёмки:
сохранение capture и подтверждение STORE_RECEIPT — разные операции.

## Приёмка подключения

Автотесты проверяют строгие SMA векторы, ошибки/motion, сохранение байтов после
перезапуска, конфликт ключа, два worker, истечение lease и соответствие JSON Schema.
Это не испытание реальных весов. Для каждой модели необходим стенд: ноль,
контрольные гири, груз выше capacity, движение, тара, неправильные единицы,
обрыв USB/TCP, рестарт шлюза, таймаут после сохранения API, отказ sender,
чужой магазин, изменение состава и одноразовое использование capture в приёмке.
Протокол измерения не заменяет метрологическую поверку.

## Исполняемый клиент поставщика

[DTO запроса v1](store-scale-request-v1.schema.json) описывает gateway poll item.
Ответ GET — `{ "items": [ ... ] }`, до50 запросов. Поля `device_policy_version`
и `calibration_ref` приходят с сервера. `capture_id = request_id`; состав проверяет
сервер по `expected_composition_signature`. Эта сигнатура не добавляется в capture
как неизвестное поле. Неизменный исходный пакет сохраняется до отправки.

Настройка через окружение: `STORE_SCALE_API_ORIGIN` (HTTPS origin без пути),
`STORE_SCALE_SENDER`, `STORE_SCALE_PASSWORD`, `STORE_SCALE_DEVICE_ID`.
Значения identity/пароля клиент не печатает. Папка outbox содержит коммерческие
данные; её ACL и резервирование обеспечивает развёртывание магазина.

```powershell
# Только опрос очереди и повтор ранее сохранённых пакетов:
python tools/store_scale_gateway.py --once --outbox runtime/scale.sqlite
# Передача реального пакета, полученного от API/SDK поставщика:
python tools/store_scale_gateway.py --once --packet-file vendor-capture.json --outbox runtime/scale.sqlite
```

Файл здесь — демонстрация интерфейса внедрения поставщика, а не ручной ввод веса
приёмщиком. Генератор фиктивных измерений отсутствует. В промышленном адаптере
поставщик вызывает `ScaleGatewayWorker.cycle(actual_packet_bytes)` непосредственно
после своего физического измерения. Без пакета клиент сообщает
WAITING_FOR_VENDOR_PACKET; это не означает подключение оборудования.
Только для loopback dev разрешён явный `--allow-loopback-http`.

Отложенный exact retry выполняется без нового замера, даже если запрос уже исчез
из очереди после успешной серверной фиксации. Другое тело с тем же ID запрещено.
После рестарта повторяется сохранённый пакет, его timestamps не освежаются.
Сроки/состав/привязка запроса проверяются при первом сохранении; окончательная
авторизация и приёмка исходных samples остаются в серверном native контракте.

Проверки клиента используют настоящий локальный HTTP сервер: потеря ответа после
фиксации в fixture, повтор идентичных bytes при исчезнувшем запросе, неверный ACK,
чужое устройство/магазин, отмена/истечение запроса, permanent 409 и HTTPS ограничения.
Это проверка протокола, не реальных весов или Oracle.

Проверка клиентского инкремента: 49 focused tests PASS; архитектурная проверка
940 файлов/0 cycles/72 debt PASS на момент проверки; encoding PASS. Проверка
совместимости ACK с live Oracle выполняется владельцем delivery отдельно.
SQL не изменялся, клиент не выполняет прямых запросов к Oracle.
