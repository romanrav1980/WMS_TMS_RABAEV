# NI01 — задания локальной модели Qwen

Владелец поручил подготовить задания на тестирование завершённой реализации NI01. Эти файлы — задания, а не результаты: запуск Qwen и тестов при подготовке не выполняется. Прежняя остановка автоматических прогонов сохраняется для разработчика NI02; локальный исполнитель выполняет только эти адресные задания.

## Порядок исполнения

Рабочий каталог: `C:\projects\TMS`. Сначала прочитай AGENTS.md, wiki/index.md, [runbook NI01](../../wiki/runbooks/nicora_ni01_sap_retail.md), [структуру RABAEV](../../wiki/database/nicora_ni01_sap_retail.md), [XML-контракт](../../exchange/contracts/ni01/README.md). Исходники — текущие локальные файлы, контрольный снимок `runtime/ni01/implementation-manifest.json`. NI02 разрабатывается одновременно: не меняй общие исходники, не останавливай чужие процессы и не применяй миграции самостоятельно. Зафиксируй hashes проверяемых файлов до и после; если они менялись, отметь затронутые сценарии как требующие повтора.

Исполнитель: локальная Qwen. Роль — независимый тестировщик. Не исправляй код продукта, не подгоняй ожидания под текущую реализацию. Тестовые скрипты/отчёты размещай в `runtime/test-evidence/ni01-qwen/<run-id>/`. Если не хватает инструментов, данных или доступа, сообщи BLOCKED с конкретной причиной; не заменяй Oracle на SQLite и реальный ответ на mock без явной отметки.

Существующий стенд: ORCL/orcl, RABAEV, только dev. Не создавай вторую схему/инстанс. Используй отдельные owned fixtures: уникальные Sender/DOCNUM/MessageId/OperationId, товары/поставка/SSCC/ячейки для текущего run-id. Запиши созданные PK и исходные значения изменённых настроек в fixture_manifest.json; сохраняй внешние строки. Не выполняй truncate, общий delete, отключение trigger/constraint или reset всего склада. Cleanup — только свои точные PK в обратном порядке зависимостей; после физических проводок применяй согласованный компенсирующий сценарий, а при его отсутствии сохраняй изолированную fixture и помечай retained. Секреты из конфигурации не печатай и не включай в отчёт.

API запускается штатным `serv.bat`, UI `/wms-admin/receiving.html`. Не перезапускай действующий API без необходимости. Используй Oracle/API и браузер для назначенного сценария; не запускай общий pytest, quality gate, массовую регрессию или нагрузку. Не отправляй сообщения в реальные SAP/CRPT/ЕГАИС; отдельные задания оборудования отмечай BLOCKED, если физического доступа нет.

## Формат результата

Каждый case: локальный ID NI01-QW-xx-nn (только ID теста, не новый ID требования), источник правила, fixture PK, предусловия, шаги, ожидаемое, фактическое, PASS/FAIL/BLOCKED, HTTP/status/body без секретов, SQL до/после, timestamps, source hash и ссылки на артефакты. Для UI приложи screenshot; для отказа покажи неизменность stock/task/fact/outbox/marks. Результаты: results.json, report.md, defects.md, fixture_manifest.json, slow_sql.md. Сводка должна разделять реально исполненное, статическое чтение, симуляцию и непроведённое внешнее испытание.

После каждого значимого функционального кейса просмотри длинные SQL/SKV по RRL_SQL_SLOW_LOG, `/api/admin/slow-sql`, API audit и доступному Oracle top SQL. Не запускай отдельную нагрузку. Для длинного запроса укажи SQL/время/план при доступности и решение: rewrite, окно, batching, cache, index/statistics либо backlog с owner/причиной. Для NI01 placement текущий owner backend/Oracle, очередь оптимизации NI08. Недоступное измерение обозначай unavailable, не нулём.

Итог: сколько PASS/FAIL/BLOCKED, какие функции можно демонстрировать, какие реальные SAP/принтер/государственные операции не проверены, список дефектов с воспроизведением и оставшихся fixtures. Не меняй статус спринта и wiki автоматически: передай отчёт владельцу/разработчику.
