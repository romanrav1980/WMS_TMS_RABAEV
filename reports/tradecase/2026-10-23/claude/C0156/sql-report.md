# C-0156 — SQL бланка CASE (только чтение)

Читатель `GET /api/case-pick/tasks/{id}/paper` в одной READ ONLY транзакции:

| # | Запрос | Сколько раз |
|---|---|---|
| 1 | `set transaction read only` | 1 |
| 2 | `RRL_CASE_TASK_ACCESS.assert_scope` (существующая область CASE, право case_pick_execute) | 1 |
| 3 | шапка задания (task + wave + order + customer) | 1 |
| 4 | строки задания + `RRL_CASE_PICK_PAPER.line_signature` для каждой строки внутри того же SELECT | 1 (до 201 строки, больше — отказ CASE_PAPER_LINE_BOUND) |
| 5 | проекция маркировки/весовой этикетки/весового кг — та же, что у marking-policy, но одна на все уникальные артикулы задания | 1 |

Итого 5 обращений к БД на бланк при любом числе строк (раньше было 2 запроса на строку; переделано по ревью root). Совпадение проекции с `case_pick_policy.py` проверяет тест `test_policy_projection_matches_the_marking_policy_endpoint`.

## Замеры (живая БД, только чтение)
- `case-paper-sql-timing.json` — задания 1019/1020 (по 1 строке): область 2–4 мс, шапка+строки 3–4 мс, проекция 2–19 мс, подпись 2–3 мс (первые вызовы после разбора до 285 мс).
- `case-paper-scale-live.json` — 3 самых больших CASE-задания в БД: **2 строки**. Строки 2–16 мс, проекция 2–19 мс, подписи 2–118 мс (холодный разбор анонимного блока), прогретые ≤6 мс.
- `case-signature-live.json` — подпись строк 921/936/937 стабильна, 2–7 мс.

## Не проверено
- Масштаб 200 строк: в БД нет CASE-задания больше 2 строк, а создавать данные запрещено. Предел 200 — граница в коде, не измерение.
- Пакет не применён, поэтому подпись в замерах выполнялась анонимным блоком (одно обращение на строку); после установки это одна функция в SELECT строк.
