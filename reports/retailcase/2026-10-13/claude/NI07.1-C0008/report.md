## Этап 1 — прямое основание допрасхода в счёте (C-0005/K-0007)

**Контракт** `GET /api/finance/expense-allocation/billing-orders/{invoice_id}`. Изменение аддитивное, прежние поля сохранены.

Новые поля строки:

| Поле | Смысл |
|---|---|
| `ware_id`, `expense_date`, `reporter`, `article_code` | склад, дата и автор расхода, код статьи |
| `logist_operation_id`, `logist_outcome`, `logist_actor`, `logist_decision_reference` | решение логиста |
| `finance_operation_id`, `finance_actor`, `finance_decision_reference` | решение финансового контроля (`finance_outcome` уже был) |
| `confirmed_total` | исходный расход плюс коррекции, подтверждённые финансовым контролем (как в `expense_correction.confirmed_total`); заполнено только у исходного расхода, у коррекции `null` |
| `expected_confirmed_total` | ожидаемый итог исходного расхода, указанный в коррекции |

Как устроено:
- **`amount`** — подписанная сумма самой строки. Формат `TM9` с точкой независимо от настроек сессии. Сумма распределения в эти поля не подмешивается.
- **SQL** вынесен в `finance/infrastructure/expense_basis_read.py`; `ExpenseAllocation.invoice` вызывает его. Финансовые команды не менялись.
- **Решения стадий** присоединяются двумя left join по `PHASE`. Ограничение `unique(EXPENSE_OPERATION_ID,PHASE)` гарантирует одну строку на стадию; на стенде дубликатов 0.
- **Права и склад** — тот же join `RUSERS`. Один запрос без N+1. Поиска по последним 100 записям больше нет.
- **Клиент** (`BillingCostsInvoice.ts`, `BillingCostsBasis.tsx`, `BillingExtraExpenses.tsx`, `BillingCostsSummary.tsx`):
  - основание берётся из самой строки;
  - если поля нет (старый сервер), основание помечено как неполное и используется прежний поиск по реестру склада;
  - для коррекции норматива без транспортного начисления в счёте указан склад и реестр исходника;
  - отказ логиста засчитывается как отклонение;
  - «Дальше» показывает, чьё решение ещё нужно;
  - CSV оснований содержит склад, дату и решения обеих стадий.

**SQL-решение.** Один запрос. Коррелированные подзапросы скалярные, по PK/FK. На 7 строках — 4–8 мс прямым SQL (5 замеров). Оставить; при росте счетов проверить план подзапроса `confirmed_total`.

## Этап 2 — рабочий экран реестра допрасходов

Файлы: `wiki-raw/wms_admin_ui_reference/logistics-expenses.html`, `logistics-expenses.js` (ядро команд), новые `logistics-expenses-model.js`, `logistics-expenses-view.js`, `logistics-expenses-actions.js`, `logistics-expenses.css`. Все прежние ID и формы сохранены (проверено сравнением списков ID). Общие `styles.css` и `admin-nav` не менялись.

1. **Карточки расходов:**
   - дата, статья, рейс или автомобиль, операция;
   - исходная сумма и валюта; для коррекции — знак и к чему она относится;
   - текущий итог с коррекциями (только у исходного расхода);
   - документ, статья, автор;
   - цепочка «зарегистрирован → логист → финконтроль → распределён»; расход автомобиля заканчивается шагом «только автомобиль»;
   - подтверждённый отказ выделен, следующие стадии помечены «не требуется».
2. **Фильтры по загруженному.**
   - Стадия со счётчиками, объект и его ID, строка поиска.
   - Окно названо прямо: сервер отдаёт не более 100 записей — первые по времени регистрации. Фильтр работает только по этому окну и не выдаётся за поиск по всей базе.
   - Когда окно заполнено, выводится предупреждение.
3. **Итоги по валютам.** Подтверждённые финконтролем и находящиеся на согласовании. Считаются точной десятичной арифметикой на BigInt; валюты не складываются; отклонённые не входят.
4. **Следующее действие** выбирает документ в существующей форме, раскрывает её и ставит фокус:
   - решение логиста: стадия, база по типу объекта с подсказкой проверить;
   - решение финконтроля: база логиста;
   - распределение;
   - коррекция подтверждённого исходного расхода.

   Решение, подпись и проведение сохраняются только кнопкой формы. При выборе карточек отправлено 0 POST.
5. **Права** взяты из действующей реализации: логист и распределение — `calc_tt_price`, финконтроль — `create_tt_price`, регистрация — `edit_bill_tt`.
   - Без права кнопка недоступна, причина видна рядом и во всплывающей подсказке.
   - Если финконтроль пытается выполнить тот же сотрудник, что был логистом, кнопка недоступна; сервер это тоже запрещает.
6. **Форма регистрации.**
   - Предпросмотр: «Новый расход … документ … от …» или «Уменьшение/увеличение … к расходу X; итог A → B».
   - Если итог станет отрицательным, предпросмотр предупреждает, что сервер откажет.
   - При выборе исходника объект и валюта подставляются из него и закрыты для правки.
   - Статьи отфильтрованы по объекту, у каждой показана версия.
   - Проверка «склад изменён после чтения».
7. **Устаревшие ответы.**
   - Поле склада доступно во время чтения; ответ, пришедший после смены склада, пользователя или прав, отбрасывается.
   - Сохранённая операция привязана к адресу API и пользователю. Повтор отправляет тот же `operation_id` и то же тело.
   - Повреждённая сохранённая запись блокирует новые команды; удалить её можно только явной кнопкой с подтверждением.
8. **Успех** показывается только после сверки ответа: `operation_id`, а для решения и распределения ещё `expense_operation_id`; для статьи — `code`. Несовпадающий ответ остаётся «не подтверждён».
   - После успеха реестр перечитывается.
   - Если перечитать не удалось, выводится «операция сохранена, реестр не прочитан, повторять не нужно».
9. **Компоновка desktop/mobile:** горизонтальной прокрутки на 390 px нет; видимый фокус; подписи и подсказки.
