## 1. Реестр допрасходов: контракт и надёжное хранение команды

**Контракт** `GET /api/finance/logistics-expenses/warehouses/{ware}` расширен аддитивно, прежние вызовы работают:
- окно — новейшие 100 записей, `CREATED_AT desc, OPERATION_ID desc`;
- `?operation_id=` — точный поиск за пределами окна в том же складе;
  - права проверяются как раньше (`require_warehouse`);
  - чужой склад → `[]`, пустой параметр → 422;
- новые поля `finance_actor`, `logist_decision_reference`, `finance_decision_reference`;
- `confirmed_total` = `null` для коррекций; `expected_confirmed_total` отдаётся отдельно.

**Файлы сервера:**
- `finance/infrastructure/logistics_expenses.py` — изменён только метод `pending`;
- новый `expense_register_read.py`;
- `contracts_expenses.py` — новый параметр со значением по умолчанию;
- `api/logistics_expense_routes.py` — Query-параметр `operation_id`.

**Экран** (`logistics-expenses*`, новый `logistics-expenses-intent.js`):
- **Перед отправкой** намерение команды записывается и сразу читается обратно. Если хранилище браузера недоступно или запись искажена, POST не отправляется.
- **Неизвестный результат** сохраняет тот же `operation_id` и тело команды.
- **Повреждённая запись** блокирует новые команды. Кнопка «Проверить по ID» ищет операцию точным поиском на сервере: это сам расход, решение стадии или распределение.
  - Найдено → результат установлен, запись можно закрыть.
  - Не найдено → команды остаются заблокированы.
  - Удалить запись без установленного результата можно, только если в ней нет ни одного ID.
- **Успех подтверждён, но запись удалить не удалось** → новые команды не разрешаются, пока запись не закрыта.
- **Точный поиск расхода по ID** на экране; строка, найденная вне окна, помечена.
- **Решение по коррекции** подставляет базу распределения исходного расхода.
- **Прямая ссылка** `?warehouse_id=&operation_id=` открывает реестр склада и выполняет точный поиск.

## 3. NI07.2: переходы из сверки дня

**Найденные пробелы** (план: «связать ERP, доставку, P/H, марки, незавершённые места/обязательства и причины расхождения; pending ACK отдельно»):

1. **Переходы в реестры терялись склад и дата.** Ссылки вели на общий экран.
2. **Сверку нельзя было открыть ссылкой на склад и день.** «Назад» из реестра возвращал пустую форму.
3. **Ответ сверки агрегатный**, ID документов в нём нет, поэтому переход ведёт в реестр, а не к документу. Нужен серверный контракт (см. ниже).
4. **9 из 12 целевых экранов** не читают склад и дату из адреса: logistics-costs, external-outbox, tare-*, store-*, supplier-handover, return-disposal, interwarehouse. Это файлы Codex.

**Сделано** (`day-reconciliation-links.js`, правки `day-reconciliation.js`, `.html`, `.css`, `-catalog.js`):
- **Перенос контекста.** Склад, дата или ID передаются только экранам, которые их читают (проверено по коду): `interwarehouse-groups` (`warehouse_id`), `logistics-expenses` (`warehouse_id`, `operation_id`), `warehouse-tasks` (`preset`, `task_id`), `pallet-composition` (`identifier`).
- **Честная подпись.** Для остальных экранов под ссылкой выводится «на экране укажите склад N и дату D».
- **Прямая ссылка** `day-reconciliation.html?warehouse_id=&day=` проверяет значения и сама формирует сверку. После чтения адрес обновляется, поэтому «назад» из реестра возвращает тот же склад и день со сформированным обзором.
- **Второй реестр и проведение не созданы.** Отсутствие ACK ERP и госсистем по-прежнему показывается отдельно от физического факта.
