WMS / MES / Reachtruck

Доменная синхронизация складских заданий

Как факт водителя в `RRL_WAREHOUSE_TASK` должен закрывать MES, волны, пополнение и отгрузку без двойного движения остатков.

Основано на ТЗ `warehouse_task_domain_sync_tz.md`
Проблема

Физический факт уже есть, но бизнес-процесс может остаться открытым

Что уже работает Водитель берет задачу, сканирует паллет и ячейку, подтверждает полный паллет или коробки. Warehouse task становится `DONE`.
Чего не хватает MES-задача, волна, пополнение или отгрузка должны получить этот факт и закрыть свой доменный шаг.
  • Без синхронизации можно увидеть `DONE` у водителя, но `IN_PROGRESS` в MES или волне.
  • Нельзя напрямую менять старые остатки WMS из водительской задачи.
  • Нужна идемпотентность: один факт водителя = одно бизнес-закрытие.

Количество

Полный паллет и коробки обрабатываются по-разному

QTY_MODE = PALLET Водитель нажимает `Паллет`. Частичный факт запрещен. Задача закрывается только как полный паллет.
QTY_MODE = BOX Водитель нажимает `Коробки`. Пустой факт означает план. Меньший факт создает остаточную задачу.
10 BOX → факт пусто = DONE 10 10 BOX → факт 4 = DONE 4 + PLANNED 6 100 PALLET → факт 50 = ошибка
Последовательность

Что происходит после нажатия `Готово` на ТСД

1

API блокирует warehouse task и проверяет статус.

2

Проверяются сканы паллета, ячейки источника и ячейки назначения.

3

Фиксируются `DONE`, `FACT_QTY`, `FINISHED_AT`; при частичном `BOX` создается остаточная задача.

4

Создается запись доменной синхронизации `PENDING`.

5

Dispatcher вызывает обработчик MES, Wave или Shipment.

6

Обработчик закрывает доменную задачу, резерв или movement и помечает sync как `SYNCED`.

Sync-state

Нужна явная таблица синхронизации

RRL_WAREHOUSE_TASK_SYNC

  • `TASK_ID` и источник бизнес-документа
  • `SYNC_STATUS`: PENDING, IN_PROGRESS, SYNCED, ERROR
  • `SYNC_ATTEMPT`, `LAST_ERROR`, `SYNC_KEY`
  • время создания, обновления и успешной синхронизации
PENDING IN_PROGRESS SYNCED ERROR RETRY_PENDING

Так мы не теряем физический факт, даже если доменный обработчик или bridge временно упал.

Идемпотентность

Retry не должен создавать двойные движения

Один sync-key Уникальный ключ связывает task, source и movement.
Проверка домена Handler сначала проверяет, не закрыт ли документ ранее.
Без прямых остатков Физические остатки меняются только через WMS/MES bridge.
  • Повторный retry не списывает сырье второй раз.
  • Повторный retry не создает второй movement.
  • Остаточная задача создается один раз.
Ошибки

Физический факт принят, бизнес-синхронизация может ждать retry

Task DONE
→
Sync ERROR
→
Диспетчер retry
ТСД Показывает короткий результат: факт принят, бизнес-синхронизация ожидает.
Диспетчерская Показывает подробный `LAST_ERROR`, число попыток и кнопку retry.

Критерии приемки

Когда считаем доменную синхронизацию готовой

  • Закрытие warehouse task создает или обновляет sync row.
  • Повторный sync не создает дублей movement/reservation.
  • `MES_RAW_SUPPLY` закрывает raw transfer task и hard reserve.
  • `FG_TO_STORAGE` фиксирует размещение без повторного выпуска продукции.
  • `WAVE/REPLENISHMENT` корректно работает с остаточными задачами.
  • Ошибки видны диспетчеру, retry исправляет временный сбой.
  • Нагрузочный тест проходит без lost residual tasks и duplicate movements.
