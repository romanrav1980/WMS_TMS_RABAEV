# NICORA: разработка моделями и независимая проверка

7 октября 2026 года. Предложение к плану NS00–NS67. Разделение ролей ниже — организация работы, не утверждение о превосходстве одной модели. Допуск определяется результатом пробных задач.

## Распределение работы

| Инструмент | Основная работа | Проверяющий |
|---|---|---|
| OpenAI Codex с имеющейся подпиской | Архитектура, Oracle, резервы, товарный баланс, транзакции, волны, сложное планирование и нагрузочные исправления | Claude Code |
| Claude Code | Интеграционные функции, рабочие места, независимые сценарии, проверки ошибок и конкуренции | Codex |
| Qwen Code с облачной Qwen | Ограниченный адаптер, формы и преобразования данных по уже утверждённому контракту | Codex или Claude Code |
| Aider + Ollama с локальной Qwen | Формы и таблицы, тестовые данные, документация, небольшие изменения в заданных файлах | Codex или Claude Code |

В карточке назначены автор и отдельный проверяющий. Проверяющий сначала читает требование и формирует ожидаемые результаты, затем рассматривает реализацию. Для сложных операций он готовит тест до написания функции. Автор может делать собственные проверки, но не принимает свою работу самостоятельно.

Конкретные версии облачных моделей фиксируются при старте карточки по доступности аккаунта. Сильная модель применяется к резервам, транзакциям, партии и составу груза. Простые задачи проходят тот же договор приёмки. Локальная модель не получает весь репозиторий или самостоятельное управление рабочей БД.

Модели готовят и запускают проверки; результат определяется pytest, Playwright, SQL-проверками и реальным выполнением процесса. Ответ «всё правильно» не заменяет протокол. Владелец принимает демонстрацию и отмечает требование выполненным.

## Локальные V100

Владелец сообщил о двух NVIDIA V100 по 16 ГБ. Это оборудование локального помощника; оно не является доказательством мощности Oracle или API.

Начальный кандидат — Qwen2.5-Coder-14B-Instruct в GGUF Q4_K_M. В NS05 проверяется Ollama на V100, контекст 8–16 тысяч токенов, память, скорость и корректность редактирования. При достаточной памяти можно проверить два независимых исполнителя, каждый на одной карте; это не означает два действительно полезных автономных разработчика до испытания.

Дополнительный кандидат — Qwen3-Coder-30B-A3B с квантованием для одной модели на двух картах. Все веса, а не только активные эксперты, должны быть размещены вместе с кэшем контекста. Две карты не образуют одну прозрачную область 32 ГБ; учитываются распределение модели, межкарточный обмен и свободная память каждого GPU. Большой заявленный контекст модели не принимается за доступный контекст сервера.

Для работы предлагается Aider с заданным списком файлов и явным ограничением контекста. Qwen Code с локальным совместимым endpoint — альтернативная оболочка после отдельной проверки tool calling. На время действующего запрета Git/GitHub Aider запускается без Git и автоматических коммитов. Настройка сервера и загрузка моделей этим планом не выполнялись.

Квалификация: 10 одинаковых ограниченных задач на копии проекта — форма, валидатор, преобразование сообщения, тест по заданному контракту, анализ ошибки. Измеряются доля принятых решений с первого раза, время генерации, число исправлений, время проверки владельца, обрезание контекста и OOM. Предлагаемый допуск — минимум 8 из 10 принятых задач и отсутствие критического нарушения. Два неудачных исправления возвращают задачу облачной модели с диагностикой. Экономия считается по завершённым принятым задачам с учётом проверки, а не по бесплатным токенам.

## Проверка каждого спринта

1. Требования и примеры. Проверяющий задаёт конкретные входные данные и ожидаемый результат. Для запаса — количество до и после, резерв, партия, ячейка; для рейса — физические места, назначения и фактическая погрузка.
2. Проверка логики. Чистые расчёты, кратности и допуски проверяются pytest. Ожидаемые значения выводятся из требований, а не повторяют программный алгоритм.
3. API и Oracle. Сценарий проходит через реальную команду; SQL подтверждает баланс и состояние. Заглушка не подтверждает фиксацию в Oracle или работоспособность ERP-адаптера.
4. Ошибка и повтор. Проверяются неверный SKU, адрес или SSCC, отсутствие права, повтор скана, тайм-аут после commit и отказ между шагами.
5. Конкуренция. Два терминала, две волны или два фоновых исполнителя одновременно претендуют на один объект. Подтверждается один допустимый товарный эффект.
6. Рабочее место. Playwright проверяет реальные интерфейсы и ответы API. Для весов, камер, принтера и терминалов добавляется испытание оборудованием; имитация подтверждает только контракт.
7. Производительность. Для затронутых команд фиксируются время ответа, ожидание Oracle, блокировки и самые долгие SQL/SKV. При существенном отклонении принимается решение об исправлении либо документированной работе.
8. Регрессия. Повторяются затронутые штатные процессы и связанные предыдущие сценарии. После исправления теста независимый проверяющий подтверждает, что бизнес-ожидание осталось прежним.

Для документальных спринтов проверяются полнота, ссылки, номера и связь с источниками. Для чисто визуальной правки без логики выполняется проверка рабочего места; искусственные тесты, повторяющие текст интерфейса, не создаются.

## Пример: NS21, мягкий резерв

Свободно 100 коробок SKU, три заказа требуют 40, 30 и 30. Ожидается обеспечение 100 коробок мягким резервом без конкретной волны. Второй параллельный расчёт не увеличивает резерв до 200. Отмена заказа на 30 освобождает только его 30. После привязки оставшейся потребности к волне количество не удваивается. Последний переход проверяется совместно с NS26.

Для NS22 отдельный случай: свободны две коробки, три заказа требуют минимум по одной. Обеспечены первые два по очередности отгрузки волн; третий не получает дробную коробку. Исходная потребность ERP остаётся видимой.

## Нагрузочная приёмка

Значение «транзакции» и профиль нагрузки пока не уточнены владельцем. Расчётное предложение: 5 млн подтверждённых бизнес-операций за 12 часов, около 116 в секунду в среднем; отдельный час на пике около 1 200 операций записи и одновременно 3 000 чтений в секунду. Предлагаемый отклик критической команды от входа в API до ответа после commit: p95 до 300 мс, p99 до 1 секунды. До утверждения эти параметры не являются договором мощности.

Locust создаёт смешанную нагрузку нескольких ролей. Генератор работает отдельно от проверяемого приложения и БД. Проверяются активные SKU с конкуренцией, открытые волны, фоновые расчёты и ERP, история согласованного объёма, холодный и прогретый кэш. Отдельно измеряется полный отклик терминала. Бизнес-отказы различаются с техническими сбоями.

Обязательные результаты: нет потери подтверждённой операции, двойного списания и нарушения баланса; очередь после пика сокращается; нагрузочный генератор не ограничивает испытание; указан точный стенд. Малая новая БД или последовательные вставки случайных строк этого результата не дают. После прогона по каждому существенному медленному SQL принимается решение о переработке, ограничении окна, пакетной обработке, кэше, индексе или проверке плана. RPO/RTO определяются и проверяются для согласованных видов отказа.

## Пакет приёмки

По каждому спринту сохраняются требование, версия результата, patch или список файлов, паспорт стенда, команды, протокол, данные до/после, SQL и решение по задержкам. Статусы: предложен → готов к работе → выполняется → независимая проверка → принят. Блокирующая причина записывается отдельно. Конкретные пути тестов и команд фиксируются NS04 и в задании до начала разработки. Никакие тесты разработки этим документом не объявлены выполненными.
