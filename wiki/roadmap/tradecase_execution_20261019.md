## Проверки и остановка

Для каждого результата сохраняются версия кода/схемы, исходные данные, действия, ожидаемый и фактический состав КМ, количества, owner, адрес, заказ, рейс и ответы обеих систем. Статусы: «не выполнялось», «пройдено», «не пройдено»; проверка на имитаторе помечается отдельно. Итоги 660/440 и 640/460 не объединяются с дополнительными тестовыми остатками 50 коробов.

Oracle-изменения получают apply/rollback/verify, запись в wiki/database и проверку живой базы после применения. Серверные права проверяются по роли, складу и собственнику; повтор неизменной команды сохраняет operation_id, конфликт содержимого отклоняется, при UNKNOWN запрашивается состояние исходной операции. Изменение политики модулей требует обоснования и независимого ревью; архитектурный baseline не расширяется.

После значимых сценариев измеряются UI, API и SQL при указанном объёме данных, числе вызовов и состоянии кэша. Для долгих запросов по RRL_SQL_SLOW_LOG, /api/admin/slow-sql и API-аудиту записывается решение: переписать, ограничить выборку, пакетировать, кэшировать, добавить индекс, проверить план/статистику либо назначить backlog с владельцем. Неутверждённый SLA не заменяется выдуманной нормой.

Перед приёмкой кода запускается `python scripts/retailcase_quality_gate.py`; перед сдачей русских текстов — `scripts/check-encoding.ps1`. Для UI проверяются desktop и 390 px, сканер/ручной ввод, подсказки действий, ссылка на локальную справку, потеря связи и восстановление. Самостоятельное чтение всего описания удаляет повторы, неполные фразы и неподтверждённые функции.

В 18:00 новые работы прекращаются: сохраняются завершённые результаты, открытые дефекты, незавершённые транзакции/очереди, занятые файлы и счётчик обращений. Полный продукт не объявляется готовым без T12 и отдельно перечисленных внешних проверок.
