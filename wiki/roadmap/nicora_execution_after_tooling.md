# NICORA: план исполнения после подготовки инструментов

Дата: 7 октября 2026 года. Основание: требования редакции 55 и [план NS00–NS67](../requirements/nikora_delivery_v55/README.md). Это порядок будущих работ; подготовка MCP и skills не закрывает разработческие спринты. Детальные зависимости и назначения автора/проверяющего остаются в [sprints.json](../requirements/nikora_delivery_v55/sprints.json).

## Подготовка инструментов — выполнено

Пять проектных MCP подключены и прошли реальные initialize/tools/list/tools/call: wiki, repo, Oracle, Docker/routing, Playwright. Smoke теперь использует корректный handshake MCP, ограниченное ожидание ответа, закрытие дочерних процессов и отдельный профиль Playwright. Доступность MCP и маршрутизаторов разделена: OSRM и Valhalla сейчас не отвечают; строгий routing gate должен отклонять такое состояние.

Шесть skills созданы в tools/skills/ и установлены в локальный каталог Codex. Проверены YAML/frontmatter, ссылки на существующие wiki/config, точное совпадение установленных копий; восемь тестов проверяют тайм-аут, ложное здоровье маршрутизации, ошибочный ответ MCP, конфликт установки и повтор установки. Для автоматического обнаружения в каталоге skills нужна свежая сессия Codex; файлы доступны для прямого чтения уже сейчас.

Повторная проверка:

```powershell
python scripts/install_nicora_skills.py
python scripts/test_mcp_servers.py --report tmp/nicora_tooling/mcp-health.json
python -m pytest tests/tooling/test_nicora_tooling.py -q -o cache_dir=tmp/nicora_tooling/pytest-cache
```

Перед транспортной приёмкой дополнительно:

```powershell
python scripts/test_mcp_servers.py --require-routing --report tmp/nicora_tooling/routing-health.json
```

Это проверка ответов HTTP, не приёмка семантики маршрутов: route smoke запускается отдельно. Пользовательские MCP уже подключены, config.toml не переписывался. Исходники существующих MCP не дублировались; общая проверка исправлена. Бизнес-код и Oracle DDL не изменялись.

## Очередь разработки

| Этап | Спринты | Законченный результат и критерий перехода |
|---|---|---|
| 1. Паспорт и обследование | NS00–NS04 | Выделенный dev-стенд ORCL со схемой RABAEV, реестр всех правил редакции 55, GAP склада/транспорта/ERP, итоговое ТЗ и договор приёмки. Каждое правило имеет источник, статус покрытия и проверку. |
| 2. Квалификация локального помощника | NS05 | Проверка V100 и ограниченных задач Qwen; измеренный допуск. Может готовиться независимо от обследования, но не блокирует работу основным инструментом. |
| 3. Техническая основа | NS06–NS12 | Воспроизводимая сборка, Oracle-пулы/аудит, атомарные команды, идемпотентность, обмен, фоновые задания, мониторинг и архив. Проверены отказы и конкуренция. |
| 4. Справочники и заказы | NS13–NS17 | SKU/упаковка, подсклады/адреса, магазины/тара/машины, обмен справочниками и приём ERP-заказов. Непригодные данные отклоняются с объяснением. |
| 5. Приёмка и доступный запас | NS18–NS23 | Фактическая приёмка, размещение/слотирование, мягкий резерв, дефицит и реестр физических/вложенных грузовых мест. Баланс и происхождение не теряются. |
| 6. План транспорта и волны | NS24–NS26 | План рейсов, сроки/подсклады и жёсткий резерв. Плановый приход не выдаётся за реальный запас, параллельные волны не резервируют одно количество дважды. |
| 7. Пополнение и ресурсы | NS27–NS33 | Мини-макс, целое/частичное пополнение, смены/техника, задания ТСД, разрешение волн и прогноз нагрузки. Нет двойных назначений и превышения вместимости. |
| 8. Комплектация и исключения | NS34–NS40 | Стеллажный отбор, весовой товар, накидывание, пикбайлайн, инвентаризация, срочное восстановление и малая тара. Фактические количества и масса подтверждены. |
| 9. Контроль и консолидация | NS41–NS45 | Вес/состав, исправление, повторный выпуск, выборочная проверка и консолидация. Изменённый состав не наследует старый допуск. |
| 10. Экспедиция и сухой цикл | NS46–NS50 | Ворота, фактическая погрузка, перенос рейсов, магазинная приёмка и сквозная репетиция сухого потока. ERP/API/Oracle/ARM/ТСД показывают согласованные факты. |
| 11. Полный бизнес-контур | NS51–NS58 | Межскладские плечи, кросс-док, вес/фото магазина, потери, возвраты, тара, нормативные/дополнительные затраты и закрытие дня. Нет скрытых расхождений. |
| 12. Оптимизация и большая приёмка | NS59–NS63 | Динамические диапазоны, общий контроль solver, фактическое восстановление, согласованная смешанная нагрузка и полная смена с реальным оборудованием. |
| 13. Пилоты и запуск | NS64–NS67 | Два наблюдаемых пилота по 10 рабочих дней, инструкции, воспроизводимая установка и итоговое закрытие всех правил. Живые операции — после предусмотренного разрешения владельца. |

Группы показывают маршрут работы, а не отменяют зависимости отдельных карточек. При готовом соответствии принимается существующая функция; недостающий фрагмент реализуется отдельным ограниченным заданием. Shared schema/API changes идут последовательно; параллельные модели не запускаются этой подготовкой.

## Первое задание

Начать NS00: инвентаризировать версии и ресурсы, зафиксировать код/конфигурацию, использовать существующую RABAEV в подтверждённом владельцем выделенном dev-экземпляре ORCL и проверить воспроизводимую fixture, проверить API/ARM/ТСД. 07.10.2026 владелец подтвердил, что текущий ORCL целиком выделен под разработку и тесты; все работы NICORA выполняются непосредственно в RABAEV. Известные 59 INVALID объектов классифицировать по путям использования; подготовка инструментов их не исправила. Изменения существующей схемы RABAEV идут по [[database/oracle_change_protocol]] и существующему разрешению пользователя на конкретный объём.

Следом NS01 присваивает постоянные ID всем правилам 15 процессов, двум блокам управления и 21 справочнику. NS02/NS03 сверяют реальный код и Oracle с этими ID; NS04 формирует итоговое ТЗ. Календарь и состав доработок уточняются после GAP и пяти принятых изменений; исторические 175–304 дня не используются как обещание срока.

Каждый функциональный результат: бизнес-ожидание → реализация → API/Oracle проверки → ошибки и конкуренция → ARM/ТСД → долгие SQL/SKV и решение → независимая проверка → приёмка владельца. Открытая независимая проверка не выдаётся за выполненную.

## Обязательный структурный gate — 7 октября 2026 года

По поручению владельца применён [договор модульной разработки](../architecture/nicora_modular_development_contract.md). Перед приёмкой каждой доработки запускается python scripts/nicora_quality_gate.py: границы и static dependency graph, legacy debt ratchet, архитектурные/поведенческие тесты и typecheck обоих frontend. Начальный результат: 123 файла, 86 пунктов наследованного долга, 23 tests passed, оба typecheck прошли. Это не заменяет API/Oracle/конкурентную и бизнес-приёмку. Начат постепенный рефакторинг на примере предметного правила типа транспорта. Следующие первые две карточки: NS00 и NS01; их готовность не заявляется.
