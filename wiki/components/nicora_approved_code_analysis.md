## Существенные стыки в прочитанном коде

1. `picking_service.py:launch_wave` фиксирует PL/SQL вызов через gateway, затем отдельно обогащает/резервирует/выпускает задания. `OracleGateway.execute/execute_plsql` открывают собственное соединение и commit. Следовательно, наличие `transaction()` рядом не объединяет существующие отдельные calls. NS08 меняет конкретный сценарий с общим cursor, а не создаёт вторую универсальную платформу.
2. `transport_service.py:close_task` подавляет ошибки вызова `TRANSPORT_TASK.can_print` (except Exception: pass), затем пишет «Отгружен». Для NICORA нельзя считать эту ветку обязательным общим контролем готовности. NS47/NS48 исправляют переходы и разделяют закрытие/погрузку/выезд.
3. `production_exchange_service.py` регистрирует тип PRODUCTION_RELEASE; SAP-only входящая поставка и retail manifest не установлены в просмотренном потоке. `outbox_service.py` выбирает MockRegulatoryAdapter по умолчанию — функциональная очередь есть, реальную интеграцию нужно подключать адресно.
4. Корневой C# Form1 действительно вызывает ту же паллетизацию, что предварительно читалась в MINI WMS. Legacy ID P_... сохранять; SSCC — отдельное внешнее требование. KOLPAL в функции переопределяет количество на паллете, не напрямую количество паллет.

## Пределы и решение

Это анализ основных бизнес-цепочек и инвентаризация остальных областей. Не построчное ревью всех 434 файлов и не приёмка runtime. Полная реализация ЕГАИС, фото-приёмки магазина, оборотной тары и NICORA-многоплечевой консолидации не установлена в рассмотренных источниках; перед их доработкой дочитать соответствующий путь. Отсутствие найденной реализации не равно доказанному отсутствию во всём архиве.

План переработан под **доработку существующей WMS/TMS**. Первое функциональное направление — входящая поставка SAP → SKU/режим маркировки → фактические паллеты → задание размещения → адрес хранения. Затем существующие волны/резервы/отбор и транспортный стык. NS05 не блокирует бизнес-функции; инфраструктурные улучшения выполняются по нужде сценария или перед выпуском. Минимум 80% ресурсов — создание функционала, дополнительные тестовые прогоны владельцем остановлены.

## Основной план после пересмотра всей очереди

По дополнительному поручению владельца основная очередь сокращена до восьми функциональных результатов NI01–NI08. NS00–NS67 теперь подробный каталог требований/доработок, не 68 обязательных спринтов. Актуальный документ: wiki/requirements/nikora_delivery_v55/implementation_plan.md. Первый результат — NI01, приход SAP и размещение; начало — доработка действующей карточки SKU. Это изменение плана, не заявление завершения новой функции.
