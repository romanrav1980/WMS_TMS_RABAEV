# NICORA: глобальное сопоставление требований и текущего продукта

7 октября 2026 года. [Построчная карта 35 возможностей](nicora_capability_matrix_20261007.md) · [пересмотренная очередь](../requirements/nikora_delivery_v55/implementation_plan.md).

## Вывод для разработки

Существующие WMS/TMS являются основой NICORA. Диспетчер, назначение СТ, транспортные справочники, карта/VRP, Ганта, биллинг, водительские операции, волны, резервы, пополнение, складские задания, контроль и аудит уже представлены кодом. Их повторное создание исключено. Основная работа — согласовать бизнес-правила и завершить товарные эффекты между уже существующими модулями. Наличие функции не равно полному соответствию ТЗ.

Очередь NI01–NI08 полностью переопределена: NI03 — складские эффекты/доступность; NI04 — вложенные SSCC и точный состав отбора; NI05 — контроль/погрузка/приёмка магазина; NI06 — межскладской поток/возвраты/тара. Старые номера NI04/NI05 теперь имеют другой объём: ссылки на прежние номера надо читать по текущему плану.

Утверждённые источники: корневой WindowsApplication2/WindowsApplication2, текущий FastAPI, React admin/terminal, raw UI, SQL и live Oracle ORCL/RABAEV. Никаких удалённых обновлений или публикаций не выполнялось. [Утверждение baseline](../sources/nicora_code_baseline_proposal_20261007.md).

## Что изменено первым: SAP → существующая СТ → существующий рейс

[legacy_preparation.py](../../api/wms_api_server/app/modules/fulfillment/infrastructure/legacy_preparation.py) принимает явно согласованную оператором укладку SAP-заказа и вызывает ORDERS.CREATE_ORDER/ADD_ORDER_ROW, RRL_SBORKA_PALLETS_ADD2 и RRL_SBORKA_PALLET_ROWS_ADD4. Заполняется существующий RRL_CUSTOMER_ORDER_FULFILLMENT с PLANNED и нулевым фактом. Повтор возвращает сохранённый результат, изменённая укладка конфликтует. Начальная потребность SAP остаётся неизменной. Полные коробки обязательны там, где действующий writer принимает целое PACK_COUNT.

В существующем [customer-orders.js](../../wiki-raw/wms_admin_ui_reference/customer-orders.js) добавлена подготовка СТ с правкой укладки. Назначение использует прежний POST tasks/{id}/sts. [st_assignment.py](../../api/wms_api_server/app/modules/transport/infrastructure/st_assignment.py) оставляет RRL_TT_ADD_PALL и прежнюю связь TRANSTASK_ID; добавляет одну транзакцию, проверку ошибки legacy writer и результата назначения. Второй транспортный пульт или таблица назначения не созданы.

Миграция [009](../../db/migrations/2026-10-07_ni02_legacy_st/009_apply.sql) установлена в RABAEV: три поля сохранённой подготовки и PLANNED в существующем fulfillment. Установка: 3 statements, 0 errors; поля и ENABLED constraint с PLANNED прочитаны из live metadata. API загружен: 374 маршрута. Бизнес-прогоны и импорт примерных заказов не выполнялись.

Ограничение: sync_fulfillment_from_legacy вставляет отсутствующие записи, но не обновляет уже созданный PLANNED. Переход к PICKED/SHIPPED должен быть связан с настоящим складским/отгрузочным эффектом в NI03/NI05. Подготовка СТ не является сборкой товара и не создаёт запас.

## Матрёшка SSCC: проверенный вывод вместо предположения

**Основа вложенной агрегации уже есть.** В live RRL_CRPT_AGGREGATION имеются SSCC/PARENT_SSCC, в ITEMS — CHILD_TYPE/CHILD_SSCC/CHILD_CIS. RRL_PRODUCTION_API.ADD_AGGREGATION_ITEM добавляет дочерний SSCC или CIS и обновляет его родителя; API production предоставляет create aggregation и add item. Источники: [002_apply.sql:470](../../db/migrations/2026-05-17_feed_factory_traceability/002_apply.sql:470), [production_service.py:186](../../api/wms_api_server/app/services/production_service.py:186), [production.py:75](../../api/wms_api_server/app/routers/production.py:75). Это больше, чем одно неиспользуемое поле parent_sscc.

**Завершённая складская матрёшка этим не подтверждена.** Прочитанный add item проверяет повтор только внутри выбранного родителя, допускает перезапись PARENT_SSCC без удаления старого items и не проверяет цикл. В live constraints ITEMS нет FK/уникального ограничения единственного владельца. NI01 известную агрегацию разворачивает в плоские физические единицы и сканированный верхний код; дерево упаковки не переносится как действующий складской объект.

RRL_OBJECT.PARENT_OBJECT относится к справочнику описаний/справки, RRL_WT.PARENT_ID — к сводным заданиям; эти связи не являются SSCC/HU деревом.

Решение NI04: расширять существующую агрегацию после определения владельца логистического состава и связи с регуляторной агрегацией. Никакой второй универсальный HU-реестр заранее не утверждён. Требуются единственный активный родитель, отсутствие циклов/сирот, версия состава, упаковка/вскрытие/перепаковка с историей, перенос дерева одним эффектом, точные партии/марки/масса и подсчёт физических верхних мест. Вложенное SSCC не добавляет отдельное место в автомобиле. Внутренние pallet identifiers остаются допустимы; SSCC — связанный стандартный идентификатор, а не ограничение всех legacy полей.

## Найденные dev-заглушки: происхождение и решение

В текущем PALL_SPLITTER split_ufa/split_vegetables и COMPL divide_st_bypal/add_art_2pall возвращают константу 0; REMAINS.close_othod_pall_row возвращает 1. Это не доказательство успешной операции. Происхождение части заглушек — [compatibility SQL 11 мая](../../db/compatibility_fixes/2026-05-11/001_client_tserver_compat.sql:459), до новых NI01/NI02 изменений.

REMAINS.trial_by_weight, set_scan_proove и close_othod_pallet имеют настоящее делегирование; найденные RRL_TRIAL_BY_WEIGHT/RRL_SET_SCAN_PROOVE2/RRL_CLOSE_OTHOD_PALLET изменяют данные. Их нельзя объединять с заглушками только из-за короткой wrapper-функции.

Для автоматического legacy split сначала восстановить полный оригинальный body из достоверного исходника. Пока новый SAP-стык использует явную ручную укладку и существующие row writers. Не писать вторую автоматическую паллетизацию и не объявлять авторазбиение готовым.

## Аудит новых предложений и добавленного кода

| Предложение/добавление | Решение и причина |
|---|---|
| Новый order–trip registry/диспетчер | Исключено: TRANSTASK_ID и готовый TMS API уже связывают СТ с рейсом |
| Новые VRP, карта, Ганта, биллинг | Исключено: готовые модули; дополнять только общие ограничения NICORA |
| Новый ARTMAS/store/supply importer и file gateway | Сохранить: production exchange другого назначения не реализует Retail ARTMAS10 и неизменный SAP-заказ; identity/inbox нужны конкретному входу |

| NI01 private pick-cell rules | Свести с опубликованным pick-face/topology authority; не вести независимое назначение одного SKU двумя справочниками |
| NI01 destination claims | Согласовать с существующими CELL_SLOT_ID reservations: назначение слота и товарный резерв имеют разные цели; без изучения владельца не удалять таблицу или данные |
| NI02 PLANNED fulfillment | Сохранить существующий registry; завершить переходы по фактам, без отдельного реестра исполнения |
| Вложенные SSCC | Переклассифицировано из отсутствующей функции в неполную существующую агрегацию; расширение NI04 |
| Новый MCP/skill для структурности | Не требуется: доступны Oracle read/apply, gateway, модульные public/application/infrastructure границы и wiki; новые механизмы создавать только при конкретной недоступной операции |

## Ограничения и порядок продолжения

NI02 manual SAP–ST bridge реализован, но поздние решения/реальный XML и восстановление автопаллетизации остаются. Следующее функциональное изменение — NI03: общий фильтр запаса и одна команда физического завершения существующего задания. Затем NI04, включая матрёшку. Задания Qwen NI01 подготовлены отдельно и не запускались. Не обещать календарь по количеству найденных функций.

Функциональные/нагрузочные прогоны не выполнялись. Поэтому новых измерений slow SQL нет; после будущего разрешённого meaningful case решение по длинным запросам обязательно согласно AGENTS.md. Исходники UTF-8, кодировочный контроль проводится отдельно; известный сырой Oracle export с legacy text не переписывается.
