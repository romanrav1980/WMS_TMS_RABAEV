Владелец: transport/inventory infrastructure; транзакция: внешний OracleGateway.transaction; проведение количества: только RRL_STOCK_POSTING_API. Штатные RRL_TRASPORT_TASK_ADD/RRL_TT_ADD_PALL и общий validator136 сохранены.

Создание рейса из кластера ранее выполняло три независимые транзакции. Теперь create_existing_cluster использует один cursor-bound TransactionGateway для создания, реквизитов и назначения исходных СТ. Ошибка любого этапа откатывает весь рейс. Поиск района остаётся прежним, максимум200 уникальных СТ; повтор после неизвестного результата пока не защищён устойчивым operation_id — следующий шаг139, весь NI08.1 не закрыт.

Авторский фактический кейс scripts/ni081_atomic_cluster_existing_case.py использовал только прежние частные СТ/машины136: машина10кг отклонена, количество рейсов и назначения не изменились; подходящая машина создала33526 с двумя СТ и настоящим USER_ID admin/driverNULL. Собственный рейс затем отменён, машины возвращены в неактивное состояние. Товарные остатки и движения не создавались.

Удалены альтернативные PREPARED-ветки физического завершения задания, SAP-приёмки и размещения из Receiving. Неактивное ядро отклоняет проведение. Прежняя регистрация паллеты/маркировки/задания выделена в ReceiptBooking: только метаданные под блокировками уже рассчитанного native плана, без вставки товарного события. Получение команды SAP отделено от планирования/staging. Назначение/старт/отмена прежнего WarehouseTaskService переиспользуются через типизированный factory/Protocol, обратного импорта legacy-сервиса из модуля нет.

Исходная SAP-операция REUSE.SAP.RECEIVE:cdbf4c0962 повторена через Receiving: сохранённый результат совпал полностью, количество RRL_EVENTS неизменно. Семь точечных проверок неактивного ядра/точного количества/AST-классификатора прошли. Новый товар для проверки не создавался.

AST отличает типизированную application-command.execute от SQL только при разрешённом исходном классе и неизменённом receiver; SQL-литерал/другой gateway/callproc не освобождаются.
