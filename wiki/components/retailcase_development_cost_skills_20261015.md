# Снижение стоимости разработки: навыки и повторяемая автоматизация

15.10.2026, анализ по поручению владельца. Ничего не установлено и настройки моделей/подписок не менялись. Основной вывод: сначала доработать существующие шесть NICORA skills короткими рецептами и проверенными скриптами. Общие инструкции по Python/React/Oracle во многом уже покрыты; повторная генерация механических операций и восстановление текущего состояния дают больше возможностей для экономии.

## Что подтверждено проектом

- В корневом `scripts/`2910 Python-файлов; имена59 содержат checkpoint,28 fixture,41 slow. Это каталог, а не измерение расходов: количество файлов не доказывает, что каждый запуск был лишним. Но разовые версии требуют повторно устанавливать актуальность и границы применения.
- CASE/TASK/GROUP tests отдельно создают actors/role/grants/resource/session, сохраняют исходные версии и затем компенсируют через canonical owners. У CASE1138 пришлось отдельно завершить права, частные группы, резерв, тару и сессию. Два GROUP quantity proof не дали APPLIED; physical guard сохранён.
- Store/assembly/CASE имеют отдельные browser/PWA runners. Последний regression потребовал явно указать production8088, повторно войти после reload и раскрыть details перед нажатием скрытой кнопки. Это конкретные настройки среды и взаимодействия, которые стоит переиспользовать.
- Handoff C0114 остановился после STATUS из-за квоты, TO_CODEX отсутствовал. Исторические TASK/index строки оставались рядом с новым состоянием. Авторство реального Claude и параллельных локальных изменений пришлось сверять отдельно.

## Готовые навыки: что рассматривать

Проверены официальные исходники15.10.2026:

- [OpenAI playwright](https://github.com/openai/skills/tree/main/skills/.curated/playwright) — CLI управление браузером. Может быть полезен для интерактивного разбора новых экранов. Сейчас проект уже использует установленный Node Playwright и готовые сценарии; bundled wrapper ориентирован на shell/npx. На Windows переносимость и пересечение с доступным browser-act нужно проверить до установки. Сам по себе не заменяет проектный evidence runner.
- [Anthropic webapp-testing](https://github.com/anthropics/skills/tree/main/skills/webapp-testing) — Python Playwright и helper запуска серверов. Подходящие общие приёмы есть, но второй Python browser stack поверх текущего Node увеличит поддержку. Не рекомендую устанавливать одновременно с другим дублирующим browser workflow ради экономии.
- [Anthropic frontend-design](https://github.com/anthropics/skills/tree/main/skills/frontend-design) — визуальное направление и самопроверка интерфейса. Вторичный кандидат для новых экранов; утверждённые warehouse сценарии и существующий digital twin стиль имеют приоритет. Навык не задаёт предметный путь сканирования/весов/восстановления.
- `skill-creator` и `skill-installer` уже доступны. Повторная установка не нужна. Релевантные Oracle/API/UI/delivery/acceptance/operations skills также уже установлены.

Предпочтение сейчас: адаптировать существующие локальные навыки. Скачивание не является доказанной экономией, пока не показано устранение конкретного повторения без нового дублирующего стека.

## Уточнение владельца: расход несоразмерен задаче

15.10.2026: владелец отдельно указал на слишком быстрый расход токенов. Рабочая рекомендация: GPT-6.1 Sol/default reasoning/Standard для основной реализации, Luna для чётких небольших задач, Astra для сложного анализа; модель и настройки за пользователя не изменялись. [Официальный выбор модели](https://learn.chatgpt.com/docs/models), [расход режимов](https://learn.chatgpt.com/docs/pricing): Fast использует включённую квоту2.5x, Ultrafast8x против Standard той же модели. Это не измерение стоимости данной сессии.

Применять сейчас: один основной исполнитель; отдельный проверяющий только на ограниченный критический diff; не передавать полную историю всем агентам; один принятый пакет за раз; адресные тесты после изменений и один общий gate на готовый пакет. Короткий current-context вместо повторного чтения истории, скрипты вместо новых одноразовых проверок, краткие отчёты. Требование работать до23:00 не расширяет scope и не оправдывает непрерывный параллельный анализ. Все лишние задания агентам прекращены, текущий HU read scope пакет завершается отдельно; SHIPPING_GROSS кандидат не установлен.

Это defaults, не доказательство effective настроек текущего приложения. Поэтому первая конкретная рекомендация — Standard вместо Priority/Fast, основную модель пока оставить. [Config reference](https://learn.chatgpt.com/docs/config-file/config-reference) подтверждает отображение Fast→priority. Конфигурация и MCP не менялись; секреты/команды серверов не выводились. В доступных локальных журналах найдены отдельные automatic-review счётчики, но полного usage этой основной сессии нет; их нельзя суммировать в её стоимость.

Для следующих пяти сопоставимых принятых инкрементов фиксировать: известные фактические token/usage данные (если доступны), число прочитанных файлов/объём вывода, ручные повторные команды после ошибок среды, gate/build прогоны на одном hash, время подготовки/компенсации фикстуры и число возвратов после review. Сравнивать стоимость принятого инкремента, а не одной генерации. Не обещать проценты или рубли без исходного замера; физическую/Oracle/конкурентную приёмку ради сокращения цифр не пропускать.

Для подписочного лимита полезно отдельно измерять время до принятой функции и расход доступной квоты; для платных API — фактическую стоимость вызовов по принятому тарифу. Тарифы и ограничения здесь не оценивались. Этот анализ не разрешает менять модель, подписку, покупать сервисы или публиковать код.
