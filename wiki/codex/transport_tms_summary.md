## Зачем это нужно

WMS работает. MES работает. Транспорт — единственная точка,
где диспетчер до сих пор работает в C# WinForms 2005 года.
Нет карты. Нет маршрутизации. Нет авто-планирования.
Координаты адресов **уже есть** в `RRL_ADDR.SHIROTA/DOLGOTA` — просто не используются.

**Задача:** перенести управление рейсами в FastAPI + React,
добавить интеллектуальное планирование, оставить C# работать параллельно без изменений.

## Модель данных

**Единица назначения — СТ** (сборочное задание).
Одно СТ = все паллеты одного адреса/заказа одной волны сборки.
`RRL_TT_ADD_PALL(TT_ID, ST_NUMBER, user_id)` — атомарная операция назначения.

**Новые таблицы (миграции 044–045):**

| Таблица | Назначение |
|---------|-----------|
| `RRL_TR_VEHICLE` +2 поля | Вместимость: WEIGHT + VOLUME для прогресс-бара |
| `RRL_ADDR` +3 поля | SERVICE_MIN, DELIVERY_FROM, DELIVERY_TO — временны́е окна |
| `RRL_ADDR_DISTANCE_MATRIX` NEW | Кэш OSRM: расстояния + время между адресами |
| `RRL_TT_ROUTE_TEMPLATE` NEW | Исторические шаблоны маршрутов по дням недели |
| `RRL_TT_RL_CORRECTIONS` NEW | Правки диспетчера → обучение системы |
| `RRL_TT_AUTO_PLAN_SESSION` NEW | Аудит всех сессий авто-планирования |


## Три VRP-решателя

```
┌─────────────────────────┬──────────────────────────────────────────────┐
│ Шаблонный   < 50 мс     │ Jaccard(сегодняшние адреса, шаблон) > 0.85  │
│                         │ → взять шаблон, скорректировать объёмы       │
│                         │ Обучается на 3 одинаковых правках диспетчера │
├─────────────────────────┼──────────────────────────────────────────────┤
│ OR-Tools    ≤ 10 сек    │ LNS + guided local search                    │
│                         │ Учитывает временны́е окна (единственный!)    │
│                         │ Качество: ~1-3% от оптимума                  │
│                         │ Seed: Clarke-Wright O(N² log N)              │
├─────────────────────────┼──────────────────────────────────────────────┤
│ Attention   < 500 мс    │ Трансформер (Kool et al., ICLR 2019)        │
│ Model       на CPU      │ Обучен на 100k синтетических + исторических  │
│                         │ Качество: ~3-5% от оптимума для N ≤ 100     │
│                         │ Переобучается ежемесячно                     │
└─────────────────────────┴──────────────────────────────────────────────┘
```

**Оркестрация:**
```
1. Jaccard-поиск шаблона (< 50 мс)
   ├─ similarity > 0.85 → Шаблон как Вариант 1
   └─ нет → пропустить
2. Attention Model + OR-Tools запускаются параллельно
3. Применить RL-коррекции (правки диспетчера) к каждому варианту
→ Вернуть 2–3 варианта с таблицей сравнения (км / часы / стоимость / ✓окна)
→ Диспетчер выбирает, редактирует, нажимает «Принять»
→ Рейсы создаются в Oracle
```

## Критерии приёмки

**Уровень 1 (ручной):**
- Рейсы и СТ загружаются на выбранную дату
- Чекбокс → «Создать рейс» / «Добавить в рейс» работают
- Снятие СТ с рейса
- C# WinForms видит всё без изменений

**Уровень 2 (полу-авто):**
- Цвета районов в таблице и на карте совпадают
- «⚡ Оптим. маршрут» → preview → диспетчер подтверждает
- Прогресс-бар обновляется мгновенно
- Манифест: порядок загрузки = обратный доставке

**Уровень 3 (авто):**
- `/auto-plan` возвращает ≥ 2 варианта за < 15 сек (50 СТ)
- Шаблон с similarity > 0.85 появляется первым (< 50 мс)
- OR-Tools не нарушает вместимость ТС
- «Принять» создаёт рейсы в Oracle, сессия фиксируется в аудите
- После 3 одинаковых правок диспетчера шаблон автоматически обновляется

**Load-test (evidence-driven):**
- Smoke: создать рейс → 5 СТ → оптим. → манифест
- Load: авто-план 50 СТ + 8 машин < 15 сек
- Артефакты: `report.json`, `report.md`, скриншоты всех 3 режимов
