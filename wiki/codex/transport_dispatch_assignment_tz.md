## 1. Контекст: как это работает сейчас в C#

### Единица назначения — СТ (сборочное задание)

**Диспетчер назначает не отдельные паллеты, а СТ целиком.**
СТ = сборочное задание = все паллеты для одного адреса по одному заказу.
Процедура `RRL_TT_ADD_PALL(TT_ID, ST_NUMBER, user_id)` обновляет
`RRL_SBORKA_PALLETS.TRANSTASK_ID` для всех паллет СТ одновременно.

### Три грида на tabPage6 («Заявки»)


### Два способа назначения

**А — Создать новый рейс:**
`RRL_TRASPORT_TASK_ADD` → TT_ID → для каждого СТ: `RRL_TT_ADD_PALL` → `RRL_TT_REORDER_ADR`

**Б — Добавить в существующий:**
Выбрать рейс кликом → отметить СТ → `RRL_TT_ADD_PALL` × N → `RRL_TT_REORDER_ADR`

## 2. Проблемы текущей реализации

1. **Порядок объезда — статическое число `ORD`**, не связанное с географией.
   Два адреса с ORD 5 и 6 могут быть на разных концах города.
2. **Нет авто-разбивки** — диспетчер вручную решает, сколько рейсов нужно.
3. **Нет индикатора загрузки машины** в момент набора.
4. **Нет стоимости рейса в реальном времени** — только после сохранения.
5. **Нет планировщика доков** — конфликты обнаруживаются постфактум.
6. **Нет обзора дня** — непонятно, сколько СТ не распределено и хватит ли машин.
7. **Только desktop** — C# WinForms.
8. **Фильтрация только по кнопке**, не live.
9. **Паллеты СТ** — только в отдельном окне по двойному клику.

**Блок «ИТОГО К ОТГРУЗКЕ»** — агрегаты по всем нераспределённым СТ на дату.

**Блок «ДОСТУПНЫЙ ПАРК»** — свободные машины (`WORKING_NOW=1`, `BLOCKED=0`),

красный индикатор «⚠️ Недостаточно машин».

Клик по точке — всплывает: адрес, СТ, паллеты, требуемый тип ТС.

**Авто-кластеризация** — кнопка `[Сформировать план дня]` запускает алгоритм
(см. раздел 4) и показывает предложенные рейсы как черновики.
Диспетчер принимает все или редактирует каждый.

### 3.4 Цветовое кодирование районов

Столбец «ц» (цвет) в таблице СТ — цветная метка по `RRL_ADDR.RAION`.
Цвета назначаются автоматически (по хешу строки района, до 12 цветов).

**Эффект:** диспетчер визуально видит, что «эти 5 строк одного цвета — один район»,
и быстро понимает, какие СТ естественно объединяются в один рейс.

Те же цвета — на карте в режиме Планирования.

### 3.6 Оценка дистанции и времени рейса

После назначения СТ система вычисляет (на Python-стороне, не в Oracle):
- **Суммарный путь** (км): Haversine-расстояния по цепочке Склад → Адр₁ → Адр₂ → … → Склад
- **Оценку времени** (ч): `RANGE_KM / AVG_SPEED + N_STOPS × SERVICE_MIN / 60`
  - `AVG_SPEED` — настраиваемый параметр (по умолчанию 40 км/ч в городе)
  - `SERVICE_MIN` — время на одну остановку (по умолчанию 15 мин)
- **Оценку стоимости**: используется `RRL_TT_BILL_PRICE_KM` для типа ТС

Всё показывается на карточке рейса в режиме реального времени при каждом изменении состава.

Расчёт делается **клиентски** из данных, уже загруженных (координаты есть в AvailableST).
Oracle-функция `RRL_TT_PLAN_SHIPPPING_HOUR` вызывается только при сохранении (как сейчас).

### 3.7 Кнопка «⚡ Авто-последовательность»

Доступна в нижнем гриде состава рейса.

Действие:
1. POST `/transport/tasks/{id}/optimize-sequence`
2. Сервер берёт координаты всех адресов рейса из `RRL_ADDR`
3. Применяет nearest-neighbour TSP от точки склада
4. Возвращает новый порядок ORD
5. Клиент показывает изменения с diff-подсветкой (какие строки переместились)
6. Диспетчер нажимает «Принять» или «Отмена»

**Это не принудительное изменение — диспетчер всегда может отказаться.**

## 4. Алгоритм авто-кластеризации (Формировать план дня)

**Вход:** список всех нераспределённых СТ на дату, список свободных ТС.

**Шаги:**

```
1. РАЗДЕЛЕНИЕ ПО ТИПУ ТС
   Группируем СТ по полю RRL_ADDR.TRANSPORT_TYPE (реф / гидробортник / обычный).
   Каждый тип — отдельный пул.

2. ГЕОГРАФИЧЕСКАЯ КЛАСТЕРИЗАЦИЯ (на Python)
   Для каждого пула применяем K-Means / DBSCAN по (SHIROTA, DOLGOTA).
   K = ceil(total_pallets_in_pool / avg_vehicle_capacity).
   Координаты берём из RRL_ADDR.

3. НАЗНАЧЕНИЕ КЛАСТЕРОВ НА ТС
   Жадный алгоритм: берём кластер с наибольшим весом → назначаем на
   наиболее вместительное свободное ТС подходящего типа.

4. СОРТИРОВКА ВНУТРИ КЛАСТЕРА (nearest-neighbour TSP)
   Стартуем из точки склада.
   На каждом шаге: следующий — ближайший непосещённый адрес (Haversine).
   Возвращаем к складу в конце.

5. РАСЧЁТ МЕТРИК ДЛЯ ПРЕДПРОСМОТРА
   Суммарный путь = Σ Haversine(i, i+1)
   Время = путь / AVG_SPEED + N × SERVICE_MIN
   Стоимость = RRL_TT_BILL_PRICE_KM[type, range]

6. ВОЗВРАТ ЧЕРНОВИКОВ
   Не создаём рейсы — только предлагаем. Диспетчер нажимает «Принять» или меняет.
```

**Ограничения алгоритма (честно):**

- Nearest-neighbour TSP — эвристика, не оптимум. Для 5–15 адресов разница с оптимумом незначительна.
- K-Means может давать «вытянутые» кластеры. Если результат плохой — диспетчер корректирует вручную.
- **Алгоритм — помощник, не замена диспетчеру.** Диспетчер знает контекст: дорожные работы, постоянные клиенты, особые договорённости.

**Вариант «Умные подсказки» (без принудительного плана):**
Вместо полного авто-плана — кнопка «🔍 Похожие СТ» рядом с каждым рейсом.
Система выделяет в правой таблице СТ, которые географически близки к уже назначенным в этот рейс (радиус N км от центроида рейса). Диспетчер сам решает, брать или нет.

## 5. Изменения модели данных

### 5.1 Добавить в RRL_TR_VEHICLE (миграция 044)

```sql
ALTER TABLE RABAEV.RRL_TR_VEHICLE ADD (
  WEIGHT_CAPACITY  NUMBER(8,0),   -- вместимость по весу, кг (NULL = не задана)
  VOLUME_CAPACITY  NUMBER(6,2)    -- вместимость по объёму, м³ (NULL = не задана)

```

### 5.2 Добавить в RRL_ADDR (миграция 044)

```sql
ALTER TABLE RABAEV.RRL_ADDR ADD (
  SERVICE_MIN  NUMBER(3,0) DEFAULT 15,  -- время на остановку, минут
  DELIVERY_TIME_FROM  VARCHAR2(5),       -- окно доставки с (HH:MM), NULL = любое
  DELIVERY_TIME_TO    VARCHAR2(5)        -- окно доставки до (HH:MM), NULL = любое

```

```sql
  A.REGION,
  A.RAION,
  A.ORD,
  A.SHIROTA,
  A.DOLGOTA,
  A.SERVICE_MIN,
  A.DELIVERY_TIME_FROM,
  A.DELIVERY_TIME_TO,
  A.TRANSPORT_TYPE,
  A.STOL                                              AS NEEDS_HYDRO_BOARD,
  P.WARE_ID,
  COUNT(DISTINCT P.PALLET_UID)                        AS PALLETS_COUNT,
  ROUND(SUM(R.ORDER_WEIGHT), 0)                       AS WEIGHT,
  ROUND(SUM(R.TARESIZE * R.PACK_COUNT) / 1000000, 2) AS VOLUME,
  RABAEV.RRL_ST_VERYFY_PERC(P.ST_NUMBER)             AS VERIFY_PCT,
  MIN(P.STDATE)                                       AS STDATE,
  MAX(P.TRANSTASK_ID)                                 AS TRANSTASK_ID
FROM RABAEV.RRL_SBORKA_PALLETS P
JOIN RABAEV.RRL_SBORKA_PALLET_ROWS R ON R.PALLET_UID = P.PALLET_UID
LEFT JOIN RABAEV.RRL_ADDR A ON A.ADDR = P.ADDR
WHERE P.DELETED IS NULL OR P.DELETED <> 1
GROUP BY P.ST_NUMBER, P.ADDR, A.REGION, A.RAION, A.ORD,
         A.SHIROTA, A.DOLGOTA, A.SERVICE_MIN,
         A.DELIVERY_TIME_FROM, A.DELIVERY_TIME_TO,
         P.WARE_ID, A.TRANSPORT_TYPE, A.STOL;
```

*Ключевое дополнение по сравнению с предыдущей версией: `SHIROTA`, `DOLGOTA`, `SERVICE_MIN`, временны́е окна.*

## 12. Автоматическое планирование рейсов

> Этот раздел описывает третий, полностью автономный уровень системы.
> Уровни 1–2 (ручное + полу-автоматическое) остаются как есть — данный слой
> добавляется сверху и всегда оставляет финальное решение за диспетчером.

---

### 12.1 Постановка задачи

**Задача:** утром, до начала работы диспетчера, система сама должна предложить
оптимальный план отгрузки на день — рейсы, состав, последовательность, доки.

Математически это **Capacitated VRP with Time Windows (CVRPTW)**:
- N адресов доставки, каждый с известными координатами, объёмом и временны́м окном
- K транспортных средств с ограниченной вместимостью (паллеты, вес)
- Одно депо (склад)
- Цель: минимизировать суммарный пробег (или стоимость, или время)

CVRPTW — NP-hard. При N > 20 точный перебор невозможен.
Для практического применения используем три независимых подхода
и выбираем лучшее решение из них.

---

### 12.2 Источник геоданных: OpenStreetMap + OSRM

#### Почему OSRM, а не Haversine

Haversine даёт расстояние «по прямой». Реальные дороги дают +20–60% к расстоянию
и совершенно другой порядок объезда. Для производственной системы нужны
**реальные дорожные расстояния и времена**.

**OSRM (Open Source Routing Machine)**:
- Использует данные OSM
- Self-hosted Docker-контейнер (данные РФ ~3 ГБ)
- `Table` API: матрица расстояний N×N за один запрос, < 100 мс для N=50
- `Route` API: точный маршрут с геометрией для отображения на карте
- Лицензия: BSD, без ограничений на использование

```
                 ┌──────────────────────────────┐
                 │  OSM Planet / Russia extract  │
                 │  osm.pbf → OSRM preprocessing │
                 └──────────────┬───────────────┘
                                │ Docker
                 ┌──────────────▼───────────────┐
                 │  OSRM HTTP Server :5000       │
                 │  /table  /route  /nearest     │
                 └──────────────┬───────────────┘
                                │ HTTP
                 ┌──────────────▼───────────────┐
                 │  WMS API: vrp_service.py      │
                 │  Кэш матриц → Oracle          │
                 └──────────────────────────────┘
```

### 12.3 Подход 1: Нейросетевой решатель (Attention Model)

#### Теоретическая основа

**Attention Model** (Kool, van Hoof, Welling — ICLR 2019) — трансформер,
обученный решать VRP методом Policy Gradient (REINFORCE).
Вход: координаты и атрибуты N узлов. Выход: последовательность посещений.

Архитектура:
```
Encoder: N × [x, y, demand] → N × d_model (self-attention, 3 слоя)
Decoder: autoregressive pointer network с context-attention
Обучение: REINFORCE с baseline (greedy rollout)
```

Качество решения: ~3–5% от оптимального для N ≤ 100.
Скорость инференса: < 50 мс на GPU, < 500 мс на CPU (для N=50).

#### Почему подходит для нашей задачи

Ключевое свойство: **обобщение без перепросчёта**.
Обученная модель принимает произвольный набор адресов и выдаёт решение мгновенно —
не нужно запускать оптимизатор каждый раз заново.

#### Реализация

**Библиотека**: `torch` + минимальная реализация Attention Model
(референс: https://github.com/wouterkool/attention-learn-to-route — ~500 строк Python).

**Данные для обучения**: синтетические + исторические маршруты:

```python
# Синтетическая генерация (для предобучения)
# Координаты — равномерно в [0,1]²; demand — [1, 9] паллет; capacity = 10
synthetic_instances = generate_vrp_instances(n=100_000, size=50)

# Исторические данные (для дообучения на реальной географии)
# Из Oracle: RRL_TRANSPORT_TASK + RRL_SBORKA_PALLETS + RRL_ADDR
# Берём одобренные диспетчером рейсы (CONDITION='DISPATCHED') за последние 6 мес
historical_routes = load_approved_routes(months=6)
```

**Обучение**:
```
Синтетические данные: 100 000 экземпляров, 100 эпох → ~2 ч на GPU
Дообучение на исторических: 10 000 экземпляров, 20 эпох → ~30 мин
Переобучение: раз в месяц (ночной cron)
```

**Инференс**:
```python
class AttentionModelSolver:
    def solve(self, addresses: list[AddrNode], vehicles: list[Vehicle]) -> VRPSolution:
        # Нормализация координат в [0,1]²
        coords = normalize([(a.lat, a.lon) for a in addresses])
        demands = [a.pallets_count for a in addresses]
        capacity = vehicles[0].pallets_capacity  # упрощение: однородный парк

        # Инференс модели
        # Возвращает список маршрутов: [[addr_idx, ...], [addr_idx, ...], ...]
        routes = self.model.sample_solution(coords, demands, capacity)

        # Денормализация + назначение машин
        return build_vrp_solution(routes, addresses, vehicles)
```

**Ограничения подхода:**
- Не учитывает временны́е окна (требует отдельной архитектуры)
- Качество падает при N > 100
- Требует GPU для быстрого инференса (без GPU — 1–3 сек на CPU, приемлемо)
- Нужно переобучать при изменении географии

### 12.4 Подход 2: Шаблонное планирование на основе мат. ожидания

#### Ключевой инсайт

Пищевой завод доставляет **в одни и те же магазины каждую неделю**.
Понедельник текущей недели ≈ Понедельник прошлой недели.
Средний заказ имеет высокую точность прогнозирования → число вариантов планирования мало.

Следствие: **не нужно решать VRP с нуля каждый день**.
Нужно найти ближайший исторический шаблон и скорректировать его.

#### Структура шаблонов

```sql
-- Миграция 045
CREATE TABLE RABAEV.RRL_TT_ROUTE_TEMPLATE (
  ID              NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  DOW             NUMBER(1),          -- день недели (1=пн, 7=вс)
  TRANSTYPE       VARCHAR2(20),       -- тип ТС
  ADDR_SIGNATURE  VARCHAR2(4000),     -- отсортированный список адресов (хеш-ключ)
  ADDR_LIST       CLOB,               -- JSON: [{addr, ord, avg_pallets}]
  TOTAL_KM        NUMBER(8,2),        -- суммарный пробег шаблона
  TOTAL_HOURS     NUMBER(5,2),        -- время выполнения
  USAGE_COUNT     NUMBER DEFAULT 0,   -- сколько раз применялся
  LAST_USED       DATE,
  QUALITY_SCORE   NUMBER(5,3),        -- оценка качества (0-1)
  CREATED_BY      VARCHAR2(100),      -- 'DISPATCHER' или 'AUTO'
  CREATE_DATE     DATE DEFAULT SYSDATE
);

CREATE INDEX IDX_TEMPLATE_DOW ON RABAEV.RRL_TT_ROUTE_TEMPLATE (DOW, TRANSTYPE);
```

#### Алгоритм накопления шаблонов

Каждый раз когда диспетчер **закрывает рейс** (`CONDITION = 'DISPATCHED'`):

```python
def on_route_dispatched(task_id: int):
    route = load_route_with_addresses(task_id)
    addr_signature = sorted_hash(route.addresses)
    dow = route.shipment_date.weekday()

    # Ищем похожий шаблон
    existing = find_template(dow, route.transtype, addr_signature, threshold=0.85)

    if existing:
        # Обновляем среднее (скользящее среднее по паллетам)
        update_template_stats(existing.id, route)
    else:
        # Создаём новый шаблон
        create_template(dow, route)
```

**Мера сходства шаблонов — Jaccard similarity:**
```
J(A, B) = |A ∩ B| / |A ∪ B|
где A, B — множества адресов
J > 0.85 → шаблоны считаются «одним и тем же маршрутом»
```

#### Алгоритм применения шаблона

```
Вход: список нераспределённых СТ на дату D

1. ПОИСК ШАБЛОНОВ
   dow = D.weekday()
   Для каждого шаблона за этот день недели:
     similarity = Jaccard(шаблон.addresses, сегодняшние_addresses)
   Сортируем по similarity DESC.

2. ОЦЕНКА ПРИМЕНИМОСТИ
   Если max(similarity) > 0.85:
     → "Высокое совпадение": предлагаем шаблон как есть
   Если max(similarity) ∈ [0.5, 0.85]:
     → "Частичное совпадение": шаблон + дельта (новые адреса добавляем через NN-TSP)
   Если max(similarity) < 0.5:
     → "Нет шаблона": передать в Подход 1 или Подход 3

3. КОРРЕКЦИЯ ОБЪЁМОВ
   Для каждого адреса шаблона: подставляем реальные паллеты сегодняшнего СТ
   (не среднее из шаблона, а факт).
   Если сумма паллет > вместимость ТС: разбиваем СТ на два рейса
   (по принципу: первые K паллет = рейс 1, остальные = рейс 2).

4. РЕЗУЛЬТАТ
   Вернуть: список черновых рейсов с маршрутами из шаблона
   + метаданные: similarity score, template_id, template_usage_count
```

**Почему это работает:**
- Для N=50 адресов, типичных для пищевого завода, число уникальных понедельных маршрутов ≤ 20
- После 3–4 недель работы покрытие шаблонами ≥ 80% дней
- Ответ мгновенный (SQL JOIN + Python Jaccard) — < 50 мс

**Обучение диспетчерских предпочтений:**
Когда диспетчер **редактирует** предложенный план:
```python
def on_dispatcher_edit(template_id, original_seq, new_seq):
    # Сохраняем правку как обучающий сигнал
    save_correction(template_id, original_seq, new_seq)
    # Если одна и та же правка делается 3+ раз — обновляем шаблон
    if count_similar_corrections(template_id, new_seq) >= 3:
        update_template_sequence(template_id, new_seq)
```

### 12.5 Подход 3: Гибридный решатель (OR-Tools + Clarke-Wright + RL)

Три дополнительных метода для случаев, когда шаблоны не подходят
и нейросеть даёт низкое качество.

#### 3А: Clarke-Wright Savings Algorithm

Классический и быстрый. Работает за O(N² log N).

```
Инициализация: каждый адрес — отдельный рейс (N рейсов)
Для каждой пары (i, j): savings(i,j) = d(depot,i) + d(depot,j) - d(i,j)
Сортируем пары по savings DESC
Последовательно объединяем рейсы, пока не нарушена вместимость
Постобработка: 2-opt улучшение каждого маршрута
```

Результат для N=50: ~8–12% от оптимума. Скорость: < 100 мс.
Используем как **быстрый baseline** и для инициализации OR-Tools.

#### 3Б: OR-Tools VRP Solver

Google OR-Tools — production-ready решатель открытый код.
Использует Large Neighborhood Search (LNS) + метаэвристики.

```python
from ortools.constraint_solver import routing_enums_pb2, pywrapcp

def solve_vrp_ortools(
    distance_matrix: list[list[int]],  # из RRL_ADDR_DISTANCE_MATRIX
    demands: list[int],
    vehicle_capacities: list[int],
    time_windows: list[tuple[int,int]],  # из RRL_ADDR.DELIVERY_TIME_FROM/TO
    time_limit_sec: int = 10
) -> VRPSolution:
    manager = pywrapcp.RoutingIndexManager(
        len(distance_matrix), len(vehicle_capacities), 0  # 0 = depot
    )
    routing = pywrapcp.RoutingModel(manager)

    # Callback расстояния
    routing.RegisterTransitCallback(...)

    # Ограничения вместимости
    routing.AddDimensionWithVehicleCapacity(demand_callback, 0, vehicle_capacities, True, 'Capacity')

    # Временны́е окна (если заданы)
    routing.AddDimension(time_callback, 30, 3600, False, 'Time')
    for node_idx, (tw_start, tw_end) in enumerate(time_windows):
        routing.CumulVar(routing.NodeToIndex(node_idx), 'Time').SetRange(tw_start, tw_end)

    # Стратегия первоначального решения: Clarke-Wright как seed
    search_params = pywrapcp.DefaultRoutingSearchParameters()
    search_params.first_solution_strategy = routing_enums_pb2.FirstSolutionStrategy.PATH_CHEAPEST_ARC
    search_params.local_search_metaheuristic = routing_enums_pb2.LocalSearchMetaheuristic.GUIDED_LOCAL_SEARCH
    search_params.time_limit.seconds = time_limit_sec

    solution = routing.SolveWithParameters(search_params)
    return extract_solution(manager, routing, solution)
```

Качество: ~1–3% от оптимума при 10 сек лимите. Скорость: ≤ time_limit_sec.
Учитывает: вместимость, временны́е окна, несколько типов ТС.

#### 3В: Reinforcement Learning с обратной связью (онлайн-обучение)

Самообучающийся компонент, который учится у диспетчера.

**Идея:** каждая правка диспетчера в авто-предложенном плане — это обучающий сигнал.

```
State:  текущий план дня (матрица [рейс × СТ])
Action: переместить СТ из рейса A в рейс B / поменять порядок
Reward: -1 за каждую правку диспетчера (цель: меньше правок)
        +1 когда диспетчер нажал "Принять без изменений"
```

**Реализация:** простой Q-learning на таблице прецедентов (не нейросеть).
Хранится в `RRL_TT_RL_CORRECTIONS`:

```sql
CREATE TABLE RABAEV.RRL_TT_RL_CORRECTIONS (
  ID            NUMBER GENERATED ALWAYS AS IDENTITY,
  DATE_OF_PLAN  DATE,
  ST_NUMBER     VARCHAR2(50),
  FROM_TASK_IDX NUMBER,   -- предложенный рейс
  TO_TASK_IDX   NUMBER,   -- фактический рейс после правки
  ADDR_FROM     VARCHAR2(200),
  ADDR_TO       VARCHAR2(200),
  DOW           NUMBER(1),
  TRANSTYPE     VARCHAR2(20)
);
```

После N=30 правок одного типа: система запоминает «этот адрес всегда идёт с этими адресами»
и начинает сразу предлагать правильный кластер.

Это не классический RL, но практически решает задачу **адаптации к предпочтениям конкретного диспетчера**.

### 12.13 Критерии приёмки (раздел 12)

#### OSRM
- [ ] Docker-контейнер OSRM запускается, отвечает на `/table` для 10 адресов за < 200 мс
- [ ] `vrp_matrix_worker` заполняет матрицу для всех адресов из `RRL_ADDR` за одну ночь
- [ ] Матрица обновляется при появлении нового адреса без ручного вмешательства

#### Шаблоны
- [ ] После 5 дней работы система накопила ≥ 3 шаблона
- [ ] Шаблон с Jaccard > 0.85 предлагается как вариант 1 (< 50 мс)
- [ ] Правка диспетчера фиксируется в `RRL_TT_RL_CORRECTIONS`
- [ ] После 3 одинаковых правок шаблон обновляется автоматически

#### OR-Tools
- [ ] При N=50, K=8 машин, без временны́х окон — решение за ≤ 10 сек
- [ ] Решение не нарушает вместимость ни одного ТС
- [ ] С временны́ми окнами (если заданы) — все адреса в пределах окна

#### Attention Model
- [ ] Модель предобучена на синтетических данных, инференс < 1 сек на CPU
- [ ] Дообучение на 1000 исторических маршрутах проходит без ошибок
- [ ] Качество решения (% от OR-Tools) ≥ 95% в среднем по тесту

#### UI
- [ ] Показываются минимум 2 варианта плана (Шаблон или NN + OR-Tools)
- [ ] Сравнительная таблица вариантов отображается корректно
- [ ] «Принять вариант 2 с правками» → рейсы созданы в Oracle, сессия сохранена
- [ ] Маршрут рейса отображается на карте как ломаная (OSRM `/route`)
