# Стратегический план развития TMS

> Файл поддерживается AI-ассистентом. Дата: 2026-05-20.
> Источник: анализ wiki/, кода, и текущего состояния базы.

---

## Принципы плана

1. **Oracle-first**: новые модули строятся как API поверх Oracle, не заменяя её.
2. **Параллельные треки**: внешние блоки (Mercury/CRPT-сертификаты) не останавливают внутреннюю разработку.
3. **Evidence-driven**: каждый модуль сдаётся с load-тестом + артефактами, не только кодом.
4. **Постепенный вывод легаси**: C# и Tserver выключаются по мере покрытия функций API.

## Горизонт 1 — Ближайший (1–2 месяца)

### Трек A: Транспортный модуль (приоритет 1)
Перенести управление транспортом и отгрузкой из C# в FastAPI + React.

**Почему сейчас:**
- Это единственный крупный операционный контур, не покрытый API
- Замыкает цепочку: wave picking → стейджинг → **транспорт → отгрузка**
- ТЗ составлено (см. [transport_management_tz.md](transport_management_tz.md))

**Состав:**
- Миграция схемы: `RRL_TRANSPORT_TASK`, `RRL_TR_VEHICLE`, `RRL_TR_VODITEL`, `RRL_SBORKA_PALLETS`
- API-пакет `RRL_TRANSPORT_API` (аналогично `RRL_PICKING_API`, `RRL_WAREHOUSE_TASK_API`)
- FastAPI роутер `transport`
- React-страница диспетчера отгрузки в admin frontend
- TSD-страница для водителя/экспедитора

### Трек B: File exchange worker
Реализовать polling `exchange/production_release/in/*.json` → создание production batch → ответный файл.

**Почему сейчас:** заложен в outbox-архитектуру, блокирует производственный цикл.

### Трек C: Топология admin — завершение
Подключить React admin к topology API (последний активный тред до краша).

## Горизонт 2 — Среднесрочный (2–4 месяца)

### Трек D: Цифровой двойник — сценарное сравнение
Сделать потери видимыми на карте, добавить "what if" (больше ричтраков / пикеров).

**Почему:** цифровой двойник — инструмент операционных решений. Сейчас даёт цифры, но не показывает их на карте.

### Трек E: Регуляторные коннекторы (при поступлении сертификатов)
- Mercury (VetIS.API): eVSD-треккинг, ветсвидетельства
- Честный знак (CRPT True API): DataMatrix, печать, валидация

**Архитектура готова** (outbox + mock-адаптеры). Только подключить реальные credentials.

### Трек F: Сервис этикетирования и печати
Импорт кодов маркировки, очереди печати, верификация сканом.

**Зависит от:** Трека E (реальные коды CRPT).

### Трек G: React admin — расширение
- Экран производственных заказов (уже есть raw HTML-прототип)
- Экран управления транспортом (из Трека A)
- Экран топологии (из Трека C)

## Горизонт 3 — Долгосрочный (4–12 месяцев)

### Трек H: Отгрузка и отзывы (Фаза 5)
- Проверка готовности к отгрузке
- Трейсабилити по клиентам
- Запрос на отзыв партии

### Трек I: Android-терминал
Kotlin/Jetpack Compose — замена legacy scanner OS клиента.
**Зависит от:** стабилизации Web-PWA (Трек J).

### Трек J: Web-PWA терминал — продакшн-готовность
Офлайн-синхронизация, конфликт-резолюция, PWA manifest, Lighthouse score.

### Трек K: Постепенный вывод C# WinForms
По мере покрытия функций API:
1. Транспорт → API (Трек A)
2. Права пользователей → новая модель через API
3. Справочники → Admin SPA
4. Оставить C# только для: прямого исправления данных в экстренных случаях

### Трек L: Брокер сообщений (опционально)
Kafka/RabbitMQ — только после того, как Oracle outbox докажет недостаточность.
**Не планировать** до появления реальной нагрузки.

### Трек M: PostgreSQL (только оценка)
Оценить миграцию Oracle → PostgreSQL после стабилизации всего API-слоя.
**Не начинать** раньше полного покрытия API.

## Критерии успеха системы

| Показатель | Текущее | Цель |
|---|---|---|
| Операционные контуры в API | 70% (нет транспорта) | 100% |
| Регуляторное покрытие | Mock-адаптеры | Реальные Mercury + ЧЗ |
| C# WinForms зависимость | Критическая (транспорт) | Только аварийные правки |
| Oracle невалидных объектов | 0 | 0 (инвариант) |
| Load-тест покрытие | Wave + MES + Case-pick | + Transport + Exchange |
| Цифровой двойник | Модель только | Map + сценарии |
