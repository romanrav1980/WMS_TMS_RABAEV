# Подпроект: 3D-двойник склада и транспорта (wms_twin_3d)

Дата создания: 14 октября 2026 года. Код: [`../../twin/wms_twin_3d/`](../../twin/wms_twin_3d/). Принципы: [[concepts/warehouse_transport_digital_twin_principles]]. Визуальная спецификация смены склада: [[concepts/warehouse_digital_twin_codex_spec]].

## Что это

Отдельное Vite-приложение (React 19, TypeScript, Three.js, React Three Fiber, drei, Zustand) — изометрическая 3D-визуализация процессов склада и связанных рейсов в стиле «стратегии», по механизму WareTrack/NuriTrack: единое состояние, `tick()` модели 10 Гц, сцена интерполирует движение, панели считают KPI из того же состояния.

Два источника: детерминированная мок-симуляция по шагам процессов WMS/TMS (`SIM · мок-данные`, по умолчанию) и live-адаптер к API ТМС (`?source=live`, только чтение): топология склада, рейсы, ворота и СТ — сверены с живым API 14.10.2026, см. «Live-сопоставление».

## Зачем

Показать смену склада и транспорт как одну цепочку: где теряется производительность, какие рейсы под угрозой окна дока и почему. Отличие от [`../../admin/wms_admin_frontend/src/components/WarehouseScene.tsx`](../../admin/wms_admin_frontend/src/components/WarehouseScene.tsx) (2D-реплей по `events.jsonl`): 3D-сцена, транспортный контур (двор, ворота, рейсы), коллизии в реальном времени.

## Что моделируется

| Процесс | Объекты | Отражение в 3D |
|---|---|---|
| Въезд, очередь, постановка | рейс, ТС, ворота, окно дока | машина въезжает, ждёт на обочине, сдаёт задним ходом к воротам |
| Приёмка и размещение | поставка, задания UNLOAD/PUTAWAY | погрузчик выгружает, ричтрак поднимает паллету в резерв |
| Пополнение | задание REPL, ячейки L1/L2–L5 | ричтрак спускает паллету из резерва в ячейку отбора |
| Отбор волны | СТ, строки, комплектовщик | человек с тележкой идёт по проходам, остаток ячейки уменьшается |
| Контроль и выставка | стадии СТ | паллеты СТ появляются у ворот своего рейса |
| Погрузка и отправка | задания LOAD, рейс | погрузчик возит паллеты в кузов, машина уезжает, ETA магазинов |
| Коллизии | 7 типов | пульсирующие метки и выноски на сцене, журнал, карточка причины |

## Live-сопоставление (рейсы, ворота, СТ — только чтение)

Код: [`../../twin/wms_twin_3d/src/adapters/tmsMapping.ts`](../../twin/wms_twin_3d/src/adapters/tmsMapping.ts) (чистые функции), загрузка — [`tmsLive.ts`](../../twin/wms_twin_3d/src/adapters/tmsLive.ts). Авторизация HTTP Basic через `VITE_ADMIN_BASIC_AUTH` в игнорируемом `twin/wms_twin_3d/.env` (шаблон `.env.example`, как в admin frontend). Обновление раз в 60 с; топология грузится один раз.

| Двойник | Эндпоинт / поле ТМС | Правило |
|---|---|---|
| Выбор площадки | `GET /api/admin/warehouse-topologies` | `?topology=ID`, иначе PUBLISHED/VALIDATED с `aisle_count > 0` и максимальным `cell_count` (на dev — 2 `LOAD-1500-2CH-60`; 45 с 5042 ячейками без проходов/ворот — фикстура, пропускается) |
| Layout | `…/{id}/map` → `topology`, `aisles`, `gates`, `cells` | плоскость топологии `x,y` → `x,z` двойника; фасад = max `gate.y` (104), ширина = max x + 8 |
| Ячейка | `cells[]`: `cell_code`, `aisle_code`, `bay_no`, `level_no`, `side_code`, `cell_kind`, `x`, `y`, `z`, `width`, `depth` | id = `cell_code`; `PICK_FACE` → отбор; `LEFT/RIGHT` → сторона; остатков в топологии нет → `stockKnown=false`, ячейки без заполненности |
| Ворота | `gates[]`: `gate_code`, `gate_kind`, `x` | id = `gate_code`; `SHIPPING/OUTBOUND` → отгрузка, `RECEIVING/INBOUND` → приёмка; занятость не известна |
| Рейс | `GET /api/admin/transport/tasks?include_readiness=true&date_from&date_to` (по умолчанию −2…+30 дней) | id = `ID`; `DELETED=1` пропускается; `TRANSPORT` → ТС, `VODITEL_NAME`, `TK_NAME`/`IS_OWN_DRIVER` → перевозчик, `TRANSTYPE` → «Тип ТС N», `PALLET_COUNT`, `ST_COUNT`, `READY_PERC` |
| Статус рейса | `CONDITION` | «Отгружен» → `done`; «Спланирован»/«Сформирован» → `planned`; прочее → `planned` + замечание. Состояний двора таблица не хранит — машин на сцене в live нет |
| Ворота рейса | `DOCK` | назначаются, только если `DOCK` совпадает с `gate_code` (без учёта регистра) |
| Окно дока | `SHIPMENT_TIME` / `SHIPMENT_DATE` | условное: время отгрузки … +60 мин; риск `late`, если рейс «Спланирован», а окно прошло |
| СТ рейса | `GET /api/admin/transport/tasks/{id}/sts` | строки сгруппированы по СТ и `ORD` → свёртка по `ST_NUMBER` (паллеты и вес суммируются, `VERIFY_PERC` по паллетам); сумма паллет = `PALLET_COUNT` рейса |
| Свободные СТ | `GET /api/admin/transport/available-sts?page_size=300` | `tripId=""`; отключаются `?freeSts=0` |
| Стадия СТ | `VERIFY_PERC`, статус рейса | рейс отгружен → «В пути»; 100 → «У ворот»; 1–99 → «Контроль»; 0 → «Создано» (приближение до появления событий отбора) |
| Коллизии | — | «Опоздание рейса» для просроченных спланированных рейсов (тот же детектор, что в симуляции) |

### Складские операции (live, по [[requirements/warehouse_operations_digital_twin]])

Код: [`tmsOperations.ts`](../../twin/wms_twin_3d/src/adapters/tmsOperations.ts) (чистое сопоставление в контракт `warehouse-twin-operation/1`), загрузка раз в 15 с в `tmsLive.ts`, слой сцены `OperationsLayer.tsx`, вкладка «Операции склада» и карточки операции/исполнителя.

- Склад и топология выбираются по правилу WMS: `?ware=` или склад с наибольшим числом открытых операций, затем его последняя `PUBLISHED` топология. Ячейки связываются через `LEGACY_CELL_CODE` = `RRL_CELLS.CELL`. `?topology=` допускается для просмотра; непубликованная помечается замечанием.
- Источники: `/api/warehouse-tasks?limit=500` (открытые статусы идут первыми), `/api/case-pick/tasks?scope=all&limit=500`, `/api/resources`, `/equipment`, `/sessions`. По выбору: `/{id}`, `/progress`, `/sync`, деталь CASE со строками.
- Фазы §10 из исходных статусов (исходный статус хранится и показывается); количества — точные строки; чужие склады отфильтрованы; лимит выдачи помечен.
- Сцена: груз в последнем подтверждённом месте (источник до завершения, назначение «план»), пунктир-намерение к назначению, кольца ячеек строк CASE; исполнитель только при `last_cell` в топологии. Непривязанное — только в списке с пометкой «нет на схеме».
- Состояние связи LIVE/STALE (> 45 с)/НЕТ СВЯЗИ с возрастом снимка. Заблокированные/ошибочные операции дают коллизию «Задание заблокировано» (метка на сцене только при привязке).
- В SIM те же операции строятся из симуляции (режим SIM, «траектория расчётная»); на сцене — пунктирные намерения.

Проверено 14.10.2026: утверждения на сохранённых ответах (фазы, ключи `WH_TASK`/`CASE_TASK`, точные количества, фильтр склада, лимит, позиция исполнителя), `?source=live` — склад 1, 118 операций, 23 открытые, все без привязки: опубликованная топология склада 1 — тестовая `IDEMP…` на 4 ячейки без `LEGACY_CELL_CODE`; у остальных складов с открытыми заданиями опубликованной топологии нет. Требования к головной системе, без которых live-сцена остаётся пустой: [[requirements/twin_source_system_requirements]].

### Находки по данным dev-стенда (14.10.2026)

- `CONDITION` встречается только «Спланирован» (33) и «Отгружен» (86) из 120 рейсов с 01.09; один рейс с мусорным значением `"1#F#B#0#D#8$0#E#2#0#D` — показан как спланированный с замечанием.
- `DOCK` заполнен кодами тестовых фикстур (`QD…`, `QO…`), с воротами топологии `G01…G10` не совпадает ни у одного рейса — бронь ворот в live пока пустая.
- У рейса нет склада; `WARE_ID` есть только у СТ, и 190 из 201 СТ относятся не к складу топологии (ware 1).
- `zone_name` топологии 2 хранится как `???? ??????` (порча кириллицы в Oracle при записи фикстуры); имена проходов и ворот корректны.
- Ответ карты топологии 2 — 5,7 МБ, из них 15 000 строк `distances`, которые двойнику не нужны.

Задача на исправление для Codex: [[requirements/twin_live_data_fixes_codex_prompt]] ([файл](../requirements/twin_live_data_fixes_codex_prompt.md)). Уточнение при постановке: `RRL_TRANSPORT_TASK.DOCK` — ключ `RRL_TT_DOCK(DOCK, WARE_ID, ORD)`, а не код ворот топологии; связи `RRL_TT_DOCK` ↔ `RRL_TOPOLOGY_GATE` в схеме нет. `GATE_KIND` допускает `BOTH`.

### Долгие запросы и решение

| Запрос | Время | Решение |
|---|---|---|
| `available-sts?unassigned_only=false&page_size=200` | 28,6 с | Двойник **не вызывает**. Причина: `list_available_sts` выбирает всё и режет страницу в Python. Backlog, владелец transport: серверная пагинация/ограничение выборки |
| `available-sts?page_size=300` (свободные) | 6,8 с | Допустимо раз в 60 с, вне критического пути (грузится после рейсов, ошибка не ломает снимок); можно отключить `?freeSts=0` |
| `tasks/{id}/sts` | 0,09 с | Используется по каждому спланированному рейсу (≤ 80, параллельно 4), в сервисе есть кэш |
| `tasks?include_readiness=true` | 0,3 с | Используется |
| `warehouse-topologies/2/map` | 1,4 с, 5,7 МБ | Один раз при старте. Backlog: параметр без `distances` для двойника |

## Где доказательства

- Код и README: [`../../twin/wms_twin_3d/README.md`](../../twin/wms_twin_3d/README.md).
- Проверено 14.10.2026: `tsc --noEmit` и `vite build` проходят; безголовый прогон симуляции 6 модельных часов (seed 20261013) без зависаний: 1109 строк отбора, 161 пополнение, 294 паллеты отгружено, 112 размещено, коллизии всех основных типов; визуальная проверка в браузере (сцена, выбор рейса, подлёт камеры, карточки).
- Проверено 14.10.2026 (live): сопоставление прогнано утверждениями на сохранённых ответах живого API (выбор топологии, 1500 ячеек/10 ворот/фасад 104, 120 рейсов, свёртка СТ и сумма паллет, СТ без рейса, совпадение `DOCK`→ворота); в браузере `?source=live`: 25 рейсов за −2…+30 дней, 305 СТ, топология отрисована, карточки рейса/СТ, 5 коллизий «Опоздание рейса», снимок за 9,7 с.
- Не проверено: Playwright-скриншоты, нагрузка на слабом GPU, live-данные складских заданий/ресурсов/GPS.

## Что можно менять безопасно

Стиль, раскладку панелей, параметры симуляции (`src/sim/*`), добавление адаптеров при сохранении контракта `src/contracts/twin.ts`.

## Что нельзя ломать

- Двойник не пишет в Oracle и не вызывает мутирующие API.
- Идентификаторы объектов совпадают с WMS/TMS.
- Режим `SIM`/`LIVE` всегда виден в верхней панели.
- Приложение не входит в `frontend_roots` архитектурного gate ([`../../config/architecture/retailcase-policy.json`](../../config/architecture/retailcase-policy.json)); при переносе в admin frontend или подключении к gate — оформить через `src/features/<area>/index.ts` и пройти `python scripts/retailcase_quality_gate.py`.

4. Режим «что если» на клоне состояния (по примеру WareTwin).
5. Playwright-скриншоты ключевых состояний.
