# NIKORA: минимальное расширение архитектуры

Дата: 15.09.2026. ADR-предложение, не утверждённая схема. Основания: [[sources/nikora_20260915]]. Противоречия Q01–Q10: [[requirements/nikora_gap_analysis_20260915]].

## 1. Решение по принципу Оккама

| Вариант | Решение |
|---|---|
| Только новые поля у СТ и XML-адаптер | Отклонить: одна СТ→один рейс, недостаточно для независимых плеч, freeze и общего HU |
| Ограниченное расширение FastAPI + React/PWA + Oracle | **Рекомендуется**: новые инварианты изолированы, существующее WMS-ядро сохранено |
| Новая платформа, микросервисы, event sourcing, графовая БД | Отклонить для пилота: нет доказанной нагрузки или организационной причины для такой миграции |

Оккам — не «ноль новых таблиц», а отсутствие лишней ответственности. Поля со скрытыми значениями и несогласованные JSON-снимки не упрощают модель.

## 2. Границы ответственности

- ERP: коммерческий заказ, owner, магазин, serviceDate, ожидаемое распределение и версии Manifest; источник master-data адресов и артикулов по согласованному XML API; получатель статусов ORDER_ASSEMBLED, INTERNAL_MOVEMENT_PLANNED, ORDER_IN_TRANSIT, ORDER_DELIVERED_TO_STORE.
- WMS источника: исполнение своей части, состав/печать исходного HU, готовность, подтверждённая погрузка.
- TMS: календарь, исходящая волна, расписание, назначения по плечам, ресурсные слоты, исключения.
- WMS/терминал cross-dock: приём, место, выгрузка, укрупнение/разбор, погрузка; TMS хранит проекцию этих фактов.
- Магазин: фактически принятое количество и расхождения.
- Бухгалтерия/регуляторика: существующие владельцы документов, не новая ответственность TMS.

У каждого события один авторитетный источник. Передача сообщения через TMS в целевую WMS сохраняет ссылки на исходный факт и не создаёт второй независимый приход.

```text
ERP Manifest ──> ожидаемые части ──> волна / расписание TMS
WMS источников ──> XML inbox ──> части + HU + назначения по плечам
                                     │
                существующие рейсы / ресурсы / Oracle
                                     │
                 outbox ──> WMS / перевозчик / cross-dock
                                     │
                физические факты HU ──> приёмка магазина
```

Один API и worker того же приложения достаточны на старте. Oracle-очередь + HTTP; не вводить Kafka или отдельные сервисы без измеренного обоснования.

## 3. Решение по каждой абстракции ТЗ

Имена новых объектов проектные. Миграции этим документом не применяются.

| Понятие | Что делать | Почему |
|---|---|---|
| Destination | Расширить CUSTOMER_ADDRESS/STORE_MAP/RRL_ADDR маппингом GLN | Не нужен второй справочник магазинов |
| Order/Line | Использовать CUSTOMER_ORDER/ROW как проекцию, добавить owner/external-key/version | Не дублировать коммерческий lifecycle ERP; сохранить LEGACY_ORDER_ID |
| FulfillmentPart | **Новая стабильная часть источника** + строки связи с ORDER_ROW | sourceSystem/warehouseGLN/externalPartId не должны меняться из-за смены машины |
| SHIPMENT_PART | Сохранить существующую транспортную нарезку; при необходимости связать с FulfillmentPart | Сейчас части пересчитывает split_order_by_pallet_capacity по CUSTOMER_ORDER_ID+PART_NO |
| DeliveryGroup | Сначала вычисляемая группа destinationGLN+serviceDate+согласованный owner-контекст | Не нужен новый master; snapshot назначения хранится в волне |
| Calendar/правила | Версионируемые настройки и календарные исключения | Универсальный rule engine не требуется |
| HandlingUnit | **Общий реестр HU**, внешний SSCC, внутренний huId, nullable mapping UID_PALLET | Legacy PALLETS имеет ARTICUL и обязательный приход; нельзя делать фиктивный приход внешнему mixed-SKU parent |
| HUContent | Строки owner/order/line/part, GTIN, batch/expiry, UoM, qty/mass | Нужен проверяемый баланс до магазина |
| HUHierarchy/операции | Активные parent–child связи, закрытая история, журнал преобразований с участниками | Текущее дерево: один parent, без циклов; repack хранит отдельную историю происхождения |
| OutboundWave | **Новый агрегат координации**: serviceDate, outboundTripId, scheduleVersion, status/freeze, snapshot | PICK_WAVE — локальное исполнение, с другим lifecycle; связать по составу через relation, не приравнивать ID |
| ShuttleTrip/Trip | Использовать RRL_TRANSPORT_TASK, добавить роль SHUTTLE/OUTBOUND/RETURN | Не создавать второй вид master-рейса |
| TripStop/ShipmentLeg | Остановки GLN с порядком; плечо = stopFrom/stopTo конкретного рейса | Отдельный ShipmentLeg master не обязателен при однозначном ключе пары |
| CargoAssignment | **Новая связь** части/верхнего HU с рейсом, stopFrom/To, секцией, версией, физическим состоянием | Одна СТ→один TRANSTASK_ID не выражает цепочку перевозки |
| Gate/Lane/ArrivalSlot | Переиспользовать topology и ресурсы, интервалы RESOURCE_ASSIGNMENT с расширением типов/ссылок | Не плодить независимые booking/slot/schedule объекты; проверить пригодность lifecycle ресурса ворот в A3 |
| ConsolidationTask | Подтип/связь WAREHOUSE_TASK и resource assignment, привязанный к волне исполнения | Сохранить wave-first, не создавать второй диспетчер складских работ |
| Message/Event | Добавить inbox/payload-reference, расширить EVENT_OUTBOX/ADAPTER_REQUEST | Аудит HTTP не обеспечивает бизнес-идемпотентность; второй outbox не нужен |
| ExceptionDecision | Неизменяемое событие решения с actor/reason и последствиями | Не нужен универсальный workflow engine |
| DeliveryReceipt | Факт приёмки и строки расхождений, связь HU/leg | Не равен закрытию рейса |
| TransportAsset | Постоянный ID оборотной тары + связи наполнений/движений | SSCC груза не равен номеру клетки; это не техника исполнителя |

Это несколько предметных семейств, не обещание «пяти таблиц»: необходимые строки, связи, версии и индексы должны присутствовать. Окончательные имена/ограничения сверяются с версией Oracle.

### Почему не переиспользовать SHIPMENT_PART как часть WMS

Она уже имеет плановые паллеты/вес/объём, но меняется при расчёте вместимости. Часть источника должна оставаться той же при двух шаттлах, PLAN→FACT и смене машины. Вариант PART_KIND с изоляцией всех старых split/reader-путей возможен, но затрагивает больше действующего кода. Отдельная стабильная source-part с явной связью безопаснее; не создавать при этом второй заказ.

### Почему CRPT_AGGREGATION не является общим HU

Её API привязан к production batch/маркировке и статусам регулятора. add_item меняет parent, но не закрывает баланс заказных строк, циклы, историю разборки и транспортную доступность. Общий HU должен работать без российского регуляторного процесса. CRPT остаётся потребителем/проекцией там, где применимо; старые API сохраняются.

## 3.1. Уточнение рабочих мест: контроль и очередь техники

ТЗ: [[requirements/nikora_ui_workplaces_tz]], [[requirements/nikora_ui_quality_tz]], [[requirements/nikora_ui_reachtruck_dispatch_tz]]. Для двух независимых пересчётов/осмотра/веса необходимы устойчивые факты и допуск по версии состава. В A2.Q сначала проверяется расширение существующего lot-check/scan journal; если он недостаточен, добавить узкие связанные QualitySession/ScanPass/WeightMeasurement и решение допуска. Один checkbox не обеспечивает независимость и аудит. Сборка остаётся фактом при HOLD; qualityStatus/readyToShip отдельно. Repack инвалидирует старый допуск.

Водитель и диспетчер ричтраков используют WAREHOUSE_TASK/RESOURCE_SESSION и существующие права, не новые параллельные задания. Минимальные расширения: серверная версия очереди, preview/confirm reorder, claim/recall и read model блокеров/deadlines. Уже взятый груз нельзя переназначить без физического подтверждения custody. ERP «в пути» не возникает от движения ричтрака внутри склада.

ERP события имеют scope части/плеча и причинные версии. INTERNAL_MOVEMENT_PLANNED может предшествовать сборке; часть заказа может выехать до готовности остальных по разрешённой политике, без объявления всего заказа собранным/доставленным.

## 4. Обязательные инварианты

1. GLN/GTIN/SSCC — строки с ведущими нулями. Контрольная цифра и master-mapping проверяются отдельно. Legacy pallet identifiers сохраняются: строгость SSCC включается на границе NIKORA.
2. Заказ: owner+externalOrderId+destinationGLN; часть дополнительно sourceSystem+warehouseGLN+externalPartId. messageId и версия не заменяют эти ключи.
3. Полнота приходит из Manifest. Молчание источника не означает ноль/отмену/готовность.
4. PLAN: факт + max(план−факт,0) до assemblyComplete/closed-short. Факт выше плана увеличивает потребность; завершение сборки закрывает остаток с причиной. Метрики паллет/веса/объёма считаются в согласованных единицах и по разрешённым правилам оценки.
5. ACTUAL_ONLY резервирует перевозку после разрешённого факта: вся часть либо каждый HU по настройке. Общий deadline не является резервированием.
6. У HU один активный parent, нет циклов и двойного размещения child. В пилоте один магазин и совместимые категории/температуры; несколько заказов с lineBinding допустимы.
7. Баланс по owner/order-line/GTIN/batch/UoM. Для catch-weight PCE и KGM не использовать постоянный коэффициент. Объём после уплотнения не обязан сохраняться; gross mass учитывает добавленную/удалённую тару и утверждённые допуски измерений.
8. Вместимость считает верхние HU и разрешённый прогноз, не parent+child. Геометрия parent определяется после упаковки, не суммой объёмов children.
9. Freeze защищает согласованный snapshot обязательств/расписания. Преобразования HU — отдельные операции. Q06 о точном объекте freeze нужно закрыть до реализации.
10. HU не погружается в две машины одновременно. Переназначение loaded только после подтверждённой выгрузки.
11. Приёмка cross-dock не закрывает магазин; статусы физического исполнения относятся к конкретному плечу.
12. Hard constraints одинаковы в ручном и автоматическом режиме; подтверждение оператора их не отменяет.

## 5. Надёжность и транзакции

Вход: аутентификация → размер/безопасный XML → allowlist локальных схем → GS1 XSD или отдельная versioned ERP XSD → отдельная Context XSD там, где она применяется → семантика/маппинг → durable inbox. HTTP 202 означает только надёжное сохранение.

Одна доменная команда: lock inbox/entity/HU/assignment в стабильном порядке → версия/права → баланс и состояние → событие/outbox → commit. Worker отправляет сообщения после commit; внешний HTTP не держит транзакцию.

Использовать OracleGateway.transaction с переданным cursor или узкий PL/SQL API без внутреннего commit. Обёртка transaction вокруг вызовов gateway.execute не объединяет их: они используют отдельные соединения/commit.

- Тот же messageId и байты возвращают прежний результат; другой hash — конфликт.
- Та же entityVersion с новым messageId проверяет нормализованный business hash, не повторяет эффект.
- Канонизация сохраняет значимый порядок очереди/остановок, не сортирует всё подряд.
- N+2 ждёт зависимости, старая версия не откатывает факт, новая версия не отменяет freeze.
- CANCEL_REQUESTED не освобождает груз/ресурс до CANCELLED.
- RECEIVED, APPLIED и принятие перевозчиком TransportInstruction — разные подтверждения. Статусы ERP также не являются подтверждением доставки: ORDER_IN_TRANSIT публикуется только после фактического DEPARTED (LOADED — только погрузка), ORDER_DELIVERED_TO_STORE — только после ReceivingAdvice.
- PROCESSING_RESULT не создаёт ACK-цикл.
- Связанные snapshots REPACK/aggregation проходят staging и атомарное согласование; неполный набор не доступен к погрузке.
- EVENT_OUTBOX расширять адресно, не меняя поведение Mercury/CRPT. Mock-адаптер запрещён в pilot-конфигурации.
- Авторизация sourceSystem/site, роли release/exception/replay, actor/reason обязательны. driver_id сам по себе не авторизация физического события.

## 6. Планировщик

Сначала утверждённый исходящий график и детерминированный backward scheduler. Не нужна глобальная оптимизация всей сети в первом инкременте.

```text
окна магазинов → departure основного рейса
→ loadCompleteBy / loadStartAt → готовность parent
→ консолидация / приём и проверка HU → окно шаттла
→ departure шаттла / загрузка источника
→ assemblyCompleteBy / запуск и порядок сборки
```

Каждая операция имеет длительность, календарь ресурса, зависимость, буфер и источник норматива. После обратного расчёта — проверка выполнимости вперёд. Одно последнее окно не выдаётся нескольким шаттлам без проверки ворот/линии.

На каждом участке load(k+1)=load(k)+pickup(k)−delivery(k), включая возвратную тару. Проверять вес/м³/места/секции/геометрию на каждом участке. Порядок загрузки зависит от доступа и секций, а не всегда равен полностью обратному списку магазинов.

Solver предлагает решение, независимый deterministic validator разрешает выпуск. Недоступность OR-Tools допускает проверенный ручной/эвристический вариант, но не обход ограничений. Attention Model не является зависимостью пилота.

## 7. Миграция и откат

1. Additive контракты/схема, feature flag по source/site; старые API не менять.
2. Изолированный Oracle: upgrade существующей схемы и clean install, индексы, rollback.
3. Shadow-проекции ограниченного горизонта заказов; сверка ключей/количеств без команд.
4. Один адаптер, ручной cross-dock на тестовой площадке, обязательные права/hard-validator.
5. Остальные потоки и recovery; затем ограниченный automatic release.
6. Rollback: остановить новый выпуск, сверить in-flight, перейти к утверждённому операционному fallback. Не удалять физические факты и не «откатывать» выполненную погрузку.

TRANSTASK_ID остаётся legacy-привязкой. NIKORA читает состав из CargoAssignment; согласованная legacy-проекция только основного плеча не является истиной для шаттла. PAY_ORDER_ID/billed-защита сохраняется вместе с freeze.

Каждая реализованная миграция должна иметь зеркало wiki/database и live verify по правилам репозитория. Этот анализ не применял DDL/DML.
