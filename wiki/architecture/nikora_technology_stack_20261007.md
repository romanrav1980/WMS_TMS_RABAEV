# NICORA: стек технологий и требования к производительности

Дата: 7 октября 2026 года. Основной стек утверждён владельцем: Python/FastAPI, React/TypeScript, Oracle и отдельные фоновые процессы. Редакция Oracle, конфигурация среды и численные нормативы нагрузки уточняются отдельно. Нагрузочная способность выбранного стека пока не подтверждена испытанием.

Владелец принял редакцию 55 за исходную версию требований и совмещает роли заказчика и программиста. Основной стек утверждён. Предложение очереди: [68 спринтов](../requirements/nikora_delivery_v55/README.md), включая GAP по текущему коду и итоговое ТЗ. Бизнес-требования не изменяются; самостоятельные правила получат постоянные номера при подготовке реестра покрытия NS01.

## Рекомендуемый стек

| Область | Решение | Граница применения |
|---|---|---|
| API и бизнес-логика | Python, FastAPI, Uvicorn | Развивать существующие модули; несколько процессов API, единые контракты команд |
| Рабочие места | React, TypeScript, Vite | Административные интерфейсы и существующий терминал PWA; отдельные потоки для ролей |
| Основная база | Oracle, SQL и PL/SQL, python-oracledb | Единственный источник товарного остатка, резервов, состава грузовых мест и подтверждённых операций |
| Версия Oracle | Предлагаемый исходный кандидат — 19c с актуальными обновлениями | Версия, редакция, лицензия и платформа устанавливаются в паспорте среды; старый 11g-совместимый стенд не принимается как целевая production-конфигурация |
| Фоновые работы | Отдельные Python-процессы, долговечные задания и outbox/inbox в Oracle | ERP-обмен, расчёты, отчёты, построение волн и рекомендации; не занимают обработчик сканирования |
| Развёртывание | Linux для API и фоновых процессов, контейнеры, обратный прокси и балансировка | Windows остаётся средой разработки и при необходимости мостом к оборудованию; платформа Oracle выбирается по поддерживаемой конфигурации |
| Фотографии и документы | Файловое или объектное хранилище с резервированием | Oracle хранит ссылки, контрольные суммы, владельца и связь с операцией; хранение файлов отдельно не отменяет их обязательность при приёмке |
| Мониторинг | Prometheus и Grafana, существующий журнал медленных SQL и API-аудит | Время команд, ошибки, ожидание соединений и блокировок, очередь, ресурсы и диск; метрики не заменяют товарный учёт |
| Проверка | pytest, Playwright, Locust и действующие SQL/API-проверки | Независимые бизнес-сценарии, реальные интерфейсы, конкуренция и нагрузка |

Точные версии Python и библиотек фиксируются после проверки совместимости на стенде. Используются воспроизводимые зависимости; текущий requirements.txt без закреплённых версий не является паспортом production-сборки. Владелец определил порядок закупки: Oracle-лицензия не покупается разработчиком; её приобретает NICORA перед вводом в эксплуатацию. Разработка идёт на имеющемся стенде. Выбранные production-версия, редакция и доступные функции проверяются перед запуском; покупка лицензии не является входным условием начала разработки.

## Архитектура исполнения

Система развивается как модульное приложение с отдельными процессами API, обмена и тяжёлых расчётов. Складские операции выполняются независимо от времени оптимизации маршрутов и ответа ERP.

Критическая команда сканирования проходит проверку прав и состояния, атомарно меняет товарный факт и обязательный бизнес-журнал, сохраняет исходящее событие в той же транзакции и только после фиксации получает успешный ответ. Ключ повторного обращения предотвращает повторное списание, погрузку или резервирование. После сетевого тайм-аута клиент сверяет результат по ключу операции.

Отчёты, аналитические проекции и отправка сообщения ERP выполняются вне этой транзакции. Незавершённая передача видна в очереди и повторяется. Фоновая доставка допускает повтор сообщения; получатель обязан распознавать дубликат. Очередь требует захвата задания одним исполнителем, срока владения, восстановления после сбоя, повторов с задержкой и отдельного состояния неисправимых ошибок.

Основные записи запаса и резерва не кэшируются как независимый источник истины. Права, версии и конфликты проверяются на записи в Oracle. Увеличение числа API-процессов требует общего бюджета соединений с БД; размер одного пула не умножается бесконтрольно.

В первой версии не предлагается делать обязательными Kubernetes, Kafka, распределённые микросервисы и вторую операционную БД. Redis для чтений и брокер сообщений могут появиться по измеренному ограничению или отдельной потребности. Наличие миллионов операций само по себе не определяет необходимость этих компонентов. Маршрутный solver также выбирается по проверке действующего кода и ограничений NICORA, а не меняется автоматически вместе со стеком.

## Предварительный профиль нагрузки

У владельца запрошено значение слова «транзакция». До ответа ниже используется расчётное допущение: 5 млн успешно подтверждённых бизнес-операций за 12 часов. Это предложение для проверки, не согласованный норматив.

| Показатель | Расчёт или предложенный тест |
|---|---|
| Средняя интенсивность | 5 000 000 / 43 200 = около 116 бизнес-операций в секунду |
| Пиковая интенсивность | Предварительно около 1 200 операций записи в секунду, десятикратный запас к среднему |
| Чтения | Отдельно проверить совместно с записью; начальный сценарий 3 000 запросов чтения в секунду, пересчитать по фактическому составу клиентов |
| Продолжительность | Полный 12-часовой прогон с суммарным объёмом 5 млн операций; отдельный час на предложенном пике |
| Отклик критической команды | Предлагается p95 не более 300 мс и p99 не более 1 секунды от входа в API до ответа после commit; полный отклик терминала измеряется отдельно |
| Корректность | Ни одной потерянной подтверждённой операции, двойного списания, повторного резерва и нарушения товарного баланса |
| Ошибки | Неожиданные технические отказы в штатном нагрузочном прогоне — не более 0,1%; ожидаемые бизнес-отказы учитываются отдельно |
| Накопленная история | Проверка на согласованном сроке хранения; маленькая пустая БД не доказывает работу на рабочем объёме |
| Отказы | Остановка API-процесса, перезапуск фонового исполнителя, недоступность ERP и восстановление связи без повторного товарного эффекта |

Одна бизнес-операция может вызывать несколько HTTP-запросов, SQL-операторов и транзакций аудита. Эти количества измеряются отдельно. Тестовая смесь должна включать подтверждения отбора, резервирование, задания, контроль и погрузку, а также конкуренцию за одинаковые SKU, ячейки и грузовые места. Последовательные вставки независимых строк не подтверждают складскую производительность.

5 млн записей в день дают около 1,825 млрд записей в год, если каждой операции соответствует ровно одна сохраняемая запись. Реальное число строк больше или меньше в зависимости от модели. Например, при 1 КБ на одну запись это около 1,8 ТБ исходных данных в год без индексов, журналов, резервных копий и фотографий. Требуются измерение размера записи, срок хранения, архивирование и ограниченные выборки. Секционирование и резервирование Oracle выбираются с учётом редакции и лицензии.

## Выявленные основания для технических доработок

Это ограниченное чтение архитектуры и нескольких исходных файлов, не полный GAP и не измерение производительности.

| Источник | Наблюдение | Необходимая проверка или доработка |
|---|---|---|
| api/wms_api_server/app/db.py | Синхронный пул min=1, max=12 на процесс, ожидание свободного соединения | Настраиваемый бюджет пулов, время ожидания, тайм-ауты и нагрузочная проверка; не считать 12 достаточным или недостаточным без измерения |
| api/wms_api_server/app/middleware/api_audit.py и services/api_audit_service.py | В async middleware выполняются синхронные вызовы аудита в Oracle и запись JSONL; часть чтений исключена | Устранить блокирование цикла обработки запросов; сохранить обязательный аудит; отделить диагностические данные от атомарного бизнес-журнала |
| api/wms_api_server/app/oracle_gateway.py | Ряд методов сам получает соединение и фиксирует изменения | Проверить транзакционную границу составных команд; несколько gateway-вызовов не считать автоматически одной атомарной операцией |
| api/wms_api_server/app/workers/outbox_worker.py | В показанном исполнителе события обрабатываются последовательно по одному | Проверить пакетную обработку, несколько исполнителей, восстановление владения и пропускную способность |
| api/wms_api_server/app/services/outbox_service.py | Адаптер по умолчанию MockRegulatoryAdapter | Этот outbox не считать доказательством реализованного ERP-обмена NICORA |
| serv.bat | Uvicorn запускается с --reload | Сохранить для разработки; подготовить отдельное production-развёртывание с несколькими процессами и управлением перезапуском |
| api/wms_api_server/requirements.txt | Основные Python-зависимости перечислены без версий | Зафиксировать проверенные зависимости и воспроизводимую сборку |

| S00.2 | Измерение текущей производительности | Отчёт по реальным командам, SQL, аудитным затратам и ожиданию пула |
| S00.3 | Бюджет соединений и исправление блокирования аудита | Одновременные запросы; сохранность аудита; отсутствие деградации цикла API |
| S00.4 | Транзакция и повтор критической команды | Повтор и авария между шагами не создают частичного товарного эффекта |
| S00.5 | Надёжное фоновое исполнение | Два исполнителя, повтор, остановка и восстановление без потери задания |
| S00.6 | Масштабирование и долговременный нагрузочный прогон | Смешанная нагрузка, пиковый сценарий, история, SQL-решения и точные характеристики стенда |

Эти спринты предварительные: полный GAP может изменить их границы. Работы по производительности не должны откладывать получение проверенного перечня бизнес-доработок. Первое ТЗ связывает требования редакции 55, существующие функции и новые задачи; затем формируются функциональные спринты.

Владелец принимает результаты как заказчик и программист. Каждое задание для модели включает конкретный участок кода, допустимые файлы, входные данные, ожидаемое поведение и независимые проверки. Объём ограничивается одной законченной функцией. Локальные модели допускаются по результатам пробного задания; название модели не заменяет проверку. Изменения резервов, товарных балансов и транзакций проходят отдельное ревью. Исполнитель не получает права объявить всю систему готовой на основании собственного локального теста.

## Что подлежит утверждению сейчас

Основное решение: сохранить Python/FastAPI, React/TypeScript и Oracle; выделить фоновые процессы, подготовить production-развёртывание и измерить нагрузку. Окончательная конфигурация серверов, лицензия Oracle, сроки хранения, RPO/RTO и профиль пиков фиксируются до обязательств по мощности. RPO/RTO должны различать отказ процесса, хоста и потерю площадки; успешный commit сам по себе не обещает сохранность при потере всей площадки.

После утверждения — реестр самостоятельных правил редакции 55, GAP с доказательствами по коду и стенду, итоговое ТЗ и небольшие спринты. Полный GAP в этой записке не выполнен.
