# NICORA: договор модульной разработки

Принят по поручению владельца 7 октября 2026 года. Основание: [[nikora_technology_stack_20261007]], требования редакции 55 и утверждённые принципы длительной разработки. Это дополнение к плану NS00–NS67, не закрытие его спринтов.

## Ответственность и слои

Система развивается как модульное приложение. [Машиночитаемый реестр](../../config/architecture/nicora-policy.json) задаёт бизнес-области и владельцев предметных данных: master_data, inventory, fulfillment, quality, resources, transport, delivery, finance, integrations, platform. Реестр описывает целевую ответственность, а не утверждает, что все legacy-таблицы уже распределены. Фактические объекты и контракт их единственного владельца уточняются в NS02/NS03 и фиксируются в wiki/database. Новое семейство добавляется после архитектурного решения; новые пустые каталоги не создаются заранее.

Backend: app/modules/<area>/{api,application,domain,infrastructure}; public.py и contracts.py служат межмодульным контрактом. Frontend: src/features/<area>/ с публичным index.ts/index.tsx. Глубокий импорт из чужой области запрещён. Один модуль может иметь только нужные ему слои.

- domain содержит бизнес-правила и состояния, зависит от своего domain и стандартной библиотеки. Не импортирует HTTP, Oracle, соседние модули или legacy services.
- application координирует сценарий, использует предметные правила и объявленные порты; конкретные адаптеры внедряются через composition root, а не импортируются сценарием.
- infrastructure реализует Oracle/ERP/оборудование и порты, не зависит от HTTP API.
- api принимает и проверяет контракт, вызывает сценарий, формирует ответ; прямые SQL и commit здесь запрещены.
- Корень модуля содержит только публичный контракт/сборку зависимостей. Не переносить туда логику ради обхода правил.

Одна бизнес-операция имеет документированную транзакционную границу. Репозитории не фиксируют части команды самостоятельно; Unit of Work/композиция фиксирует необходимые товарные изменения, бизнес-журнал и исходящее событие вместе. Внешние вызовы выполняются после фиксации через долговечный обмен. Python и PL/SQL не реализуют независимые версии одного правила; authoritative implementation и ограничение Oracle указываются в карточке. React может предварительно проверять ввод, но не подтверждает товарный эффект.

Состояния и разрешённые переходы документов оформляются явно, с правами, версиями и последствиями. Типы входов/выходов и ошибок публичны; ERP-сообщения имеют версии и идентификаторы. SQL-пакеты изменяются по [[database/oracle_change_protocol]]. Межмодульные чтения выполняются через согласованный контракт или выделенную read model, записи — через владельца данных.

## Автоматическая проверка

```powershell
python scripts/nicora_quality_gate.py
```

Команда запускает Python AST/TypeScript AST анализ, тесты архитектурных правил и обоих frontend typecheck. Нужны локальные зависимости frontend и Python test/API packages; Oracle и запущенные API не нужны. Node использует установленный TypeScript, а не регулярные выражения для импорта. TypeScript module resolution учитывает aliases, export, dynamic literal imports; type-only imports не образуют runtime cycles. Python относительные, app и api.wms_api_server.app импорты нормализуются; TYPE_CHECKING исключается из runtime graph. Ошибка синтаксиса, неразрешённый локальный импорт и пустой frontend inventory не выдаются за PASS.

Проверяется: межмодульный публичный доступ, направление слоёв, новые typed Python functions в modules/, прямые calls execute/commit вне инфраструктуры новых модулей, router→Oracle/db, service→router, циклы статических импортов и размер файлов/функций. 600 строк файла и 100 строк функции — стартовые пороги структурного сигнала, а не доказательство хорошего дизайна. Изменение порогов требует обоснования и ревью. frontend уже имеет strict TypeScript; полное статическое typecheck Python и форматтер для legacy этим шагом не внедрены.

[Legacy debt](../../config/architecture/legacy-debt.json) содержит точный ключ, максимальную величину, owner, reason и remediation для каждого существующего нарушения. Первый полный снимок: 123 файла, 86 пунктов долга, ноль найденных циклов. Обычная проверка не записывает и не расширяет baseline; новые нарушения и рост текущих блокируются. Удаление/уменьшение требует:

```powershell
python scripts/check_architecture.py --tighten-baseline
```

Эта команда только уменьшает разрешения, не может принять новые нарушения. Первичная --capture-baseline отказывается перезаписывать существующий файл. Прямая редакция policy/baseline возможна как обычная правка кода и должна быть независимо проверена; её нельзя использовать для получения зелёного результата без причины. Долг не считается устранённым только из-за перемещения файла или переименования функции.

Локальный workflow .github/workflows/nicora-quality.yml подготовлен для Windows/Linux pull_request и workflow_dispatch. Он не опубликован и не запускался в GitHub. Его проверка не заменяет функциональную/API/Oracle/нагрузочную приёмку. Отчёт: tmp/nicora_quality/architecture.json. --skip-typecheck даёт только явно обозначенную частичную проверку.

## Практический пример и работа с legacy

Нормализация типа транспорта вынесена из transport_service.py в modules/transport/domain/transport_type.py, доступна через public.py. Существующее имя _normalize_transtype в сервисе сохранено импортом; поведения None, пробелов, числовых/неизвестных кодов и алиаса «газель»→«5» проверены. Предметное правило больше не требует HTTP/Oracle. Это один небольшой пример постепенного выделения, не объявление всей транспортной подсистемы модульной.

Для следующей функции определить владельца и контракт, вынести связанную ответственность из большой legacy-функции и уменьшить baseline. Не добавлять новый сценарий в выросший монолит. Удалять заменённую ветку после проверки совместимости. Абстракции вводить при подтверждённых повторениях. Большая перестройка соседних подсистем не включается молча в задачу.

## Приёмка и ограничения анализа

Карточка включает module owner, источник правила, authoritative implementation (Python/PLSQL), состояние/переходы, transaction owner, публичные контракты, совместимость и выбранные проверки. Проверяющий оценивает поведение и структуру. Автор не выдаёт собственный тест за независимую приёмку. После значимых runtime-кейсов обязательна проверка долгих SQL/SKV и решение. Архитектурные решения записываются с проблемой, выбором и последствиями; временные исключения имеют owner и условие удаления.

Статический граф не доказывает товарный баланс, владение произвольным SQL, атомарность PL/SQL, корректность переходов или отсутствие скрытой динамической зависимости. Их подтверждают контракт, ревью и реальные API/Oracle/конкурентные тесты. В новом modules-коде неразрешимый динамический импорт требует явного архитектурного решения; произвольные алиасы/рефлексия не полностью анализируются. Полная независимая проверка изменений и CI-run остаются отдельным evidence.

Новый MCP не нужен: проверка должна исполняться локальным CLI и в CI независимо от модели. Существующий tms-repo читает правила и отчёт, а tms-wiki восстанавливает решения. MCP-обёртка по необходимости сможет вызвать ту же команду, но не станет вторым набором правил или условием работы проверки.
