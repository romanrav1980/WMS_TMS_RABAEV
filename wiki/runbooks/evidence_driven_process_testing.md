# Runbook: evidence-driven тестирование бизнес-процесса

## Назначение

Этот runbook задает обязательный пакет приемки для новых WMS/MES процессов.

Процесс считается готовым к демонстрации только если у него есть:

- ТЗ или сценарий;
- изолированное модельное состояние данных;
- smoke/load runner;
- Oracle/API инварианты;
- ARM screenshot;
- TSD screenshot, если есть пользовательское выполнение на терминале;
- `report.json`;
- `report.md`;
- HTML-презентация или короткий HTML evidence page.

## Минимальная структура артефактов

```text
wiki/requirements/<process>_tz.md
tests/load/<domain>/<process>_load_test.py
runtime/test-evidence/<process>/
  report.json
  report.md
  evidence-presentation.html
  summary.png
  T0_*.png
  T1_*.png
  live-ui/
    arm-*.png
    tsd-*.png
    live-ui-report.md
```

Для простого процесса вместо `tests/load/` допускается `tests/smoke/`, но evidence-папка все равно нужна, если процесс показывается пользователю.

## Обязательные вопросы перед реализацией

| Вопрос | Ответ должен быть в ТЗ |
|---|---|
| Какая волна или доменный документ является центром процесса? | `RRL_PICK_WAVE`, production wave, MES order, shipment context |
| Какие ресурсы выполняют процесс? | `RRL_RESOURCE`, `RRL_RESOURCE_SESSION`, equipment/trolley |
| Какой факт вводит ТСД? | скан, количество, старт, завершение, вычерк, контроль |
| Где хранится факт? | `RRL_WAREHOUSE_TASK`, `RRL_CASE_PICK_*`, event journal |
| Как закрывается домен? | sync handler, case-pick state transition, retry |
| Какие остатки меняются? | free stock, hard reservation, physical remain |
| Что будет видно в ARM? | KPI, прогресс, проблемы, блокирующие задачи |
| Что будет видно на ТСД? | задача, ячейка, паллета/SSCC, SKU, факт |

## Runtime-инварианты

Runner должен проверять:

- HTTP/API failed request count = `0`;
- Oracle invalid objects = `0`;
- нет дублей driver-facing задач, если операция идемпотентна;
- sync rows дошли до `SYNCED`, если процесс использует `RRL_WAREHOUSE_TASK_SYNC`;
- case-pick строки и поддоны дошли до ожидаемого статуса;
- физический остаток меняется только после факта выполнения;
- свободный остаток/резерв меняется на этапе планирования или запуска волны;
- ARM и TSD показывают те же статусы, что Oracle/API.

## Этапы снимков

Минимальный stage-набор:

| Stage | Смысл |
|---|---|
| `T0_FIXTURE` | создано чистое модельное состояние |
| `T1_CREATED` | создан центральный документ процесса |
| `T2_LAUNCHED` | процесс запущен, резервы/задачи созданы |
| `T3_FIRST_EXECUTION` | первый исполнительский факт записан |
| `T4_PROGRESS` | процесс в середине выполнения |
| `T5_DOMAIN_SYNC` | доменная синхронизация закрыла шаг |
| `T6_FINAL` | процесс достиг целевого конечного состояния |

Для длинных процессов допускаются дополнительные `T7..Tn`.

## Правило хранения

`runtime/test-evidence/` является runtime-артефактом, а не wiki-слоем. В wiki нужно хранить:

- ТЗ;
- ссылку на runner;
- краткий результат последнего значимого прогона;
- путь к runtime evidence;
- ограничения и известные слабые места теста.

## Приемочный текст

В финальном отчете по процессу должно быть коротко написано:

- что проверяли;
- какой run id;
- сколько объектов было создано;
- какие задачи/факты закрылись;
- какие ошибки отсутствуют;
- где лежат ARM/TSD screenshots;
- какие ограничения остаются.
