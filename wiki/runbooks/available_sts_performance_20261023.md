# Свободные СТ: исследование запроса23.10

## Причина работы

В slow log повторяется `/api/admin/transport/available-sts`:631мс в прогоне бумажного задания. Проверена существующая страница100 и выборка одного склада. API продолжает выполнять прежний SQL; ни один исследованный вариант в работающий процесс не загружался.

## Что измерено

Таблица заголовков имеет статистику380734строки от30.05; строк состава394744 от11.10. Существуют индексы RRL_ST_PAGE_KEYS_I(ST_NUMBER,ADDR,WARE_ID,CONDITION,PALLET_UID) и индекс состава по PALLET_UID. Дата статистики сама по себе не доказывает неверную оценку.

EXPLAIN PLAN существующего запроса показывает два полных чтения заголовков: для выбора ключей страницы и для обратного соединения. Это расчётный план, фактический runtime plan не получен. Hint nested loops не дал устойчивого выигрыша.

CROSS APPLY с разделением NULL/не-NULL номера совпал по строкам, но на складе7 замедлил медиану397→4789мс. Разделение всех трёх ключей дало264против754мс на одном замере склада, но другая страница ухудшилась975→1199мс. Четыре ветви для одного склада дали312→427мс на первой странице,405→305мс на второй,356→337мс на20строках. Чередование старого/нового SQL показало сильное колебание времени. Устойчивый выигрыш не подтверждён.

NULL номера/адреса/склада, повторяющиеся группы, пустой PALLET_UID, исключённое состояние, страница2 и фильтр склада проверены READ ONLY синтетическими CTE в настоящем Oracle. Строки совпали с прежним SQL и малым полным эталоном. Это не загрузочный тест.

## Решение

Кандидаты отклонены, исходный Python-файл восстановлен до HEAD. Новый индекс, обновление статистики, hint и кэш не добавлены. Пустое восстановление SQL не требует перезапуска API. До правок сохранены HTTP снимки4страниц; товарные данные не менялись.

Codex/T12 продолжает с измерения CPU/buffer gets/чтений и сравнения статистики с фактической кардинальностью. Перед изменением статистики нужно сохранить её для отката и проверить планы связанных транспортных выборок. Глобальную страницу без периода следует проверять отдельно от работы по выбранному складу. Доступ к фактическому плану и производственный SLA остаются открытыми; задержка631мс не объявлена устранённой.

## Фактическая работа курсора
Отдельный READ ONLY запрос с gather_plan_statistics вернул100строк склада7 за518мс в первом запуске и389мс в следующем. V$SQL конкретного курсора:13559/12150 buffer gets,508/380мсCPU,3229/0diskreads. Это два инструментированных запуска, не производственная медиана. DISPLAY_CURSOR сообщил об отсутствии SELECT на V$SQL_PLAN_STATISTICS_ALL; прямое чтение V$SQL_PLAN далоORA-00942. Поэтому per-nodeactualplan не получен; расчётныйEXPLAIN не подменяет его. Источник: tests/tradecase/profile_available_sts_runtime.py, T12/available-sts-runtime-plan.json. Решение Codex/T12: запросить/получить runtimeplan через штатный диагностический доступ перед новым индексом/статистикой; в текущем коде сохранить SQL и ограниченную страницу. Привилегии не расширялись.
