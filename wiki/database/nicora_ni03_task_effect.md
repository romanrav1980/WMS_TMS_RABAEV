# NI03 — завершение существующего задания и движение товара

Migration 2026-10-07-010-ni03-task-effect добавляет COMPLETION_HASH/JSON к существующей RRL_WAREHOUSE_TASK. Подтверждение, остаточное задание, resource event, domain sync, движение и резерв выполняются через один cursor. Повтор того же подтверждения не создаёт нового движения; иной payload/actor получает конфликт. Старые DONE без hash не получают выдуманной identity.

Используются существующие RRL_WAREHOUSE_TASK_SYNC и RRL_WAREHOUSE_TASK_STOCK_MOVE с unique TASK_ID. WAVE REPLENISHMENT и FULL_PALLET PICKING_MOVE записывают TYPE_EVENT=2 в RRL_EVENTS; единственный enabled legacy event trigger обновляет RRL_REMAINS. Прямой UPDATE/merge остатков в этом обработчике удалён. Партия/срок/марки остаются привязаны к той же pallet identity.

Частичное пополнение уменьшает QTY своего действующего HARD source reservation на перемещённое количество. Завершение всей цепочки потребляет оставшийся резерв. Количество, паллета, источник и состояние резерва проверяются; чужой/недействующий резерв отвергается с rollback.

Checkpoint и результат применения — runtime/ni03. Rollback отказывается удалять identity при наличии подтверждений; не запускался.

010 установлена 07.10.2026 в существующей RABAEV/orcl: 3 statements, 0 errors. Live metadata подтверждает VARCHAR2/CLOB поля, ENABLED JSON constraint и APPLIED ledger. API import — 374 routes. Бизнес-прогоны не проводились.

Клетки и stock pallet блокируются; warehouse/cell/quantity сверяются. Целая паллета должна перемещаться полностью. Частичный marked move требует точного состава единиц и пока отвергается: NI04, без потери помарочного состава. Складская матрёшка не объявляется завершённой.

MES domain handlers сохранены с их существующими правилами жизненного цикла, но gateway calls объединены транзакцией. SAP PUTAWAY сохраняет свой отдельный готовый атомарный путь. Общая доступность кандидатов, унификация резервов между всеми командами, отдельный case-pick API, fulfillment и запуск волны целиком — оставшийся объём NI03, не объявленный выполненным этой миграцией.

## Рекомендация по большому потоку, 07.10.2026

**Последующее решение владельца:** шесть принципов приняты, постепенный перевод отменён. Подготовлено [ТЗ единого ядра](../requirements/stock_posting_core_tz.md): один cutover всей системы, общая STOCK_LEGACY_TRIGGER_ENABLED=0 по умолчанию, legacy writer при OFF получает явный отказ. Предыдущий текст ниже — история рекомендации; действующий код/trigger пока не переключены.

Текущая редакция ТЗ — **2.0**, см. [[nicora_stock_posting_target]]. Она определяет P/H и их атомарный UPDATE, перенос продолжающегося HARD при пополнении, полный общий порядок ресурсов, whole-operation rollback и карантин через недоступные ячейки. Уменьшение source HARD в описанном выше первом NI03 срезе — действующее ограниченное поведение, которое не заменяет целевой перенос покрытия. Полный NI03/cutover ещё не выполнен.

По вопросу владельца о миллионах операций рассмотрена архитектура проводки. Это рекомендация, а не разрешение отключить trigger или заменить рабочую структуру. Обычный DML trigger действует внутри транзакции и сам по себе не вызывает искажения от роста объёма; проблемы возникают из-за алгоритма, конкурентного доступа, повторов и обходных writers. [Oracle: ошибки triggers](https://docs.oracle.com/en/database/oracle/oracle-database/19/lnpls/exception-handling-triggers.html), [блокировки](https://docs.oracle.com/en/database/oracle/oracle-database/19/cncpt/data-concurrency-and-consistency.html).

Текущий legacy event trigger выполняет SUM/select и отдельные insert/update/delete, допускает отрицательный остаток при отсутствии источника и не блокирует повтор бизнес-команды сам. Поэтому NI03 проверяет источник и duplicate rows до события. Эти гарантии относятся к новому пути, не ко всем legacy writers. Новый lock_domain сериализует одну волну, cell locks сериализуют разные паллеты в общей ячейке; это временно широкие блокировки, не подтверждённое решение для миллионов операций.

Целевой вариант — явная PL/SQL posting command на существующих таблицах: operation identity, проверка/блокировка точного stock key и состава, журнал движения, изменение остатка/резерва/задания и outgoing obligation атомарно. Журнал сохраняет историю; исправления — обратная/корректирующая операция. Внешние отправки и аналитика могут быть асинхронными; доступный запас для нового отбора/резерва обновляется синхронно. Это не требование перехода на распределённый event sourcing или новый MCP.

Миграция должна сохранить единственного исполнителя изменения остатка: trigger и новая процедура не уменьшают его одновременно. Сначала извлечь общий posting core и оставить legacy trigger как тонкий вызов этого core либо контролируемо перевести все writers; прямое отключение trigger до перевода несовместимо с legacy приёмкой/MES. Unique/CHECK/FK обеспечивают простые инварианты, business posting сохраняет сложные. [Oracle: trigger guidelines](https://docs.oracle.com/en/database/oracle/oracle-database/19/lnpls/trigger-design-guidelines.html).

Миллион операций за 24 часа — примерно 11,6/с, десять миллионов — 115,7/с; за 8 часов — 34,7/с и 347,2/с. Это арифметика, не измеренная мощность: важны пики, количество SQL и кодов на бизнес-команду, конфликты по stock key, redo/commit и индексам. Подтверждение мощности потребует ограниченного измерения целевой команды, когда владелец разрешит соответствующие прогоны; сейчас они не запускались.
