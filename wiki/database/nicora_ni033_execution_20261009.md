# NI03.3: фактическое исполнение и частичная СТ

Продолжение [[nicora_ni033_physical_fulfillment_20261009]]. Изменения локальные, GitHub не обновлялся.

## Установлено в RABAEV

032: SHIPPED проецируется из фактических BASE-количеств проводки, а не из количества упаковок документа. Сохраняются состав SKU/единиц, идентификатор операции и момент отгрузки. 033 нормализует Oracle TM9 (.125 → 0.125) без округления. 034 сохраняет владельца резерва при явном пополнении задания.

035: реальный STARTED_AT_INSTANT и часовая зона начала шага. Обнаружено: legacy Oracle wall clock -04, сессия +03; сравнивать эти наивные timestamps нельзя. Legacy поле не переписано. Начатый внутри смены шаг можно закончить после её окончания; новый остаточный шаг требует действующей смены.

036: принятая недостача продолжает блокировать исходную ячейку/SKU до завершения связанной инвентаризации. Решение ACCEPT_SHORT не делает заявленный отсутствующий товар снова доступным.

037: новые инциденты получают CREATED_AT_INSTANT. Исторические timestamps не подменяются временем миграции; для них сохраняется явно настраиваемое смещение архива CCTV. Реальное подключение NVR не выполнялось.

## Частичная СТ

[PartialShipmentLayout](../../api/wms_api_server/app/modules/inventory/infrastructure/partial_shipment_layout.py) использует существующие ST/FULFILLMENT и журнал CASE. Завершённый CASE с утверждённой недостачей предлагает уменьшение состава СТ до физически собранного. Исходный заказ SAP остаётся прежним; исходное количество/вес СТ сохраняются, удалённые строки остаются в неизменяемом событии.

Назначенную на рейс СТ сначала снимают прежним транспортным механизмом. После изменения состава используется прежнее назначение. Контроль версии CASE, физического состава и состава СТ выполняется в одной metadata-транзакции. Неизвестный исход запроса повторяется с тем же ID и содержимым. Число упаковок задаётся явно, если пропорция не целая. Вес по нормативу отмечен PROPORTIONAL_NORM и не объявляется измеренным весом.

API GET/POST /api/case-pick/tasks/{id}/partial-shipment-layout и отдельный раздел существующего ТСД CASE. Экран исполнения заказа показывает собранное и остаточную потребность отдельно, без суммирования EA и KG.

## Изменённые реальные случаи

- SHIP: 3 EA = 0.125 BOX; фактическое исполнение SHIPPED равно 3 EA, P/H=0, повтор без второго списания.
- Смена: позднее завершение 1 EA допустимо, START остаточных 2 EA вне смены запрещён; после открытия смены остаток выполнен.
- Маркировка CRPT+ЕГАИС: 3 физических штуки проведены как 1+2, несколько профилей не удваивают количество.
- Частичная СТ: собрано 1 из 3, ACCEPT_SHORT 2; СТ уменьшена до 1, исходный заказ 3 сохранён, точный повтор одно событие; возврат CASE сбрасывает текущую проекцию.

Приватные фикстуры очищены командами ядра, журналы сохранены. Независимые/Qwen/браузерные и промышленные прогоны не объявляются выполненными.

## SQL-решение

Проекция отгрузки ~12.45 ms, чтение факта ~10.05 ms; чтение частичной СТ ~1.87 ms, изменение ~2.96 ms в целевых случаях. Сохраняются существующие ключи и ограничения ≤200 строк. Новые индексы без свидетельства плохого плана не добавляются. При устойчивом >500 ms владелец inventory/fulfillment проверяет план и статистику по RRL_SQL_SLOW_LOG/Oracle top SQL.

## Открыто

сквозная FULLPAL-проекция; альтернативная ячейка при нехватке вместимости. NI03.2 и NI03.3 целиком не закрыты.


## 038: отдельный допуск отбора

RRL_PICK_WAVE получает PICK_RELEASED_AT/BY/OPERATION_ID. WAVE_LAUNCH по-прежнему начинает подготовку и физическое пополнение; WAVE_PICK_RELEASE отдельно разрешает отбор. Старый get_wave_readiness остаётся монитором завершения сборки, иначе возникает круговая зависимость.

RRL_STOCK_WAVE_READY проверяет ≤200 выбранных CASE/FULLPAL заданий, ≤500 принадлежащих им HARD и ≤200 открытых пополнений. По каждому SKU показывает BASE-потребность, допустимый резерв в нужной ячейке и недостающую часть. EA/KG не суммируются. Открытое пополнение показывает существующее складское задание и исполнителя. Нельзя заменить физическое завершение статусом подготовки.

Команда собирает полный план anchors/fences и повторяет snapshot под упорядоченными блокировками; изменение состава отклоняется CLOSURE_CHANGED. Журнал/outbox и разрешение фиксируются одной транзакцией. CASE CLAIM/START/CONFIRM и FULLPAL START/COMPLETE проверяют допуск в Oracle, включая администратора. Переназначение и сообщение недостачи остаются доступны для восстановления. Исторические волны не получают фиктивного времени допуска.

Установлена 038 APPLIED, шесть пар пакетов VALID. Реальный случай: нет покрытия → отказ; открытое пополнение → отказ; Root TASK_COMPLETE 3 → HARD 3 в отборе → разрешение; точный replay одна APPLIED-операция. Другой случай подтвердил запрет CASE до допуска и сохранил частичную СТ после него. Private fixture P/H очищены ядром.

Readiness query 75dtqqnq1wuw6: 25.16 ms в четырёх целевых чтениях. Решение: сохранить bounded windows; нагрузочную мощность не заявлять. Волну с потребностью больше вместимости нельзя разрешить фиктивно: альтернативная ячейка/разделение остаются следующей функциональной задачей.
