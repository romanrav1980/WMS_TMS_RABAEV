09.10.2026. Реализация в RABAEV/orcl; NI03.2 остаётся in_progress.

021 APPLIED: RRL_STOCK_REPL_BIND планируется существующим TASK_PLAN и вызывается TASK_CORE после физического перемещения в той же транзакции. Для generic RT.PICK_TASK_ID=NULL выбираются действующие CASE-строки данной волны/SKU/целевой ячейки. Покрытая HARD потребность вычитается; очередь сохраняется по PICK_SEQUENCE. До блокировок собираются CASE/task/reservation anchors и новые reservation IDs. Locked execute повторно проверяет потребность/факт/покрытие. Старая WAVE coverage освобождается и тот же объём закрепляется за существующим PICK_TASK; unit keys переносятся точно, без прибавления P или двойного H. Излишек доставленного chunk возвращается в свободный запас. Срочный SHORT с explicit PICK_TASK_ID сохраняет прежний путь. Partial transfer получает фактический relocated reservation ID.

Адресный scripts/ni032_generic_bind_case.py passed: Ptarget1/capacity2/demand3 → delivery1, targetP2/H1 и CASE consumer HARD1, sourceP2; идентичный replay не меняет запас. Own stock restored through root. Случай без consumers также passed: delivered surplus свободен.

Snapshot SOFT demand учитывает HARD и подтверждённый pick fact с вычитанием их overlap: CASE carrier lot либо выполненный physical pick-move target. Нет двойного вычитания факта, всё ещё покрытого HARD до отгрузки. Новый code установлен/VALID; полный marked/partial/shipment overlap case ещё отдельный remaining ticket.

023–024 APPLIED: существующий RRL_PICK_WAVE_REPLENISH_TASK дополнен RESERVE_OPERATION_ID, MINIMAX_CYCLE_ID, MINIMAX_TARGET_BASE, MINIMAX_FINISHED_AT. Таблица/журнал остатков не заменены. Нормы берутся из прежних PICK_FACE/PICK_FACE_ARTICUL/ARTICUL_REPLENISH_RULE; explicit BOX threshold переводится в BASE через текущую конверсию. Legacy MIN_QTY/MAX_QTY используются как прежние BASE limits; NULL maximum может определяться canonical volume capacity. Неоднозначные слоты/неполные нормы дают явную причину. Будущий перенос legacy норм иной единицы требует подтверждённой конверсии, не угадывания.

MinimaxService повторно использует WAVE_KIND=REPLENISHMENT (уже существовавший enum), operational metadata и root WAVE_RESERVE_SOURCES; resource task creation внедрено из replenishment_composition. Один maintenance wave на warehouse под CONFIG X, существующая открытая подача исключает дубли. Метаданные планирования фиксируются до root reserve; durable source ID хранится на RT. После partial доставка цикл сохраняет исходный MAX и продолжается при появлении источника, даже если остаток уже выше MIN. Завершение цикла — только после физического достижения MAX. При отсутствии пригодного источника WAIT_STOCK без создания новых FAILED строк каждую итерацию. Окончательный source admission/capacity/composition проверяет прежнее ядро.
