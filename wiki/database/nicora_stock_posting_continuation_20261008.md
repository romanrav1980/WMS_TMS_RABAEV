# Продолжение перехода: компоненты 121–130

08.10.2026. Продолжение [[nicora_stock_posting_extension_20261008]]. Цель владельца остаётся полной заменой проводок в существующей RABAEV/orcl. Переключение ещё не выполнено.

## Реализовано

- INVENTORY_REGISTER_LOT проводит начальную инвентаризацию через открытый RRL_REVIZION, точную базовую единицу, указанный срок годности и причину. Паллетный идентификатор допускает внутренний формат. RRL_ADD_INV_LINE подключён к команде, прежняя реализация доступна только через адаптер в PREPARED.
- Если в ячейке уже есть положительный остаток данного артикула, новая начальная загрузка отклоняется: требуется измеренный INVENTORY_COUNT существующих партий. Проверка выполняется после общей блокировки CELL/SLOT, которую получают также движения в эту ячейку. Это предотвращает повторную загрузку под другой ревизией/идентификатором.
- WinForms импорт invent.xls создаёт настоящий документ REVIZION вместо inventory_id=1. Связь файла и документа сохраняется локально; повтор того же файла использует тот же документ. Количество и цена используют Decimal. Цикл завершается по пустому Value2.
- StockCommandIntent сохраняет ID команды и исходные параметры до вызова Oracle. Подключены три существующих вызова RRL_INTERNAL_MOVE2 и импорт RRL_ADD_INV_LINE. При неизвестном исходе повтор использует прежний ID; изменение параметров незавершённой команды отклоняется с путём к сохранённым параметрам. Ошибка удаления локального файла после подтверждённой Oracle проводки не объявляет проводку неуспешной.
- Административная страница inventory-count.html/js: создание ревизии, загрузка партий ячейки, измеренное количество, причина, сохранённая команда для повтора. Идентификаторы паллет общие, не ограничены SSCC.
- Для маркированной инвентаризации сканируются фактически присутствующие уникальные коды. Пакетный resolver связывает их с текущими единицами; сумма присутствующих единиц должна совпасть с измеренным количеством. Отсутствующие зарегистрированные единицы передаются команде как списываемые. Положительная корректировка маркированного товара без capture по-прежнему не реализована.
- STOCK_POSTED contract 3 содержит снимки остатков до/после и изменения состава единиц/резервов. RRL_STOCK_CHANGE_AUDIT читает только запланированные, заблокированные ключи; сообщение пишется в outbox той же транзакцией. Это не означает подтверждения государственных операций.
- Исправлена identity base-policy версия при резервировании из BOX/другой входной единицы. Входная версия применяется к конверсии; balance core получает базовую версию.
- WarehouseTaskDomainSyncService в ACTIVE читает только подтверждённый TASK_COMPLETE, связанный с physical stock move и SYNCED. Повтор не вызывает прежние товарные эффекты. Непроведённый факт возвращает TASK_POSTING_REQUIRED; DRAINING возвращает 503. PREPARED сохраняет прежний маршрут. Это изменение не означает миграции старых завершённых заданий.

## Дополнительные исправления MES API

Release-to-production в ACTIVE входит в MES_RELEASE_TO_PRODUCTION до чтения изменяемого статуса заказа. Существующее ядро создаёт HARD и оба вида заданий в одной транзакции; Python не повторяет создание warehouse tasks после commit. В PREPARED исправлен пропущенный bind p_operation_id к установленному native адаптеру.

При повторе MES apply с явно указанным operation_id загружается сохранённый CANONICAL_REQUEST. Проверяются пользователь, заказ, явно заданные movement_ids и состав units_by_movement. Используется первоначальный набор движений, даже если после commit больше нет ожидающих строк. Изменение содержания возвращает OPERATION_CONFLICT. Для первоначального выбора всех ожидающих движений operation_id обязателен.

Production-orders.js сохраняет команду MES apply до HTTP-вызова и сохраняет её при неизвестном исходе. Исправлены также лишний аргумент p_operation_id при создании MES заказа и неверные/лишние binds в legacy issue/apply вызовах. Шесть регрессионных случаев проверяют восстановление набора, конфликт пользователя/заказа/состава/ID и release replay до проверки закрытого документа.

## Установка и доказательства

Manifest содержит 47 package pairs и native inventory adapter. Source checkpoints и парные rollback: 123_stock_change_payload, 124_shipping_reserve_projection, 127_inventory_import, 128_inventory_duplicate_guard, 129_reservation_base_policy. Миграции 043–046 записаны через 130_inventory_audit_ledger.sql. Полная копия базы/VM не создавалась.

Свежая Oracle выборка: PREPARED; в реестре 10 ADAPTED / 21 UNCONVERTED; изменённые RRL_STOCK_* и RRL_ADD_INV_LINE без INVALID. Installer preflight подтверждает 47 pairs и отсутствие недостающих прямых grants; это не физическая приёмка.

StockCommandIntent.cs отдельно скомпилирован C# ISO-2; полная сборка WinForms не выполнялась. 11 тестов MES replay и StockPosting UoW проходят. Короткая проверка sync подтверждает чтение APPLIED без legacy DML, отказ для неприменённого факта и DRAINING. Python синтаксис, inventory и MES JavaScript проверены. Визуальная проверка страницы браузером не получена: вызов навигации завис и был остановлен.

Свежая выборка дополнительно подтверждает VALID у RRL_SAP_RECEIPT_API spec/body и RRL_SAP_STORE_ROW_GUARD, без USER_ERRORS. Их прежний INVALID baseline больше не описывает текущую компиляцию; функциональная приёмка не проводилась.

Новых успешных физических проводок этим этапом не подтверждено. Нагрузочная мощность и отсутствие deadlock под нагрузкой не объявляются доказанными.

## Обнаруженный старый алгоритм

RRL_CLEAR_OTBOR_CELL оставляет одну паллету с самым большим сроком годности и создаёт TYPE_EVENT=3 на полные остатки остальных. Это списание, а не освобождение ячейки перемещением. Сохранить его под новым названием без подтверждённого физического основания было бы ошибкой. Обработчик остаётся UNCONVERTED; требуется явная коррекция/пересчёт с причиной либо реальное перемещение.

## Остаток работы

Legacy receipt/reversal/REVIZION/ARTICULS и косвенные callers; физический состав CASE carrier; partial marked split и вложенные HU; полный охват metadata/config/regulatory fences; реестр, B0 и единое переключение. Ни guards, ни успешная компиляция не заменяют эти функции.

SQL: новых физических случаев/нагрузочных прогонов здесь нет. Чтение sync ограничено task_id и FETCH FIRST 1, resolver ограничен пакетами и числом единиц. Решение по ранее отсутствующим slow SQL остаётся прежним: после первого реального проведения снять slow/top SQL; владелец — разработчик ядра. Индексы без измерения не добавлялись.

Encoding check: единственная найденная проблема — прежний raw TRANSPORT_TASK_PACKAGE_BODY.sql с маркером U+0420 U+00A0. Поддерживаемые правки нового этапа не отмечены; raw источник не изменялся.
