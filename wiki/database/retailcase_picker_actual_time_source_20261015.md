## Граница первого инкремента

Оператор своей учётной записью подтверждает ACTUAL_SHIFT_START/FINISH, WORK_START, PAUSE, RESUME и WORK_FINISH. Native owner назначает aware `SYSTIMESTAMP`; браузер не передаёт actor, timestamp, origin или confirmed. Вход в приложение, план смены, heartbeat и старые naive clocks не создают фактическую смену. События обозначены `MANUAL_CONFIRMED`: они не подменяют native подтверждение физического подбора.

Четыре новые таблицы: RRL_PICKER_TIME_STREAM — текущая версия и единственное активное состояние оператора; EVENT — неизменные переходы; SPAN — неизменные закрытые интервалы; COMMAND — исходные байты/SHA и APPLIED либо окончательный REJECTED. Новые native API/AUTH/READ/WRITE и guards изменяют только эти таблицы. WRITE доступен только API; контекст записи привязан к текущей TX и оператору. У существующих CASE/TASK/SESSION нет новых триггеров и изменений пакетов.

| Действие | Требуемое состояние | Результат |
|---|---|---|
| ACTUAL_SHIFT_START | OFF / IDLE | OPEN / IDLE, серверное начало присутствия |
| WORK_START | OPEN / IDLE, текущее назначенное задание | WORK, исходное задание и начало |
| PAUSE | WORK того же задания | PAUSED, начало зарегистрированной паузы |
| RESUME | PAUSED, задание по-прежнему назначено оператору | WORK, закрытый PAUSE; исходный WORK продолжается |
| WORK_FINISH | WORK или PAUSED того же источника | IDLE, закрытый WORK и при необходимости PAUSE |
| ACTUAL_SHIFT_FINISH | OPEN / IDLE | OFF, закрытый ACTUAL_SHIFT; контекст текущего склада очищен |

Каждый новый APPLIED увеличивает stream_version на один. Повтор прежней операции возвращает прежний receipt, не создаёт событие. Нулевой интервал не превращается в положительную длительность. При регрессе серверных часов действие не подтверждается. Исправления старых границ и заднее датирование этим API не поддерживаются; история не переписывается.

## Права и транзакция

Все маршруты self-only: оператор берётся из terminal Basic auth. Требуются активный RUSERS, собственная фактическая RESOURCE_SESSION и совпадение склада ресурса/смены. Начало присутствия/работы и RESUME требуют ACTIVE session, активный ресурс и OPEN плановую смену; даты её naive плана не используются как фактические границы. Завершение ручного времени допускает уже закрытую собственную сессию при сохранённых текущих правах, чтобы не выдумывать LOGOUT_AT как время окончания.

Права проверяются через RRL_ACCESS_API по **фактическому WAREHOUSE** и владельцу self: для присутствия — case_pick_execute либо warehouse_task_execute; для WORK — соответствующее право конкретного CASE/warehouse-task источника. WORK_START/RESUME дополнительно проверяют текущие assigned actor/session/resource/WARE и IN_PROGRESS-подобное состояние. Обычный warehouse источник ограничен PICK/PICKING_MOVE в одном складе по обоим фактическим адресам. Это не новый допуск выполнения или quantity writer.

Standalone command: предварительная текущая авторизация → чистый begin_plan → ACCESS_REV SHARE → RELEASE/CONFIG X → **полный заранее объявленный** OP/ROW mutex plan, включая ROW(RRL_PICKER_TIME_STREAM,operator) → при необходимости source row → actor/session → stream row → повторная авторизация → exact receipt → expected_version/effect. Конфликт версии/допустимого состояния сохраняет REJECTED только после авторизации и fences; 403, неизвестная ORA и ошибки связи не объявляются окончательными. Неуспешный эффект откатывается к savepoint, затем receipt либо весь вызов откатывается. Native процедуры не COMMIT; Python проверяет typed ACK до gateway commit.

GET receipt и чтение используют текущие права. Полное окно не фильтрует скрыто другие склады/виды источника: недопустимый scope даёт отказ. Права GROUP/DC/NETWORK наследуются существующим ACCESS owner, но runtime проверки именно этого нового журнала ещё не выполнены.

## Полнота и as_of

READ adapter открывает Oracle READ ONLY transaction, берёт серверный aware as_of и только уже закрытые SPAN, пересекающие запрос ≤31 дня. Фильтр применяется до предела5000; превышение — явный отказ, не частичный ответ. Права кешируются в рамках чтения по складу/виду источника, а не перечитываются на каждую строку.

Закрытый ACTUAL_SHIFT подтверждает полноту только своего явно зарегистрированного окна; паузы в нём сохраняются. Пробел между двумя сменами не считается доказанным отсутствием работы. Открытый SHIFT/WORK показывается в текущем состоянии, но в первом инкременте не получает выдуманного finish=as_of. Поэтому отчёт, захватывающий неизвестный участок, возвращает NO_DATA.

**WORK и PAUSE coverage всегда uncertified/INCOMPLETE в этом инкременте.** Ручные положительные интервалы можно читать, но они не доказывают регистрацию всех начал, пауз, передач и окончаний физических задач. Application передаёт kernel только ACTUAL_SHIFT coverage закрытых окон; знаменатель фактической сборки остаётся NO_DATA. Числители и коэффициенты не рассчитываются.

## Следующий same-TX источник

Первый согласуемый комплект instrumentation — новый native CASE_ASSIGNMENT START и существующий Python case_carrier_close. Затем legacy CASE start/transfer/cancel, warehouse task START/COMPLETE/transfer/cancel и SESSION pause/resume/logout. До покрытия всей семьи и отдельной сертификации нельзя включать общий complete WORK.

Каждый owner заранее добавляет ROW(stream,assigned_operator) к **своему исходному resource plan до begin_plan/acquire**, а не из позднего row-trigger. Hook после source/session locks лишь assert_held, блокирует stream и пишет событие в той же owner TX; не вызывает begin_plan/reset/COMMIT. Передача требует anchors обоих операторов заранее и сортированный порядок блокировки streams. Actor команды и assigned operator хранятся отдельно для native origin. Текущий manual-only CHECK/контракт расширяется отдельной forward миграцией; из этой страницы не следует, что instrumentation уже реализован.

Фактический аудит обнаружил: CASE close сейчас принадлежит Python metadata TX, а не выдуманному RRL_STOCK_CASE_CLOSE_CMD; legacy SESSION pause/resume меняет статус Python UPDATE без отдельной aware operation/version и не связывает request.updated_by с authenticated actor. Эти пути требуют явного owner patch, не автоматического доверия строке UPDATED_BY.
