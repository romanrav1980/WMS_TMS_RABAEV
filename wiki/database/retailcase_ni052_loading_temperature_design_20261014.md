## Правила исполнения

- Температурные ограничения читаются из действующих правил SKU склада для фактических member ST текущего места. Неполная/противоречивая настройка не маскируется. Отсутствующее правило не объявляется доказательством пригодности ambient.
- Для товара с явно заданными температурными пределами требуются текущий READY профиль машины, его версия и подтверждение оператора непосредственно при погрузке. Допустимая температура находится в пересечении заявленных возможностей и всех ограничений товара.
- Подтверждение оператора содержит origin=MANUAL_AT_LOADING, decimal observed_c, vehicle_profile_version и observation_reference. Это запись ручного подтверждения; датчик, поверка и непрерывное соблюдение температуры этим не доказываются.
- До товарного эффекта выполняется повторная проверка под уже существующими CONFIG и vehicle→TT→dock→ST блокировками. Смена версии/правил/состава отказывает всей команде.
- Результат подтверждения фиксируется неизменяемым фактом, связанным с исходной LOAD_OPERATION_ID, в той же Root транзакции: движение, остатки/резервы, состав, факт погрузки, температурный факт и обязательный outbox. Новая отдельная транзакция подтверждения запрещена.
- Повтор сохранённой операции возвращает прежний результат. Новое значение температуры под тем же operation_id — конфликт. Старые факты/рейсы не получают выдуманных измерений.
- Для выезда нужна самостоятельная текущая проверка температурного подтверждения; факт при погрузке не считается бессрочной гарантией. Длительная выдержка, датчики и срок свежести требуют явной конфигурации, а не придуманного TTL.
- Разные независимые температурные отсеки требуют отдельной модели привязки места к отсеку; текущий профиль имеет одно общее температурное пространство.

## Совместимость и границы

Транспортное назначение и quantity writer остаются прежними. Отсутствующий SKU диапазон показан как неподтверждённый; его нельзя превращать в numeric default. Действующие пути HU, standalone CASE/FULLPAL и reconciliation используют общий load core. Допуск в Python/UI не заменяет native guard. Rollback сохраняет историю и не возвращает бесконтрольную отгрузку температурного товара.

## Подготовленная реализация1162–1163

RRL_STOCK_LOAD_THERMAL вычисляет диапазоны member ST и текущую версию профиля, повторно проверяет frozen результат под CONFIG/vehicle/TT locks. RRL_TT_LOAD_THERMAL_FACT имеет FK к исходному физическому load и профилю; запись возможна только из общего load core с rootcontext/lock/privatewriting flag, UPDATE/DELETE запрещены. Факт создаётся после исходного loadfact в той же транзакции; ошибка отменяет оба и товарное движение.

Для SKU с заданным пределом подтверждение обязательно. Если ни у одной SKU не задан диапазон, прежний поток не получает выдуманный режим; отсутствие правила сохраняется как неподтверждённое. Смешанный набор фиксирует configured/unconfirmed SKU counts; температурная пригодность всех неизвестных SKU не заявляется. Один открытый предел поддерживается точно; обратный диапазон отклоняется.

Typed API поддерживает новый блок отдельно от старых полей. Отсутствующий блок не добавляет null/новые ключи в старый canonical request, поэтому прежние сохранённые повторы совместимы. Raw loading UI читает действующий профиль, требует ручное подтверждение и сохраняет точный запрос до отправки. История читается boundedIN≤200 после текущих складских прав в том же READ ONLY снимке.
