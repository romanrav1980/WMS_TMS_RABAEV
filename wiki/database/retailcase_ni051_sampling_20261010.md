# NI05.1: постоянная выборка и полная сверка

064 APPLIED в RABAEV/orcl: QC_MARK, QC_ITEM, QC_POLICY, QC_GATE, PALLET_QC_CMD и новые metadata guards VALID, checkpoints336–338. [Migration](../../db/migrations/2026-10-10_ni051_sampling/apply.sql). Продолжает [[retailcase_ni051_independent_control_20261010]], полный спринт открыт.

В существующей СТ: QC_SAMPLE_BUCKET (0..9999), sticky QC_SAMPLE_REQUIRED, QC_RESCAN_REQUIRED и SCAN_ITEM_PROVED. Warehouse settings: OUTGOING_QC_SAMPLE_PERCENT с точностью0.01, default0. Bucket новой СТ назначается один раз session random; legacy NULL получает значение только под root lock. Никакого массового backfill. Selected bucket < percent*100;100 выбирает всех,0 не назначает новых. Старое назначение не снимается снижением процента/повтором/изменением состава.

Предъявление — existing OUTGOING_PALLET_CHECK quality_kind PLAN. Оно сохраняет выборку/исход контрольного плана, не подтверждает QC и не проводит P/H. POST /outgoing-quality/{id}/plan использует frozen operation/body. GET — read preview; назначение сохраняет POST. При legacy NULL bucket и включённой выборке QC/shipment требуют PLAN: попытки неуспешной проверки не дают переигрывать случайный выбор.

Полная проверка нужна при explicit SCAN/BOTH, выбранном месте или повторной сверке после неуспешного QC. Обычный SKU: каждый scan_id/barcode/quantity1 соответствует одной штуке или целой коробке; server определяет SKU и EA/BOX по существующему master, переводит точным UOM, сверяет весь BASE состав. Неизвестный/неоднозначный/чужой barcode и недостаток/избыток не подтверждают QC. Повтор одного scan_id с тем же содержимым считается один раз; другое содержимое фиксирует конфликт. Разные события одного EAN могут представлять разные единицы — EAN не является уникальным идентификатором физической штуки. Проверка повторного physical BOX/HU требует NI04.2.

Маркированный SKU сохраняет точное доказательство unit/profile062; EAN его не заменяет. Full ordinary proof не нужен для marked-only состава, но every applicable unique profile нужен всегда. BASE/box barcode входят в semantic signature; изменение master barcode отзывает старое подтверждение.

Расхождение валидного сканирования фиксируется как APPLIED failed QC (verified0/failure_reason), отзывает старые approval signatures и требует full rescan; P/H/units не исправляются автоматически. Это бизнес-результат проверки, не неопределённая ошибка сети. Invalid actor, stale composition, отсутствующая конфигурация и bounds остаются command rejection. Failed result replay не создаёт второй факт. Хороший повторный вес не снимает full-rescan requirement. Исправление физического состава — отдельная явная stock команда.

API/ARM: «Предъявить» читает context и сохраняет root PLAN; обычный scanner input и QR profile input, события/список сохраняются локально, можно убрать ошибочный последний скан. Результат immutable до подтверждения. Successful first weight в BOTH сохраняет ещё не отправленные сканы. Settings API/receiving panel — процент, omitted field сохраняет прежний выбор; Decimal bind без NLS предположения. Missing shipment404, rule reasons показываются оператору.
