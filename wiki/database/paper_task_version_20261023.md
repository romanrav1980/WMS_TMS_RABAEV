# Бумажное складское задание: сверка версии

## Контракт

`GET /api/warehouse-tasks/{task_id}/paper` читает задание в одной READ ONLY транзакции с проверкой действующего доступа к складу. Ответ содержит точные количества, имена складов и исполнителя, подпись текущей версии и Code128. Печать не назначает исполнителя и не подтверждает выполнение.

Штрихкод содержит `WTASK:<task_id>:<task_signature>`. При повторном открытии бланка клиент передаёт подпись как `expected_signature`; изменённое задание возвращает `409 PAPER_TASK_CHANGED`. Физический сканер и принтер пока не проверены.

Обычный `TASK_COMPLETE` уже проверяет необязательный `expected_task_signature`. [Миграция](../../db/migrations/2026-10-23_paper_task_version/manifest.json) `2026-10-23-paper-task-version` добавляет такую же проверку для `HU_TASK_COMPLETE` и перемещения CASE с физическим заданием. Она меняет только два тела пакетов: `RRL_STOCK_HU_TASK` и `RRL_STOCK_CASE_MOVE_CMD`.

HU проверяет подпись при компиляции команды; существующая проверка полного снимка задания после блокировки строки остаётся. CASE проверяет подпись при компиляции и после существующей блокировки физического задания перед перемещением. CASE с подписью без номера физического задания отклоняется. Команды без подписи сохраняют прежний контракт. Возврат ранее сохранённой квитанции не проверяет устаревшую подпись повторно.

## Развёртывание и восстановление

Кандидат подготовлен по свежему `USER_SOURCE` схемы RABAEV/orcl. До применения сохранены SHA исходных тел и SQL отката; preflight отказывает при дрейфе. Товарные остатки, удержания и задания миграция не изменяет. Применение, откат и повторное применение ещё не проверены.

Перед откатом следует отключить новые клиенты бумажной сверки: прежние тела HU/CASE не проверяют дополнительную подпись. Файлы `verify.sql` и `rollback_verify.sql` проверяют SHA тел и отсутствие INVALID.
