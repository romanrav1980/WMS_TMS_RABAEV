# СНС/BLC: удержание товара для добивки

## Граница внедрения

Миграция `2026-10-22-trade-topup-proposal` подготовлена для RABAEV/orcl. Preflight Codex подтвердил пять исходных SHA, отсутствие новых объектов и INVALID0. На момент этой записи применение и откат ещё не выполнены. `approval_available=false` сохраняется до живой приёмки и атомарной передачи удержания волне.

Предложение сохраняет количество, потребность и версию расчёта вместимости. Подтверждение должно создать настоящий HARD по выбранным единицам, запись решения и исходящий запрос SAP в одной StockPosting-транзакции. Отказ SAP или отмена должны освободить только удержания этого предложения. Ответ с номером заказа сам не создаёт заказ или задания склада: заказ поступает обычным входящим документом.

Пока штатная волна не умеет атомарно принять удержание предложения, её запуск для такого заказа блокируется. Новые удержания не разрешают собирать товар без подтверждённого заказа. Добивка после начала погрузки также остаётся заблокированной. T08 этим срезом не закрывается.

## Ревью Codex перед применением

Исходный кандидат Claude — коммит9f62fcb8, REVIEW_READY_C0143 и RELEASE K0096; Claude в БД его не применял. Codex исправил:

- Текущие права и доступ к собственнику проверяются до сохранённого ответа SAVE/ADJUST/REJECT/SAP. StockPosting проверяет новые командные права и при cached replay, до исполнения. Версия состояния при точном повторе заново не применяется.
- Видимые предложения фильтруются по собственнику до ограничения200. Захват ACCESS_REV SHARE предшествует блокировке площадки.
- Повтор SAVE ищет результат по хешу исходного HTTP-запроса до повторного расчёта. Изменившийся запас не должен менять исходную команду после потерянного ответа.
- Пригодность свободного товара до заказа проверяется физическим режимом REPLENISH; отбору это разрешения не даёт. Выбранные единицы отдельно проверяются по складу, собственнику, товару, МРЦ, сроку, маркировке и отсутствию финансового удержания. Обычный ALLOCATE по-прежнему требует своё основание заказа.

## Техническое приложение

Владелец — integrations; физические изменения выполняет inventory через StockPosting. SQL: [миграция](../../db/migrations/2026-10-22_trade_topup_proposal/apply.sql), парные rollback/verify и before-исходники лежат рядом. Манифест хранит пять общих объектов до/после. Новые таблицы: предложения, решения, ссылки на настоящие резервы и события SAP. Новые пакеты: READ/API/CMD. Общие изменения: POSTING_API, TRADE_STOCK_GUARD, TRADE_PICK_CONTEXT и ACCESSIBLE BY двух stock-core спецификаций.

Порядок проверки: checkpoint → apply → verify → пустой rollback → reapply → verify → изолированный товарный набор. Откат с решениями/резервами отказывает и не удаляет доказательства. Промышленный SAP, атомарная передача волне, полная конкурентная матрица, оборудование и пилот пока не приняты.
