# NI03.2: альтернативная динамическая ячейка

039 APPLIED в RABAEV. Переиспользованы RRL_PICK_FACE_ASSIGNMENT, RRL_PICK_FACE и маршрут RRL_PICK_ROUTE_CELL. Второй планировщик не создавался.

[AlternativePickFaces](../../api/wms_api_server/app/modules/inventory/infrastructure/alternative_pick_faces.py) заменяет прежний inline PL/SQL блок выбора динамической ячейки. До физического старта, если основная вместимость меньше выбранной потребности, выбирается свободная динамическая ячейка того же склада и действующего маршрута. Ячейка должна вместить всю выбранную потребность и фактическую целую паллету источника. Занятость, блокировки, активные назначения и входящие задания исключают кандидата.

В одной короткой metadata-транзакции под CONFIG X изменяются адрес пополнения, demand, задания отбора и CASE, маршрут и версия состава. Событие FACE_TARGET_REROUTED сохраняет старый/новый адрес. Уже собранный CASE, HARD в старой ячейке или выпущенное физическое задание не перенаправляются изменением metadata.

В существующем назначении сохранены UNIT_VOLUME_M3/BASE_UOM. Норма BASE берётся из прежней конфигурации, а не из количества коробок. Динамический допуск PICK разрешён только владельцу HARD той же волны. В карточке артикула не создаётся постоянная публикация временной ячейки. Пустое назначение снимается только после отсутствия P/H/входящих заданий и окончания потребности либо закрытия волны.

## Повторы

RRL_PICK_WAVE_REPLENISH_TASK.RESERVE_REQUEST_JSON хранит канонический запрос и RESERVE_OPERATION_ID. Неизвестный исход повторяется с тем же телом/ID/исходным исполнителем. Новое решение после подтверждённого APPLIED без источника получает новый ID. Обычная волна и продолжение потребности используют общий wave_commands.reserve_wave_sources.

## Реальный изменённый случай

Основная capacity 2, CASE demand 3 → свободная динамическая capacity 3; маршрут CASE перенесён, одно событие и назначение; durable source intent один; фактический Root arrival 3 → собственный HARD 3 в динамической ячейке → отдельный допуск отбора/replay. Очищены только приватные P/H через ядро. Повторный whole continuation 20+30 также прошёл после объединения механизма intent.

## SQL и ограничения

Выбор ≤50 исходных строк/≤200 кандидатов, source existence прекращает поиск на первой подходящей строке. Последнее освобождение назначений ~77 ms, запись назначения ~8.13 ms в целевом случае. Решение: сохранить короткие окна; освобождение ограничить 200 строками, рост проверять по slow log/плану, без необоснованного нового индекса. Однократный DDL ~763 ms не считается складской операцией.

Общий спринт не закрыт. Разбиение выбранной потребности между несколькими адресами, безопасный перенос владельцев ранее созданного HARD и независимый ТСД/нагрузочный приёмочный прогон остаются открытыми. Случай с большой паллетой, не помещающейся ни в одну ячейку, не разрешается фиктивно.
