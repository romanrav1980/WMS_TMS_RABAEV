# NI03.2: общая физическая подача и несколько ячеек

044–047 APPLIED в RABAEV/orcl. Продолжение [[nicora_ni032_alternative_faces_20261009]], [[nicora_ni033_fullpal_20261009]]. Полный NI03.2 остаётся в работе.

## Существующий планировщик и владельцы

046 исправляет классификацию FULL_PALLET: свободная часть паллеты не считается целой физической паллетой. Native create_plan для заказов 12+8 на физической паллете20 теперь создаёт CASE задания. 045 позволяет единственную целую подачу этой паллеты, сохраняя HARD12+8 разных заданий, только если все владельцы CASE идут в тот же фактический адрес. Другое назначение запрещается до движения. Closure включает anchors всех владельцев.

044/047 продолжают существующие explicit RT по оставшейся потребности конкретного PICK_TASK_ID. Старый замороженный JSON не наследуется дочерней строкой с новым ID. Доставленная целая паллета5 при потребности3 оставляет HARD3 и свободный запас2. Target coverage считается только по допустимому фактическому запасу в адресе отбора, а не старому резерву в хранении.

## Несколько альтернативных ячеек

Планировщик уже создаёт задания по исходным физическим паллетам. AlternativePickFaces использует эти группы, не создаёт второй планировщик и не дробит владельцев одной целой паллеты между адресами. Две разные исходные паллеты могут получить два динамических адреса. Обновляются только соответствующие existing WT/PT/CASE/RT, агрегированная WAVE_DEMAND разделяется по тем же заданиям. P/H и исходный заказ не изменяются.

Окна: 50 RT, 200 владельцев и 200 кандидатов. Выданное физическое задание, начатый отбор или существующий HARD в старом адресе исключают metadata rerouting. На пустом динамическом адресе проверяется вместимость фактической целой исходной паллеты; занятый слот не переиспользуется.

## Реальные адресные случаи

- Native create_plan12+8 → wave launch → одна физическая подача20 → HARD12+8 → явный допуск → CASE12/8, точные повторы. Попытка другого адреса второго владельца отклонена; P/H20/20 сохранены.
- Native create_plan6+6 на двух паллетах10+10 → существующие source groups10+2 → два dynamic face → две целые подачи10+10 → HARD10+2/free8 → допуск. Товар и резерв не удваиваются.
- Явная подача5 для CASE3 → HARD3/free2; continuation20+30 повторён с реальным frozen source intent.

История сохранена, очищены только приватные P/H через ядро. Независимый/browser/промышленный прогон не объявлен проведённым.

## SQL и следующий функционал

Native case выявил MERGE deficit6mu4fhbhaypbz ~39.04ms: общий UNION всего stock/SR. Переписан на текущие wave target/SKU, канонический P−H и общий eligibility с фактическим customer shelf policy. Capacity hold теперь читает capacity до UPDATE: исправлен ORA04091. Решение — ограничить запрос и использовать существующие ключи; не создавать индекс без evidence. Владелец: inventory.

Физически свободный MINIMAX arrival сам по себе не даёт владельцу CASE HARD. Explicit RT больше не отменяется только по чужому/свободному запасу; требуется атомарное перераспределение собственного невыданного HARD из хранения на пригодный целевой запас. Этот следующий ticket открыт, P/H не меняются двумя несогласованными транзакциями. Также открыты общий lifecycle завершения волн, межволновое размещение владельцев и независимая приёмка.
