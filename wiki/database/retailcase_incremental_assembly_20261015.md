## Ответственность и граница

Inventory владеет mass policy, assembly session/step/evidence/use. Integrations OPC клиент получает только серверный контекст и реальные серии GROSS; не определяет артикул/количество. Авторизованный оператор открывает шаг с физическими сканами и конкретным количеством. AUTO требует явного согласия, сохранённого с operation_id до физического изменения; BUTTON фиксирует отдельное намерение «Положил». Dedicated sender всегда отличается от бизнес-оператора.

Новая метадата отдельно фиксирует BEFORE→ARMED→AFTER→READY. Лишь после завершения archive transaction сервер получает из native stored consent текущего оператора и вызывает чистую транзакцию единственного CASE_PICK_CONFIRM. Native assert/claim повторно проверяет текущие права/назначение/склад/документ/версию/политику/consent. Ссылка STEP_USE вставляется и шаг становится APPLIED в той же товарной транзакции. Нет отдельного stock writer, отправитель не передаёт actor, архив сам по себе не подтверждает товарный эффект.

Существующий RRL_CASE_SCALE_ADMISSION делегирует только при явном assembly_step_id, остальные прежние правила сохранены. Активная assembly session блокирует обход через старое подтверждение CASE без step. Compiler CASE добавляет UNIQUE anchor шага и требует реальную EA базу выбранных резервов. Изменение RRL_STOCK_POSTING_API выполняет root отдельно только для порядка текущего revision guard; assembly agent его не меняет.

## Ограничения первого инкремента

Только обычный немаркированный, несерийный штучный SKU с явной EA базой и версионированной настройкой min/max kg на единицу, абсолютным допуском и минимальной различимой delta. Неизвестная масса, weighted/serialized/marked SKU не получают автоматического подтверждения. Отрицательная/нулевая/неразличимая/не соответствующая диапазону delta сохраняется как расхождение и блокирует следующий шаг. Исправление/уменьшение количества не выполняется скрыто.

Session привязана к настоящему EMPTY_TARE существующего малого CASE, назначенному оператору, устройству GROSS, станции и текущей конфигурации. Нормативы/режим станции и максимальная длительность1мин..8ч задаются явно. Initial zero не подделывается новым timestamp. Общая стабильность/точность/ёмкость/порядок sample/свежесть вынесены в один private core RRL_SCALE_PACKET_READ; старый validate_json сохраняет прежнюю проверку zero600сек, новая GROSS series entry использует начальную тару session и непрерывность предыдущего принятого веса.

Метаданные берут CASE→SESSION→STEP locks, ни одного физического ожидания в транзакции. Финал требует отдельный свежий существующий FINAL_GROSS после последнего AFTER, той же тары/состава/устройства/отправителя; независимый QC не обходится. Явный cumulative_tolerance_kg станции сохраняется в session: финал также сверяет final−initial_tare−ΣAPPLIED delta с этим допуском, накопленный дрейф не скрывается. Сначала используется существующий close-pallet (он не меняет content_version), затем физическое финальное взвешивание и session finish.
