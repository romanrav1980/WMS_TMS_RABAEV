# Карантинное перемещение по назначенной роли склада

Живой сотрудник с ролью склада и правом работы с собственником получил403 при перемещении собственной паллеты в карантин. Native MOVE_QUARANTINE проверял только legacy-группу. Сотрудник отключён, назначение и owner-допуск отозваны; собственная тестовая1EA осталась в ячейке хранения. Предыдущие2EA списания не восстанавливались.

Миграция [2026-10-23-quarantine-role-scope](../../db/migrations/2026-10-23_quarantine_role_scope/apply.sql) сохраняет прежние legacy-права и добавляет проверку назначенного права именно по действительному складу из заблокированного плана перемещения. Проверка выполняется до эффекта после STOCK-блокировок. Разрешение на карантин и разрешение на перемещение нужны одновременно; доступ по собственнику и native удержание сохраняются. Обычные INTERNAL_MOVE этим изменением не получают нового способа допуска.

## Техническое приложение

Заменяется только RRL_STOCK_INTERNAL_CMD body. Для MOVE_QUARANTINE допускаются назначенные quarantine_move и internal_move либо stock_posting_manual_move через RRL_ACCESS_API.allowed. Старые RRL_HAS_WRIGHT остаются альтернативой для совместимости. Спецификация, количество и схема назначений не меняются. Свежий before body/SHA, откат и verify сохранены рядом. Состояние: кандидат, не применён.

Возобновляемая проверка: [live_quality_release_scope.py](../../tests/tradecase/live_quality_release_scope.py), состояние runtime/test-evidence/tradecase/2026-10-23/T11/quality-release-scope.json. Использует уже созданную Q23.GOOD.25cadbfc в складе212476763, новую приёмку при повторном запуске не создаёт. После исправления должна проверить выпуск годного товара и штатно списать собственную тестовую единицу отдельным делом. Полный T11 не закрывается подготовкой миграции.
