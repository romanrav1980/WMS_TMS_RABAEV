# Назначение сборки из 250 мест в рейс

Контрольный набор склада 210069361 завершил отбор 660 коробов. Назначение четырёх сборок (200, 150, 250 и 60 мест) остановилось: функция назначения ограничивала одну сборку 200 физическими местами, хотя общий ручной состав рейса уже допускает 1000.

Миграция `2026-10-27-grouped-st-assignment` меняет только эту границу функции на 1000. Сохраняются порядок блокировок рейсов и мест, проверка снимка состава, запреты изменения погруженных и отгруженных мест, защита выставленного счёта и транзакция вызывающего пакета. Лимит выбора 200 номеров сборок не меняется. Миграция не изменяет остатки и задания.

[Комплект с исходником и откатом](../../db/migrations/2026-10-27_grouped_st_assignment/manifest.json) фиксирует фактический исходник функции и двух зависимых пакетов. Применение и откат отказывают при изменении этих исходников. Состояние: APPLIED после checkpoint ae1d2a8c. Применение, откат и повторное применение прошли: 9/9/9 операторов, ошибок 0. Компиляция чистая: INVALID 0, USER_ERRORS 0. Прежний запрос назначил 660 мест в тот же рейс 33698. Повтор вернул 200; состав не изменился, остаток 11000 и резерв 6600 сохранены. Первый запрос после перекомпиляции получил 503 из-за ORA-04068; проверка подтвердила отсутствие частичного назначения, повтор выполнен исходным запросом.

Все 60 мест добивки сейчас входят в одну сборку. Малый набор Claude проверил снятие целой сборки. Штатное выделение 20 мест из существующей сборки ещё нужно проверить; прямое изменение назначений SQL не заменяет эту проверку.

[Доказательства](../../reports/tradecase/2026-10-27/codex/grouped-st-assignment.json): повтор назначения занял 1491 мс HTTP, 1155 мс транзакции; первое успешное назначение — 1785 мс транзакции. Журнал содержит название транзакции, а не отдельный SQL. Сохраняем ограничение 1000 мест; индекс без профиля конкретного запроса не добавляем. Дальнейшее ускорение этого участка требует профиля существующего поштучного writer; исполнитель Codex.
