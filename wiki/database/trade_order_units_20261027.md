# Единицы строки торгового заказа (C-0175) — первый этап

- Правило владельца — `wiki/requirements/nicora_order_units_20261027.md`.
- Первый этап: обработанная единица EA/BOX для TRADECASE ORDER. Весовой SKU с базой KG end-to-end и загрузка NI02 (StoreOrders) не закрыты.
- Контракт:
  - `TradeSku` + `processing_uom` (EA|BOX), `processing_step` (явный шаг в этой единице, не точность реестра), `round_to_processing_unit`;
  - `TradeOrderLine.uom` = EA, BOX, BLOCK, BLK, G, KG (BLOCK и BLK явно сопоставлены коду реестра BLK; исходный код сохраняется).
- Нормализация один раз при приёме документа: `domain/order_units.py` + `infrastructure/order_unit_registry.py` (RRL_STOCK_UOM_CONVERSION, последняя версия, неоднозначность — нет коэффициента), точная рациональная арифметика, всегда вниз до шага.
  - В строке: `quantity`/`uom` = обработанные; `normalization` — исходные количество и единица, база, обработанная база, разница, версии коэффициентов, версия SKU, шаг, флаг, статус и код ошибки.
  - Флаг выключен и единица отличается — строка загружена с `ORDER_UNIT_ROUNDING_NOT_ALLOWED` (даже при точном переводе 24 EA → 2 BOX).
  - Ответ ACCEPTED + `line_results` и `loaded_with_integration_error`.
  - Точный повтор отдаёт сохранённый запрос без повторной нормализации.
- Native NOT_APPLIED `db/migrations/2026-10-27_trade_order_units/`: нулевые и безкоэффициентные строки хранятся неисполнимыми, TRIP их не назначает, привязка пропускает.
- Доказательства: `tests/tradecase/live_order_units.py` (ASGI-приложение текущего кода + настоящий Oracle, свой склад), `runtime/test-evidence/tradecase/2026-10-27/C0175/order-units.json`, `tests/tradecase/test_order_units.py`.


## Независимое ревью Codex перед применением

В освобождённом Python-коде исправлены смешанный заказ (строки с настройкой и без неё) и ответ при гонке одинаковых сообщений: квитанция берётся из фактически сохранённого REQUEST_JSON, а не пересчёта проигравшей попытки. Текст рационального числа теперь выводится без округления контекстом Decimal; периодическая дробь сохраняет исходную строку неисполнимой с диагностикой. Настройка EA/BOX не допускает дробный шаг; это ограничение нынешнего дискретного исполнения, а не запрет дробного KG в будущем.

13 адресных тестов прошли с PYTHONPATH=api/wms_api_server. Комплект двух тел пакетов проверен по всем SHA и сравнению с исходником. Frozen root manifest: coordination/tradecase-20261019/reviews/C0175-root-manifest.json, SHA 3a9a5c84e7ac083918b5905830917c30029c41909610a737b20f27f12ee00178. Применение ещё не выполнено; сначала контрольный коммит, затем применение/пустой откат/повтор и after-kit на своём наборе.

Остаются открытыми base KG end-to-end, NI02 и разрешение новой единицы после позднего появления SKU. Принятый неисполнимый документ сам не получает количество после изменения настройки; нужен отдельный проверенный механизм, его здесь не объявляем готовым.


## Применение и проверка в Oracle

После checkpoint 91908992 комплект применён, откачен до появления новых неисполнимых документов и применён повторно: 6/8/6 операторов, ошибок 0. USER_ERRORS и INVALID — 0, ledger APPLIED. Замороженные файлы комплекта сохраняют исходный NOT_APPLIED как состояние передачи; текущий статус определяется этой проверкой.

After-kit на собственном складе 223057509 прошёл через ASGI и настоящий Oracle: нулевые/безкоэффициентные строки сохранены, их назначение в рейс запрещено, обработанные 2/4/3 BOX привязаны без второго пересчёта. Независимый смешанный заказ содержит нормализованную и прежнюю строку; ответ и повтор прошли. Две одновременные доставки дали одинаковый бизнес-результат и одну запись сообщения. Старое диагностическое поле replayed сохраняет прежнюю совместимость и может отличаться.

Остаток тестового склада 0/H0; исходный набор 210069361 сохранил 11000/H6600. Смешанная загрузка заняла 403 мс ASGI, n=1; записей медленного SQL привязки в этом наборе нет. Индекс без обнаруженного долгого запроса не добавляем. Это не измерение served-8088 или нагрузки; Python общего сервера обновится при следующем безопасном перезапуске root.

[Независимые доказательства](../../reports/tradecase/2026-10-27/codex/order-units-acceptance.json). База KG, NI02 и разрешение строки после позднего появления SKU остаются открытыми.


## Ограничение повторных чтений

На том же собственном складе 223057509 нормализация 200 строк одного SKU выполняла 401 SQL-запрос. Четыре READ ONLY прогона дали 1830/2091/1887/1594 мс; медиана последних трёх — 1887 мс. После объединения единиц и чтения настроек один раз на SKU в пределах этого заказа — 3 SQL и 49/34/34/36 мс, тёплая медиана 34 мс. Полный нормализованный результат равен исходному. Между заказами кэш не сохраняется; схема и индексы не менялись.

Это прямой Oracle-профиль нормализации, не замер HTTP, всей загрузки или промышленной пропускной способности. Дополнительная настоящая ASGI-проверка смешивает EA/BOX/BLK одного SKU и строку без новой настройки: количества 2 BOX / 24 EA / 4 BOX, повтор и пара одновременных доставок прошли, одна запись сообщения, исходный запас не изменился. Состояние WAITING теперь не помечается как загруженное с ошибкой; 15 адресных тестов прошли. Разрешение нового SKU после ожидания остаётся открытым.
