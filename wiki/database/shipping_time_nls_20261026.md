# Расчёт времени отгрузки и формат дат Oracle — 26.10.2026

Назначение СТ вызывает RRL_TT_REORDER_ADR, затем RRL_TT_PLAN_SHIPPPING_HOUR. Этот унаследованный путь заново рассчитывает SHIPMENT_TIME по STDATE и RRL_ADDR.SHIPPING_TIME. В закрытом тестовом рейсе33681 у33СТ дата27.10, а время адреса не задано; действующий расчёт дал28.10 00:00. Это объясняет наблюдение, не требует менять историю рейса и не подтверждает настройку настоящего адреса СНС/BLC.

Отдельно воспроизведён дефект FTIME_SHIPPING_PLAN. При NLS_DATE_FORMAT=DD.MM.YYYY вход26.10/10:15 даёт27.10 10:15; при YYYY-MM-DD тот же вход молча возвращает26.10 00:00 через обработчик ошибки. Значение зависит от настройки сеанса. Доказательство runtime/test-evidence/tradecase/2026-10-26/T09/shipping-time-nls-before.json.

Комплект2026-10-26_shipping_time_nls задаёт явный формат DD.MM.YYYY в преобразовании даты туда и обратно. Два изменения строки не меняют сигнатуру, права, выбор календарного дня и fallback для пустого/неверного времени. Действующий код использует порог часа20; старый комментарий упоминает12 и противоречит коду. Порог не меняется и не объявляется новым правилом TRADECASE. Перерыв водителя120/15 этим изменением не затрагивается.

Свежие SHA защищают функцию и вызывающие функции/пакеты. После замены перекомпилируются только известные вызывающие объекты, если Oracle пометил их невалидными; их исходники не изменяются. Парный откат восстанавливает точный прежний источник. До применения статус NOT_APPLIED. Проверка должна пройти четыре формата сеанса и28контрольных сочетаний, пустой откат/повтор, INVALID0. Функции расчёта рейса, выполняющие UPDATE, в SELECT не вызывались; проверялась только заранее прочитанная чистая функция преобразования.
