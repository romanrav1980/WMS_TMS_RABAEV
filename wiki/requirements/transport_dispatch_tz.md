## 1. Назначение

Модуль `Транспортный Диспетчер` обеспечивает полный цикл формирования и отгрузки рейсов:

- Просмотр сборочных заданий (СТ), готовых к погрузке, с агрегацией по складу, региону и адресу.
- Быстрый визуальный подбор СТ под конкретный рейс: выбор чекбоксами, Shift-выделение диапазона.
- Контроль суммарного веса и объёма выделенных СТ относительно вместимости машины.
- Формирование рейсов: создание, назначение ТС / водителя / дока / времени отгрузки.
- Контроль минимальной загрузки машины перед закрытием рейса.
- Мониторинг прогресса сборки паллет внутри рейса.

Модуль является частью цепочки: **Wave Picking → Стейджинг → Транспортный Диспетчер → Отгрузка**.

Легаси-реализация существует в C# WinForms (`tabPage6`, `TRANSPORT.cs`). Новый модуль реализуется на FastAPI + React без изменения C# кода и без прямых INSERT/UPDATE — только через Oracle-пакеты.

## 2. Ключевые Термины

| Термин | Значение |
|--------|----------|
| `СТ` | Сборочное задание. Единица назначения в рейс. Одно СТ = один клиент + один адрес + список паллет. |
| `Заявка` | Синоним СТ в интерфейсе диспетчера: заказ клиента, пересчитанный в паллеты. |
| `Рейс` | Транспортная задача (`RRL_TRANSPORT_TASK`). Один рейс = одна машина + один водитель + список СТ. |
| `ТС` | Транспортное средство (`RRL_TR_VEHICLE`). |
| `ORD` | Порядковый номер адреса в рейсе. Определяет последовательность объезда. |
| `LOAD_TYPE` | Способ погрузки: `Г` = государственный борт, `П` = прицеп, пусто = стандарт. |
| `ZONE_TIME_PLAN` | Временно́е окно доставки: IN = начало, OUT = конец. |
| `TT_READY_PERC` | Процент паллет рейса, прошедших проверку/сборку (0..1). |
| `VERIFY_PERC` | Процент выполнения сборки конкретного СТ. |
| `Требования адреса` | Ограничения по ТС: тип (реф / тент), максимальная грузоподъёмность, наличие гидроборта. |

## 3. Эталонный Интерфейс (C# WinForms)

Раздел фиксирует поведение легаси-приложения как обязательный эталон UX для React-реализации.

### 3.1 Структура экрана

Экран состоит из трёх вкладок:

| Вкладка | Содержание |
|---------|-----------|
| **Заявки** | Таблица доступных СТ с фильтрами и кнопками формирования рейса. Основная рабочая вкладка диспетчера. |
| **Маршруты** | Список созданных рейсов. Выбор рейса открывает его состав. |
| **Паллеты заявки** | Детализация паллет по выбранному СТ. |

### 3.2 Вкладка «Заявки» — строка итогов

В верхней части вкладки **всегда видна строка итогов по выделенным СТ**:

```
СТ:  Палл = 20;  Вес = 2748;  Объём = 10,6;  РЕГИОН P=2  M=885  V=3
```

Обновляется мгновенно при изменении выделения. Диспетчер ориентируется по ней при подборе нагрузки под вместимость машины.

### 3.3 Вкладка «Заявки» — таблица СТ

Каждая строка = одно СТ. Столбцы:

| # | Колонка | Источник | Описание |
|---|---------|---------|----------|
| 1 | `☐` | — | Чекбокс выделения. Влияет на строку итогов и кнопки действий. |
| 2 | Склад | `RRL_SKLADNAME_BY_ID(WARE_ID)` | Номер / имя склада. Цветовая подсветка по складу. |
| 3 | Палл | `COUNT(PALLET_UID)` | Количество паллет в СТ. |
| 4 | Вес | `SUM(ORDER_WEIGHT)`, кг | Суммарный вес брутто. |
| 5 | Объём | `SUM(TARESIZE*PACK_COUNT)/1e6`, м³ | Суммарный объём. |
| 6 | РЕГИОН | `RRL_ADDR.REGION` | Регион доставки. |
| 7 | Адрес | `P.ADDR` | Адрес доставки. |
| 8 | СТ | `P.ST_NUMBER` | Номер сборочного задания. |
| 9 | ТранспортноеЗадание | `RRL_GET_TT_INFO(TRANSTASK_ID)` | Номер рейса или «пусто» если не назначен. |
| 10 | РАЙОН | `RRL_ADDR.RAION` | Район адреса. |
| 11 | ТС-макс | `RRL_ADDR.TRANSPORT_TYPE` | Тип/грузоподъёмность ТС, допустимого на адрес. |
| 12 | Гидроборт | из `RRL_TRANSPORT_TYPE` | Флаг требования гидроборта. |
| 13 | СТОЛ | `RRL_ADDR.STOL` | Флаг требования стол-лифта. |
| 14 | Примечание | `RRL_ADDR.PRIM1` | Свободный комментарий к адресу. |
| 15 | ДатаЗагрузки | `MIN(P.CREATE_DATE)` | Дата загрузки первой паллеты СТ. |
| 16 | Полнопалетная отборка | `SUM(RRL_SUGAR_HAS(ARTICUL))`, legacy API field `SUGAR` | Исторический legacy-термин в коде эквивалентен полнопалетной отборке; в пользовательских текстах писать только `Полнопалетная отборка`. |

### 3.4 Цветовая индикация строк

| Условие | Цвет строки | Смысл |
|---------|------------|-------|
| Склад = 5 | Красно-розовый | Склад 5 (горячий/критичный) |
| Склад = 6 | Белый/нейтральный | Склад 6 |
| Склад = 7 | Зелёный | Склад 7 (приоритетный) |
| Чекбокс отмечен | Синий | СТ выделено для включения в рейс |
| Вес = 0 и Паллет ≤ 1 | Оранжевый/красный | СТ без физической нагрузки — скорее всего ошибочное или пустое |

Цветовая схема по складам настраивается через `RRL_WARES` (поле или внешний конфиг). В React — массив цветов по WARE_ID.

### 3.5 Механика выделения СТ

Диспетчер работает с таблицей следующими способами:

| Действие | Результат |
|---------|---------|
| Клик по чекбоксу одной строки | Выделить / снять выделение одного СТ |
| Shift+Click по строке | Выделить диапазон от последней отмеченной до текущей строки |
| Клик по ячейке РАЙОН | Выделить все СТ с тем же значением РАЙОН |
| Клик по ячейке РЕГИОН | Выделить все СТ с тем же РЕГИОН |
| Shift+Click по РАЙОН/РЕГИОН | Расширить выделение до второго района/региона включительно |

Это **критически важный** UX-элемент: диспетчер выбирает «Лысьва + Чусовой» двумя кликами и сразу видит суммарную нагрузку. Скорость — главное требование.

### 3.6 Панель фильтров (правая колонка)

| Фильтр | Тип | Поведение |
|--------|-----|-----------|
| Маска складов | ComboBox | Фильтр по `RRL_SKLADNAME_BY_ID(WARE_ID)`, несколько через запятую |
| Дата СТ | Дата + чекбокс | Равенство `P.STDATE = :date` |
| ДатаДо | Дата + чекбокс | `P.STDATE <= :date` (диапазон в сочетании с «Дата СТ») |
| НЕ РАСПРЕДЕЛЁННЫЕ | Чекбокс | `TRANSTASK_ID IS NULL` — скрыть уже назначенные в рейс |
| АДР | Текст | `P.ADDR LIKE '%:mask%' OR REGION LIKE '%:mask%'` |
| СТ | Текст | `P.ST_NUMBER LIKE '%:mask%'` |
| Не эти СТ | Чекбокс рядом с «СТ» | Инвертировать фильтр по номеру СТ: `NOT LIKE` |
| ИСКАТЬ СТ ПО ЧАСТИ | Чекбокс | Применять маску `%mask%` вместо точного совпадения |
| Фильтр ТС | ComboBox | Фильтр по требуемому типу ТС (`RRL_ADDR.TRANSPORT_TYPE`) |
| Фильтр по собранным | Чекбокс | `VERIFY_PERC > 0` |
| Фильтр по НЕ собр | Чекбокс | `VERIFY_PERC = 0` |
| Артикул | Текст | Фильтр по строкам `RRL_SBORKA_PALLET_ROWS.ARTICUL` |
| V< | Число | `ОБЪЁМ < :val` (HAVING) |
| M< | Число | `ВЕС < :val` (HAVING) |

**Поведение «НЕ РАСПРЕДЕЛЁННЫЕ»:**
- Включён (по умолчанию) → список показывает только СТ без рейса. После успешного создания рейса и добавления СТ — строки исчезают из таблицы автоматически.
- Выключен → показываются все СТ, включая уже назначенные, с заполненной колонкой «ТранспортноеЗадание».

## 5. Требования к новым фичам (бэклог)

### 5.1 Строка итогов по выделенным СТ

Вычисляется на фронтенде по данным уже загруженной таблицы (без доп. запроса к API).

Формат: `Палл = N; Вес = N кг; Объём = N м³`

При каждом изменении выделения — пересчёт мгновенный.

### 5.2 Цветовая подсветка строк

В React: `rowClassName` или `style` по WARE_ID. Цвета — массив из 8 позиций (по `RRL_WARES.ID`). Жёстко прописанные дефолты, позволяющие переопределить через конфиг.

### 5.3 Shift-выделение строк и клик по региону/району

- Shift+Click по обычной строке → выделить диапазон.
- Клик по значению РАЙОН или РЕГИОН в любой строке → выделить все строки с тем же значением (toggle: повторный клик снимает).
- Shift+Click по РАЙОН/РЕГИОН → расширить текущее выделение.

Реализуется через `onRowClick` с отслеживанием `lastSelectedIndex` и `event.shiftKey`.

### 5.4 Фильтры (расширение `GET /api/admin/transport/available-sts`)

Добавить query-параметры:

| Параметр | Тип | Oracle-условие |
|----------|-----|----------------|
| `addr_mask` | str | `(P.ADDR LIKE '%:v%' OR A.REGION LIKE '%:v%')` |
| `st_mask` | str | `UPPER(P.ST_NUMBER) LIKE UPPER('%:v%')` |
| `st_mask_exclude` | bool | Инвертировать `st_mask` → `NOT LIKE` |
| `ware_ids` | list[int] | `P.WARE_ID IN (:ids)` |

## 10. АРМ Диспетчера: Транспорт как Ресурс

### 10.1 Концепция

Управление собственным транспортом как ресурсом с отображением занятости автомобилей в диаграмме Ганта, планированием повторного использования транспорта в течение дня, контролем нормативов операций, режимов труда и отдыха водителей, а также последующим план-фактным анализом рейсов.

**Цель** — дать диспетчеру возможность видеть каждый автомобиль как ограниченный ресурс во времени, управлять его доступностью, планировать отгрузки и повторные рейсы с учётом складских операций, маршрута, возвратов, отдыха водителя и повторной постановки автомобиля на ворота.

### 10.1.1 Функциональные требования

| Область | Требование |
|---------|-----------|
| Транспорт как ресурс | Каждый автомобиль отображается как отдельная строка ресурса в диаграмме Ганта. |
| Планирование рейсов | Система показывает доступные машины на основании планового времени отгрузки заказа. |
| Диаграмма Ганта | Для каждой машины отображается полная временна́я цепочка операций: склад, рейс, магазин, возвраты, очистка, отдых, повторная постановка на ворота. |
| Нормативы операций | Система учитывает нормативное время погрузки, доставки, возврата, очистки от возвратов, сдачи возвратов и повторной постановки на ворота. |
| Режим труда и отдыха | Система учитывает обязательные перерывы водителя: 15 мин каждые 2 ч, суточный лимит вождения по требованиям законодательства. |
| Повторное использование ТС | Система позволяет планировать несколько рейсов одной машины в течение дня. |
| Plan-fact | Система сравнивает плановые и фактические времена по каждой операции и показывает отклонения. |
| Смена водителя | При необходимости система отображает смену водителя как отдельное событие на временной шкале. |

### 10.2 Дискретные операции рейса

Каждый рейс разбивается на следующие операции. Операции образуют непрерывную цепочку от постановки машины на ворота до освобождения дока после сдачи возвратов. Каждая операция принадлежит цветовой группе, которая отображается в диаграмме Ганта.

| # | Отображаемое название | Код | Цветовая группа | Источник нормы |
|---|----------------------|-----|-----------------|----------------|
| 1 | Постановка на ворота | `DOCK_ASSIGN` | 🔵 Складские операции | Норматив, константа (мин.) |
| 2 | Ожидание погрузки | `WAIT_LOAD` | 🔵 Складские операции | Буфер между готовностью дока и приходом машины |
| 3 | Погрузка | `LOADING` | 🔵 Складские операции | `NORM_LOAD_PER_PALLET × кол-во_паллет` |
| 4 | Закрытие ворот | `CLOSE_GATE` | 🔵 Складские операции | Норматив, константа (мин.) |
| 5 | Документы | `DOCUMENTS` | 🔵 Складские операции | Норматив, константа (мин.) |
| 6 | Уход в рейс | `DEPART` | 🔵 Складские операции | Нулевая длительность, маркерное событие |
| 7 | Переезд | `DRIVE` | 🟢 Переезд | `NORM_DRIVE_MIN` или плановое значение из рейса |
| 8 | Выгрузка | `UNLOAD` | 🟡 Доставка / Выгрузка | `NORM_UNLOAD_PER_PALLET × кол-во_паллет` |
| 9 | Загрузка возвратов | `LOAD_RETURNS` | 🟣 Возвраты | Норматив или 0 если возвратов нет |
| 10 | Возврат на склад | `DRIVE_BACK` | 🟣 Возвраты | Аналог `DRIVE` |
| 11 | Сдача возвратов | `RETURN_HANDOVER` | 🟣 Возвраты | Норматив, константа (мин.) |
| 12 | Очистка от возвратов | `CLEAN_RETURNS` | 🟣 Возвраты | Норматив, константа (мин.); выполняется после сдачи возвратов перед повторной постановкой на ворота |
| — | Отдых / Перерыв | `REST` | ⬜ Отдых / Перерывы | Авто: 15 мин после каждых 2 ч вождения (§10.3) |
| — | Смена водителя | `DRIVER_CHANGE` | 🩷 Смена водителя | Явный блок, вставляется диспетчером вручную |

Если рейс охватывает несколько точек доставки (несколько СТ), операции `DRIVE → UNLOAD → LOAD_RETURNS` повторяются для каждой точки согласно порядку `ORD`.

Завершение цикла: `RETURN_HANDOVER` → `CLEAN_RETURNS` → `DOCK_ASSIGN` следующего рейса. Машина не может быть поставлена на следующую погрузку раньше, чем завершена очистка от возвратов.

**Смена водителя** вставляется явным блоком `DRIVER_CHANGE` между любыми двумя операциями — если сменный водитель назначается на продолжение рейса.

### 10.3 Нормативы отдыха водителя

Требования законодательства РФ (Приказ Минтранса № 424):

| Правило | Параметр |
|---------|---------|
| Непрерывное управление ≤ 2 ч | После каждых 2 ч вождения обязательный перерыв |
| Перерыв | ≥ 15 мин. (откладывается поверх Ганта как блок `REST`) |
| Суточная норма вождения | ≤ 9 ч (расширенная — ≤ 10 ч, не более 2 раз в неделю) |

На диаграмме Ганта блоки `REST` отображаются автоматически поверх операций `DRIVE_TO_CLIENT` / `DRIVE_BACK`, если суммарное время в пути превышает 2 ч. Цвет — серый, не кликабельный.

### 10.7 Умный подбор машины при создании рейса

При открытии диалога «Создать маршрут» (Sprint 2) система предлагает машины, **доступные к плановому времени отгрузки заказа**. Для каждой машины выполняются следующие проверки:

| Проверка | Описание |
|---------|---------|
| Текущая занятость | Машина не должна пересекаться с другим рейсом или складской операцией в запрашиваемый интервал. |
| Время возврата на базу | Машина должна успеть вернуться (`DRIVE_BACK`) до начала следующей постановки на ворота. |
| Время сдачи возвратов | `RETURN_HANDOVER` + `CLEAN_RETURNS` должны завершиться до планового времени отгрузки. |
| Очистка и подготовка | `CLEAN_RETURNS` должна быть завершена — машина готова к `DOCK_ASSIGN`. |
| Режим отдыха водителя | Нельзя предлагать машину, если водитель нарушит норматив отдыха в результате назначения. |
| Смена водителя | Если продолжение смены невозможно, система учитывает необходимость замены водителя как блок `DRIVER_CHANGE`. |

**Отображение в диалоге:**

- Колонка **«Свободна с»** — ближайшее время готовности машины.
- Цветовая индикация: 🟢 свободна к нужному времени / 🟡 освободится с опозданием < 1 ч / 🔴 конфликт или нарушение режима.
- Сортировка: сначала зелёные, затем жёлтые.
- При выборе красной машины — предупреждение с деталями нарушения.

Источник: `GET /api/admin/transport/vehicles/available?shipment_time=&pallets=`.

### 10.8 План-фактный анализ

После выполнения рейса система фиксирует фактические времена операций и сравнивает с плановыми. Сравнение ведётся по каждой операции отдельно:

| Операция | Что сравнивается |
|---------|-----------------|
| Постановка на ворота | Плановое и фактическое время прибытия на ворота (ДОК) |
| Ожидание погрузки | Плановое и фактическое время ожидания |
| Погрузка | Нормативное и фактическое время погрузки |
| Уход в рейс | Плановое и фактическое время выезда |
| Переезд к магазину | Плановое и фактическое время прибытия к точке доставки |
| Выгрузка | Нормативное и фактическое время выгрузки |
| Возврат на склад | Плановое и фактическое время прибытия на склад |

## 11. Транспортный Оптимизатор: Карта и Авто-планирование Рейсов

### 11.1 Назначение и цель

Текущий процесс: диспетчер вручную группирует СТ по районам, подбирает машину и создаёт рейс. Время — 15–45 мин на день. Утилизация парка — неоптимальная: машины уходят с неполной загрузкой, часть маршрутов нерациональна географически.

**Цель этапа** — сократить время работы диспетчера на 70–80%, увеличить среднее число паллет на рейс и снизить пустой пробег за счёт:
1. **Карты заказов** — диспетчер видит все СТ на OpenStreetMap с цветовой индикацией по складу, срочности, типу ТС.
2. **Визуального подбора** — очертить полигон на карте → система предлагает рейс.
3. **Алгоритмического оптимизатора** — OR-Tools CVRPTW автоматически формирует оптимальный набор рейсов на день.
4. **Шаблонного подбора** — быстрый вариант на основе истории закрытых рейсов.

### 11.2 Постановка задачи оптимизации

Формально задача — **CVRPTW** (Capacitated Vehicle Routing Problem with Time Windows):

> Дано: N адресов с координатами, весом/объёмом, временны́м окном доставки и ограничением по типу ТС. Дан парк из K машин с разной грузоподъёмностью и доступностью. Найти распределение адресов по машинам и порядок объезда, минимизирующий общий пробег при соблюдении всех ограничений.

Для системы: N ≤ 300 адресов, K ≤ 30 машин. Задача такого масштаба решается OR-Tools за 5–30 секунд.

### 11.3 Подходы к оптимизации: сравнение

| # | Подход | Скорость | Качество | Усилия диспетчера | Когда использовать |
|---|--------|---------|---------|-------------------|--------------------|
| A | **Визуальный полигон** на карте | Мгновенно | Среднее | Высокие | Нестандартные ситуации, ручная коррекция |
| B | **Географические кластеры** (по RAION/REGION) | 1–2 сек | Среднее | Низкие | Ежедневный базовый маршрут |
| C | **OR-Tools CVRPTW** (полный оптимизатор) | 5–30 сек | Высокое | Минимальные | Стандартный ежедневный запуск |
| D | **Шаблонный подбор** (Jaccard из истории) | < 1 сек | Среднее | Минимальные | Спрос аналогичен прошлым периодам |
| E | **Кластер + локальный VRP** (гибрид) | 3–10 сек | Высокое | Низкие | **Рекомендуется как основной режим** |
| F | **Интерактивный what-if** | Мгновенно | Зависит от диспетчера | Средние | Тонкая ручная настройка |

#### Нереализуемые / нецелесообразные подходы

| Подход | Почему не рекомендуется |
|--------|------------------------|
| Чистые нейросети (Pointer Network, Attention Route) | Требуют 6+ месяцев истории рейсов для обучения; хуже OR-Tools на < 500 точек |
| Pre-computed TSP словарь всех маршрутов | 300 клиентов = 300! вариантов; комбинаторный взрыв, не реализуемо |
| Генетические алгоритмы | Медленнее OR-Tools без преимущества качества для данного масштаба |

### 11.4 Рекомендуемая архитектура: Гибридный оптимизатор

**Уровень 1 — Кластеризация** (предобработка):
- Кластеры формируются по полю `RRL_ADDR.RAION` / `REGION` — уже есть в БД.
- Опционально: географические кластеры через DBSCAN по (LATITUDE, LONGITUDE) — для адресов вдоль одной трассы.
- Диспетчер видит кластеры на карте, может объединять / разбивать.

**Уровень 2 — OR-Tools CVRPTW** (основной движок, внутри каждого кластера или глобально):
- Входные данные: координаты, вес, объём, тип ТС, временно́е окно доставки, время разгрузки.
- Матрица расстояний: OSRM (реальные дороги) или Haversine (быстрая заглушка).
- Результат: набор рейсов с порядком объезда, временны́ми интервалами, назначенной машиной.

**Уровень 3 — Шаблонный matching** (быстрый старт):
- Из истории последних 90 дней выбираем закрытые рейсы с Jaccard similarity ≥ 0.7 по набору клиентов.
- Предлагаем шаблон как стартовую точку → диспетчер принимает/корректирует.

**Последовательность работы:**
```
1. Нажать «Авто-план»
2. Система: кластеризует СТ → запускает OR-Tools CVRPTW → возвращает план
3. Диспетчер видит план на карте + метрики качества
4. Корректирует вручную (перетаскивает точки между маршрутами)
5. Нажимает «Применить» → создаются рейсы в системе
```

### 11.5 Входные данные и ограничения

#### 11.5.1 Новые поля в `RRL_ADDR`

| Поле | Тип | Назначение |
|------|-----|-----------|
| `LATITUDE` | `NUMBER(10,7)` | Широта (градусы) |
| `LONGITUDE` | `NUMBER(10,7)` | Долгота (градусы) |
| `MAX_VEHICLE_TONS` | `NUMBER(4)` | Максимальная грузоподъёмность принимаемой машины (10 / 15 / 20 т) |
| `UNLOAD_NORM_MIN` | `NUMBER(5)` | Нормативное время разгрузки у клиента, мин. (по умолчанию из `RRL_TRANSPORT_NORMS.UNLOAD`) |
| `TW_STRICT` | `NUMBER(1)` | 1 = жёсткое временно́е окно (нельзя приехать вне окна), 0 = мягкое (штраф) |

`ZONE_TIME_PLAN_IN` / `ZONE_TIME_PLAN_OUT` из `RRL_SBORKA_PALLETS` — уже существуют, используются как временно́е окно доставки.

#### 11.5.2 Матрица ограничений

| Ограничение | Источник | Проверка в OR-Tools |
|-------------|---------|---------------------|
| Грузоподъёмность машины | `RRL_TR_VEHICLE.MAX_WEIGHT_KG` | Сумма весов СТ ≤ max_weight |
| Вместимость по паллетам | `RRL_TR_VEHICLE.MAX_PALLET_LOAD` | Количество паллет ≤ max_pallets |
| Тип ТС клиента | `RRL_ADDR.MAX_VEHICLE_TONS` | `vehicle.tons ≤ addr.max_tons` |
| Временно́е окно | `ZONE_TIME_PLAN_IN/OUT` | Arrival ∈ [tw_in, tw_out]; штраф если `TW_STRICT=0` |
| Время разгрузки | `RRL_ADDR.UNLOAD_NORM_MIN` | Добавляется к arrival time в матрице |
| Доступность машины | Ганта из §10 | Машина не занята другим рейсом в это время |
| Режим водителя | §10.3 | Суммарное время вождения ≤ 9 ч |

#### 11.5.3 Целевая функция оптимизатора

OR-Tools минимизирует взвешенную сумму:
```
min: α × total_distance_km
   + β × total_vehicles_used
   + γ × Σ time_window_violations_min   (только мягкие окна)
   + δ × Σ max(0, capacity_overload)    (штраф за перегруз, не должен возникать)
```
Веса (α, β, γ, δ) — настраиваемые параметры в интерфейсе «Настройки оптимизации».

### 11.6 Матрица расстояний — архитектурный принцип

**Матрица строится один раз и кэшируется в Oracle. OR-Tools при каждом запуске читает готовую матрицу из БД — без обращений к внешним сервисам.**

|---------|---------|
| **Утилизация парка** | `Σ фактические_паллеты / Σ max_паллеты × 100%` по всем рейсам плана |

| **Машин без рейса** | Автомобили парка, не задействованные в плане |
| **Оценка качества** | `Score = утилизация × 0.5 + (1 - нарушения/N) × 0.3 + (1 - пробег/baseline) × 0.2` |

### 11.9 Шаблонный matching (исторический решатель)

При выборе `solver=template`:
1. Из таблицы `RRL_TRANSPORT_TASK` (закрытые рейсы за последние 90 дней) извлекаются наборы `{addr_id}` для каждого закрытого рейса.
2. Для текущего набора СТ вычисляется Jaccard similarity с каждым историческим рейсом: `|A ∩ B| / |A ∪ B|`.
3. Лучшие совпадения (similarity ≥ 0.7) предлагаются диспетчеру как готовые шаблоны.
4. Если история < 30 рейсов — ответ `{ "available": false, "reason": "insufficient_history" }`.

Шаблон показывается на карте как предлагаемый маршрут — диспетчер принимает или запускает полный VRP.

#### 11.12.1 Хранение координат в Oracle

**Выбор: `NUMBER(10,7)` без Oracle Spatial.**

Oracle предоставляет два варианта:

| Вариант | Когда подходит | Почему не для нас |
|---------|---------------|------------------|
| `SDO_GEOMETRY` (Oracle Spatial) | Сотни тысяч точек, пространственные JOIN-ы внутри Oracle | Лицензируется отдельно; R-tree индекс избыточен для 300 адресов |

#### 11.12.3 Расчёт расстояний по дорогам

Расстояние «по прямой» (Haversine) систематически занижает реальный пробег на 15–30%. Для корректной работы VRP-оптимизатора необходимы **дорожные расстояния** — с учётом реальной дорожной сети, ограничений скорости, разворотов и улиц с односторонним движением.

**Ключевой архитектурный принцип:** матрица строится один раз, кэшируется в `RRL_ADDR_DISTANCE_MATRIX`, OR-Tools никогда не обращается к внешним сервисам в реальном времени. При 300 адресах пересчёт занимает ~200 мс (OSRM/Valhalla).

---

##### Абстракция провайдера маршрутизации

Все три источника реализуют единый интерфейс `RoutingProvider`. OR-Tools и VRP-сервис работают только через него — источник меняется одной переменной окружения без изменения кода оптимизатора.

```python
# services/routing.py
from abc import ABC, abstractmethod
import numpy as np, requests

class RoutingProvider(ABC):
    """Единый интерфейс для всех источников дорожных расстояний."""

    @abstractmethod
    def matrix(self, lats: list[float], lons: list[float]) -> tuple[np.ndarray, np.ndarray]:
        """Возвращает (distance_m: N×N int, duration_s: N×N int)."""
        ...

    @property
    @abstractmethod
    def source_name(self) -> str:
        """Строка для поля SOURCE в RRL_ADDR_DISTANCE_MATRIX."""
        ...

    def is_available(self) -> bool:
        return True   # Haversine всегда доступен; OSRM/Valhalla переопределяют


def get_routing_provider() -> RoutingProvider:
    """Выбор провайдера по ROUTING_SOURCE; автоматический fallback по цепочке."""
    src = settings.ROUTING_SOURCE   # "haversine" | "osrm" | "valhalla"
    candidates = {
        "osrm":     lambda: OsrmProvider(settings.OSRM_HOST),
        "valhalla": lambda: ValhallaProvider(settings.VALHALLA_HOST),
    }
    if src in candidates:
        p = candidates[src]()
        if p.is_available():
            return p
        # основной недоступен — пробуем резерв
    return _fallback_chain()

def _fallback_chain() -> RoutingProvider:
    """OSRM → Valhalla → Haversine: берётся первый доступный."""
    for factory in [
        lambda: OsrmProvider(settings.OSRM_HOST),
        lambda: ValhallaProvider(settings.VALHALLA_HOST),
    ]:
        p = factory()
        if p.is_available():
            return p
    return HaversineProvider()
```

##### Провайдер A — Haversine × 1.3 (MVP / offline-fallback)

Без внешних зависимостей. Коэффициент 1.3 — эмпирическая поправка: дорожное расстояние ≈ 1.2–1.4× прямой линии.

```python
class HaversineProvider(RoutingProvider):
    ROAD_FACTOR = 1.3
    AVG_SPEED_KMH = 50

    def matrix(self, lats, lons):
        R = 6371.0
        lat = np.radians(np.array(lats))
        lon = np.radians(np.array(lons))
        dlat = lat[:, None] - lat[None, :]
        dlon = lon[:, None] - lon[None, :]
        a = (np.sin(dlat/2)**2
             + np.cos(lat[:,None]) * np.cos(lat[None,:]) * np.sin(dlon/2)**2)
        dist_km = R * 2 * np.arctan2(np.sqrt(a), np.sqrt(1 - a)) * self.ROAD_FACTOR
        dist_m  = (dist_km * 1000).astype(int)
        dur_s   = (dist_km / self.AVG_SPEED_KMH * 3600).astype(int)
        return dist_m, dur_s

    @property
    def source_name(self): return "HAVERSINE"
```

**Погрешность:** 15–25%. Допустимо для MVP. **Недопустимо** для точного соблюдения временных окон клиентов.

class OsrmProvider(RoutingProvider):
    def __init__(self, host: str = "http://osrm:5000"):
        self.host = host

    def is_available(self) -> bool:
        try:
            return requests.get(f"{self.host}/health", timeout=2).ok
        except Exception:
            return False

    def matrix(self, lats, lons):
        coords = ";".join(f"{lon},{lat}" for lat, lon in zip(lats, lons))
        r = requests.get(
            f"{self.host}/table/v1/driving/{coords}",
            params={"annotations": "duration,distance"},
            timeout=30,
        )
        r.raise_for_status()
        data = r.json()
        return (np.array(data["distances"], dtype=int),   # метры N×N
                np.array(data["durations"],  dtype=int))  # секунды N×N

    @property
    def source_name(self): return "OSRM"

**Python-клиент:**

```python
class ValhallaProvider(RoutingProvider):
    def __init__(self, host: str = "http://valhalla:8002"):
        self.host = host

    def is_available(self) -> bool:
        try:
            return requests.get(f"{self.host}/health", timeout=2).ok
        except Exception:
            return False

    def matrix(self, lats, lons):
        locations = [{"lat": lat, "lon": lon} for lat, lon in zip(lats, lons)]
        r = requests.post(
            f"{self.host}/sources_to_targets",
            json={"sources": locations, "targets": locations,
                  "costing": "truck", "units": "km"},
            timeout=30,
        )
        r.raise_for_status()
        rows = r.json()["sources_to_targets"]
        n = len(lats)
        dist_m = np.zeros((n, n), dtype=int)
        dur_s  = np.zeros((n, n), dtype=int)
        for i, row in enumerate(rows):
            for j, cell in enumerate(row):
                dist_m[i][j] = int((cell.get("distance") or 0) * 1000)
                dur_s[i][j]  = int(cell.get("time") or 0)
        return dist_m, dur_s

    @property
    def source_name(self): return "VALHALLA"
```

**Профиль `truck` в Valhalla** — учитывает грузоподъёмность моста, высоту тоннеля, запрет въезда грузовиков в жилые зоны. При будущей необходимости здесь можно задавать параметры конкретного ТС (`weight`, `height`, `axle_load`).

```python
# services/distance_matrix_service.py

def rebuild_matrix(addr_ids: list[int] | None = None) -> dict:
    """Пересчитывает матрицу для указанных адресов (или всех).
    Сохраняет результат в RRL_ADDR_DISTANCE_MATRIX."""
    provider = get_routing_provider()
    addrs = load_addresses(addr_ids)   # SELECT из RRL_ADDR где LATITUDE IS NOT NULL
    lats  = [a.latitude  for a in addrs]
    lons  = [a.longitude for a in addrs]

    dist_m, dur_s = provider.matrix(lats, lons)

    rows = [
        (addrs[i].id, addrs[j].id,
         int(dist_m[i][j]) / 1000,   # → км
         int(dur_s[i][j])  / 60,     # → мин
         provider.source_name)
        for i in range(len(addrs))
        for j in range(len(addrs)) if i != j
    ]
    bulk_upsert_matrix(rows)   # MERGE INTO RRL_ADDR_DISTANCE_MATRIX
    return {"pairs": len(rows), "source": provider.source_name}
```

Решатель CVRPTW (Capacitated VRP with Time Windows) — точное название задачи, которую нужно решить:

- K разнородных машин (разная грузоподъёмность, разный тип ТС)

**Для кластеризации: scikit-learn DBSCAN**

DBSCAN (Density-Based Spatial Clustering) группирует адреса по географической плотности без указания числа кластеров:

```python
from sklearn.cluster import DBSCAN
import numpy as np

def cluster_addresses(lats, lons, eps_km=15, min_samples=3):
    coords = np.radians(np.column_stack([lats, lons]))
    # eps в радианах: 15 км / 6371 км
    db = DBSCAN(eps=eps_km / 6371, min_samples=min_samples, metric="haversine")
    labels = db.fit_predict(coords)
    return labels   # -1 = шум (изолированная точка)
```

`eps_km=15` означает: адреса ближе 15 км попадают в один кластер. Для «ветки вдоль трассы» подходит, для городских районов — уменьшить до 5–8 км.

**Почему не другие алгоритмы:**

| Алгоритм | Проблема |
|---------|---------|
| Concorde (точный TSP) | Решает только одну машину; требует компиляции C |
| LKH-3 | Лучший точный TSP, но нет Python API, overkill для VRP |

## 13. Обработка ошибок и атомарность

### 13.1 Атомарность создания рейса (`POST /tasks` + добавление СТ)

Создание рейса выполняется в три шага через Oracle-функции:
1. `RRL_TRASPORT_TASK_ADD` → возвращает `tt_id`
2. Цикл `RRL_TT_ADD_PALL` для каждого СТ
3. `RRL_TT_REORDER_ADR` → рассчитывает порядок объезда и цену

**Проблема частичного создания:** если шаг 2 прерывается (ошибка Oracle, таймаут сети) после нескольких итераций — рейс создан, но наполнен частично.

**Решение:** backend выполняет весь цикл в одном Oracle-соединении. При исключении на любом шаге вызывается `DELETE /tasks/{tt_id}` (через `RRL_TT_DELETE` если такой пакет есть, иначе — прямой DELETE без нарушения правила, т.к. рейс не «закрытый»). Если откат тоже упал — ошибка логируется с `tt_id` для ручного разбора.

### 13.2 Атомарность `POST /planner/apply`

Применение VRP-плана создаёт N рейсов через те же Oracle-функции. Выполняется как последовательный цикл. Если на k-м рейсе произошла ошибка — первые k-1 рейсов уже созданы. Поведение:
- Ответ: `207 Multi-Status` с массивом `{tt_id, status, error}` для каждого рейса.
- Frontend показывает частичный успех: «Создано 5 из 8 рейсов. Ошибки: [...]».
- Диспетчер сам решает — доделать вручную или расформировать.

### 13.3 Oracle-таймауты

Все запросы к Oracle через `cx_Oracle` выполняются с таймаутом 30 сек (параметр `outputtypehandler` на уровне соединения). При `cx_Oracle.DatabaseError` с кодом ORA-01013 (user requested cancel) или ORA-03113 (end-of-file) — возвращается `503`.

### 13.4 can_print и 422

При закрытии рейса (`POST /tasks/{id}/close`) результат `TRANSPORT_TASK.can_print()` проверяется **до** фактического закрытия. Если не `'ok'` — возвращается `422 Unprocessable Entity` с телом `{"detail": "<текст из can_print>"}`. Frontend показывает этот текст в диалоге подтверждения.

Право `SEND_EMPTY_TRUCK` позволяет обойти проверку — в этом случае `can_print()` не вызывается.

### 13.5 Изменение рейса, включённого в биллинг

Рейс с непустым `PAY_ORDER_ID` (привязан к счёту) **не может быть**:
- Расформирован (`DELETE /tasks/{id}` → `409 Conflict`)
- Изменён по составу СТ (`POST/DELETE /tasks/{id}/sts` → `409 Conflict`)

Допускается: изменение примечания (`PATCH` поле `comment`) и редактирование ORD/LOAD_TYPE внутри состава.

Frontend скрывает кнопки «Расформировать» и «Удалить из маршрута» для таких рейсов, показывает бейдж `billed`.

### 13.6 WebSocket — обрыв соединения

При разрыве `/ws/dispatch` клиент делает exponential backoff (1s → 2s → 4s → 8s → max 30s) и переподключается. При успешном переподключении — выполняет рефетч `GET /tasks` и `GET /available-sts` для синхронизации состояния.

### 13.7 SSE — прогресс VRP-решателя

`POST /planner/solve` возвращает `text/event-stream`. События:
```
data: {"type": "progress", "step": "clustering", "pct": 10}
data: {"type": "progress", "step": "solving", "pct": 45}
data: {"type": "done", "plan_id": 123, "score": 84.5}
data: {"type": "error", "detail": "solver_timeout"}
```
При закрытии вкладки браузера SSE-соединение разрывается — backend отменяет OR-Tools через `solver.solver.set_time_limit(0)`.

## 14. Принятые технологические решения

### 14.1 Диаграмма Ганта — SVG

**Выбор:** кастомный SVG-компонент `GanttChart` в `TransportGanttPage.tsx`.

**Почему SVG, не Canvas:**
- Блоки кликабельны без математики hit-test (SVG-элементы получают события нативно)
- Drag реализуется через `onMouseDown`/`onMouseMove` без сторонних библиотек
- CSS-анимации для live-линии (`animation: moveRight linear 60s`)
- Тултипы — стандартный `<title>` или React-портал

**Почему не библиотека (`dhtmlx/gantt`, `frappe-gantt`):**
- Требуют платную лицензию или несовместимы с React 19
- Не поддерживают кастомные цветогруппы по бизнес-коду операции
- Проще написать 400 строк SVG-рендера, чем бороться с чужим API

**Структура компонента:**
```tsx
<svg viewBox={`0 0 ${WIDTH} ${height}`}>
  <TimeAxis from={6*60} to={22*60} stepMin={30} />
  {vehicles.map(v => <VehicleRow key={v.id} vehicle={v} ops={v.operations} />)}
  <NowLine offsetX={nowOffset} />
</svg>
```

**Рендеринг:** виртуализация строк через `@tanstack/react-virtual` (если машин > 50).

### 14.2 TanStack Query — стратегия кэширования

| Запрос | `staleTime` | `refetchOnWindowFocus` | Инвалидация |

| `GET /available-sts` | 30 сек | `true` | После `POST /tasks`, `POST/DELETE /tasks/{id}/sts` |

При WebSocket-событии от сервера — немедленная инвалидация соответствующего ключа.

`@tanstack/react-virtual` — обязательно при числе СТ > 200. Настройки:

const rowVirtualizer = useVirtualizer({
