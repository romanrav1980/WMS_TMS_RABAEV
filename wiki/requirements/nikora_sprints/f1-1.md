# F1.1. ERP XML: адреса, артикулы и экран маппинга

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F1.1. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** ERP присылает магазин и товар; они однозначно сопоставлены, отображаются в интерфейсе; конфликт показан и исправлен новой ревизией.

Входит:

- MasterDataSnapshot/Change магазина/адреса/артикула/UoM/склада; source ownership и version/effectiveFrom.
- Расширить имеющиеся справочники, не создавать дубликаты; UI-02 mapping и UI-01 ошибки.
- Неизвестная/неоднозначная ссылка сохраняется с причиной; изменение справочника не переписывает исполненный snapshot.

Не входит: Не включать OrderManifest, физические статусы и произвольные прямые SQL-записи во внешнюю БД.

Зависимости для READY: [A1.2](a1-2.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Используются ingress A1 и MasterDataSnapshot/Change: destinationGLN/address/window/timezone/active; owner/SKU/GTIN/UoM/dimensions/weight/temp/stackability; source key mapping и effective version. UI получает bounded projection/errors.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- api/wms_api_server/app/services/product_service.py
- api/wms_api_server/app/services/customer_order_service.py
- admin/wms_admin_frontend/src/components/
- tests/nikora/

## 3. Ограниченные шаги реализации

1. C1: один master mapping с positive/negative fixture.
2. L2: таблица/детали/состояния на утверждённом API.
3. T3: независимый XML→Oracle→UI тест.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. leading zero, inactive/unknown, GTIN ambiguity, revision replay/hash conflict.
2. Форма показывает источник/версию/ошибку, права edit отдельно от view.
3. Контракт и реальный ERP endpoint: при отсутствии последнего статус contract-ready, не production-ready.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f1_1.py и, если UI входит в scope, tests/ui/nikora_f1_1.cjs; плюс Oracle verify SQL и reports/nikora/F1.1/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **C — Claude Code Sonnet, Codex проверяет**.

- Основной исполнитель: Claude Code claude-sonnet-5 medium.
- Независимая проверка/тесты: Codex gpt-5.6-terra medium/high + тестовые runner.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
