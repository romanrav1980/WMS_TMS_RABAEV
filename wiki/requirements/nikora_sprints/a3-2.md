# A3.2. Ресурсы ворот и версионируемая очередь техники

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: architecture; родитель прежнего плана: A3. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Два клиента не занимают один ресурс сверх вместимости и не назначают один груз двум водителям.

Входит:

- Переиспользовать topology/resources/warehouse tasks: интервалы ворот/линий и назначение техники.
- Атомарный claim, queueVersion, preview/confirm reorder, request recall/ACK; без второго списка задач.
- Read projection занятости, deadlines/blockers/custody на ограниченную смену.

Не входит: Нет нового ресурсного движка, оптимизации перемещений или финальных экранов.

Зависимости для READY: [A3.1](a3-1.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Расширить warehouse task/resource APIs: queueVersion, taskVersion, resource/session, priority/deadline/blockers; preview-reorder/confirm-reorder/claim/recall. Booking интервал resourceId/from/to/capacity с конкурентным lock.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- api/wms_api_server/app/services/resource_management_service.py
- api/wms_api_server/app/services/warehouse_task_service.py
- api/wms_api_server/app/services/warehouse_task_domain_sync_service.py
- db/migrations/
- tests/nikora/

## 3. Ограниченные шаги реализации

1. H1: пригодность RESOURCE_ASSIGNMENT и необходимые узкие расширения.
2. H2: booking/queue commands и read model.
3. H3: concurrency/rights/SQL acceptance.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Конкурентное бронирование, incompatible resource, reorder 409, недоступная техника.
2. Груз на технике не переходит другой машине до физической передачи.
3. Offline водитель не становится свободным; bounded SQL без N+1.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_a3_2.py и, если UI входит в scope, tests/ui/nikora_a3_2.cjs; плюс Oracle verify SQL и reports/nikora/A3.2/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **H — Сильный GPT, независимый Claude**.

- Основной исполнитель: Codex gpt-5.6-sol high.
- Независимая проверка/тесты: Claude Code claude-sonnet-5 high + Oracle/pytest.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 6. Время и стоимость — оценка, не обещание

Рабочие дни: **3 / 4 / 7** (нижняя / базовая / верхняя оценка). Базовое окно в последовательном плане: дни **47–50** от готовности ресурсов. Внешнее ожидание не включено. Спринт включает создание тестов, review, исправления и техническую приёмку.

Ориентиры: 18.00 агент-часов (включая tool/test ожидание), 2.00 локальных server-hours, 18.00 часов техлида/QA. Эти часы **не суммируются** в календарную длительность: часть работы идёт параллельно, время людей уже учтено в базовых днях.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
