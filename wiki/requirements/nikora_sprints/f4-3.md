# F4.3. Физическая консолидация, шов и перепаковка в UI

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F4.3. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Оператор объединяет два HU одного магазина, разъединяет по шву и отдельно перепаковывает в новые — состав не теряется.

Входит:

- UI-07/08 preview HU tree/balance/newIDs с тремя отдельными командами aggregate/seam/repack.
- Физическое сканирование/подтверждение, version conflicts и новый quality status.
- Capacity верхних HU и прослеживание исходного SSCC в целевой WMS.

Не входит: Нет графовой БД, автоматического упаковочного solver и обхода контроля.

Зависимости для READY: [F4.2](f4-2.md), [A2.3](a2-3.md), [A2.Q2](a2-q2.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Использовать aggregate/seam/repack A2, отдельный preview и confirm expectedVersions; target WMS получает operationId/old/new HU/line bindings/causation без создания независимого stock receipt.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- admin/wms_admin_frontend/src/components/
- terminal/wms_terminal_web/src/
- api/wms_api_server/app/services/ (HU)
- tests/nikora/

## 3. Ограниченные шаги реализации

1. H1: командные DTO/preview и интеграционные binding.
2. L2: дерево и отдельные формы операций.
3. H3: full balance/target-WMS/scan acceptance.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Wrong store/cycle/double parent, 2→1→2 и 2→3, concurrent repack.
2. Новый состав инвалидирует old PASS, loaded заблокирован.
3. Целевая WMS принимает согласованные факты без второго прихода, source ID прослеживается.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f4_3.py и, если UI входит в scope, tests/ui/nikora_f4_3.cjs; плюс Oracle verify SQL и reports/nikora/F4.3/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **H — Сильный GPT, независимый Claude**.

- Основной исполнитель: Codex gpt-5.6-sol high.
- Независимая проверка/тесты: Claude Code claude-sonnet-5 high + Oracle/pytest.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
