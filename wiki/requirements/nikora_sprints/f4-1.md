# F4.1. Cross-dock: приёмка, линия и очередность выгрузки

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F4.1. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Шаттл выгружен в нужном порядке; HU принят на правильную линию, история источника и время dwell сохранены.

Входит:

- UI-07/08: назначенные ворота/линия, ожидаемые HU, приёмка с источником/плечом, dwell.
- Очередь выгрузки и задания ричтрака по существующим ресурсам.
- Расхождения/неизвестный HU в управляемое ожидание, не обычный доступный складской запас.

Не входит: Нет окончательной отгрузки в магазин и aggregate/repack UI.

Зависимости для READY: [F3.2](f3-2.md), [F2.6](f2-6.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Receipt command: scanId/HU/contentVersion/sourceLeg/targetSite/gate/lane/time; atomic custody + event + next warehouse task. unknown HU → dependency/exception, не новый несвязанный товар.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- api/wms_api_server/app/services/warehouse_task_domain_sync_service.py
- admin/wms_admin_frontend/src/components/
- terminal/wms_terminal_web/src/
- tests/nikora/

## 3. Ограниченные шаги реализации

1. C1: receipt/line projection и task routing.
2. L2: логистическая таблица/доска и короткий терминал.
3. T3: E2E source→cross-dock и негативные сканы.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Wrong store/door/HU, duplicate receipt, occupied line, missing source.
2. Cross-dock receipt не создаёт ERP store delivery; repack не сбрасывает dwell.
3. UI+ТСД+Oracle проверка приёмки и повторной синхронизации.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f4_1.py и, если UI входит в scope, tests/ui/nikora_f4_1.cjs; плюс Oracle verify SQL и reports/nikora/F4.1/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **C — Claude Code Sonnet, Codex проверяет**.

- Основной исполнитель: Claude Code claude-sonnet-5 medium.
- Независимая проверка/тесты: Codex gpt-5.6-terra medium/high + тестовые runner.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 6. Время и стоимость — оценка, не обещание

Рабочие дни: **2 / 3 / 5** (нижняя / базовая / верхняя оценка). Базовое окно в последовательном плане: дни **88–90** от готовности ресурсов. Внешнее ожидание не включено. Спринт включает создание тестов, review, исправления и техническую приёмку.

Ориентиры: 14.40 агент-часов (включая tool/test ожидание), 2.40 локальных server-hours, 14.40 часов техлида/QA. Эти часы **не суммируются** в календарную длительность: часть работы идёт параллельно, время людей уже учтено в базовых днях.

Ваше время показано в часах, без перевода в доллары. Для локальной модели учитывается только электричество; покупка и амортизация не учитываются. ## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
