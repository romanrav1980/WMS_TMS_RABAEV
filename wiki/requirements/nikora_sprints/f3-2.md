# F3.2. Ручной маршрут: два плеча и секции

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F3.2. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Ручной шаттл и основной рейс созданы один раз; диспетчер видит ограничения каждого участка и фактический состав.

Входит:

- Расширить существующие диспетчер/планировщик/Ганта ролями плеч, остановками/секциями и последовательностью.
- Manual preview/apply с общей версией, explained hard failures.
- Остаток capacity kg/m³/мест на каждом участке; возвраты как будущий extension.

Не входит: Нет нового картографического продукта, геокодинга и алгоритма оптимизации.

Зависимости для READY: [F3.1](f3-1.md), [A3.1](a3-1.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Reuse transport planner/dispatch/Gantt contracts + legs/compartments; manual apply принимает planId/expectedVersion/idempotency key и не создаёт legacy relation конфликт.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- admin/wms_admin_frontend/src/components/TransportDispatchPage.tsx
- admin/wms_admin_frontend/src/components/TransportPlannerPage.tsx
- admin/wms_admin_frontend/src/components/TransportGanttPage.tsx
- api/wms_api_server/app/services/transport_service.py
- tests/nikora/

## 3. Ограниченные шаги реализации

1. H1: projected fields и manual assignment contract.
2. C2: таблица/детали/временной вид existing UI.
3. H3: independent hard-validator/apply/UI acceptance.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Повтор apply, failure второй операции, windows/temperature/geometry/section.
2. Нет silent unassigned; billed legacy рейс нельзя изменить.
3. Регресс TransportDispatch/Planner/Gantt и две конкурирующие правки.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f3_2.py и, если UI входит в scope, tests/ui/nikora_f3_2.cjs; плюс Oracle verify SQL и reports/nikora/F3.2/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **H — Сильный GPT, независимый Claude**.

- Основной исполнитель: Codex gpt-5.6-sol high.
- Независимая проверка/тесты: Claude Code claude-sonnet-5 high + Oracle/pytest.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
