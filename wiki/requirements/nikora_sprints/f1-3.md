# F1.3. ERP: исходящие события и рабочее место интегратора

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F1.3. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** ERP получает по одному эффекту каждого из четырёх тестовых типов событий; оператор видит ошибку и безопасно повторяет доставку.

Входит:

- Контракт четырёх ERP-событий; outbox delivery, technical ACK vs APPLIED/business receipt.
- UI-01 filters/detail/masked payload/attempts/dependency/owner; dry-run и bounded retry/reconcile.
- Отдельный тестовый event producer для квалификации контракта; production запрещён на fixture-пути.

Не входит: Не редактировать XML в очереди, не ставить APPLIED вручную и не подключаться прямо к таблицам ERP.

Зависимости для READY: [F1.2](f1-2.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Versioned ERP event: eventId/type/entityScope/order/part/leg/HU/contentVersion/occurredAt/causalEventId/qty/UoM/qualityStatus/readyToShip. UI различает transport receipt, business APPLIED и физическую приёмку.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- api/wms_api_server/app/services/outbox_service.py
- api/wms_api_server/app/workers/outbox_worker.py
- wiki-raw/wms_admin_ui_reference/external-outbox.html (образец)
- admin/wms_admin_frontend/src/components/
- tests/nikora/

## 3. Ограниченные шаги реализации

1. C1: ERP delivery adapter и contract harness.
2. L2: интеграционный журнал по существующему audit/outbox UI.
3. T3: retry/ACK/reconcile и отрицательные UI тесты.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Нет ASSEMBLED без causal assembly; нет IN_TRANSIT от LOADED; delivery только receiving.
2. Timeout после commit, hash conflict, stale revision, rights/redaction.
3. Реальные producers ещё не заявляются готовыми; они подключаются в F2/F3/F4/F6.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f1_3.py и, если UI входит в scope, tests/ui/nikora_f1_3.cjs; плюс Oracle verify SQL и reports/nikora/F1.3/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **C — Claude Code Sonnet, Codex проверяет**.

- Основной исполнитель: Claude Code claude-sonnet-5 medium.
- Независимая проверка/тесты: Codex gpt-5.6-terra medium/high + тестовые runner.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 6. Время и стоимость — оценка, не обещание

Рабочие дни: **2 / 3 / 5** (нижняя / базовая / верхняя оценка). Базовое окно в последовательном плане: дни **20–22** от готовности ресурсов. Внешнее ожидание не включено. Спринт включает создание тестов, review, исправления и техническую приёмку.

Ориентиры: 12.00 агент-часов (включая tool/test ожидание), 2.00 локальных server-hours, 12.00 часов техлида/QA. Эти часы **не суммируются** в календарную длительность: часть работы идёт параллельно, время людей уже учтено в базовых днях.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
