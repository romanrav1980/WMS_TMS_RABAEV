# F6.2. Магазинная приёмка и ERP delivery

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F6.2. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Магазин принял 10 из 12, причина сохранена и передана ERP; недостающие две не исчезли и не считаются доставленными.

Входит:

- UI-11 ожидаемый HU/адрес, скан, принято/недостача/повреждение/отказ и причина.
- ReceivingAdvice/receipt rows и подтверждение синхронизации; offline только draft.
- ERP ORDER_DELIVERED_TO_STORE с фактическим part/order scope и расхождением.

Не входит: Не делать полноценную розничную WMS; фото/подпись только по согласованной политике.

Зависимости для READY: [F6.1](f6-1.md), [F4.2](f4-2.md), [F1.3](f1-3.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

ReceivingAdvice: receiptId/order/part/leg/store/HU lines/acceptedQty/rejectedQty/damage/short/reason/time/receiver; store authority from auth. Partial event не объявляет весь заказ доставленным.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- terminal/wms_terminal_web/src/
- api/wms_api_server/app/services/transport_service.py
- tests/nikora/

## 3. Ограниченные шаги реализации

1. C1: receipt command и ERP event producer.
2. L2: мобильный экран/причины/ошибки.
3. H3: независимый partial/duplicate/causal E2E.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Чужой магазин, повтор receipt, revision/cancel после частичного физического факта.
2. Cross-dock receipt/закрытие рейса/геопозиция не публикуют store delivery.
3. Телефон/реальная точка подтверждения/ERP ACK, права получателя.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f6_2.py и, если UI входит в scope, tests/ui/nikora_f6_2.cjs; плюс Oracle verify SQL и reports/nikora/F6.2/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **C — Claude Code Sonnet, Codex проверяет**.

- Основной исполнитель: Claude Code claude-sonnet-5 medium.
- Независимая проверка/тесты: Codex gpt-5.6-terra medium/high + тестовые runner.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 6. Время и стоимость — оценка, не обещание

Рабочие дни: **2 / 3 / 5** (нижняя / базовая / верхняя оценка). Базовое окно в последовательном плане: дни **113–115** от готовности ресурсов. Внешнее ожидание не включено. Спринт включает создание тестов, review, исправления и техническую приёмку.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
