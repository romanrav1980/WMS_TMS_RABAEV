# F3.1. Ручная волна консолидации и обратный график

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F3.1. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Для одного магазина из нескольких источников назначен согласованный ручной подвоз/выпуск либо показан конкретный блокер.

Входит:

- UI-10 магазин/date×источники, время консолидации/ворота/волна/ETA/deadline сборки.
- Обратный расчёт по нормам/latency, preview/ACK/confirm/release на общем handler.
- ERP INTERNAL_MOVEMENT_PLANNED с версией плана; manual не обходит hard constraints.

Не входит: Нет solver и автоматического выпуска whitelist.

Зависимости для READY: [F2.1](f2-1.md), [F2.5](f2-5.md), [F2.7](f2-7.md), [A3.3](a3-3.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Schedule DTO: waveId/version/destination+date/source parts/gate/lane/consolidateAt/pickupAt/pickDeadline/latency/normRefs/ACKs. API рассчитывает интервалы и общие constraints; ERP planned event с scheduleVersion.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- api/wms_api_server/app/services/transport_service.py
- admin/wms_admin_frontend/src/components/
- tests/nikora/

## 3. Ограниченные шаги реализации

1. H1: обратный расчёт и canonical schedule commands.
2. C2: матрица/календарь/preview статусов.
3. H3: Oracle/ERP/конкурентная приёмка одной волны.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. PLAN допускает прогноз, ACTUAL_ONLY не резервируется до разрешённого факта.
2. Missing/quality/ACK/capacity блокируют выпуск; два слота не превышают ресурс.
3. Новое расписание не переписывает старый event; Freeze/частичная отправка по утверждённой политике.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f3_1.py и, если UI входит в scope, tests/ui/nikora_f3_1.cjs; плюс Oracle verify SQL и reports/nikora/F3.1/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **H — Сильный GPT, независимый Claude**.

- Основной исполнитель: Codex gpt-5.6-sol high.
- Независимая проверка/тесты: Claude Code claude-sonnet-5 high + Oracle/pytest.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 6. Время и стоимость — оценка, не обещание

Рабочие дни: **3 / 4 / 7** (нижняя / базовая / верхняя оценка). Базовое окно в последовательном плане: дни **80–83** от готовности ресурсов. Внешнее ожидание не включено. Спринт включает создание тестов, review, исправления и техническую приёмку.

Ориентиры: 18.00 агент-часов (включая tool/test ожидание), 2.00 локальных server-hours, 18.00 часов техлида/QA. Эти часы **не суммируются** в календарную длительность: часть работы идёт параллельно, время людей уже учтено в базовых днях.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
