# A3.3. Единый validator, freeze и атомарный apply

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: architecture; родитель прежнего плана: A3. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Допустимый ручной API-план подтверждён один раз; недопустимый не создаёт частичный рейс; snapshot выпуска неизменяем.

Входит:

- Один deterministic validator секций/участков/capacity/window/temp/geometry/quality.
- OutboundWave/scheduleVersion/immutable RELEASED; calculate/confirm/release на общем command handler.
- Idempotent apply и rollback create+assign в существующем пути, защита billed.

Не входит: Нет solver, UI, auto-policy; если validator превышает 3–4 tickets, отдельный scope change с пересчётом, не скрытый рост.

Зависимости для READY: [A3.2](a3-2.md), [A2.Q2](a2-q2.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Предлагаются calculate/confirm/release по waveId+expectedVersion; applyId уникален. Validator возвращает violations(code, objectKey, actual, limit, reason), unassigned и planVersion; одна транзакция create+assign+snapshot+outbox.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- api/wms_api_server/app/services/transport_service.py
- api/wms_api_server/app/routers/transport.py
- db/migrations/
- tests/transport/
- tests/nikora/

## 3. Ограниченные шаги реализации

1. X1: Astra формулирует validator/freeze transaction и fixtures.
2. H2: Sol реализует reuse handler + atomic apply.
3. X3: Opus проверяет crash/race/legacy/billed пути.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Повтор apply даёт те же IDs; ошибка второй операции не оставляет первой.
2. Hard-limit одинаков для manual/auto fixture; отсутствие геометрии не зелёный успех.
3. Q06/Q01 утверждены до бизнес-допуска; RELEASED нельзя обычным refresh изменить.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_a3_3.py и, если UI входит в scope, tests/ui/nikora_a3_3.cjs; плюс Oracle verify SQL и reports/nikora/A3.3/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **X — Критические инварианты**.

- Основной исполнитель: Codex gpt-6-astra high: контракт/опасное ядро; gpt-5.6-sol high: реализация.
- Независимая проверка/тесты: Claude Code claude-opus-5 high + Oracle concurrency tests.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 6. Время и стоимость — оценка, не обещание

Рабочие дни: **4 / 5 / 8** (нижняя / базовая / верхняя оценка). Базовое окно в последовательном плане: дни **51–55** от готовности ресурсов. Внешнее ожидание не включено. Спринт включает создание тестов, review, исправления и техническую приёмку.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
