# F1.2. ERP XML: операционные заказы и полнота

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F1.2. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Заказ с отсутствующим артикулом дождался справочника и применился один раз; актуальная ревизия/отмена не затирает факт.

Входит:

- OrderManifest create/revision/cancel, owner/order/store/date/lines/ожидаемые части.
- WAITING_DEPENDENCY с восстановлением после master data; immutable executed facts.
- Карточка UI-10 read-only и UI-01 dependency chain; предварительная волна/ID по Q05.

Не входит: Не вычислять физическую готовность по плану и не реализовывать все WMS адаптеры.

Зависимости для READY: [F1.1](f1-1.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

OrderManifest: owner/externalOrderId/destinationKey/serviceDate/revision/completeness, lines(SKU/UoM/qty), expected source parts; cancelRevision + reason. Ошибки зависимости сохраняют payload; не исполнять необработанный заказ.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- api/wms_api_server/app/services/customer_order_service.py
- api/wms_api_server/app/routers/customer_orders.py
- admin/wms_admin_frontend/src/components/
- tests/nikora/

## 3. Ограниченные шаги реализации

1. H1: Manifest lifecycle/ownership и seed.
2. H2: обработчик/projections и связанные запросы.
3. C3: карточка полноты + независимые интеграционные тесты.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Ревизии вне порядка, messageId/hash conflict, чужой owner, частичное исполнение перед отменой.
2. Молчание источника не принимается за ноль, полнота из Manifest.
3. Один настоящий ERP заказ в тестовом контуре, SQL balance и UI empty/stale/error.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f1_2.py и, если UI входит в scope, tests/ui/nikora_f1_2.cjs; плюс Oracle verify SQL и reports/nikora/F1.2/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **H — Сильный GPT, независимый Claude**.

- Основной исполнитель: Codex gpt-5.6-sol high.
- Независимая проверка/тесты: Claude Code claude-sonnet-5 high + Oracle/pytest.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
