# F5.1b. Реальный OR-Tools через общий validator

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F5.1. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** OR-Tools решает маленький допустимый кейс и корректно отказывает/возвращает unassigned при невозможности; применяется один раз.

Входит:

- Запустить реальную ветку OR-Tools и исправить подтверждённый дефект n_orders/контракта результата.
- Ограничить solver time, deterministic seed где поддержан, unassigned/reason и fallback без обхода validation.
- Сравнить один набор с manual/savings без обещания глобального оптимума.

Не входит: Нет глобального оптимума, ML-прогноза и новой платформы маршрутизации.

Зависимости для READY: [F5.1a](f5-1a.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Тот же solver contract, provider=ortools, timeout и runtimeVersion; solver-specific response адаптируется до canonical validator. fallback возвращает provider/reason, не подменяет успех.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- api/wms_api_server/app/services/transport_service.py
- tests/transport/
- tests/nikora/

## 3. Ограниченные шаги реализации

1. H1: dependency/runtime и реальные fixtures solver.
2. H2: adapter result/timeout/validation path.
3. C3: независимое сравнение solver и UI отказа.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Overweight/temperature/windows/section и routing matrix ошибки.
2. Пакет отсутствует/timeout → явный статус; validator остаётся включён.
3. Малый эталон с известной допустимостью и фиксированный performance workload.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f5_1b.py и, если UI входит в scope, tests/ui/nikora_f5_1b.cjs; плюс Oracle verify SQL и reports/nikora/F5.1b/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **H — Сильный GPT, независимый Claude**.

- Основной исполнитель: Codex gpt-5.6-sol high.
- Независимая проверка/тесты: Claude Code claude-sonnet-5 high + Oracle/pytest.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
