# F7.3e. ERP + четыре источника: сквозная сверка

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F7.3. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Вся цепочка воспроизведена без потери/двойного количества; сверены ERP, источники, cross-dock и магазин.

Входит:

- Один магазин/дата, все четыре источника и целевая WMS, real ERP order/master.
- Сверка четырёх ERP-событий по part/leg/version с первичными фактами и происхождением HU.
- Контролируемый отказ после commit/до ACK и replay диапазона, нет silent cut FULL snapshots.

Не входит: Не разрабатывать заново отсутствующий adapter в этом gate; он возвращается в свой отдельный спринт.

Зависимости для READY: [F7.3a](f7-3a.md), [F7.3b](f7-3b.md), [F7.3c](f7-3c.md), [F7.3d](f7-3d.md), [F6.2](f6-2.md), [F7.2](f7-2.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Cross-system reconciliation по source/message/entityVersion/part/HU/leg/order; evidence ledger содержит producerEvent→outbox→receiver effect, суммы в одинаковых единицах.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- tests/nikora/
- api/wms_api_server/app/services/outbox_service.py
- wiki/sources/

## 3. Ограниченные шаги реализации

1. H1: матрица cross-system evidence и golden end-to-end case.
2. L2: сверочные запросы/отчёты по утверждённым ключам.
3. H3: запуск с контрагентами и разбор несовпадений.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. PLAN planned movement до сборки и ACTUAL_ONLY после факта, partial order independently moving.
2. Downstream replay не превращается во второй приход; delay ACK/unknown reference resolved.
3. Все adapters production-oriented, никакой simulator на пути gate.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f7_3e.py и, если UI входит в scope, tests/ui/nikora_f7_3e.cjs; плюс Oracle verify SQL и reports/nikora/F7.3e/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **H — Сильный GPT, независимый Claude**.

- Основной исполнитель: Codex gpt-5.6-sol high.
- Независимая проверка/тесты: Claude Code claude-sonnet-5 high + Oracle/pytest.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
