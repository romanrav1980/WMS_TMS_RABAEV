# F2.4. Контроллер: два прохода и осмотр

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F2.4. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Два физических пересчёта совпали — доступен осмотр; несовпадение попадает ответственному и не допускает отгрузку.

Входит:

- UI-05 с одним активным сканером, independent pass state и скрытым прошлым/ожидаемым количеством.
- Завершение каждого прохода, сравнение, осмотр, HOLD и ранняя очередь UI-13.
- Second-operator policy и API ограничение доступа к прошлому проходу.

Не входит: Два скана SSCC не считаются двумя пересчётами; вес в следующем спринте.

Зависимости для READY: [F2.3](f2-3.md), [A2.Q1](a2-q1.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Quality API A2.Q1; один active passage, close-pass command с sessionVersion, inspection result/reason. Сервер применяет visibility policy, не только hidden поля React.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- terminal/wms_terminal_web/src/
- api/wms_api_server/app/services/ (quality)
- tests/nikora/
- tests/ui/

## 3. Ограниченные шаги реализации

1. H1: связать терминал с независимыми сессиями.
2. L2: активный экран/ошибки и тестовые наборы.
3. C3: независимые fraud/mismatch/reconnect тесты.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Q-01…05 и Q-11/12, same GTIN/different scanId, blind API.
2. Нельзя править closed pass, concurrent session/actor policy.
3. Реальный сканер и сохранённые evidence rows; простые UI-snapshots не заменяют тест API.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f2_4.py и, если UI входит в scope, tests/ui/nikora_f2_4.cjs; плюс Oracle verify SQL и reports/nikora/F2.4/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **H — Сильный GPT, независимый Claude**.

- Основной исполнитель: Codex gpt-5.6-sol high.
- Независимая проверка/тесты: Claude Code claude-sonnet-5 high + Oracle/pytest.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 6. Время и стоимость — оценка, не обещание

Рабочие дни: **3 / 4 / 7** (нижняя / базовая / верхняя оценка). Базовое окно в последовательном плане: дни **66–69** от готовности ресурсов. Внешнее ожидание не включено. Спринт включает создание тестов, review, исправления и техническую приёмку.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
