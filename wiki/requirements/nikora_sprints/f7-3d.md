# F7.3d. Fresh: один внешний адаптер

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: functional; родитель прежнего плана: F7.3. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Один названный реальный поток прошёл от заказа до целевой WMS с повтором/восстановлением; подписан mapping/passport и production-ready gate.

Входит:

- Реализовать/донастроить один TMS-side adapter profile fresh (без овощей/фруктов), включая catch-weight/температуру.
- Проверить master/order references, AssemblyPlan/Actual, schedule ACK, source/target SSCC correlation, реальные технические credentials.
- Один поток/один вариант системы; при одинаковом контракте переиспользовать код, не копировать адаптер.

Не входит: Разработка закрытого кода внешней WMS/ERP поставщиком не входит в токенную смету: отдельная коммерческая оценка; ожидание доступа продлевает календарь. Нет новых типов сообщений сверх согласованного профиля.

Зависимости для READY: [F2.1](f2-1.md), [F4.3](f4-3.md), [F1.3](f1-3.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Один adapter profile использует утверждённые A1/F1/F2 XML contracts. Конфигурация: source authority, site/owner/store/SKU/UoM mapping, schema version, ACK profile, bounded reconciliation checkpoint; секреты вне repo/logs.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- api/wms_api_server/app/services/ (nikora adapters)
- tests/nikora/
- wiki/sources/

## 3. Ограниченные шаги реализации

1. C1: паспорт/mapping и sanitized golden exchange.
2. C2: adapter/config + контрактный regression.
3. T3: совместная квалификация с владельцем внешней WMS.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. Реальные XML/endpoint и физические HU; эмулятор не закрывает gate.
2. Дубликаты, out-of-order, full snapshot limit, неправильный store/owner/UoM/SSCC.
3. Транспортный факт принадлежит одному источнику, proxy не создаёт второй приход; разобрать длинные SQL.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_f7_3d.py и, если UI входит в scope, tests/ui/nikora_f7_3d.cjs; плюс Oracle verify SQL и reports/nikora/F7.3d/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **C — Claude Code Sonnet, Codex проверяет**.

- Основной исполнитель: Claude Code claude-sonnet-5 medium.
- Независимая проверка/тесты: Codex gpt-5.6-terra medium/high + тестовые runner.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 6. Время и стоимость — оценка, не обещание

Рабочие дни: **2 / 3 / 5** (нижняя / базовая / верхняя оценка). Базовое окно в последовательном плане: дни **131–133** от готовности ресурсов. Внешнее ожидание не включено. Спринт включает создание тестов, review, исправления и техническую приёмку.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
