# A1.2. Идемпотентное применение, outbox и версии

Дата: 15.09.2026. Статус: DRAFT к реализации, не выполнено. Тип: architecture; родитель прежнего плана: A1. Обязателен [[requirements/nikora_sprint_contract]]. Общий план: [[roadmap/nikora_agent_delivery_plan]].

## 1. Результат и границы

**Законченный проверяемый результат:** Одна тестовая доменная команда атомарно применяется и выдаёт один внешний эффект при повторе/сбое; recovery воспроизводим.

Входит:

- Общая транзакция command+domain event+outbox; бизнес-ключ/version/causation отдельно от messageId.
- Повторы, порядок зависимостей, WAITING_DEPENDENCY, hash conflict, bounded retry/dead letter/reconcile.
- Переиспользовать EVENT_OUTBOX/ADAPTER_REQUEST и worker; утвердить причинность четырёх ERP-событий по part/leg.

Не входит: Нет Kafka, второго outbox, реальных производителей сборки/выезда или «exactly once network» обещания.

Зависимости для READY: [A1.1](a1-1.md). Требуются решения бизнес-владельцев и реальные контрагенты/устройства, указанные ниже. BLOCKED/CONTRACT_READY не превращается в ACCEPTED по эмулятору.

## 2. Интерфейс и данные

Apply(messageId) и retry/reconcile по существующему outbox; statuses RECEIVED/WAITING_DEPENDENCY/APPLIED/REJECTED/RETRY/DLQ. Domain changes + event + outbox единым commit; network ACK не участвует в Oracle transaction.

Все новые URL/имена — предложение к согласованию с действующим API, не описание уже реализованного endpoint. Любая write-команда сохраняет expectedVersion, correlation и аудит. Контракт не ослабляется ради удобства UI.

Точки расширения (перед ticket выбрать точный allowlist, не переписывать папку целиком):

- api/wms_api_server/app/services/outbox_service.py
- api/wms_api_server/app/workers/outbox_worker.py
- db/migrations/
- tests/nikora/

## 3. Ограниченные шаги реализации

1. X1: Astra фиксирует state machine, idempotency key и crash matrix.
2. H2: Sol реализует handler/retry на существующем outbox.
3. X3: Opus проверяет concurrency/rollback и регресс outbox.

Каждый шаг — отдельный handoff с patch/test evidence. Local подзадачи только по готовому контракту; изменение инварианта/миграции переводится в H/X. Максимальный scope и stop-rule — в общем контракте.

## 4. Проверки и критерий приёмки

1. 100 повторов и два worker → один эффект; сбой до commit и после commit/до ACK.
2. N+2 ждёт N+1; тот же ID с другим hash не меняет факт; результат обработки не зацикливается.
3. LOADED fixture не создаёт IN_TRANSIT, DEPARTED создаёт; cross-dock receipt не создаёт store delivery.

Дополнительно обязательны права/дубли/ошибка связи/конкурентная версия, legacy regression и SQL review по общему контракту. Приёмку подтверждают независимый reviewer и владелец сценария; авторский summary недостаточен.

Целевые test artifacts после реализации: tests/nikora/test_a1_2.py и, если UI входит в scope, tests/ui/nikora_a1_2.cjs; плюс Oracle verify SQL и reports/nikora/A1.2/<run>/. Это **планируемые** файлы, их наличие/прохождение сейчас не заявляется.

## 5. Кто программирует и тестирует

Профиль **X — Критические инварианты**.

- Основной исполнитель: Codex gpt-6-astra high: контракт/опасное ядро; gpt-5.6-sol high: реализация.
- Независимая проверка/тесты: Claude Code claude-opus-5 high + Oracle concurrency tests.
- Локальные помощники: только утверждённые механические/изолированные patches и fixtures. Детерминированные pytest/Playwright/SQL runner не расходуют LLM-токены сами по себе.
- Установка и параметры: [[runbooks/nikora_agent_launch]]. Для решения нового класса сначала S0/shadow test, затем повторное использование профиля.

## 7. Условия остановки и передачи

Остановить ticket при повторяющемся дефекте, выходе за контракт/allowlist, нарушении баланса/прав, отсутствии обязательного внешнего факта или исчерпании бюджета. Не ставить зелёный статус и не менять тест под ошибочный код. Handoff: сделанное, diff, failing case, израсходованные токены/деньги, следующий ограниченный шаг. Новый функционал сверх scope — отдельная карточка с пересчётом.
