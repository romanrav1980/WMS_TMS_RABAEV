## 1. Назначение

Административный блок `Сборка по волнам` нужен для управления волнами сборки в WMS-админке.

Блок должен позволять:

- видеть открытые заказы, доступные для включения в волну;
- создавать волну вручную или по фильтрам;
- рассчитывать preview волны до запуска;
- запускать волну с созданием жестких WMS-резервов по конкретным паллетам/партиям/количествам;
- видеть задачи пополнения и отбора;
- видеть жесткие резервы, дефициты и конфликты;
- отменять волну, если физические движения еще не начаты;
- освобождать резервы по правам;
- вести аудит всех действий оператора.

Админка не должна выполнять физическое сканирование товара. Физическое исполнение задач должно выполняться терминальным контуром или старым WMS-механизмом. Админка управляет запуском, контролем и аварийным администрированием волн.

## 2. Место В Админке

Нужна отдельная страница:

```text
wave-picking.html
```

Страница должна быть отдельным разделом, а не блоком на вкладке `Главная`.

Рекомендуемый пункт меню:

```text
Комплектация -> Волны сборки
```

Для raw UI прототипа файл должен лежать в:

```text
wiki-raw/wms_admin_ui_reference/wave-picking.html
wiki-raw/wms_admin_ui_reference/wave-picking.js
```

Визуально страница должна соответствовать текущему стилю WMS PRO admin UI:

- левое меню;
- верхняя панель с поиском и пользователем;
- плотные рабочие таблицы;
- компактные панели;
- статусы бейджами;
- кнопки действий только там, где они нужны оператору;
- без маркетинговых или декоративных экранов.

## 3. Права Доступа

Права должны использовать существующую модель `RUSERS` / `USER_GROUP` / `RIGHTS`.

Нельзя хардкодить администратора или права в JavaScript.

Минимальные права:

- `PICK_WAVE_VIEW`: просмотр страницы волн.
- `PICK_WAVE_CREATE`: создание черновика волны.
- `PICK_WAVE_CALCULATE`: расчет preview волны.
- `PICK_WAVE_LAUNCH`: запуск волны.
- `PICK_WAVE_CANCEL`: отмена волны.
- `PICK_WAVE_RELEASE_RESERVES`: освобождение резервов.
- `PICK_WAVE_RECALCULATE`: пересчет волны.
- `PICK_WAVE_TASK_ASSIGN`: назначение задач сотрудникам.
- `PICK_WAVE_SETTINGS_VIEW`: просмотр настроек волн.
- `PICK_WAVE_SETTINGS_EDIT`: изменение настроек волн.
- `PICK_WAVE_AUDIT_VIEW`: просмотр аудита волны.

Правила:

- пользователь без `PICK_WAVE_VIEW` не должен видеть страницу;
- кнопка `Запустить волну` видна только при `PICK_WAVE_LAUNCH`;
- кнопка `Отменить волну` видна только при `PICK_WAVE_CANCEL`;
- освобождение резервов требует отдельного права и обязательной причины;
- редактирование настроек волны требует отдельного права;
- аудит должен быть доступен только тем, кому разрешен просмотр audit log.

- номер волны;
- только активные;
- только с ошибками;
- только с дефицитом;
- только требующие внимания.

Колонки:

- склад;

### 4.2. Диалог `Запуск Волны`

Диалог запуска является центральным экраном.

Шаги диалога:

1. Выбор фильтров.
2. Выбор открытых заказов.
3. Расчет preview.
4. Проверка конфликтов и дефицитов.
5. Подтверждение запуска.
6. Результат запуска.

Фильтры:

- дата отгрузки;
- время сборки с/по;
- маршрут;
- ворота;
- склад;
- зона отбора;
- клиент;
- тип машины;
- приоритет заказа;
- статус заказа;
- только заказы без активной волны;
- только заказы с доступным остатком;
- только заказы без критического дефицита.

Список заказов должен показывать:

- номер заказа;
- клиент;
- адрес;
- дата отгрузки;
- окно сборки;
- маршрут;
- ворота;
- строк;
- коробов;
- расчетных паллет;
- статус планирования;
- есть ли активная волна;
- есть ли дефицит;
- приоритет.

Оператор может:

- выбрать заказы вручную;
- выбрать все подходящие заказы;
- исключить заказ из волны;
- открыть карточку заказа;
- увидеть причины, почему заказ нельзя включить.

### 4.3. Preview Волны

Preview показывается до запуска и не должен создавать жесткие резервы.

Preview работает с мягкой потребностью. Мягкая потребность не содержит окончательной партии/паллета/ячейки и не занимает WMS-остаток. Она нужна для предварительного расчета, оценки дефицита и показа кандидатов.

Жесткий резерв появляется только после запуска волны, когда система выбрала конкретную партию, паллету, ячейку и количество. WMS занимается именно жестким резервом.

Preview должен показывать:

- клиентов в волне;
- заказов;
- строк;
- SKU;
- полных паллет;
- объем покоробочного отбора;
- потребность пополнения pick face;
- планируемые задачи пополнения;
- планируемые задачи отбора;
- паллеты-кандидаты для будущего жесткого резерва;
- дефициты;
- конфликты;
- предупреждения.

Конфликты:

- превышен лимит клиентов;
- заказ уже в активной волне;
- не указан маршрут;
- не указаны ворота;
- нет свободного остатка;
- паллет уже зарезервирован;
- партия не подходит по сроку годности;
- партия еще на вылежке;
- маркировка не подходит клиенту;
- pick face не вмещает расчетный объем;
- нет паллета-источника для пополнения.

Preview должен иметь два уровня:

- краткий summary для оператора;
- детальная расшифровка для администратора.

### 4.4. Карточка Волны

Карточка волны открывается из реестра.

Разделы карточки:

- `Сводка`;
- `Заказы`;
- `Строки`;
- `Резервы`;
- `Пополнение`;
- `Задачи отбора`;
- `Дефицит`;
- `Аудит`;
- `Ошибки`.

Сводка:

- номер волны;
- статус;
- склад;
- маршрут;
- ворота;
- дата и окно;
- клиентов;
- заказов;
- строк;
- паллет;
- коробов;
- задач;
- процент выполнения.

Заказы:

- список заказов в волне;
- статус по каждому заказу;
- плановый объем;
- выполненный объем;
- дефицит;
- ссылка на заказ клиента.

Строки:

- артикул;
- товар;
- заказано;
- запланировано;
- полнопалетный отбор;
- покоробочный отбор;
- дефицит;
- причина дефицита.

Резервы:

- вид резерва `SOFT` / `HARD`;
- статус `ACTIVE` / `CONSUMED` / `RELEASED`;
- паллет;
- SSCC;
- партия;
- ячейка;
- количество;
- кто и когда создал;
- кто и когда освободил.

Для строк `SOFT` поля паллет, SSCC, партия и ячейка должны быть пустыми или показываться только как кандидаты отдельно от самой строки резерва. Для строк `HARD` эти поля обязательны, иначе это не WMS-резерв.

Пополнение:

- источник;
- целевая pick face;
- артикул;
- партия;
- количество;
- статус задачи;
- исполнитель;
- ошибка, если есть.

Раздел `Пополнение` должен показывать физические задачи из `RRL_WAREHOUSE_TASK` с `TASK_TYPE = REPLENISHMENT` и `TASK_SOURCE = WAVE`. Доменная строка `RRL_PICK_WAVE_REPLENISH_TASK` может использоваться как расчетная ссылка, но назначение, старт, завершение и отмена водительской работы выполняются через общий warehouse task.

Задачи отбора:

- тип задачи `FULL_PALLET` / `CASE_PICK`;
- заказ;
- клиент;
- артикул;
- паллет;
- ячейка;
- количество;
- последовательность обхода;
- статус;
- исполнитель.

Аудит:

- действие;
- пользователь;
- старый статус;
- новый статус;
- payload;
- результат;
- ошибка;
- дата и время.

## 5. Статусы И Доступные Действия

Матрица действий:

| Статус | Действия |
|---|---|
| `DRAFT` | расчет, удаление черновика |
| `CALCULATED` | запуск, пересчет, отмена |
| `LAUNCHED` | просмотр, отмена до старта задач, назначение задач |
| `REPLENISHING` | просмотр, назначение задач, контроль ошибок |
| `READY_TO_PICK` | просмотр, старт отбора |
| `PICKING` | просмотр, контроль задач |
| `PARTIAL` | просмотр, анализ дефицита, корректирующие действия |
| `COMPLETED` | только просмотр и аудит |
| `CANCELLED` | только просмотр и аудит |
| `FAILED` | просмотр ошибок, пересчет, отмена |

Запрещено:

- запускать волну без preview;
- запускать волну с критическими конфликтами;
- отменять волну простым действием, если физические перемещения уже начаты;
- освобождать резервы без причины;
- редактировать состав запущенной волны без специального сценария пересчета.

## 6. Настройки Волн

В админке нужен раздел `Настройки волн`.

Настройки:

- склад;
- код настройки;
- название;
- максимальное количество клиентов в волне;
- максимальное количество заказов;
- максимальное количество строк;
- максимальное количество паллет;
- стратегия пополнения;
- стратегия отбора;
- разрешать частичную волну;
- разрешать запуск с некритическим дефицитом;
- активность настройки.

По умолчанию:

```text
MAX_CUSTOMERS_PER_WAVE = 30
REPLENISHMENT_STRATEGY = TO_WAVE_DEMAND
PICK_STRATEGY = FEFO
ALLOW_PARTIAL_WAVE = 1
```

Изменение настроек должно писаться в audit log.

## 8. Требования К UX

Интерфейс должен быть рабочим инструментом диспетчера склада.

Обязательные UX-правила:

- важные действия требуют подтверждения;
- запуск волны показывает итог до выполнения;
- отмена требует причину;
- освобождение резервов требует причину;
- ошибки показываются рядом с объектом, а не только общим текстом;
- длинные таблицы должны иметь фиксированную шапку;
- статусы должны быть цветными бейджами;
- критические конфликты должны блокировать запуск;
- некритические предупреждения должны позволять запуск только при наличии права;
- действия должны быть недоступны, если статус волны не позволяет их выполнить.

Нельзя:

- прятать дефицит;
- запускать волну одной кнопкой без preview;
- показывать управление волнами на главной странице;
- давать пользователю кнопку, которая все равно завершится ошибкой из-за статуса или прав;
- делать права на фронте без проверки на backend.

## 9. Аудит И Диагностика

Каждое действие должно писать:

- пользователя;
- действие;
- исходный статус;
- новый статус;
- входные параметры;
- результат;
- ошибку;
- дату и время.

Особенно важно логировать:

- расчет preview;
- запуск волны;
- создание жестких резервов;
- ошибки резервирования;
- создание задач пополнения;
- создание задач отбора;
- отмену волны;
- освобождение резервов;
- изменение настроек.

В карточке волны должен быть виден audit trail.

## 10. Ошибки И Сообщения Оператору

Сообщения должны быть понятными:

- `Заказ уже находится в активной волне`;
- `Превышен лимит клиентов в волне`;
- `Не указаны ворота отгрузки`;
- `Нет свободного паллета для пополнения`;
- `Паллет уже зарезервирован другой волной`;
- `Партия не подходит по сроку годности клиента`;
- `Партия еще не разрешена к отгрузке`;
- `Нельзя отменить волну, так как задачи уже начаты`;
- `Резерв освобожден`;
- `Волна успешно запущена`.

Для системных ошибок показывать короткое сообщение оператору и деталь в audit log.

## 11. MVP Scope

В MVP админки нужно сделать:

1. Отдельную страницу `wave-picking.html`.
2. Пункт меню `Комплектация -> Волны сборки`.
3. Проверку прав через legacy rights.
4. Реестр волн с фильтрами.
5. Диалог `Запуск волны`.
6. Список открытых заказов.
7. Preview волны.
8. Запуск волны.
9. Карточку волны.
10. Просмотр заказов и строк волны.
11. Просмотр резервов.
12. Просмотр задач пополнения.
13. Просмотр задач отбора.
14. Просмотр дефицитов.
15. Отмену волны до старта физических задач.
16. Освобождение резервов по праву.
17. Настройки волн.
18. Audit log в карточке волны.

## 12. Не В MVP

На первом этапе не делать:

- drag-and-drop планирование волн;
- карту склада;
- live tracking исполнителей;
- мобильное исполнение задач;
- голосовой отбор;
- автоматическое ML-разбиение заказов на волны;
- сложную оптимизацию маршрута комплектовщика;
- автоматическое восстановление уже начатой волны после физического сбоя.

## 13. Smoke-Тесты

Минимальные проверки:

1. Пользователь без `PICK_WAVE_VIEW` не видит страницу.
2. Пользователь с `PICK_WAVE_VIEW` видит реестр.
3. Пользователь без `PICK_WAVE_LAUNCH` не видит кнопку запуска.
4. Диалог показывает открытые заказы.
5. Preview считается без создания жестких резервов.
6. Запуск волны создает жесткие резервы.
7. Повторный запуск другой волны не может взять тот же паллет.
8. Отмена до старта задач освобождает резервы.
9. Отмена после старта задач блокируется.
10. Дефицит отображается в карточке волны.
11. Все изменяющие действия записаны в audit log.

## 14. Definition Of Done

Админский блок считается готовым для MVP, когда:

- есть отдельная страница управления волнами;
- права работают через legacy rights;
- оператор может выбрать открытые заказы и рассчитать preview;
- preview показывает мягкую потребность, кандидатов, пополнения, задачи, дефициты и конфликты;
- запуск волны создает жесткие резервы;
- другие волны не могут забрать зарезервированный товар;
- задачи пополнения и отбора видны в карточке волны;
- отмена волны корректно освобождает резервы до старта физических задач;
- действия пишутся в audit log;
- страница соответствует визуальному стилю WMS PRO admin UI;
- API smoke проходит;
- Oracle invalid objects = `0`;
- изменения описаны в wiki.
