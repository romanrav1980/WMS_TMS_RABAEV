# NIKORA: двойной контроль, осмотр и вес

Дата: 15.09.2026. Проект требований; UI-05/06 из [[requirements/nikora_ui_workplaces_tz]]. Подспринты F2.4/F2.5, архитектурный инкремент A2.Q из [[roadmap/nikora_ui_subsprints]].

## 1. Смысл операции

«Дважды перепикать» означает **два независимых прохода сканирования физических товаров**, а не два скана одного SSCC. Правило включается по складу/потоку/категории. Один контроллер может выполнить оба прохода; требование другого сотрудника — отдельная согласованная политика. При secondOperatorRequired тот же пользователь не может начать проход 2.

Сборка закрывает фактический assembly. ERP ORDER_ASSEMBLED содержит фактическую полноту, qualityStatus и readyToShip; «собрано» не означает «контроль пройден». Готовность к погрузке проверяется сервером отдельно.

## 2. Экран: один пост, без хождения по меню

Верх: идентификатор HU, магазин, версия состава, задание, оператор. Полоса этапов: «Проход 1 / Проход 2 / Осмотр / Вес / Итог». В центре один активный ввод сканера и текущий результат; снизу одна главная команда. Предыдущие результаты скрыты до завершения второго прохода, но номер прохода и число его сканов видны.

| Шаг | Что видно | Действие и результат |
|---|---|---|
| Открытие | HU, магазин, пломба, состояние, версия | Скан HU получает/возобновляет сессию; занятый другим оператором не перехватывается |
| Проход 1 | Текущие сканы и единицы этого прохода, не плановая подсказка количества | Скан товара/серии/партии, физический пересчёт; завершить с подтверждением окончания |
| Проход 2 | Пустой независимый список и собственный счётчик; проход 1 и эталон скрыты | Повторный физический пересчёт, затем завершить |
| Сравнение | Ожидание / проход 1 / проход 2 / разница по SKU/партии/UoM | Совпало → осмотр; нет → HOLD с заданием на разбор |
| Осмотр | Упаковка/целостность/срок/температура, если требуется профилем | Зафиксировать результат, причину/фото при дефекте |
| Вес | Брутто, тара, нетто, ожидаемая масса, допуск, устройство, стабильность | Получить стабильное измерение; годное → итог, негодное/нет данных → HOLD |
| Итог | Все результаты, версия правил, авторы, readyToShip | Закрыть сессию; повтор не создаёт второй допуск |

Для каждого скана хранить scanId, deviceId, локальную последовательность, время устройства и приёма сервером, passageId, идентификатор товара/партии/серии, количество/UoM, actor. Повтор транспортной доставки одного scanId безопасен. Повтор того же GTIN **не является дублем сам по себе**: две физические единицы одного артикула имеют одинаковый код. Защита от дребезга сканера не должна уничтожать легитимный повтор.

Корректировка ошибочного скана — сторно с причиной в открытом проходе, не удаление истории. Закрытый проход не редактируется. Разбор расхождения создаёт новую ревизию/повторную контрольную сессию. Сравнение идёт по номенклатуре/партии/единицам, а не только общему числу сканов.

## 3. Весовая проверка

- Ожидаемый net: сумма подтверждённого содержимого по доступной весовой модели. Для catch-weight используется фактическая масса партии/единицы, а не постоянный перевод PCE→KGM.
- Показывать gross, tare, net = gross − tare и источник тары: взвешено/справочник/подтверждённое значение. Нельзя применять выдуманную или отрицательную тару.
- Допуск задаётся версией правила: абсолютный/относительный и правило их сочетания, класс груза/упаковки, точность весов. Универсальный процент не устанавливается этим ТЗ.
- deviceId, модель/единица, пригодность/срок проверки, measurementId, measuredAt, stableFlag, предел измерения. Нестабильный, просроченный, перегруженный или неизвестный прибор не даёт автоматического допуска.
- Ручная масса разрешается только отдельной политикой/правом и помечается manual с причиной; она не выдаётся за телеметрию весов. Нет весов — ожидание/передача на другой пост, а не «ноль кг».
- Контроль нетто не заменяет проверку максимального gross для транспорта.
- Пример только для макета: expected 12,000 кг, допуск ±0,150 кг, gross 12,860, tare 0,800 → net 12,060 — годно. Gross 13,400 → net 12,600 — блокировка. Производственные параметры утверждает владелец качества.

## 4. Версия состава и отгрузка

Состояния сессии: NEW → PASS1 → PASS2 → INSPECTION → WEIGH → PASSED либо HOLD. ABORTED не равен PASSED. Политика может освобождать категорию от конкретной проверки только явно, с сохранением версии политики и причины «не требуется».

Результат связан с HU+contentVersion и набором правил. Repack/смена состава инвалидируют прежний допуск для изменённого HU. При seam-split неизменные дочерние единицы сохраняют историю, но политика должна заново определить пригодность; не копировать PASS родителя всем детям. Loaded HU менять нельзя. Сервер погрузки и auto-release проверяет актуальность допуска, а не UI-checkbox.

Агрегирование уже проверенных закрытых детей может наследовать проверку содержимого только по утверждённому правилу неизменности; упаковка/масса нового родителя проверяется отдельно. До утверждения правила новый HU требует контроль, без молчаливого наследования.

## 5. Приёмка Q-UI

1. Q-01: два прохода совпали по SKU/партии/UoM, осмотр и вес пройдены → один допуск.
2. Q-02: одинаковая общая сумма, но разные SKU → HOLD; погрузка и auto-release запрещены.
3. Q-03: во втором проходе невозможно получить результат первого через обычный UI/API этой роли.
4. Q-04: повтор scanId после обрыва не удваивает; два разных scanId одного GTIN учитываются как две единицы.
5. Q-05: второй оператор обязателен только по политике; обход через новую сессию запрещён.
6. Q-06: стабильный вес в допуске проходит, за границей/без стабильности/просроченный прибор/отрицательная тара блокируют.
7. Q-07: пропала связь с весами или backend → явное ожидание, не ложный зелёный результат.
8. Q-08: изменение состава после проверки делает допуск устаревшим; конкурентная погрузка видит актуальную версию.
9. Q-09: две параллельные сессии/повтор завершения не создают разные действующие допуски.
10. Q-10: внешний WMS-факт контроля принимается только от разрешённого источника по согласованному профилю, с contentVersion и доказательством; иначе контроль нужен на целевой площадке.
11. Q-11: телефон 360 px, аппаратный сканер, RU/KA, ошибки и восстановление сессии; один активный ввод.
12. Q-12: ORDER_ASSEMBLED сохраняется как факт сборки при HOLD, readyToShip=false; «в пути» не возникает.

## 6. Архитектурная граница

Переиспользовать задания, операторские сессии, события сканирования и локальный журнал WMS. Добавить только недостающие устойчивые факты: QualitySession, два ScanPass со scan facts, InspectionResult, WeightMeasurement и версионируемое решение допуска. Это логические объекты, не требование пяти новых таблиц. До миграции проверить существующий lot-check и события CASE_PICK на достаточность; один флаг «контроль» не хранит независимые проходы/измерения и недостаточен. Не вводить новую WMS/ERP/систему учёта остатков.
