## Общие правила реализации
- Минимум 80% усилий — функционал. Только необходимые адресные проверки, затем обязательный существующий gate перед заявлением готовности; без повторных полных прогонов без причины.
- Рабочая база — существующая RABAEV/ORCL. Для этих параллельных заданий Oracle DDL/DML, seed и запуск фабрик данных не нужны. Не создавать копию базы, схему NICORA или второй Oracle.
- Не редактировать занятые Codex файлы, общие styles/auth/layout/router и канонический план без согласования. Нужный общий patch описать отдельно.
- Сохранять чужие изменения. Не выполнять reset/clean/checkout, массовое форматирование или перемещение проекта.
- Не перезапускать общие serv.bat/front.bat/terminal.bat без координации: они очищают порты.
- Не выполнять commit/push/fetch/PR в рамках этого handoff. Финальная публикация — отдельный согласованный шаг владельца общей поставки. SAP/SAP_INTEGRATION исключены из публикации.
- Не сохранять пароли, токены и уникальные государственные коды в отчётах/скриншотах.
- В идентификаторах паллет разрешены SSCC и внутренние/legacy значения.
- Карантин определяется недоступностью ячеек. Не добавлять независимый флаг, меняющий доступность иначе.
- Источник остатков — единое ядро; UI не вычисляет и не проводит свой баланс.
- При количественном действии серверный успех обязателен; ошибки соединения и подтверждённый отказ различаются.
- Если отсутствует API, не выдавать мок за реализованную функцию. Подготовить контракт, а независимые UI-части закончить.
