## 1. Назначение

Модуль `Комплектация / Picking Planning` отвечает за планирование комплектации заказов клиентов.

Главная задача модуля: выбрать партии, паллеты и зоны отбора под конкретный заказ клиента с учетом:

- клиента;
- маршрута;
- ворот отгрузки;
- срока годности;
- вылежки партии;
- FEFO/FIFO;
- маркировки и агрегации;
- клиентских правил;
- топологии склада;
- полнопалетного и покоробочного отбора.

Важно: модуль не должен жестко блокировать старые WMS-остатки. Он должен формировать план комплектации, который учитывает готовность партии, но не запрещает физические операции старого WMS.

## 2. Ключевой Архитектурный Принцип

`IS_SHIPMENT_ALLOWED` из `RRL_PROD_BATCH_READY_V` не является запретом на уровне WMS.

Это критерий для алгоритма планирования комплектации.

Правильное разделение:

- WMS хранит физические остатки, паллеты, ячейки и движения.
- MES/Traceability хранит партии, вылежку, качество, маркировку и прослеживаемость.
- Picking Planning выбирает, какие партии и паллеты назначить в комплектацию заказа клиента.

## 3. Границы Модуля

Модуль отвечает за:

- ведение канонического заказа клиента для планирования;
- связь legacy-заказа WMS с новым заказом клиента;
- просмотр исполнения заказа клиента по факту комплектации и отгрузки;
- планирование комплектации заказа клиента;
- разделение заказа на полнопалетный и покоробочный отбор;
- выбор партий и паллет по FEFO/FIFO;
- учет ограничений клиента по сроку годности;
- учет клиентского норматива укладки;
- учет готовности партии к отгрузке;
- учет маршрута и ворот отгрузки;
- учет порядка обхода ячеек отбора;
- формирование задач на отбор;
- объяснимость решения: почему выбрана партия/паллет/ячейка.

Модуль не отвечает за:

- физическое изменение остатков;
- прямое списание товара;
- регистрацию выпуска продукции;
- оформление Меркурия;
- ввод/вывод кодов Честного Знака;
- фактическое сканирование терминалом;
- волну пополнения динамических ячеек.

Эти процессы должны вызываться после или рядом с планом комплектации.

## 4. Основные Термины

- `Customer Order`: заказ клиента.
- `Customer Registry`: реестр клиентов. В legacy-контуре клиент по умолчанию соответствует магазину/адресу доставки.
- `Store`: магазин или точка доставки из старой WMS-модели.
- `Fulfillment Fact`: фактическое исполнение заказа, то есть что реально было скомплектовано и отгружено.
- `Picking Plan`: рассчитанный план комплектации.
- `Picking Wave`: группа заказов/строк, объединенных для выполнения.
- `Full Pallet Picking`: отбор целого паллета рич-траком.
- `Case Picking`: покоробочный отбор из ячеек отбора.
- `Pick Face`: регулярная ячейка отбора.
- `Dynamic Pick Face`: временная ячейка отбора, создаваемая под волну или операционную ситуацию.
- `Pick Route`: порядок обхода ячеек комплектовщиком.
- `FEFO`: first expired, first out.
- `FIFO`: first in, first out.
- `Shipment Readiness`: пригодность партии для назначения в комплектацию.

## 5. Бизнес-Правила

### 5.1. Комплектация Всегда В Разрезе Клиента

Планирование начинается не с товара и не со склада, а с заказа клиента.

Система должна знать:

- клиента;
- заказ;
- дату отгрузки;
- маршрут;
- ворота отгрузки;
- склад/зону отгрузки;
- строки заказа;
- клиентские ограничения.

План комплектации должен быть привязан к клиенту и заказу.

### 5.1.1. Legacy-Контекст: Магазин Как Клиент

В текущей Oracle-схеме legacy WMS нет отдельной явной таблицы `STORE` или `SHOP`.

Проверенные факты по живой схеме:

- клиентские заказы хранятся в `RRL_ORDERS`;
- строки заказа хранятся в `RRL_ORDER_ROWS`;
- адрес/магазин заказа хранится в `RRL_ORDERS.ADDR`;
- в текущих данных `RRL_ORDERS` около 320 уникальных значений `ADDR`;
- факт сборки хранится в `RRL_SBORKA_PALLETS` и `RRL_SBORKA_PALLET_ROWS`;
- в `RRL_SBORKA_PALLETS` также есть `ADDR`, `ST_NUMBER`, `ORIGINAL_ORDER_NUMBER`, `NAKLAD_NUMBER`;
- новый справочник регуляторных профилей клиентов уже существует как `RRL_CLIENT_REG_PROFILE`.

Архитектурное решение:

- в новом контуре должен быть отдельный реестр клиентов;
- для совместимости с legacy клиент по умолчанию совпадает с магазином/адресом из `RRL_ORDERS.ADDR`;
- `RRL_CLIENT_REG_PROFILE` можно использовать как начальный профиль клиента для Меркурия/Честного Знака, но для комплектации нужен расширенный customer registry;
- нужен bridge/mapping между legacy `ADDR` и новым `CUSTOMER_ID`;
- если отдельного клиента еще нет, система может создать customer draft из legacy `ADDR`.

Минимальная логика идентификации:

```text
legacy_store_key = normalize(RRL_ORDERS.ADDR)
customer_id = mapping(legacy_store_key) или legacy_store_key
```

В дальнейшем один клиент может объединять несколько магазинов, а один магазин может иметь отдельные правила по срокам годности, укладке, маршруту и маркировке.

### 5.1.2. Данные И Требования Клиента

Клиент должен быть отдельной сущностью, а не только строкой адреса из заказа.

У клиента и его точек доставки должны храниться:

- код клиента;
- наименование;
- адрес;
- юридические реквизиты;
- GLN/EDI-идентификаторы;
- признак сети или отдельного магазина;
- требования к сроку годности;
- требования к укладке по отдельным продуктам;
- требования к возможности комплектовать товар сверху на паллет;
- требования к типу и емкости машины;
- правило деления заказа на несколько машин.

Требования клиента могут быть:

- общими для клиента;
- отдельными для магазина/точки доставки;
- отдельными для артикула;
- отдельными для группы товаров;
- временными, с периодом действия.

Если специального правила нет, применяется системное правило по умолчанию из карточки товара и стандартного типа машины.

### 5.2. Маршрут И Ворота Известны До Комплектации

Перед расчетом плана комплектации система должна понимать, куда физически будет собираться заказ.

Минимальные данные:

- `route_id`;
- `route_no`;
- `shipment_date`;
- `dock_id`;
- `dock_code`;
- `staging_zone`;
- при необходимости `truck_id` или `vehicle_no`.

Это нужно для того, чтобы:

- полные паллеты сразу спускались в правильную зону;
- покоробочный отбор собирался под правильные ворота;
- несколько клиентов одного маршрута не смешивались без правил;
- позже можно было строить wave picking.

### 5.3. Ограничения Клиента По Сроку Годности

У клиента может быть ограничение по сроку годности:

- в днях: клиент принимает товар, если до окончания срока годности осталось не меньше `N` дней;
- в процентах: клиент принимает товар, если осталось не меньше `N%` от полного срока годности;
- по конкретному артикулу;
- по группе товаров;
- по умолчанию для клиента.

Пример:

- срок годности товара 180 дней;
- клиент принимает не менее 70%;
- значит на дату отгрузки должно оставаться не менее 126 дней.

Если правило задано и партия ему не соответствует, партия не должна попадать в план комплектации для этого клиента.

### 5.4. Норматив Укладки Может Отличаться По Клиенту

В карточке товара есть базовый норматив укладки.

Но для части клиентов норматив может отличаться:

- коробов на паллете;
- слоев на паллете;
- коробов в слое;
- максимальная высота;
- допустимый тип паллета;
- весовое ограничение.

Для планирования нужно использовать клиентский норматив, если он задан. Если не задан, используется норматив из карточки товара.

Для отдельных продуктов и клиентов также нужно хранить признак, можно ли комплектовать товар сверху на уже собранный поддон.

Пример:

- тяжелые коробки нельзя ставить сверху на легкие;
- мягкую упаковку нельзя ставить под тяжелый товар;
- некоторые продукты клиент разрешает докладывать сверху;
- некоторые продукты должны ехать только отдельным паллетом.

Эти правила должны учитываться при формировании контейнеров покоробочного отбора и при делении заказа на паллеты.

### 5.4.1. Типы Машин И Емкость Заказа

У клиента могут быть требования к типу машины и максимальной емкости отгрузки.

Примеры:

- фура: 33 паллета;
- 10-тонник: емкость задается отдельно;
- малотоннажная машина: емкость задается отдельно;
- клиент разрешает только определенный тип машины;
- клиент требует делить заказ, если он превышает емкость машины.

Если заказ клиента после расчета комплектации превышает допустимую емкость машины, система должна разделить заказ на несколько shipment parts.

Пример:

```text
Заказ клиента: 80 паллет.
Тип машины: фура.
Емкость фуры: 33 паллета.

Система должна сформировать минимум 3 части:
1. 33 паллета;
2. 33 паллета;
3. 14 паллет.
```

Правило деления должно учитывать:

- максимальное количество паллет;
- максимальный вес;
- максимальный объем;
- тип машины;
- маршрут;
- ворота;
- совместимость товаров;
- требования клиента.

### 5.5. Сначала Полнопалетный Отбор

Для каждой строки заказа система должна сначала рассчитать объем, который можно закрыть полными паллетами.

Пример:

- заказ: 200 коробов;
- норматив: 60 коробов на паллете;
- сначала планируются 3 полных паллета по 60 коробов;
- остаток 20 коробов идет в покоробочный отбор.

Полнопалетный отбор означает:

- выбрать целый паллет;
- назначить задачу рич-траку;
- переместить паллет в зону отгрузки или staging-зону ворот;
- не вскрывать паллет;
- сохранить связь с партией, SSCC и агрегацией.

### 5.6. Потом Покоробочный Отбор

Остаток после полнопалетного отбора должен планироваться как покоробочный отбор.

Покоробочный отбор должен:

- идти из ячеек отбора;
- учитывать порядок обхода;
- укладываться в тару/поддон комплектовщика;
- учитывать ограничения по весу;
- учитывать ограничения по объему;
- не превышать клиентские нормативы укладки;
- при необходимости создавать несколько picking containers.

### 5.7. Вес И Объем Для Покоробочного Отбора

Для поддонов или контейнеров покоробочного отбора должны быть ограничения:

- максимальный вес;
- максимальный объем;
- максимальная высота;
- максимальное количество коробов;
- допустимые группы совместимости.

Система должна останавливать заполнение текущего контейнера, когда раньше наступает одно из ограничений:

- достигнут максимальный вес;
- достигнут максимальный объем;
- достигнута максимальная высота;
- нарушается правило совместимости;
- закончилась текущая группа маршрута обхода.

После этого создается следующий контейнер.

### 5.8. Порядок Отбора

Порядок отбора - это последовательность ячеек, которую проходит комплектовщик.

Порядок может быть:

- линейный;
- Z-образный;
- ручной;
- по зонам;
- по приоритету товара;
- смешанный.

Должна быть отдельная таблица настройки порядка отбора по складу.

Минимальные параметры:

- склад;
- зона;
- ряд;
- секция;
- уровень;
- ячейка;
- номер последовательности;
- направление;
- активность;
- тип маршрута.

Алгоритм покоробочного отбора должен сортировать задачи по этому порядку.

### 5.9. Несколько Ячеек Отбора Для Одного SKU

Один SKU может иметь:

- одну регулярную ячейку отбора;
- несколько регулярных ячеек отбора;
- динамические ячейки отбора;
- резервные ячейки хранения;
- ячейки пополнения.

В MVP нужно учитывать регулярные ячейки отбора и признак динамической ячейки.

Логика динамических ячеек будет детально проектироваться отдельно в модуле волн и пополнения.

### 5.10. FEFO/FIFO

Для готовой продукции базовым правилом должен быть FEFO.

Если срок годности отсутствует или для товара задан другой режим, допускается FIFO.

При выборе партии:

1. Отфильтровать партии по клиентским ограничениям.
2. Отфильтровать партии по готовности для комплектации.
3. Отфильтровать партии по маркировке/агрегации, если это требуется клиенту.
4. Отсортировать:
   - FEFO: по ближайшей дате истечения срока годности;
   - FIFO: по дате поступления/выпуска.
5. Выбрать полные паллеты.
6. Выбрать остаток для покоробочного отбора.

### 5.11. Маркировка И Агрегация

Для товаров с Честным Знаком система должна учитывать:

- наличие DataMatrix;
- статус кодов;
- привязку кодов к партии;
- агрегацию короб/паллет;
- SSCC;
- принимает ли клиент агрегацию;
- можно ли отгружать без передачи кодов клиенту;
- нужен ли полный состав паллета.

Если клиент принимает агрегацию, предпочтение должно отдаваться паллетам с корректным SSCC и закрытой агрегацией.

Если клиент не принимает агрегацию, модуль должен планировать передачу кодов на уровне, который нужен клиенту.

### 5.12. Меркурий

Для продукции или сырья, где требуется ветеринарная прослеживаемость, план комплектации должен видеть:

- связанную производственную партию;
- сырьевые ВСД;
- статус оформления партии;
- возможность оформить или передать ВСД на клиента.

В MVP достаточно заложить поля и проверки статуса. Реальная интеграция идет через Mercury Connector.

### 5.13. Резервирование Остатков

В модуле комплектации нужно различать два вида резерва:

- мягкий резерв - это потребность заказа без конкретной партии, паллеты и ячейки. Он нужен для планирования, прогноза дефицита и диспетчеризации, но не занимает WMS-остаток;
- жесткий резерв - это резерв на конкретную партию, паллету, ячейку и количество. Только он исключает физический остаток из следующих назначений.

WMS занимается жестким резервом. Поэтому резерв, который влияет на доступный остаток, обязан иметь конкретный `UID_PALLET` или конкретную ячейку/партию/количество для покоробочного отбора.

При предварительном расчете плана комплектации система может создавать мягкую потребность. При подтверждении плана к исполнению система должна создать жесткие резервы на выбранные остатки.

Цель жесткого резервирования: исключить двойное назначение одного и того же поддона или одной и той же части поддона в несколько заказов клиентов.

Правила:

- если полнопалетный отбор зарезервировал `UID_PALLET`, этот поддон не может быть зарезервирован другим активным планом комплектации;
- если покоробочный отбор зарезервировал часть поддона, следующему плану доступен только незарезервированный остаток;
- мягкая потребность может быть создана в момент расчета picking plan;
- жесткий резерв создается в момент подтверждения/публикации picking plan к исполнению;
- расчет-кандидат может быть выполнен без жесткого резерва, но опубликованный план обязан создать жесткий резерв;
- резерв должен иметь статус;
- активными считаются резервы в статусах `ACTIVE`, `ALLOCATED`, `PICKING`;
- при отмене плана резерв должен освобождаться;
- при завершении отбора резерв должен переходить в `CONSUMED`;
- при ошибке пересчета резерв должен оставаться видимым для диагностики, а не пропадать молча.

Резервирование не должно напрямую менять старые WMS-остатки. Жесткий резерв является WMS-уровнем занятости остатка и уменьшает доступное количество для следующих планов комплектации. Мягкая потребность не уменьшает доступный физический остаток.

Для доступного количества нужно считать:

```text
available_for_planning = physical_available_qty - active_hard_reserved_qty
```

Для полнопалетного отбора:

```text
active_hard_reserved_qty > 0 по UID_PALLET означает, что паллет уже занят.
```

Для покоробочного отбора:

```text
можно создавать жесткий резерв частично, но сумма активных жестких резервов по UID_PALLET / ячейке / артикулу не должна превышать доступный физический остаток.
```

Желательно использовать транзакционный расчет с блокировкой строк-кандидатов или проверкой уникальных ограничений, чтобы два параллельных планировщика не смогли одновременно зарезервировать один и тот же паллет.

### 5.14. Частичная Комплектация При Нехватке Свободного Остатка

При запуске задачи на комплектацию система должна проверять свободный остаток.

Свободный остаток - это физический остаток за вычетом активных жестких резервов:

```text
free_qty = physical_available_qty - active_hard_reserved_qty
```

Если свободного остатка полностью хватает на строку заказа, система формирует обычные задачи комплектации.

Если свободного остатка не хватает полностью, система должна:

- сформировать задачи комплектации только на доступный свободный объем;
- создать план в режиме частичной комплектации;
- зарезервировать только реально доступное количество;
- не пытаться резервировать отсутствующий товар;
- записать в протокол, какого товара не хватило;
- указать заказанное количество;
- указать свободное количество;
- указать зарезервированное количество;
- указать недостающее количество;
- указать причину, если она известна: нет физического остатка, остаток уже зарезервирован, партия не прошла правила клиента, партия на вылежке, нет подходящей маркировки, нет pick face.

Частичная комплектация не должна скрывать дефицит. План может быть выпущен только по доступной части, а недостающая часть должна оставаться видимой для диспетчера комплектации.

Статусы плана должны поддерживать минимум:

- `PLANNED_FULL`: заказ обеспечен полностью;
- `PLANNED_PARTIAL`: заказ обеспечен частично;
- `NO_STOCK`: по заказу не удалось назначить ни одной позиции;
- `CANCELLED`: план отменен.

Пример:

```text
Заказ: 200 коробов.
Физически на складе: 180 коробов.
Активные резервы других заказов: 60 коробов.
Свободно для планирования: 120 коробов.

План создается на 120 коробов.
В протокол дефицита пишется: не хватает 80 коробов.
```

### 5.15. Исполнение Заказа Клиента

Помимо плана комплектации система должна хранить факт исполнения заказа клиента.

План - это намерение:

- что система планирует собрать;
- какие партии и паллеты зарезервированы;
- какой объем должен быть отобран.

Факт исполнения - это результат:

- что реально скомплектовано;
- какие паллеты реально ушли;
- какие коробки реально отобраны;
- какие DataMatrix/SSCC реально переданы;
- какая часть заказа осталась не исполненной;
- какие расхождения возникли.

Для каждого заказа клиента должен быть отдельный экран/реестр исполнения:

- заказано;
- запланировано;
- зарезервировано;
- скомплектовано;
- отгружено;
- не хватает;
- заменено;
- отменено;
- расхождения по количеству;
- расхождения по партии, сроку годности или маркировке.

Legacy-факт сборки должен читаться из:

- `RRL_SBORKA_PALLETS`;
- `RRL_SBORKA_PALLET_ROWS`;
- `ORDER_AUDIT`;
- `ORDER_AUDIT_ERROR_LINES`.

Новый модуль должен не ломать legacy-факт, а строить рядом каноническое представление исполнения заказа клиента.

## 7. Алгоритм Планирования

Для каждого заказа клиента:

1. Получить или создать канонический `RRL_CUSTOMER_ORDER` из legacy `RRL_ORDERS`.
2. Определить клиента через `RRL_CUSTOMER_STORE_MAP` или legacy `RRL_ORDERS.ADDR`.
3. Проверить, что заказ имеет клиента, маршрут и ворота.
4. Загрузить клиентские правила по сроку годности, укладке, маркировке и агрегации.
5. Загрузить требования клиента к типу машины и емкости.
6. Для каждой строки заказа:
   - определить норматив коробов на паллете;
   - рассчитать количество полных паллет;
   - рассчитать остаток для покоробочного отбора.
7. Найти доступные партии и паллеты.
8. Исключить партии, которые не подходят под правила клиента.
9. Учесть `IS_SHIPMENT_ALLOWED` как критерий планирования, а не как WMS-блокировку.
10. Отсортировать кандидатов по FEFO/FIFO.
11. Рассчитать физический доступный остаток.
12. Вычесть активные резервы из доступного количества.
13. Получить свободный остаток для планирования.
14. Если свободного остатка не хватает, рассчитать доступную часть и дефицит.
15. Назначить полные паллеты на доступную часть.
16. Назначить покоробочный отбор из pick face ячеек на доступный остаток.
17. Разбить покоробочный отбор по контейнерам с учетом веса, объема и правил укладки.
18. Если заказ превышает емкость машины, разбить его на `RRL_SHIPMENT_PART`.
19. Отсортировать задачи по порядку обхода ячеек.
20. Создать план комплектации, задачи и резервы только на доступный свободный объем.
21. Проверить, что резервы не конфликтуют с уже активными резервами.
22. Записать shortage-протокол по недостающим позициям.
23. Проставить статус плана и заказа `PLANNED_FULL`, `PLANNED_PARTIAL` или `NO_STOCK`.
24. Сохранить объяснение выбора.

1. Таблицы клиентских правил.
2. Реестр клиентов с legacy-маппингом `RRL_ORDERS.ADDR`.
3. Канонический заказ клиента и строки заказа.
4. Факт исполнения заказа клиента.
5. Требования клиента по сроку годности.
6. Требования клиента по укладке отдельных продуктов.
7. Типы машин и требования клиента по емкости машины.
8. Деление заказа на части при превышении емкости машины.
9. Таблицы порядка отбора.
10. Таблицы pick face.
11. Таблицы плана комплектации и задач.
12. Расчет полнопалетного отбора.
13. Расчет покоробочного остатка.
14. FEFO/FIFO выбор партии.
15. Учет `IS_SHIPMENT_ALLOWED`.
16. Учет минимального срока годности клиента.
17. Учет клиентского норматива коробов на паллете.
18. Привязку плана к клиенту, маршруту и воротам.
19. Резервирование полного паллета.
20. Частичное резервирование для покоробочного отбора.
21. Освобождение резерва при отмене плана.
22. Исключение активных резервов из следующих расчетов.
23. Проверку свободного остатка с учетом резервов.
24. Частичную комплектацию при нехватке свободного остатка.
25. Протокол дефицита по строкам заказа.
26. API для расчета и просмотра плана.
27. API/экран исполнения заказа клиента.
28. Raw admin page для просмотра плана.

## 10. Не В MVP

На первом этапе не реализовывать:

- полноценный wave picking;
- автоматическое пополнение dynamic pick face;
- оптимизацию маршрута в реальном времени;
- мобильное исполнение задач терминалом;
- печать листов отбора;
- фактическое сканирование DataMatrix;
- оформление ВСД;
- передачу кодов клиенту.

Эти блоки должны быть следующими инкрементами.

## 11. Edge Cases

Нужно предусмотреть:

- заказ меньше одной паллеты;
- legacy-заказ имеет `ADDR`, но клиента в новом реестре еще нет;
- один клиент объединяет несколько магазинов/адресов;
- один магазин требует индивидуальные правила комплектации;
- клиент требует индивидуальную укладку для одного артикула;
- товар можно комплектовать сверху только для части клиентов;
- товар должен ехать отдельным паллетом;
- заказ превышает 33 паллета и должен быть разделен на несколько фур;
- клиент разрешает только 10-тонник, и емкость меньше стандартной фуры;
- по весу машина заполнена раньше, чем по паллетам;
- по объему машина заполнена раньше, чем по паллетам;
- факт сборки есть в `RRL_SBORKA_PALLETS`, но нового fulfillment еще нет;
- заказ частично скомплектован в legacy до запуска нового планирования;
- заказ ровно кратен паллете;
- несколько партий подходят под один заказ;
- партия готова физически, но не подходит по сроку годности клиента;
- партия еще на вылежке;
- паллет подходит по партии, но не подходит по агрегации;
- клиентский норматив укладки меньше стандартного;
- не хватает полных паллет;
- не хватает товара в pick face;
- SKU имеет несколько pick face;
- pick face динамический и требует пополнения;
- нет маршрута или ворот;
- товар есть на складе, но нет подходящей партии по правилам клиента;
- физический остаток есть, но весь он уже зарезервирован под другие планы;
- свободного остатка хватает только на часть строки заказа;
- по заказу не удалось назначить ни одной позиции, но нужно показать полный дефицит;
- конфликт FEFO и клиентского правила срока годности;
- заказ смешивает товары с разными требованиями маркировки;
- два планировщика одновременно пытаются зарезервировать один паллет;
- первый заказ зарезервировал часть поддона, второй может взять только остаток;
- план отменен, но резерв не освободился;
- отбор завершен, но резерв остался активным;
- физический остаток изменился после создания резерва;
- резерв создан на паллет, который позже переместили в другую ячейку.

## 12. Definition Of Done

Модуль считается готовым для MVP, когда:

- заказ клиента можно рассчитать в picking plan;
- заказ клиента виден как отдельный объект с привязкой к legacy `RRL_ORDERS`;
- реестр клиентов поддерживает режим совместимости, где клиент по умолчанию является магазином из `RRL_ORDERS.ADDR`;
- факт исполнения заказа клиента виден отдельно от плана;
- у клиента можно настроить адреса, срок годности, укладку продуктов и типы машин;
- план делит заказ на части, если заказ превышает емкость машины клиента;
- план разделен на full pallet и case picking;
- план учитывает клиента, маршрут и ворота;
- план учитывает срок годности в днях или процентах;
- план учитывает клиентский норматив укладки;
- план учитывает `IS_SHIPMENT_ALLOWED`, но не блокирует WMS-остатки;
- план создает резервы на полные паллеты и покоробочный остаток;
- последующий план не может использовать уже зарезервированную часть остатка;
- отмена плана освобождает активные резервы;
- если свободного остатка не хватает, план создается как частичный;
- по каждой недостающей позиции есть запись в shortage-протоколе;
- shortage-протокол показывает заказанное, физически доступное, уже зарезервированное, свободное и недостающее количество;
- задачи покоробочного отбора отсортированы по порядку ячеек;
- каждая задача имеет объяснение выбора партии/паллеты/ячейки;
- API smoke проверяет минимум один заказ с полнопалетным и покоробочным отбором;
- Oracle invalid objects = `0`;
- изменения описаны в wiki.

## 16. Уточнение модели клиентских правил от 2026-05-17

Транспортные параметры не являются строкой товарного правила комплектации.

Правильная модель:

- тип машины, емкость машины, вес, объем и правило деления по емкости привязаны к адресу доставки клиента;
- один клиент может иметь несколько адресов, и для каждого адреса может быть свой тип машины и своя емкость;
- при планировании заказа система выбирает транспортные ограничения через адрес доставки заказа;
- если у адреса транспорт не задан, допускается fallback на настройку клиента или системный тип по умолчанию.

Товарное правило комплектации должно быть одной строкой по клиенту/адресу/артикулу или группе товаров. В этой строке одновременно хранятся:

- минимальный остаточный срок годности в днях;
- минимальный остаточный срок годности в процентах;
- коробов на паллете;
- коробов в ярусе;
- количество ярусов;
- максимальный вес, объем и высота паллеты;
- разрешение ставить товар сверху;
- требование отдельной паллеты;
- группа совместимости укладки.

Старые раздельные таблицы сроков годности, укладки и машин могут сохраняться как совместимость/исторический слой, но новый UI и новая бизнес-логика должны использовать:

- адрес клиента для транспорта;
- единую строку товарного правила для срока годности и укладки.

На рабочих экранах админки не должны отображаться технические строки с именами прав и локальное поле `API base`.
