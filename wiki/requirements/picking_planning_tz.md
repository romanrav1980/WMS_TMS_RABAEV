## 1. Назначение

Модуль `Комплектация / Picking Planning` отвечает за планирование комплектации заказов клиентов.

Главная задача модуля: выбрать партии, паллеты и зоны отбора под конкретный заказ клиента с учетом:

- клиента;
- маршрута;
- ворот отгрузки;
- срока годности;
- вылежки партии;
- FEFO/FIFO;
- маркировки и агрегации;
- клиентских правил;
- топологии склада;
- полнопалетного и покоробочного отбора.

Важно: модуль не должен жестко блокировать старые WMS-остатки. Он должен формировать план комплектации, который учитывает готовность партии, но не запрещает физические операции старого WMS.

## 2. Ключевой Архитектурный Принцип

`IS_SHIPMENT_ALLOWED` из `RRL_PROD_BATCH_READY_V` не является запретом на уровне WMS.

Это критерий для алгоритма планирования комплектации.

Правильное разделение:

- WMS хранит физические остатки, паллеты, ячейки и движения.
- MES/Traceability хранит партии, вылежку, качество, маркировку и прослеживаемость.
- Picking Planning выбирает, какие партии и паллеты назначить в комплектацию заказа клиента.

## 3. Границы Модуля

Модуль отвечает за:

- планирование комплектации заказа клиента;
- разделение заказа на полнопалетный и покоробочный отбор;
- выбор партий и паллет по FEFO/FIFO;
- учет ограничений клиента по сроку годности;
- учет клиентского норматива укладки;
- учет готовности партии к отгрузке;
- учет маршрута и ворот отгрузки;
- учет порядка обхода ячеек отбора;
- формирование задач на отбор;
- объяснимость решения: почему выбрана партия/паллет/ячейка.

Модуль не отвечает за:

- физическое изменение остатков;
- прямое списание товара;
- регистрацию выпуска продукции;
- оформление Меркурия;
- ввод/вывод кодов Честного Знака;
- фактическое сканирование терминалом;
- волну пополнения динамических ячеек.

Эти процессы должны вызываться после или рядом с планом комплектации.

## 4. Основные Термины

- `Customer Order`: заказ клиента.
- `Picking Plan`: рассчитанный план комплектации.
- `Picking Wave`: группа заказов/строк, объединенных для выполнения.
- `Full Pallet Picking`: отбор целого паллета рич-траком.
- `Case Picking`: покоробочный отбор из ячеек отбора.
- `Pick Face`: регулярная ячейка отбора.
- `Dynamic Pick Face`: временная ячейка отбора, создаваемая под волну или операционную ситуацию.
- `Pick Route`: порядок обхода ячеек комплектовщиком.
- `FEFO`: first expired, first out.
- `FIFO`: first in, first out.
- `Shipment Readiness`: пригодность партии для назначения в комплектацию.

## 5. Бизнес-Правила

### 5.1. Комплектация Всегда В Разрезе Клиента

Планирование начинается не с товара и не со склада, а с заказа клиента.

Система должна знать:

- клиента;
- заказ;
- дату отгрузки;
- маршрут;
- ворота отгрузки;
- склад/зону отгрузки;
- строки заказа;
- клиентские ограничения.

План комплектации должен быть привязан к клиенту и заказу.

### 5.2. Маршрут И Ворота Известны До Комплектации

Перед расчетом плана комплектации система должна понимать, куда физически будет собираться заказ.

Минимальные данные:

- `route_id`;
- `route_no`;
- `shipment_date`;
- `dock_id`;
- `dock_code`;
- `staging_zone`;
- при необходимости `truck_id` или `vehicle_no`.

Это нужно для того, чтобы:

- полные паллеты сразу спускались в правильную зону;
- покоробочный отбор собирался под правильные ворота;
- несколько клиентов одного маршрута не смешивались без правил;
- позже можно было строить wave picking.

### 5.3. Ограничения Клиента По Сроку Годности

У клиента может быть ограничение по сроку годности:

- в днях: клиент принимает товар, если до окончания срока годности осталось не меньше `N` дней;
- в процентах: клиент принимает товар, если осталось не меньше `N%` от полного срока годности;
- по конкретному артикулу;
- по группе товаров;
- по умолчанию для клиента.

Пример:

- срок годности товара 180 дней;
- клиент принимает не менее 70%;
- значит на дату отгрузки должно оставаться не менее 126 дней.

Если правило задано и партия ему не соответствует, партия не должна попадать в план комплектации для этого клиента.

### 5.4. Норматив Укладки Может Отличаться По Клиенту

В карточке товара есть базовый норматив укладки.

Но для части клиентов норматив может отличаться:

- коробов на паллете;
- слоев на паллете;
- коробов в слое;
- максимальная высота;
- допустимый тип паллета;
- весовое ограничение.

Для планирования нужно использовать клиентский норматив, если он задан. Если не задан, используется норматив из карточки товара.

### 5.5. Сначала Полнопалетный Отбор

Для каждой строки заказа система должна сначала рассчитать объем, который можно закрыть полными паллетами.

Пример:

- заказ: 200 коробов;
- норматив: 60 коробов на паллете;
- сначала планируются 3 полных паллета по 60 коробов;
- остаток 20 коробов идет в покоробочный отбор.

Полнопалетный отбор означает:

- выбрать целый паллет;
- назначить задачу рич-траку;
- переместить паллет в зону отгрузки или staging-зону ворот;
- не вскрывать паллет;
- сохранить связь с партией, SSCC и агрегацией.

### 5.6. Потом Покоробочный Отбор

Остаток после полнопалетного отбора должен планироваться как покоробочный отбор.

Покоробочный отбор должен:

- идти из ячеек отбора;
- учитывать порядок обхода;
- укладываться в тару/поддон комплектовщика;
- учитывать ограничения по весу;
- учитывать ограничения по объему;
- не превышать клиентские нормативы укладки;
- при необходимости создавать несколько picking containers.

### 5.7. Вес И Объем Для Покоробочного Отбора

Для поддонов или контейнеров покоробочного отбора должны быть ограничения:

- максимальный вес;
- максимальный объем;
- максимальная высота;
- максимальное количество коробов;
- допустимые группы совместимости.

Система должна останавливать заполнение текущего контейнера, когда раньше наступает одно из ограничений:

- достигнут максимальный вес;
- достигнут максимальный объем;
- достигнута максимальная высота;
- нарушается правило совместимости;
- закончилась текущая группа маршрута обхода.

После этого создается следующий контейнер.

### 5.8. Порядок Отбора

Порядок отбора - это последовательность ячеек, которую проходит комплектовщик.

Порядок может быть:

- линейный;
- Z-образный;
- ручной;
- по зонам;
- по приоритету товара;
- смешанный.

Должна быть отдельная таблица настройки порядка отбора по складу.

Минимальные параметры:

- склад;
- зона;
- ряд;
- секция;
- уровень;
- ячейка;
- номер последовательности;
- направление;
- активность;
- тип маршрута.

Алгоритм покоробочного отбора должен сортировать задачи по этому порядку.

### 5.9. Несколько Ячеек Отбора Для Одного SKU

Один SKU может иметь:

- одну регулярную ячейку отбора;
- несколько регулярных ячеек отбора;
- динамические ячейки отбора;
- резервные ячейки хранения;
- ячейки пополнения.

В MVP нужно учитывать регулярные ячейки отбора и признак динамической ячейки.

Логика динамических ячеек будет детально проектироваться отдельно в модуле волн и пополнения.

### 5.10. FEFO/FIFO

Для готовой продукции базовым правилом должен быть FEFO.

Если срок годности отсутствует или для товара задан другой режим, допускается FIFO.

При выборе партии:

1. Отфильтровать партии по клиентским ограничениям.
2. Отфильтровать партии по готовности для комплектации.
3. Отфильтровать партии по маркировке/агрегации, если это требуется клиенту.
4. Отсортировать:
   - FEFO: по ближайшей дате истечения срока годности;
   - FIFO: по дате поступления/выпуска.
5. Выбрать полные паллеты.
6. Выбрать остаток для покоробочного отбора.

### 5.11. Маркировка И Агрегация

Для товаров с Честным Знаком система должна учитывать:

- наличие DataMatrix;
- статус кодов;
- привязку кодов к партии;
- агрегацию короб/паллет;
- SSCC;
- принимает ли клиент агрегацию;
- можно ли отгружать без передачи кодов клиенту;
- нужен ли полный состав паллета.

Если клиент принимает агрегацию, предпочтение должно отдаваться паллетам с корректным SSCC и закрытой агрегацией.

Если клиент не принимает агрегацию, модуль должен планировать передачу кодов на уровне, который нужен клиенту.

### 5.12. Меркурий

Для продукции или сырья, где требуется ветеринарная прослеживаемость, план комплектации должен видеть:

- связанную производственную партию;
- сырьевые ВСД;
- статус оформления партии;
- возможность оформить или передать ВСД на клиента.

В MVP достаточно заложить поля и проверки статуса. Реальная интеграция идет через Mercury Connector.

## 7. Алгоритм Планирования

Для каждого заказа клиента:

1. Проверить, что заказ имеет клиента, маршрут и ворота.
2. Загрузить клиентские правила по сроку годности, укладке, маркировке и агрегации.
3. Для каждой строки заказа:
   - определить норматив коробов на паллете;
   - рассчитать количество полных паллет;
   - рассчитать остаток для покоробочного отбора.
4. Найти доступные партии и паллеты.
5. Исключить партии, которые не подходят под правила клиента.
6. Учесть `IS_SHIPMENT_ALLOWED` как критерий планирования, а не как WMS-блокировку.
7. Отсортировать кандидатов по FEFO/FIFO.
8. Назначить полные паллеты.
9. Назначить покоробочный отбор из pick face ячеек.
10. Разбить покоробочный отбор по контейнерам с учетом веса и объема.
11. Отсортировать задачи по порядку обхода ячеек.
12. Создать план комплектации и задачи.
13. Сохранить объяснение выбора.

## 10. Не В MVP

На первом этапе не реализовывать:

- полноценный wave picking;
- автоматическое пополнение dynamic pick face;
- оптимизацию маршрута в реальном времени;
- мобильное исполнение задач терминалом;
- печать листов отбора;
- фактическое сканирование DataMatrix;
- оформление ВСД;
- передачу кодов клиенту.

Эти блоки должны быть следующими инкрементами.

## 11. Edge Cases

Нужно предусмотреть:

- заказ меньше одной паллеты;
- заказ ровно кратен паллете;
- несколько партий подходят под один заказ;
- партия готова физически, но не подходит по сроку годности клиента;
- партия еще на вылежке;
- паллет подходит по партии, но не подходит по агрегации;
- клиентский норматив укладки меньше стандартного;
- не хватает полных паллет;
- не хватает товара в pick face;
- SKU имеет несколько pick face;
- pick face динамический и требует пополнения;
- нет маршрута или ворот;
- товар есть на складе, но нет подходящей партии по правилам клиента;
- конфликт FEFO и клиентского правила срока годности;
- заказ смешивает товары с разными требованиями маркировки.

## 12. Definition Of Done

Модуль считается готовым для MVP, когда:

- заказ клиента можно рассчитать в picking plan;
- план разделен на full pallet и case picking;
- план учитывает клиента, маршрут и ворота;
- план учитывает срок годности в днях или процентах;
- план учитывает клиентский норматив укладки;
- план учитывает `IS_SHIPMENT_ALLOWED`, но не блокирует WMS-остатки;
- задачи покоробочного отбора отсортированы по порядку ячеек;
- каждая задача имеет объяснение выбора партии/паллеты/ячейки;
- API smoke проверяет минимум один заказ с полнопалетным и покоробочным отбором;
- Oracle invalid objects = `0`;
- изменения описаны в wiki.
