# Техническое задание: BOM-блок для MES

Статус: MVP реализован в Oracle migration `009` и FastAPI `/api/bom`; следующий шаг — связать BOM с production order.

Дата: 2026-05-17.

Связанные документы:

- [WMS+MES+Traceability EDD](../architecture/wms_mes_traceability_edd.md)
- [Тактический план WMS+MES+Traceability](../roadmap/wms_mes_traceability_tactical_plan.md)
- [Oracle Change Protocol](../database/oracle_change_protocol.md)

## 1. Назначение

BOM-блок отвечает за хранение и применение рецептов производства.

В рамках проекта `BOM` означает `Bill of Material`: рецепт производства готового товара или полуфабриката, на основании которого создается производственное задание.

Производственное задание должно приходить или создаваться в формате:

- что нужно произвести;
- в каком количестве;
- по какому BOM;
- на какой линии/смене/площадке;
- на какую дату производства.

У одного конечного продукта может быть несколько BOM. При этом основной BOM для продукта должен быть один в рамках периода действия и области применения.

## 2. Цели

1. Создать отдельный производственный справочник BOM.
2. Поддержать несколько рецептов для одного товара или полуфабриката.
3. Поддержать основной BOM и альтернативные BOM.
4. Поддержать период действия BOM.
5. Использовать BOM как обязательную основу production order.
6. Рассчитывать плановую потребность сырья и полуфабрикатов по BOM.
7. Связать BOM с traceability: сырье -> production order -> finished goods lot.
8. Не смешивать BOM с Меркурием и Честным Знаком:
   - BOM описывает технологический состав;
   - Меркурий описывает юридическую ветеринарную прослеживаемость;
   - Честный Знак описывает маркировку и сериализацию.

## 3. Границы Блока

BOM-блок отвечает за:

- карточку BOM;
- версии BOM;
- строки состава BOM;
- основной/альтернативный признак;
- период действия;
- статус согласования;
- нормы расхода;
- технологические потери;
- допустимые отклонения;
- расчет плановой потребности для production order.

BOM-блок не отвечает за:

- фактическое списание сырья;
- выбор конкретных партий сырья;
- оформление ВСД в Меркурии;
- заказ и печать DataMatrix;
- агрегацию SSCC;
- лабораторные пробы;
- отгрузку клиенту.

Эти процессы используют BOM, но живут в своих bounded contexts.

## 4. Основные Термины

- `BOM`: рецепт производства одного целевого продукта или полуфабриката.
- `BOM version`: версия рецепта. После утверждения версия не редактируется напрямую.
- `Target product`: продукт, который должен быть произведен по BOM.
- `Component`: сырье, материал, упаковка или полуфабрикат, входящий в BOM.
- `Base quantity`: базовое количество выпуска, на которое рассчитаны нормы BOM.
- `Primary BOM`: основной BOM для продукта в заданном периоде.
- `Alternative BOM`: допустимый альтернативный BOM, который можно выбрать явно.
- `Effective period`: период действия `valid_from` / `valid_to`.
- `Yield`: выход готовой продукции.
- `Loss`: технологическая потеря.

## 5. Бизнес-правила

### 5.1. Несколько BOM На Один Продукт

Для одного `target_articul` допускается несколько BOM:

- основной BOM;
- альтернативный BOM для другой линии;
- сезонный BOM;
- BOM под другого поставщика сырья;
- BOM для опытной партии;
- BOM для полуфабриката.

### 5.2. Основной BOM

В один момент времени у продукта должен быть только один основной BOM в рамках одинаковой области применения.

Область применения:

- `target_articul`;
- производственная площадка, если используется;
- производственная линия, если используется;
- период действия.

Если линия/площадка не указана, BOM считается общим.

Запрещено иметь два активных основных BOM с пересекающимся периодом действия для одной и той же области применения.

### 5.3. Период Действия

У BOM есть:

- `valid_from`: дата начала действия;
- `valid_to`: дата окончания действия, может быть пустой.

Production order может использовать BOM, если плановая дата производства попадает в период действия BOM.

Если production order создается без явного BOM, система должна выбрать основной BOM, действующий на дату производства.

Если основной BOM не найден, production order не должен создаваться автоматически.

### 5.4. Статусы BOM

Рекомендуемые статусы:

- `DRAFT`: черновик.
- `APPROVED`: утвержден, но еще не обязательно активен по дате.
- `ACTIVE`: утвержден и применим.
- `BLOCKED`: временно запрещен к применению.
- `ARCHIVED`: больше не используется.

Production order может ссылаться только на BOM со статусом `APPROVED` или `ACTIVE` и валидным периодом действия.

### 5.5. Версионность

После утверждения BOM нельзя редактировать с изменением исторического смысла.

Любое существенное изменение создает новую версию:

- изменение компонента;
- изменение нормы;
- изменение единицы измерения;
- изменение допустимого отклонения;
- изменение технологических потерь;
- изменение выхода.

Старая версия остается доступной для истории и traceability.

### 5.6. Строки BOM

Строка BOM должна хранить:

- компонент;
- тип компонента;
- норму расхода;
- единицу измерения;
- процент или абсолютную норму;
- признак обязательности;
- допустимый заменитель или группа заменителей;
- допустимое отклонение мин/макс;
- технологическую потерю;
- порядок строки;
- комментарий технолога.

Типы компонентов:

- `RAW`: сырье.
- `SEMIFINISHED`: полуфабрикат.
- `PACKAGING`: упаковка.
- `ADDITIVE`: добавка.
- `SERVICE`: технологическая операция или служебная строка без складского списания.

### 5.7. Базовое Количество

BOM рассчитывается на базовое количество выпуска:

Пример:

```text
Target product: Корм A
Base quantity: 1000 KG
Component 1: Сырье X, 600 KG
Component 2: Сырье Y, 350 KG
Component 3: Добавка Z, 50 KG
Loss: 2%
```

При production order на `5000 KG` система масштабирует нормы в 5 раз.

### 5.8. Полуфабрикаты

Компонент BOM может сам быть полуфабрикатом, для которого существует отдельный BOM.

Система должна поддерживать:

- одноуровневый расчет BOM;
- в будущем многоуровневый расчет BOM explosion.

MVP: production order использует выбранный BOM только на один уровень. Многоуровневое планирование фиксируется как future extension.

### 5.9. Замены

Для строки BOM могут быть заданы допустимые заменители:

- конкретный альтернативный артикул;
- группа взаимозаменяемых сырьевых позиций;
- правило замены с коэффициентом.

MVP может не реализовывать заменители полностью, но модель должна оставить место под `substitution_group` и `replacement_ratio`.

### 5.10. Качество И Блокировки

BOM может быть заблокирован:

- технологом;
- QA/QC;
- администратором производства.

Причины:

- устаревший состав;
- запрет компонента;
- претензия качества;
- регуляторное ограничение;
- опытный рецепт не разрешен к массовому выпуску.

При блокировке BOM production order по нему создавать нельзя.

## 6. Процессная Модель

### 6.1. Создание BOM

1. Технолог создает BOM.
2. Указывает целевой продукт.
3. Указывает базовое количество.
4. Добавляет строки компонентов.
5. Указывает период действия.
6. Указывает, является ли BOM основным.
7. Сохраняет как `DRAFT`.

### 6.2. Утверждение BOM

1. Ответственный проверяет состав.
2. Система проверяет пересечение периодов основного BOM.
3. Система проверяет наличие обязательных полей.
4. BOM переводится в `APPROVED`.
5. При наступлении даты действия он считается применимым.

### 6.3. Создание Production Order По BOM

1. Внешняя система или оператор передает:
   - целевой продукт;
   - количество;
   - дату;
   - BOM ID или признак использовать основной BOM.
2. Если BOM ID не передан, система выбирает основной BOM.
3. Система рассчитывает плановую потребность компонентов.
4. Production order получает ссылку на BOM и BOM version.
5. В дальнейшем фактическое вовлечение сырья сравнивается с планом BOM.

### 6.4. Изменение BOM

Для `DRAFT` разрешено редактирование.

Для `APPROVED` / `ACTIVE`:

- прямое изменение запрещено;
- создается новая версия на основании старой;
- старая версия архивируется или остается активной до конца периода.

### 6.5. Закрытие BOM

BOM закрывается через:

- установку `valid_to`;
- статус `ARCHIVED`;
- статус `BLOCKED`.

Исторические production orders продолжают ссылаться на старую версию.

## 7. Данные И Сущности

### 7.1. `RRL_BOM`

Карточка BOM.

Поля:

```text
BOM_ID              NUMBER PRIMARY KEY
BOM_CODE            VARCHAR2(100)
BOM_NAME            VARCHAR2(255)
TARGET_ARTICUL      VARCHAR2(40)
TARGET_MOD_ID       NUMBER
TARGET_GTIN         VARCHAR2(14)
BOM_KIND            VARCHAR2(30)    -- FINISHED_GOODS / SEMIFINISHED
BASE_QTY            NUMBER
BASE_UNIT_CODE      VARCHAR2(20)
IS_PRIMARY          NUMBER(1)
STATUS              VARCHAR2(30)
VALID_FROM          DATE
VALID_TO            DATE
WARE_ID             NUMBER
PRODUCTION_LINE     VARCHAR2(100)
VERSION_NO          NUMBER
PARENT_BOM_ID       NUMBER
COMMENT_TEXT        VARCHAR2(1000)
CREATED_AT          DATE
CREATED_BY          VARCHAR2(50)
UPDATED_AT          DATE
UPDATED_BY          VARCHAR2(50)
APPROVED_AT         DATE
APPROVED_BY         VARCHAR2(50)
```

### 7.2. `RRL_BOM_LINE`

Строки состава BOM.

Поля:

```text
BOM_LINE_ID         NUMBER PRIMARY KEY
BOM_ID              NUMBER
LINE_NO             NUMBER
COMPONENT_TYPE      VARCHAR2(30)
COMPONENT_ARTICUL   VARCHAR2(40)
COMPONENT_MOD_ID    NUMBER
COMPONENT_NAME      VARCHAR2(255)
QTY_PER_BASE        NUMBER
UNIT_CODE           VARCHAR2(20)
LOSS_PERCENT        NUMBER
MIN_TOLERANCE_PCT   NUMBER
MAX_TOLERANCE_PCT   NUMBER
IS_REQUIRED         NUMBER(1)
SUBSTITUTION_GROUP  VARCHAR2(100)
REPLACEMENT_RATIO   NUMBER
COMMENT_TEXT        VARCHAR2(1000)
```

### 7.3. `RRL_BOM_AUDIT`

Журнал изменений BOM.

Поля:

```text
BOM_AUDIT_ID        NUMBER PRIMARY KEY
BOM_ID              NUMBER
ACTION_TYPE         VARCHAR2(50)
OLD_STATUS          VARCHAR2(30)
NEW_STATUS          VARCHAR2(30)
MESSAGE             VARCHAR2(1000)
PAYLOAD_JSON        CLOB
CREATED_AT          DATE
CREATED_BY          VARCHAR2(50)
```

### 7.4. Связь С Production Order

Будущий production order должен иметь:

```text
PRODUCTION_ORDER_ID NUMBER
TARGET_ARTICUL      VARCHAR2(40)
PLANNED_QTY         NUMBER
UNIT_CODE           VARCHAR2(20)
BOM_ID              NUMBER
BOM_VERSION_NO      NUMBER
PLANNED_START_AT    DATE
STATUS              VARCHAR2(30)
```

## 8. API

### 8.1. BOM Catalog

- `GET /api/bom`
- `GET /api/bom/{bom_id}`
- `POST /api/bom`
- `PATCH /api/bom/{bom_id}`
- `POST /api/bom/{bom_id}/lines`
- `PATCH /api/bom/{bom_id}/lines/{line_id}`
- `DELETE /api/bom/{bom_id}/lines/{line_id}`

Удаление строки разрешено только в `DRAFT`.

### 8.2. Lifecycle

- `POST /api/bom/{bom_id}/approve`
- `POST /api/bom/{bom_id}/block`
- `POST /api/bom/{bom_id}/archive`
- `POST /api/bom/{bom_id}/clone`
- `POST /api/bom/{bom_id}/make-primary`

### 8.3. Расчет

- `POST /api/bom/{bom_id}/calculate`
- `GET /api/bom/default?target_articul=...&planned_date=...`

`calculate` принимает количество выпуска и возвращает плановую потребность компонентов.

### 8.4. Production Order Integration

- `POST /api/production-orders`

Production order должен принимать:

```json
{
  "targetArticul": "FG-001",
  "plannedQty": 1000,
  "unitCode": "KG",
  "plannedStartAt": "2026-05-17T08:00:00+05:00",
  "bomId": 123
}
```

Если `bomId` не передан, API ищет основной BOM.

## 9. Права

Рекомендуемые права:

- `bom_view`: просмотр BOM.
- `bom_edit`: создание и редактирование черновиков.
- `bom_approve`: утверждение BOM.
- `bom_block`: блокировка/разблокировка BOM.
- `bom_make_primary`: назначение основного BOM.
- `bom_use_alternative`: создание production order по альтернативному BOM.

`GLOBAL_ADMIN` получает все права через legacy rule `*`, но сами права должны быть заведены в `RIGHTS` для обычных групп.

## 10. UI Требования

В админке должен быть отдельный раздел `BOM`.

Экран списка:

- фильтр по целевому продукту;
- фильтр по статусу;
- фильтр по дате действия;
- признак основного BOM;
- версия;
- линия/площадка;
- дата утверждения.

Карточка BOM:

- шапка BOM;
- строки компонентов;
- расчет на заданный объем;
- история изменений;
- кнопки lifecycle;
- предупреждение о пересечении периодов;
- предупреждение, если основной BOM не назначен.

## 11. Валидации

Обязательные проверки:

- `target_articul` заполнен;
- `base_qty > 0`;
- `base_unit_code` заполнен;
- у BOM есть хотя бы одна строка компонента перед approve;
- у строки BOM заполнен компонент и количество;
- `qty_per_base > 0` для материальной строки;
- период `valid_to` не раньше `valid_from`;
- нет пересечения активных primary BOM для одной области применения;
- нельзя создать production order по `DRAFT`, `BLOCKED`, `ARCHIVED`;
- нельзя изменить строки утвержденного BOM без создания новой версии.

## 12. События

BOM-блок должен писать события в trace/outbox infrastructure:

- `BomCreated`
- `BomLineAdded`
- `BomApproved`
- `BomBlocked`
- `BomArchived`
- `BomMadePrimary`
- `BomCloned`
- `ProductionOrderBomSelected`

Для MVP достаточно писать audit и, при создании production order, trace event `ProductionOrderBomSelected`.

## 13. Связь С Меркурием И Честным Знаком

BOM не хранит ВСД и DataMatrix.

Но BOM влияет на:

- плановое сырье для будущей операции Меркурия;
- проверку, что фактически вовлеченное сырье соответствует рецепту;
- genealogy edges сырье -> production order;
- состав готовой партии, которая дальше получает GTIN/DataMatrix/SSCC.

Если компонент требует ветеринарного учета, это признак справочника товара/сырья, а не строки BOM как регуляторного документа.

## 14. MVP

Минимальная реализация:

1. Таблицы `RRL_BOM`, `RRL_BOM_LINE`, `RRL_BOM_AUDIT`.
2. Package `RRL_BOM_API`.
3. CRUD черновика BOM.
4. Добавление/редактирование строк в `DRAFT`.
5. Approve BOM.
6. Назначение primary BOM с контролем пересечения периода.
7. Расчет потребности по объему выпуска.
8. Endpoint выбора primary BOM для production order.
9. Wiki mirror и smoke test.

## 15. Критерии Приемки

1. Можно создать BOM для готового продукта.
2. Можно создать несколько BOM для одного продукта.
3. Можно назначить один BOM основным.
4. Система запрещает два основных BOM с пересекающимся периодом.
5. Можно указать период действия BOM.
6. Можно добавить строки сырья/полуфабрикатов/упаковки.
7. После утверждения строки нельзя менять без новой версии.
8. Можно рассчитать потребность компонентов на заданный объем выпуска.
9. Production order может ссылаться на конкретный BOM.
10. Если BOM не передан, production order может найти основной BOM по продукту и дате.
11. Все изменения проходят через Oracle migration и PL/SQL API.
12. Русские тексты проходят `check-encoding.ps1`.

## 16. Открытые Вопросы

- Нужно ли различать BOM по заводу/площадке уже в MVP?
- Нужно ли различать BOM по линии уже в MVP?
- Где находится мастер-справочник единиц измерения?
- Нужно ли хранить стоимость BOM?
- Нужно ли поддерживать проценты состава, когда итоговая сумма должна быть 100%?
- Нужно ли поддерживать многоуровневый BOM explosion сразу или оставить на следующий этап?
- Кто утверждает BOM: технолог, QA/QC, начальник производства или несколько ролей?
- Нужно ли согласование BOM с лабораторией перед `APPROVED`?
