# Техническое задание: современное терминальное приложение WMS

## 1. Назначение

Нужно заменить устаревшее терминальное приложение, написанное под старую операционную систему терминалов, на современный контур, который работает на Android-терминалах, может запускаться с обычного компьютера для отладки и резервной работы, не подключается напрямую к Oracle и повторяет ключевые сценарии старого `Tserver`.

Существующий `Tserver` рассматривается как древний аналог API. Новый терминальный контур должен сохранить бизнес-смысл старых функций, но заменить транспорт и интерфейс на поддерживаемые технологии.

## 2. Принятый технологический подход

Рекомендуемый базовый вариант: **Web/PWA терминальное приложение**.

Стек MVP:

- React;
- TypeScript;
- Vite или Create React App по аналогии с текущим frontend-подходом;
- Ant Design / Ant Design Mobile для интерфейса;
- Axios или Fetch-клиент поверх OpenAPI-контракта;
- PWA manifest + service worker для установки на Android как приложение;
- IndexedDB для короткого локального буфера черновиков и повторов;
- Playwright для browser/e2e-проверок;
- запуск через локальный `.bat`-скрипт с очисткой порта, аналогично `front.bat` и `serv.bat`.

Почему Web/PWA первым:

- один код работает на ТСД, планшете и ПК;
- проще отлаживать рядом с API и Oracle VM;
- можно быстро покрыть старые `Tserver`-сценарии;
- большинство терминалов умеет передавать скан как keyboard wedge, то есть как обычный ввод;
- можно пилотировать без сборки APK и без привязки к одному производителю ТСД.

Второй слой, если потребуется доступ к железу:

- Capacitor-обертка над тем же Web/PWA приложением;
- Android shell для публикации APK;
- интеграция со scanner SDK производителя: Zebra DataWedge, Honeywell, Chainway, Urovo или другой фактический парк устройств;
- обработка аппаратных кнопок сканирования, intents, вибрации, звука и блокировки экрана.

Нативный Kotlin с Jetpack Compose оставляем как резервный вариант. Он сильнее для глубокого доступа к Android-устройству, но хуже подходит для запуска с ПК и замедлит первый пилот.

## 3. Целевая архитектура

```text
Android TSD / PC browser
        |
        | HTTPS JSON
        v
Modern Terminal Web/PWA
        |
        | WMS API endpoints
        v
Python FastAPI WMS API
        |
        +-- typed handlers for new operations
        +-- legacy Tserver compatibility layer
        +-- allowlisted CALL_SPF adapter
        |
        v
Oracle RABAEV schema / PL/SQL
```

Старые терминалы на переходный период могут продолжать работать через старый `Tserver`, но новые экраны не должны вызывать Oracle напрямую и не должны знать имена хранимых процедур.

## 4. Место в проекте

Рекомендуемая будущая структура:

```text
terminal/
  wms_terminal_web/
    package.json
    README.md
    public/
      manifest.json
    src/
      main.tsx
      config.ts
      api/
      components/
      pages/
      flows/
      scanner/
      store/
      styles/
```

Скрипт запуска:

```text
terminal.bat
```

Он должен использовать порт `3010`, перед стартом завершать процесс, который слушает `3010`, выставлять `REACT_APP_API_BASE_URL=http://127.0.0.1:8088` или аналогичную переменную и запускать терминальное приложение в dev-режиме.

## 5. Роли пользователей

| Роль | Назначение |
| --- | --- |
| `terminal_operator` | Оператор склада, сканирование и подтверждение назначенных операций. |
| `forklift_operator` | Водитель погрузчика, перемещения, пополнение, размещение. |
| `inventory_operator` | Инвентаризация и ревизия ячеек. |
| `shift_supervisor` | Контроль ошибок, повторов, зависших операций. |
| `admin` | Настройка терминалов, тестовые режимы, диагностика. |

Аутентификация MVP:

- пользователь вводит код/логин, аналог текущего `GET_RUSER`;
- API возвращает пользователя и права;
- сессия хранится локально ограниченное время;
- в production-версии нужна JWT/session-схема через WMS API.

## 6. Основные сценарии MVP

### 6.1 Вход оператора

API:

- `GET /api/terminal/users/{user_id}`;
- legacy mapping: `GET_RUSER`.

Экран:

- ввод/скан кода пользователя;
- отображение имени и роли;
- выбор режима работы по доступным правам.

### 6.2 Поиск товара по штрихкоду

API:

- `GET /api/products/by-barcode/{barcode}`;
- legacy mapping: `GET_PRODUCT_INFO`.

Экран:

- поле сканирования;
- карточка товара;
- упаковка, EAN, артикул, модификация;
- сообщение, если товар не найден.

### 6.3 Проверка паллеты / лота

API:

- `GET /api/lots/{usscc}/items`;
- `POST /api/terminal/lots/{usscc}/check`;
- legacy mapping: `GET_LOT_ITEMS`, `LOT_CHECK_PASSED`, `VP`, `ERROR_LOT_LINE`.

Экран:

- скан идентификатора паллеты;
- список строк паллеты;
- подтверждение строк;
- фиксация расхождений;
- отправка результата проверки.

Правило идентификаторов паллеты:

- поля идентификатора паллеты должны принимать стандартный `SSCC`;
- поля идентификатора паллеты должны принимать внутренние/legacy идентификаторы паллеты WMS;
- UI не должен называть такое поле только `SSCC`, если фактически допускается несколько типов идентификаторов;
- рекомендуемое название поля: `Идентификатор паллеты`;
- GS1 AI `00` формы вроде `(00)123456789012345678`, `00123456789012345678` и scanner-prefix форма `]C100123456789012345678` должны нормализоваться к 18-значному SSCC перед API-вызовом;
- legacy Pallet ID, например `OP_СТешв000451_1`, должен передаваться без изменения.

Требование: операция записи должна иметь `requestId` или `idempotencyKey`; повторная отправка того же результата не должна создавать дубли.

### 6.4 Проверка ячейки / места

API:

- `GET /api/places/{place_id}/items`;
- `POST /api/terminal/place-checks`;
- legacy mapping: `GET_PLACE_ITEMS`, `PLACE_CHECK_PASSED`, `ERROR_PALLET_CHECK_LINE`, `INVENTORY_LINE_PALLET_AUDIT`.

Экран:

- скан ячейки;
- отображение ожидаемых остатков;
- скан факта;
- ввод расхождений;
- отправка результата ревизии.

### 6.5 Проверка заказа

API:

- `POST /api/terminal/order-checks`;
- legacy mapping: `ORDER_CHECK_PASSED`, `ERROR_LOT_LINE`.

Будущие недостающие API:

- `GET /api/orders/{orderUid}`;
- `GET /api/orders/by-lot/{usscc}`;
- `GET /api/orders/by-lot/{usscc}/items`;
- `PUT /api/orders/{orderUid}/picker`;
- `PUT /api/orders/{orderUid}/zone`.

### 6.6 Операции погрузчика

Через allowlisted `CALL_SPF` на переходном этапе:

| Операция | Legacy procedure | Будущий endpoint |
| --- | --- | --- |
| Получить ячейку назначения | `RABAEV.RRL_GIVE_DESTINATION_CELL2` | `GET /api/forklift/pallets/{palletUid}/destination` |
| Пополнение пиковой ячейки | `RABAEV.RRL_GIVE_POPOLNENIE2` | `GET /api/forklift/cells/{cell}/replenishment` |
| Информация по паллете | `RABAEV.RRL_GET_PAL_INFOTEXT` | `GET /api/pallets/{palletUid}/info-text` |
| Внутреннее перемещение | `RABAEV.RRL_INTERNAL_MOVE3` | `POST /api/internal-moves` |
| Статистика погрузчика | `RABAEV.RRL_GIVE_KARSH_STAT_INFO` | `GET /api/forklift/users/{userId}/stats` |

Новый UI не должен отправлять произвольное имя процедуры. Он вызывает только явные операции API.

### 6.7 Инвентаризация

| Операция | Legacy procedure | Будущий endpoint |
| --- | --- | --- |
| Создать строку инвентаризации | `RABAEV.RRL_INV_CREATE_LINE4` | `POST /api/inventory/documents/{uidDoc}/lines` |
| Следующая ячейка | `RABAEV.RRL_GIVE_NEXT_CELL` | `GET /api/cells/{cell}/next` |
| Предыдущая ячейка | `RABAEV.RRL_GIVE_PREVIOUS_CELL` | `GET /api/cells/{cell}/previous` |
| Ревизия ячейки по коробам | `RABAEV.RRL_REVIZION_CELL_KOR` | `POST /api/inventory/cell-revisions` |

### 6.8 Производство и прослеживаемость

Новые сценарии, связанные с фабрикой кормов:

- скан паллеты готовой продукции;
- просмотр партии производства;
- просмотр SSCC-агрегации;
- просмотр статуса "Честного знака";
- просмотр статуса "Меркурия";
- подтверждение приемки паллеты готовой продукции на склад;
- фиксация расхождений по партии.

API-основа:

- `GET /api/production-batches/{id}/status`;
- `POST /api/production-batches/{id}/pallets`;
- `POST /api/production-batches/{id}/aggregations`;
- будущие read endpoints по `SSCC`, `uid_pallet`, `gtin`, `cis`.

## 7. Требования к интерфейсу

Терминальный интерфейс должен быть рабочим экраном оператора, а не админкой.

Требования:

- крупные зоны сканирования;
- минимальное количество текста;
- четкий текущий шаг;
- большие кнопки подтверждения и отмены;
- работа одной рукой;
- быстрый возврат к главному меню;
- цветовая индикация: успех, предупреждение, ошибка, блокировка;
- звуковой и вибро-сигнал в Android-режиме;
- поддержка русских подписей;
- возможность открыть тот же экран на ПК для теста.

Типовые экраны:

- вход;
- главное меню операций;
- универсальный экран сканирования;
- карточка паллеты;
- карточка ячейки;
- список строк проверки;
- экран расхождений;
- экран успешной отправки;
- журнал последних операций устройства;
- диагностика соединения с API.

## 8. Работа со сканером

MVP:

- сканер работает как клавиатура;
- приложение держит фокус в scan input;
- Enter после скана запускает обработчик;
- поддерживается ручной ввод для ПК.

Android-расширение:

- Capacitor shell;
- прием broadcast/intents от DataWedge или SDK производителя;
- настройка профиля сканера;
- аппаратные кнопки;
- вибрация и звук.

DataMatrix / CRPT:

- приложение должно принимать длинные строки DataMatrix без обрезки;
- UI должен показывать распознанный `GTIN`, `CIS`, `serial`, если API умеет разобрать код;
- сырая строка DataMatrix должна уходить в API для серверной валидации.

## 9. Offline и очереди

Базовая политика: **online-first**.

Разрешено локально хранить:

- текущую сессию;
- последний выбранный режим;
- последние успешные операции;
- черновики сканов до отправки;
- диагностический лог устройства.

Опасные складские изменения нельзя silently выполнять offline.

Если включается offline-буфер записей, обязательно:

- `operationId`;
- `idempotencyKey`;
- `resourceKey`: паллета, ячейка, заказ или документ;
- статус `pending/sent/accepted/rejected`;
- запрет на повторное редактирование принятой операции;
- явный экран "ожидает отправки";
- серверная защита от дублей.

До реализации полноценного command journal в API offline-запись должна быть ограничена пилотными низкорисковыми сценариями.

## 10. Требования к API

Новые терминальные экраны должны использовать только WMS API.

Правила:

- никакого прямого Oracle connection string в терминальном приложении;
- никакого произвольного `SPF_NAME` от клиента;
- все write endpoints принимают `requestId` или `idempotencyKey`;
- ошибки возвращаются в едином формате;
- API логирует пользователя, терминал, операцию, ресурс и результат;
- каждая операция должна быть воспроизводима в тесте.

Единый формат ошибки:

```json
{
  "code": "LOT_ALREADY_CONFIRMED",
  "message": "Паллета уже подтверждена",
  "details": {
    "usscc": "..."
  },
  "legacyReason": "END_LOT_CHECK_PASSED already exists"
}
```

## 11. Связка со старым Tserver

Цель перехода: не переписать все сразу, а получить функциональную совместимость.

Подход:

1. Старый `Tserver` остается источником реестра операций.
2. Новый API уже имеет compatibility endpoints для части функций.
3. Терминальное Web/PWA приложение вызывает typed endpoints.
4. Если typed endpoint еще не готов, API внутри себя использует allowlisted legacy handler.
5. После стабилизации операция выносится из `CALL_SPF` в явный endpoint и сервис.

Сопоставление MVP:

| Старый контур | Новый контур |
| --- | --- |
| `CS_CATClient` screen | React/PWA screen |
| TCP `FUNC=...|` | HTTP JSON |
| `Tserver` switch/call | FastAPI router/service |
| Dynamic `CALL_SPF` | Allowlisted internal adapter |
| Oracle writes | PL/SQL package/procedure through API |

## 12. Отладка и тестирование

Локальный запуск:

- API: `serv.bat`, порт `8088`;
- терминальное приложение: будущий `terminal.bat`, порт `3010`;
- raw/admin frontend: `front.bat`, порт `3000`.

Тестовая база:

- `RABAEV@127.0.0.1:1521/orcl`;
- перед разрушительными тестами нужен snapshot Oracle VM или disposable-схема;
- таблицы не удалять без отдельного явного подтверждения.

Виды тестов:

| Уровень | Что проверяет |
| --- | --- |
| Unit | парсинг скана, валидация форм, генерация idempotency key |
| API contract | соответствие frontend-клиента OpenAPI |
| Legacy parity | старый `FUNC` и новый endpoint дают одинаковый бизнес-результат |
| Integration | API вызывает Oracle и возвращает ожидаемый ответ |
| E2E browser | основной сценарий сканирования в Chrome/Edge |
| Device smoke | реальный ТСД сканирует штрихкод и отправляет операцию |

Первый набор smoke-тестов:

1. Открыть приложение на ПК.
2. Проверить `/health` API.
3. Войти по пользователю `GET_RUSER`.
4. Сканировать товар и получить `GET_PRODUCT_INFO`.
5. Сканировать существующую паллету и получить `GET_LOT_ITEMS`.
6. Выполнить read-only просмотр ячейки `GET_PLACE_ITEMS`.
7. В тестовом сценарии подтвердить проверку лота через `LOT_CHECK_PASSED`-совместимый endpoint.

## 13. Версионирование и поставка

Версии:

- `terminal-web` version в `package.json`;
- API version в `WMS_API_VERSION`;
- изменения API фиксировать в OpenAPI и wiki;
- изменения Oracle делать только через versioned migrations `apply/rollback/verify`.

Поставка:

- dev: запуск через `.bat`;
- test: статическая сборка frontend + API на тестовом сервере;
- pilot: ограниченная группа терминалов;
- production: после параллельной работы со старым контуром.

## 15. Критерии приемки MVP

MVP считается готовым, когда:

- приложение запускается на ПК и Android-терминале;
- вход оператора работает через WMS API;
- минимум три read-only операции работают против локального Oracle через API;
- один write flow работает end-to-end через API и Oracle;
- результат write flow совпадает по бизнес-смыслу со старым `Tserver`;
- нет прямого подключения терминального приложения к Oracle;
- нет произвольного вызова `CALL_SPF` из frontend-кода;
- есть запуск через `.bat` с очисткой порта;
- есть инструкция локальной отладки;
- есть список известных ограничений и план миграции следующих операций.

## 16. Не входит в MVP

- Полное отключение старого `Tserver`.
- Полная offline-работа склада.
- Переписывание всей PL/SQL-логики.
- Замена C# desktop client.
- Произвольный вызов Oracle-процедур из нового клиента.
- Интеграция с реальным API "Честного знака" и "Меркурия" прямо из терминального приложения.

## 17. Решение

Создаем отдельное терминальное Web/PWA приложение как новую ветку пользовательских экранов. Оно должно работать и на терминале, и с компьютера. Бизнес-операции выполняются через Python FastAPI WMS API, который постепенно заменяет `Tserver`, но на переходном этапе использует его реестр функций и совместимые handlers.

Такой путь дает быстрый пилот, сохраняет совместимость со складскими сценариями и оставляет возможность позже собрать APK под конкретный парк Android-ТСД без переписывания всей логики.
