## Исполнение и границы

Первым ticket открыть конкретные existing callers/пункт ТЗ редакции 57. Если правило уже реализовано — переиспользовать и оформить подтверждение, не создавать второй модуль. Каждый способ/система — отдельный ограниченный ticket.

Module owner: inventory для stock-effects; соседние modules через public; transaction owner RRL_STOCK_POSTING_API. Данные RABAEV/orcl. Вход/роль/право уточняются по существующему действию и проверяются сервером RUSERS, новые полномочия не предполагаются.

Неопределённый ответ повторяется исходным operation_id/body. Иной payload отклоняется; ошибка/устаревшая версия не оставляет частичного P/H/units/domain/outbox. Маркировка по WMS SKU/profile, точные единицы/партии/состав; несколько профилей не умножают P. Внешний ACK отдельно от физического факта; для не маркированного SKU коды единиц не требуются.

Ограниченное dev-подтверждение: действие/видимый результат/точный факт и существенный отказ/повтор. Широкие прогоны не назначаются; после meaningful case — решение по slow SQL. Минимум 80% ресурсов на функционал. Приёмка полного спринта ещё не выполнена.

## Первый ticket

Вход: существующий заказ/волна, кандидат UID/ячейка/партия, P/H, блокировки ячейки, входящее задание и pick-face mapping. Сопоставить один existing planner selection с authoritative проверкой команды; исправить только подтверждённое расхождение, сохранив правила остальных путей.

Исполнитель: планировщик/начальник смены с действующими правами волны. Результат: тот же допуск, что при исполнении, или конкретная причина отказа. Решение не создаёт запас, не снимает H и не приписывает PICKED подготовленной СТ.

Подтверждение: доступная ячейка допускается; карантинная исключается без изменения P; занятое H не доступно повторно. Незавершённое размещение/прямой отбор проверяются по настроенной стратегии, без тотального запрета экспедиции. Повторная проверка под locks ядра остаётся обязательной.
