# NICORA: пересмотренный план доработок существующей WMS/TMS

7 октября 2026 года, revision 10. [Глобальный разбор и решения](../../components/nicora_global_reuse_analysis_20261007.md) · [35 возможностей с исходниками](../../components/nicora_capability_matrix_20261007.md) · [metadata](implementation_plan.json).

Последующее архитектурное решение: [ТЗ достоверных остатков](../stock_posting_core_tz.md), редакция **2.0**. Определены P/H, единственный канонический HARD, перенос покрытия, уникальный stock key и полный порядок координации с матрицей существующих таблиц; карантин через недоступные ячейки хранения/отбора. Шесть принципов приняты владельцем; перевод всех writers — одним cutover, compatibility trigger выключен по умолчанию. Это общий объём NI03/NS08 и stock-зависимых модулей. Реализация, полная перепись writer SQL и мощность ещё не подтверждены; текущие NI статусы не повышаются.

Основная очередь ниже полностью заменяет прежний объём NI01–NI08. Номера сохранены для истории, назначения NI04–NI06 изменены. 68 NS-карточек и 363 сценария остаются каталогом требований, а не 68 этапами написания продукта с нуля. Существующие WMS/TMS, ORCL/orcl и схема RABAEV — единая основа. Второй Oracle, новая схема и новые платформенные MCP не нужны. Не создавать повторно диспетчер, назначение СТ, карту/VRP, Ганту, биллинг, базовые волны, mini-max, резервы и ресурсы.

Минимум 80% ресурсов направлять на функционал. Дополнительные бизнес/регрессионные/нагрузочные прогоны остановлены владельцем; задания Qwen подготовлены, но не запускаются автоматически. Анализ исходников и установка 009 выполнены по текущему поручению. Ни один найденный модуль не получает промышленную приёмку только за наличие кода.

## Что уже сделано и что было переоценено

NI01: ARTMAS10, WarehouseSupplyOrder, приёмка по паллетам, профили маркировки/физические коды, HTML/ZPL labels, stock event/putaway и обмен файлами/ACK реализованы; 001–007 установлены. Это **реализованная основа с обнаруженными пробелами**, а не полностью закрытая приёмка по всему ТЗ. Новая паллета не должна преждевременно стать кандидатом отбора; прямой отбор/карантин и общий downstream допуск завершаются в NI03. Состав агрегаций/сквозная маркировка — NI04. Реальные SAP/принтер/госоперации не приняты.

NI02: неизменный заказ/календарь и 008 реализованы. Теперь также установлен SAP→СТ bridge через существующие ORDERS/SBORKA writers, заполнен PLANNED fulfillment и сохранена подготовка; 009 применена в RABAEV. Укладку подтверждает оператор в существующем customer-orders UI, затем используется готовое назначение рейса. Функция назначения сохраняет RRL_TT_ADD_PALL/TRANSTASK_ID и теперь проверяет legacy error/result в одной транзакции. Автоматический splitter в текущем dev содержит compatibility stubs: его оригинальный body надо восстановить, не писать второй алгоритм. NI02 целиком не закрыт: late decisions/ERP refusal и перечисленные правила остаются.

**NI03 начат:** реализована общая транзакция существующего warehouse completion/domain sync, WAVE movement через RRL_EVENTS, частичный резерв/residual и durable повтор; 010 установлена в RABAEV. [Выполненный срез и остаток](../../runbooks/nicora_ni03_task_effect.md). NI03 целиком не закрыт. Невыполненный auto-split/календарь NI02 ведётся отдельными доработками.

## NI03: малые изменения в порядке выполнения

1. Общая доступность: склад, блокировки, пригодность партии/срока, входящий статус/размещение и разрешённый источник прямого отбора. Использовать один authoritative источник опубликованных pick faces.
2. Согласовать RRL_PICK_RESERVATION и RRL_STOCK_RESERVATION: связь одной потребности/владельца, резервировать доступное один раз. Не создавать третий stock registry.
3. Завершение существующего warehouse task: статус/факт/движение/резерв одним эффектом; повтор после потери ответа возвращает тот же результат. Отдельный domain sync не должен создавать ложный DONE без товарного эффекта. Существующий процесс и атомарность SAP PUTAWAY сохраняются; его товарный writer также переводится на общий posting core при cutover.
4. Case-pick/short: блокировка, один cursor, правильный повтор закрытой строки и действующий barcode resolver.
5. PLANNED fulfillment переводить в PICKED по физическому факту; объём/вес исполнения не приписывать подготовленной СТ.
6. Единая команда запуска готовой волны с восстановлением; использовать существующие readiness/mini-max/ресурсы. Правила сложных способов отбора продолжаются в NI04.

Каждый пункт — отдельный ограниченный ticket с исходником, владельцем транзакции и видимым результатом. Не объединять весь NI03 в массовое переписывание service.py.

## NI04: матрёшка уже имеет основу — завершить её

В live Oracle и API найдена вложенность SSCC → SSCC/CIS: RRL_CRPT_AGGREGATION/ITEMS и RRL_PRODUCTION_API. Поэтому предложение создать агрегацию с нуля отменено. До DDL определить границу логистического состава и регуляторной агрегации; новая дублирующая HU-таблица заранее не предписана.

Доработки: один активный родитель и отсутствие циклов/сирот; версия состава и история упаковки/вскрытия/перепаковки; движение верхнего HU вместе с вложениями; ограничения прямого перемещения вложения; частичный отбор с изменением состава/допуска; привязка точных партий/марок и массы. Количество считается по физическим товарным листьям один раз, масса — с учётом тары без повторной суммы родителей, машиноместа — по реально загруженным верхним местам. Несколько Track & Trace профилей одной единицы не увеличивают запас. Внутренние pallet identifiers также поддерживаются.

Карточка SKU определяет маркированность, применимые системы/страны/периоды/профили, уровни сканирования и обязательность внешнего подтверждения. Поддерживать CRPT/табак, ЕГАИС и другие применимые системы; QR/код товарной единицы не заменять EAN артикула. Переносить единицы через получение, пополнение, сборку, контроль, отгрузку и возврат. Настоящие adapters подключаются по применимости; mock outbox не считается ответом государства.

## Структура разработки и доказательства

Сохранять public → application/domain → infrastructure, composition root и одного владельца транзакции. Расширять действующую команду и рабочее место, когда они уже решают задачу. Не удалять текущие данные/таблицы по одному предположению о дублировании. Schema changes — versioned SQL, wiki/database и live metadata после применения.

Снимок прежнего плана: runtime/nicora-capability-analysis/plan-before-global-analysis/. Установка 009 и hashes: runtime/ni02/. Полные бизнес-кейсы не запускались; сроки не измерены и промышленная мощность не объявляется подтверждённой. Реальные медленные SQL после следующего разрешённого meaningful case должны получить конкретное решение согласно AGENTS.md.
