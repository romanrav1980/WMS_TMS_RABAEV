# Минимальные данные обмена ERP — WMS

Дата: 07.11.2026. Основа: стендовые требования NICORA и существующие примеры CSV. Документ задаёт **предлагаемый состав обмена**, а не утверждает, что подключение к ERP уже работает. Для запуска с конкретной ERP необходимо сопоставить её объекты и согласовать значения полей.

## 1. Принцип обмена

Ниже перечислены логические таблицы: строки можно передавать через API, сообщения, XML, IDoc или CSV. Это не требование создавать именно такие таблицы в ERP. Каждая строка получает устойчивый код источника; ERP и WMS хранят соответствие своих идентификаторов. Коды передаются строками, включая ведущие нули.

**О** — обязательно для сценария; **У** — условно, когда данные или функция применимы. Условные справочники не нужны, если соответствующий сценарий исключён. Необязательное поле не означает разрешение подставлять вымышленное значение.

Состав первого обмена: склады, адреса и магазины, товары, единицы и упаковки, штрихкоды, заказы и строки. Для полноценного складского запуска также нужны основания приходов и начальные остатки либо отдельная согласованная загрузка остатков. Дерево товаров и параметры слоттинга нужны при использовании автоматического слоттинга. Прогноз продаж и прогноз перемещений — самостоятельные наборы с разным назначением.

## 2. Общие поля сообщения

| Поле | Обязательность | Назначение |
|---|---|---|
| source_system | О | Код системы-источника. |
| message_id | О | Уникальный неизменный идентификатор сообщения в системе-источнике. |
| message_type | О | Вид объекта или документа и направление обмена. |
| event_type | О | Создание, изменение, отмена либо снимок; допустимые значения согласуются. |
| object_id | О | Код объекта в источнике. Для пакетного сообщения — в каждой записи. |
| revision | О | Версия объекта или другой согласованный признак порядка изменений. |
| occurred_at | О | Время формирования события с часовым поясом. |
| schema_version | О | Версия согласованного формата. |
| correlation_id | У | Связь с исходным документом, запросом или ответом. |
| snapshot_at | У | Единый момент снимка остатков или полного справочника. |

Повтор одного `message_id` с неизменным содержимым возвращает прежний результат без повторного создания или движения товара. Изменённое содержимое с тем же идентификатором — конфликт. Обновление объекта передаётся с новой версией и новым идентификатором сообщения. Доставка сообщения, принятие данных и результат складской операции — отдельные состояния. Удаление справочника заменяется признаком неактивности или датой окончания действия.

## 3. Справочники ERP → WMS

### 3.1. `warehouses` — склады

| Поле | Обязательность | Содержание |
|---|---|---|
| warehouse_id | О | Устойчивый код склада в ERP. |
| name | О | Наименование склада. |
| active | О | Признак активности. |
| address_id | У | Ссылка на адрес, если для склада используется отдельная запись адреса. |
| plant_code, storage_location_code | У | Коды структурных единиц ERP, если они различают остатки и источник. |
| shipping_point_code | У | Код пункта отгрузки, если используется при планировании. |

### 3.2. `addresses` — адреса

| Поле | Обязательность | Содержание |
|---|---|---|
| address_id | О | Устойчивый код адреса. |
| country, city, street_address | О | Страна, населённый пункт и адрес. |
| timezone | О | Часовой пояс адреса в согласованном формате. |
| latitude, longitude | У | Координаты для маршрутизации; при отсутствии не подменять нулём. |

### 3.3. `recipients` и `recipient_sources` — магазины и получатели

| Таблица / поле | Обязательность | Содержание |
|---|---|---|
| recipients.recipient_id | О | Код конкретного получателя или адреса склада-получателя. |
| customer_id | О | Код клиента, которому принадлежит адрес. |
| recipient_kind | О | Тип получателя: магазин или склад; значения согласуются. |
| name, active | О | Наименование и активность. |
| address_id, timezone | О | Адрес и часовой пояс приёмки. |
| source_warehouse_id | О* | Основной склад-источник; альтернативно передаётся связь в `recipient_sources`. |
| topup_enabled | У | Разрешение добивки для конкретного адреса. |
| topup_horizon_days | У | Предел X дней при включённой добивке. |
| receipt_strategy | У | Стратегия приёмки: вес, пересчёт по документам или сканирование; обязательна при использовании приложения магазина. |
| recipient_sources.recipient_id, warehouse_id | У | Разрешённая связь адреса и склада-источника, если источников несколько. |
| priority, valid_from, valid_to | У | Приоритет и период действия связи, когда применяются. |

Не смешивать клиента и адрес: настройки добивки и приёмки относятся к конкретному получателю. Время начала и конца окна приёмки можно передать в отдельной таблице `delivery_windows`: `address_id`, дата или день недели, `window_start`, `window_end`, признак перехода на следующий день, время обслуживания и признак закрытия.

### 3.4. `products` — товары

| Поле | Обязательность | Содержание |
|---|---|---|
| product_id | О | Устойчивый код товара ERP. |
| name | О | Наименование. |
| active | О | Активность. |
| base_uom | О | Базовая единица учёта. |
| batch_required, expiry_required | О | Требуются ли партия и срок годности. |
| single_handling_uom | О | Признак единственной разрешённой единицы обработки. |
| standard_handling_uom, handling_step | У | Единица обработки и шаг, обязательные при ограничении обработки. |
| round_to_standard_handling_uom | У | Разрешено ли округление при несовпадении единиц; обязательно при единственной единице обработки. |
| handling_policy_revision | У | Версия настроек обработки, чтобы принятая строка не пересчитывалась незаметно. |
| weight_control_type | У | Признак весового товара и согласованный режим учёта, если товар весовой. Значения сопоставляются с фактической настройкой WMS. |
| valid_from, valid_to | У | Период действия, если применяются версии. |

### 3.5. `product_uom` — единицы и фасовки товара

| Поле | Обязательность | Содержание |
|---|---|---|
| product_id, uom | О | Товар и единица: штука, блок, коробка, грамм, килограмм и др. |
| numerator, denominator | О | Точный коэффициент к базовой единице; направление коэффициента согласуется до загрузки. Знаменатель положительный. |
| conversion_revision | О | Версия коэффициента. |
| quantity_step, base_scale | У | Допустимый шаг и точность, если ограничивают обработку. |
| net_weight, gross_weight, weight_uom | У | Нормативные массы и их единица, если нужны для вместимости и планирования. |
| length, width, height, dimension_uom | У | Размеры упаковки для размещения и расчёта вместимости. |
| valid_from, valid_to | У | Период действия коэффициента. |

Для нескольких видов фасовки нужны устойчивый идентификатор фасовки, товар, вложенность, масса тары, нормативная масса единицы и штрихкоды. Они должны быть сопоставлены с действующими видами фасовки WMS. **Нормативная масса упаковки не заменяет фактическую массу конкретной весовой коробки.** Коэффициенты штук/коробок нельзя применять как постоянный пересчёт переменной массы без подтверждённого правила товара.

### 3.6. `product_barcodes` — штрихкоды

| Поле | Обязательность | Содержание |
|---|---|---|
| product_id, barcode | О | Товар и код, переданный строкой. |
| uom | О | Единица или фасовка, которую обозначает код. |
| barcode_type | О | Тип кода и правило разбора. |
| packaging_id | У | Конкретный вид фасовки, если у товара их несколько. |

Для весового штрихкода отдельно согласуются правила выделения товара и фактической массы. Индивидуальные коды прослеживаемости не заменяются общим штрихкодом товара.

### 3.7. `product_categories` и `product_category_assignments` — дерево товаров

| Таблица / поле | Обязательность | Содержание |
|---|---|---|
| product_categories.taxonomy_id, taxonomy_revision | О | Код и версия дерева. |
| category_id, parent_category_id | О* | Код узла и родителя; у корня родитель отсутствует. |
| name, is_leaf, active | О | Название, признак конечного узла и активности. |
| product_category_assignments.product_id, taxonomy_id, taxonomy_revision, category_id | О | Привязка товара к узлу конкретной версии дерева. |
| purpose, assignment_revision | У | Назначение классификации и версия привязки. |
| valid_from, valid_to | У | Срок действия, если версии действуют по датам. |

Для автоматического слоттинга товар должен быть привязан к **конечному узлу** дерева. Дополнительно передаются `category_slotting_parameters`: дерево и категория, код параметра, значение, тип, единица при необходимости, версия и период действия. Перечень кодов параметров согласуется со слоттингом; не выводится только из названия категории.

### 3.8. `owners` и `batches`

| Таблица / поле | Обязательность | Содержание |
|---|---|---|
| owners.owner_id, name, active | У | Владелец товара — обязательно, если товар разных собственников учитывается раздельно. |
| batches.product_id, batch_id | У | Товар и код партии — обязательно для партийного учёта. |
| manufactured_date, expiry_date | У | Дата производства и срок годности, когда требуются карточкой товара и процессом. |

## 4. Документы и плановые данные ERP → WMS

### 4.1. `supplies` — ожидаемые поставки на склад

| Поле | Обязательность | Содержание |
|---|---|---|
| supply_id, line_id, revision | О | Документ, строка и версия. |
| supplier_id, destination_warehouse_id | О | Поставщик и принимающий склад. |
| product_id, quantity, uom | О | Товар, ожидаемое количество и единица. |
| planned_receipt_at | О | Плановая дата и время приёмки с поясом. |
| status | О | Статус или отмена строки. |
| owner_id, batch_id, expiry_date | У | Собственник, партия и годность, если требуются процессом. |
| parent_pallet_id, package_id, barcode, net_weight | У | Состав грузовых мест и фактическая масса, если отправитель передаёт их достоверно. |

Набор входящей поставки выше — логический контракт. Существующий пример `supplies.csv` также используется для поставок получателю; направление, роли источника/получателя и связь с заказом необходимо сопоставить с конкретным документом ERP.

### 4.2. `orders` и `order_lines` — заказы магазинов

| Таблица / поле | Обязательность | Содержание |
|---|---|---|
| orders.order_id, revision | О | Код заказа и версия. |
| document_type, status | О | Тип и состояние, включая изменение/отмену. |
| customer_id, recipient_id, source_warehouse_id | О | Клиент, адрес получателя и склад-источник. |
| created_at, changed_at | О | Время создания и изменения с поясом. |
| requested_arrival_from, requested_arrival_to | О | Плановое окно прибытия в магазин. |
| order_lines.line_id, product_id | О | Устойчивый код строки и товар. |
| requested_qty, uom, status | О | Исходное количество, единица и состояние строки. |
| fulfilled_qty, cancelled_qty, open_qty | О* | Для загрузки открытых заказов — количества исполнено, отменено и осталось; их определения и момент снимка согласуются. |
| order_schedule.schedule_id, requested_arrival_from, requested_arrival_to, open_qty, uom | У | Отдельные графики, если строка делится на несколько окон. |

Количество может поступить в штуках, блоках, коробках, граммах или килограммах. WMS сохраняет исходные количество и единицу, применённый коэффициент и версию настройки, результат и разницу. Если единица отличается от единственной единицы обработки, количество пересчитывается и округляется вниз до шага. При запрещённом округлении строка всё равно загружается с округлением вниз и ошибкой интеграции. Без коэффициента исходная строка и ошибка сохраняются; результат не выдумывается. Нулевой результат не создаёт задание.

### 4.3. `stocks` — начальные остатки

| Поле | Обязательность | Содержание |
|---|---|---|
| snapshot_at, warehouse_id, product_id, uom | О | Единый момент снимка, склад, товар и единица. |
| physical_qty, reserved_qty, blocked_qty | О | Физический остаток, резерв и блокировка с согласованными определениями. |
| storage_location_id | У | Адрес хранения, если загружаются адресные остатки. |
| owner_id, batch_id, expiry_date | У | Обязательны, если включены собственник, партии или срок годности. |
| pallet_id, packaging_id, actual_net_weight | У | Идентификатор места, фасовка и фактическая масса, если ведётся такой уровень учёта. |

Согласовать, включает ли ERP-резерв блокировку и какие резервы принадлежат WMS. Нельзя повторно загрузить начальный остаток как приход или сложить резерв с физическим остатком.

### 4.4. `sales_forecast` и `movement_forecast`

| Поле | Обязательность | Содержание |
|---|---|---|
| forecast_id, revision, generated_at | О | Идентификатор, версия и время расчёта прогноза. |
| recipient_id, product_id | О | Получатель и товар. |
| sales_date / receipt_date | О | Дата продажи или ожидаемого перемещения соответственно. |
| quantity, uom | О | Прогнозное количество и единица. |
| scenario | У | Сценарий прогноза продаж, если их несколько. |
| source_warehouse_id | У | Источник в прогнозе перемещений, если значим для расчёта. |

Для стенда передать прогноз продаж **по каждому магазину и товару на месяц вперёд** с дневной детализацией. Прогноз перемещений передаётся отдельно. **Добивка рассчитывается только по прогнозу перемещений**, только при включённой настройке конкретного адреса получателя и не далее X дней из его настроек. Прогноз продаж или заказ не заменяют прогноз перемещений.

## 5. Результаты WMS → ERP

| Логическая таблица | Минимальные поля | Когда передаётся |
|---|---|---|
| `receipt_results` | operation_id, supply_id, line_id, warehouse_id, product_id, accepted_qty, uom, status, occurred_at | Подтверждение приёмки; партия, годность, собственник и фактический вес — при необходимости. |
| `shipment_results` | operation_id, order_id, line_id, recipient_id, warehouse_id, product_id, shipped_qty, uom, occurred_at, status | Фактическая отгрузка; идентификатор грузового места и фактическая масса — когда учитываются. |
| `inventory_adjustments` | operation_id, warehouse_id, product_id, quantity_delta, uom, reason, occurred_at | Утверждённое изменение остатков; собственник/партия/место — при наличии. |
| `store_receipt_results` | operation_id, shipment_id, recipient_id, receipt_strategy, status, occurred_at | Если ERP требуется подтверждение магазина; состав и расхождения передаются по согласованным строкам. |
| `integration_results` | source_system, message_id, object_id, revision, status, error_code, error_description | Технический и бизнес-результат обработки входящего сообщения. |

Каждое фактическое событие имеет устойчивый `operation_id` для повтора. Частичную поставку отражают фактическим количеством и отдельными последующими событиями; повтор не увеличивает факт. Фактическая масса нетто, брутто, тара и источник измерения передаются раздельно, если они требуются получателю.

## 6. Формат и проверка перед загрузкой

- Время — ISO 8601 с часовым поясом; день прогноза и срок годности — календарная дата. Часовой пояс магазина указывается отдельно.
- Количества и коэффициенты — десятичные числа без двоичного округления; точность и допустимые единицы согласуются по каждому товару.
- Ключи строк уникальны в своей области; все ссылки указывают на действующие объекты. Дерево категорий не содержит циклов, а товар для слоттинга привязан к конечной категории.
- Для каждого файла/пакета передаются источник, версия схемы, время снимка, период и количество записей. Обновления, отмены и повторная доставка должны быть различимы.
- Для SAP приложить фактические IDoc XML, message type, basic type, расширения и описание сегментов WE60. Соответствие конкретным IDoc NICORA ещё нужно согласовать; приведённые имена не являются стандартными сегментами SAP.
