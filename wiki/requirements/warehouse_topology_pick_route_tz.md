## 1. Главный Принцип

Топология склада и порядок обхода - это не ежедневный результат планирования заказов.

Это отдельный административный процесс управления мастер-данными склада. Он выполняется редко:

- при первичном запуске склада;
- при изменении стеллажей, ворот, проходов, зон накопления;
- при изменении логики отбора;
- при плановом пересмотре примерно раз в месяц;
- при внеплановом пересмотре не чаще раза в неделю, если операционная статистика показывает устойчивую проблему.

При поступлении ежедневных заказов система не пересчитывает топологию и не меняет порядок обхода автоматически. Ежедневное планирование только использует опубликованную версию топологии и активные маршруты обхода.

Статистика прошлых заказов, потерь времени, коллизий, ожиданий пополнения и длинных переходов может показываться как рекомендация администратору. Решение о перестройке топологии или порядке обхода принимает пользователь с правом управления топологией.

## 2. Назначение Модуля

Модуль "Управление топологией склада" нужен для того, чтобы:

- удобно создать карту склада и адресную структуру ячеек;
- описать зоны, секции, аллеи, ряды, проходы, ворота и зоны накопления;
- указать, какие ячейки являются ячейками хранения, ячейками отбора, dynamic pick-face, воротами или зонами накопления;
- графически расположить ячейки на карте склада;
- назначить порядок обхода ячеек отбора;
- опубликовать версию топологии для использования в комплектации, пополнении и цифровом двойнике;
- анализировать накопленную статистику и получать рекомендации по улучшению топологии без автоматической ежедневной перестройки.

## 3. Разделение Объектов

Нужно строго разделять четыре слоя.

1. Физическая топология склада.
   Это карта склада: помещения, зоны, проходы, ряды, ячейки, ворота, зоны накопления, координаты и габариты.

2. Ячейки отбора и назначение SKU.
   Это связь артикула с pick-face ячейкой, емкостью, стратегией пополнения и признаком regular/dynamic.

3. Порядок обхода.
   Это отдельный объект, который задает последовательность посещения ячеек комплектовщиком. Он строится поверх топологии, но не является самой топологией.

4. Ежедневные задачи.
   Это планы, волны, задачи комплектовщиков, задачи ричтраков и отгрузки. Они используют опубликованную топологию и порядок обхода, но не меняют их.

## 4. Версионирование

Топология должна быть версионируемой.

Минимальные статусы версии:

- `DRAFT` - черновик;
- `VALIDATED` - прошла проверки;
- `PUBLISHED` - используется в runtime;
- `ARCHIVED` - историческая версия.

Только одна версия топологии по складу может быть активной для runtime. Новая версия готовится в черновике, проверяется, сравнивается с текущей, затем публикуется.

Публикация версии не должна ломать открытые волны и уже выданные задания. Для открытых операций используется snapshot той версии топологии и маршрута, которая действовала на момент запуска волны или выдачи задания.

### 5.5. `RRL_TOPOLOGY_PICK_FACE_SLOT`

Операционная ячейка отбора внутри физического pick-face места.

Причина выделения отдельного объекта: одно нижнее паллето-место может быть разделено на несколько мелкоштучных ячеек отбора. Например, место `A01-B008-L1-R` физически занимает один нижний поддонный габарит, но для мелких SKU делится на сетку `3 x 3`: три горизонтальные секции и три вертикальных уровня. Тогда комплектовщик физически пришел в одну точку прохода, но система должна показать и отсортировать до девяти отдельных pick-face слотов.

Поля:

- `PICK_FACE_SLOT_ID`;
- `TOPOLOGY_ID`;
- `TOPOLOGY_CELL_ID` - ссылка на физическую ячейку/место;
- `WARE_ID`;
- `SLOT_CODE` - полный операционный адрес, например `A01-B008-L1-R-H02-V03`;
- `LEGACY_SLOT_CODE`;
- `SKU_ID` или ссылка на настройку назначения SKU;
- `SLOT_COLUMNS_TOTAL` - сколько горизонтальных секций задано в родительском месте;
- `SLOT_ROWS_TOTAL` - сколько вертикальных уровней задано в родительском месте;
- `HORIZONTAL_INDEX` - позиция внутри места по ширине;
- `VERTICAL_INDEX` - позиция внутри места по высоте;
- `SLOT_LEVEL_NO` - логический уровень pick-face внутри физического места;
- `SLOT_POSITION_NO`;
- `SLOT_KIND`: `NORMAL`, `SMALL_GOODS`, `CASE_BIN`, `DYNAMIC`;
- `MAX_VOLUME_M3`;
- `MAX_WEIGHT_KG`;
- `MAX_QTY`;
- `PICK_SEQUENCE_OFFSET` - порядок внутри физического места;
- `LABEL_X`, `LABEL_Y` - координаты подписи внутри визуального места;
- `ACTIVE`.

Важно: `RRL_TOPOLOGY_CELL.LEVEL_NO` описывает физический уровень стеллажа/места, а `RRL_TOPOLOGY_PICK_FACE_SLOT.SLOT_LEVEL_NO` описывает внутреннее деление pick-face места. Эти уровни нельзя смешивать.

Минимальные режимы деления:

- `1 x 1` - обычная ячейка отбора;
- `2 x 1`, `3 x 1` - горизонтальное деление;
- `1 x 2`, `1 x 3`, `1 x 4`, `1 x 5` - вертикальные уровни pick-face;
- `2 x 2`, `3 x 2`, `3 x 3`, `4 x 4`, `5 x 5` - мелкоштучная сетка;
- произвольная сетка допускается только после проверки габаритов, эргономики и читаемости адресных этикеток.

Базовое ограничение MVP: не больше `5 x 5` слотов в одном физическом месте. Если нужен больший разрез, это должно быть отдельное решение по таре, этикеткам, сканированию и эргономике, а не скрытое увеличение сетки.

Для расстояний до ворот и проходов используется физическая координата `RRL_TOPOLOGY_CELL`. Для порядка взятия и задания комплектовщику используется слот `RRL_TOPOLOGY_PICK_FACE_SLOT`.

### 5.11. `RRL_TOPOLOGY_CELL_GATE_DIST`

Матрица расстояний от ячеек до ворот.

Поля:

- `CELL_GATE_DISTANCE_ID`;
- `TOPOLOGY_ID`;
- `TOPOLOGY_CELL_ID`;
- `TOPOLOGY_GATE_ID`;
- `FLOW_KIND`: `INBOUND`, `OUTBOUND`, `BOTH`;
- `DISTANCE_M`;
- `TRAVEL_TIME_SEC`;

- `CALC_METHOD`: например `MANHATTAN`, `GRAPH_PATH`, `MANUAL`;
- `ACTIVE`.

Матрица расстояний должна храниться отдельно от ячейки, потому что у одной ячейки может быть разная близость к разным воротам. Для outbound-сценария система выбирает ближайшие или назначенные shipping gates; для inbound-сценария - receiving gates. В MVP допускается расчет Manhattan-distance по координатам как приближение движения по проходам, но целевой расчет должен использовать граф разрешенных проходов.

## 6. Генерация Топологии

Генератор должен поддерживать создание структуры по шаблону:

- склад;
- помещение;
- зона;
- секция;
- аллея;
- ряд/стеллаж;
- ярус;
- позиция;
- сторона прохода;
- тип ячейки.

Настройки генерации:

- кодовый шаблон адреса, например `A{aisle}-S{bay}-L{level}-{side}`;
- диапазон аллей;
- количество стеллажей/секций;
- количество уровней;
- количество позиций;
- сторона: левая, правая, обе;
- тип ячейки по умолчанию;
- режим деления pick-face места: `1x1`, `2x1`, `3x1`, `1x2`, `1x3`, `1x4`, `1x5`, `2x2`, `3x2`, `3x3`, `4x4`, `5x5`;
- шаблон кода внутреннего слота, например `{cell}-H{h}-V{v}`;
- направление нумерации внутренних слотов: слева-направо / справа-налево, сверху-вниз / снизу-вверх;
- стратегия внутреннего обхода слотов: `ROW_MAJOR`, `COLUMN_MAJOR`, `SNAKE`, `MANUAL`;
- рабочий участок;
- область хранения;
- уровень доступности;
- типоразмер;
- объем и вес;
- режим "создать новые";
- режим "обновить существующие".

Перед применением генератор должен показывать предварительный просмотр:

- список будущих адресов;
- список внутренних slot-адресов, если pick-face делится на несколько слотов;
- карту;
- количество создаваемых ячеек;
- количество создаваемых внутренних pick-face слотов;
- конфликты с существующими адресами;
- предупреждения по пересечению координат;
- предупреждения по отсутствующим проходам;
- предупреждения по слишком мелким слотам, если габариты, этикетка или эргономика отбора становятся сомнительными.

## 7. Построение Порядка Обхода

Порядок обхода строится поверх опубликованной или черновой топологии.

Поддержать режимы:

- `LINEAR` - прямой порядок по одной стороне или одному проходу;
- `Z` - проход по аллее с посещением левой и правой стороны в заданной очередности;
- `SNAKE` - чередование направления по соседним аллеям;
- `U_SHAPE` - вход в секцию, обход через разрешенный поперечный проход и выход;
- `MANUAL` - ручная перестановка последовательности.

Для Z-логики нужно хранить не "нарисованную линию", а последовательность ячеек:

```text
A01 left  bay 001
A01 right bay 001
A01 left  bay 002
A01 right bay 002
...
```

Если на складе физически принято сначала брать справа, потом слева, это должно задаваться параметром шаблона, а не кодом renderer-а.

Для разделенного pick-face маршрут имеет два уровня:

1. Внешний порядок физического прохода: аллея, сторона, bay, физическое место.
2. Внутренний порядок внутри места: горизонтальная секция, вертикальный уровень, позиция слота.

Система не должна добавлять лишний пробег между слотами одной физической ячейки. Переход между `A01-B008-L1-R-H01-V01` и `A01-B008-L1-R-H02-V01` имеет нулевую или минимальную локальную стоимость, потому что комплектовщик стоит у того же места. При этом задания должны быть отдельными, чтобы TSD показывал точный slot-адрес и SKU.

## 8. Использование В Ежедневной Работе

Ежедневное планирование:

1. Берет активную опубликованную топологию.
2. Берет активный опубликованный `RRL_PICK_ROUTE`.
3. Разрешает pick-face через `RRL_PICK_TOPOLOGY_API.resolve_pick_face`.
4. Сохраняет в задачи `PICK_ROUTE_CELL_ID`, `PICK_SEQUENCE`, `PICK_FACE_ID`.
5. Сортирует строки покоробочного отбора по `PICK_SEQUENCE`.
6. Не пересчитывает и не меняет топологию.

Если администратор позже публикует новую топологию, старые открытые задания продолжают жить на snapshot старой последовательности, а новые планы используют новую опубликованную версию.

## 9. Статистика И Рекомендации

Модуль должен показывать аналитику по прошлым заказам, но только как рекомендации.

Источники статистики:

- фактические маршруты комплектовщиков;
- фактические маршруты ричтраков;
- потерянные минуты;
- ожидание пополнения;
- коллизии в проходах;
- перегрузка зон накопления;
- частота отбора SKU;
- ABC/XYZ SKU;
- частота использования dynamic pick-face;
- длина маршрута на поддон;
- количество возвратов к пропущенным строкам.

Примеры рекомендаций:

- перенести A-SKU ближе к фронтальному проезду или зоне отгрузки;
- поменять порядок обхода аллеи;
- выделить больше dynamic pick-face в конце аллеи;
- увеличить емкость pick-face для SKU;
- изменить тыловой/пожарный переход в маршруте;
- изменить привязку ячейки к рабочему участку.

Применение рекомендации должно создавать черновик новой версии топологии или нового маршрута обхода. Автоматически публиковать рекомендации нельзя.

- координаты ячеек не пересекаются недопустимо;
- ворота имеют зону накопления;
- staging-зона имеет емкость;
- route не ссылается на отсутствующие ячейки.

## 13. Интеграция С Цифровым Двойником

Цифровой двойник должен перестать выводить Z-логику из координат или четности слота.

Он должен получать:

- опубликованную топологию;
- физические проходы;
- pick-face ячейки с `SIDE_CODE`;
- опубликованный `RRL_PICK_ROUTE`;
- `PICK_SEQUENCE`;
- фактические события движения ресурсов.

Карта должна визуализировать реальную модель:

- аллея имеет две стороны отбора;
- комплектовщик идет по последовательности `PICK_SEQUENCE`;
- переход между аллеями возможен только через разрешенный проход;
- ричтрак едет по аллеям и поперечным проходам;
- накопление перед воротами рисуется по емкости staging-зоны.
- скорость перемещения к воротам и от ворот рассчитывается через `RRL_TOPOLOGY_CELL_GATE_DIST`, а не через условную константу.

## 14. Инварианты

1. Нельзя иметь две опубликованные активные топологии для одного склада на один момент времени.
2. Нельзя публиковать маршрут, если он ссылается на ячейки другой топологии.
3. Нельзя удалять ячейку, если на нее ссылается опубликованный маршрут или активная pick-face настройка; нужно архивировать или создать новую версию.
4. Ежедневный план комплектации не имеет права менять `RRL_PICK_ROUTE_CELL`.
5. Рекомендация аналитики не имеет права менять топологию без действия администратора.
6. Открытая волна использует snapshot `PICK_ROUTE_CELL_ID` и `PICK_SEQUENCE`, созданный при запуске.
7. Renderer цифрового двойника не имеет права сам придумывать сторону ячейки или порядок обхода.
8. Внутренние слоты pick-face наследуют физическое расстояние до ворот, аллею и сторону от родительской `RRL_TOPOLOGY_CELL`.
9. Для split pick-face планирование и TSD обязаны показывать `SLOT_CODE`, если строка отбора назначена на внутренний слот.
10. Переход между слотами одной физической ячейки не должен увеличивать маршрут как переход между разными паллето-местами.

## 15. Acceptance Criteria

Модуль считается готовым, когда:

- оператор может создать черновик топологии;
- оператор может сгенерировать адреса ячеек по шаблону;
- оператор может увидеть предварительную карту;
- оператор может редактировать физические координаты ячеек только в явном режиме редактирования топологии;
- оператор может в основном режиме перетаскивать и переназначать связи порядка обхода, не меняя физические места;
- оператор может назначить ячейкам стороны аллеи;
- оператор может разделить физическую pick-face ячейку на 2-5 вертикальных уровней и/или несколько горизонтальных секций;
- оператор может увидеть и подписать внутренние slot-адреса на карте;
- оператор может назначить SKU на внутренний pick-face slot;
- порядок обхода может включать `PICK_FACE_SLOT_ID` и сортировать строки внутри одного физического места без добавления лишнего пробега;
- оператор может выделить участок и построить Z-порядок обхода;
- порядок обхода сохраняется в `RRL_PICK_ROUTE_CELL.PICK_SEQUENCE`;
- планирование покоробочного отбора сортирует строки по `PICK_SEQUENCE`;
- цифровой двойник рисует маршруты из опубликованной топологии;
- статистика прошлых заказов показывает рекомендации, но не публикует изменения сама;
- публикация новой версии не ломает открытые волны;
- все изменения пишутся в журнал.

## 16. MVP

В первом инкременте реализовать:

1. Черновик и публикацию версии топологии.
2. Таблицы зон, аллей и ячеек с координатами.
3. Генератор адресов ячеек.
3.1. Генератор внутренних pick-face слотов для деления физического места на мелкоштучные ячейки.
4. Страницу `Управление топологией склада`.
5. Графическую карту с zoom, pan, выделением участков и редактированием связей обхода.
6. Построение `Z` и `MANUAL` порядка обхода.
7. Валидацию маршрута.
8. Связь `RRL_PICK_ROUTE` с `TOPOLOGY_ID`.
9. Использование `PICK_SEQUENCE` в планировании покоробочного отбора.
10. Обновление цифрового двойника, чтобы он брал стороны и порядок из топологии.

## 17. Не В MVP

Не реализовывать в первом инкременте:

- автоматическое ежедневное изменение топологии;
- ML-оптимизацию маршрутов;
- автоматическую публикацию рекомендаций;
- полноценный 3D-редактор стеллажей;
- расчет строительных ограничений склада;
- автоматическое управление WMS layout без подтверждения администратора.

## 23. Редактирование Связей Обхода От 2026-05-20

Уточнение по админке: ячейки отбора являются физической данностью склада. Их нельзя воспринимать как свободно перетаскиваемые объекты при обычном редактировании порядка обхода. Основная работа страницы - редактирование связей и последовательности обхода поверх фиксированной топологии.

Добавлены правила первого инкремента:

- карта показывает подписи ячеек отбора коротким кодом `bay + side`, например `08L`;
- Shift/Alt + протянуть мышью по карте выделяет область pick-face ячеек;
- для выделенной области можно назначить стратегию обхода кнопками или правым кликом по карте через контекстное меню;
- поддержаны стратегии `Z`, `U_SHAPE`, `SNAKE`, `LINEAR`;
- Z/SNAKE-обход чередует направление по соседним аллеям: если A01 заканчивается в нижнем торце, следующая связь идет к нижнему торцу A02, а не диагональю к верхнему началу A02;
- backend `POST /api/admin/pick-routes/build` принимает `cell_ids`, чтобы строить маршрут только для выделенной области;
- повторный build с тем же `topology_id + ware_id + route_code` переиспользует существующий маршрут, а не создает дубль route header;
- карта визуализирует связи от торцов аллей до ворот/зоны накопления и показывает оценку плеча в метрах;
- ворота визуально отнесены от стеллажей, чтобы отразить типичный проход 18-24 метра между стеллажами и воротами/зоной накопления.

## 24. Split Pick-Face Для Мелкоштучного Отбора

Нужно поддержать ситуацию, когда одно физическое нижнее место отбора делится на несколько операционных ячеек:

- пример: одно место под паллету внизу делится на `3 x 3`, то есть дает девять отдельных pick-face slot для мелкоштучных SKU;
- физический адрес места остается один: аллея, сторона, bay, уровень;
- операционные адреса отбора становятся дочерними slot-адресами;
- маршрут по складу идет до физического места один раз, а внутри места TSD ведет комплектовщика по слотам.

Следствие для цифрового двойника и аналитики:

- на карте нужно уметь включать детализацию внутренних слотов;
- высота/цвет заполненности должен отображаться на уровне слота, если SKU назначен на slot;
- если несколько слотов находятся в одном физическом месте, задержка пополнения или пустой slot не должна выглядеть как отдельная дальняя точка маршрута;
- рекомендации ABC/layout могут предлагать не только перенос SKU между аллеями, но и изменение деления конкретного pick-face места: например `1x1 -> 3x3` для мелкоштучного ассортимента.

Следствие для пополнения:

- родительское физическое место имеет общую габаритную емкость;
- каждый slot имеет свою операционную емкость по SKU;
- пополнение может идти в конкретный slot коробками, но ричтрак/паллетный спуск относится к физическому месту;
- hard reservation источника для пополнения должен ссылаться на физическую потребность, а TSD/оператор отбора видит slot-уровень.

## 25. Улучшение Выделения И Различие Стратегий От 2026-05-20

## 27. Визуализация Строк Таблицы Порядка Обхода

Уточнение по карте топологии:

- `RRL_PICK_ROUTE_CELL` хранит не граф переходов, а точки линейного порядка обхода: ячейка/slot получает порядковый ранг внутри маршрута;
- порядковый ранг хранится как Oracle `NUMBER`, например `PICK_SEQUENCE NUMBER(18,6)`, чтобы можно было вставлять ячейки между существующими значениями без полной перенумерации;
- альтернативных маршрутов, развилок и условных переходов в базовом WMS-порядке отбора не предусматривается;
- стрелки порядка обхода в UI являются вычисляемым представлением: после сортировки active route rows по `PICK_SEQUENCE` строится переход `previous row -> current row`;
- одна стрелка на карте соответствует одному вычисленному переходу между соседними строками маршрута, то есть при 48 строках маршрута на карте должно быть 47 стрелок;
- карта не должна одновременно рисовать строки всех route headers одной топологии: если API возвращает несколько маршрутов, UI показывает только один активный/выбранный маршрут;
- tooltip на стрелке должен содержать все поля текущей записи `RRL_PICK_ROUTE_CELL`, включая `pick_route_cell_id`, `pick_route_id`, `topology_cell_id`, `pick_sequence`, `cell_code`, `aisle_code`, `side_code`, `path_segment_no`, `distance_from_prev_m`, `turn_cost_sec`, а также вычисленную пару `FROM/TO` с идентификаторами предыдущей и текущей ячейки;
- стрелка должна иметь явное направление через SVG marker, чтобы было видно `откуда -> куда`.

Инварианты одного активного маршрута:

- стартовая ячейка имеет `0` входящих и `1` исходящую вычисленную стрелку;
- конечная ячейка имеет `1` входящую и `0` исходящих вычисленных стрелок;
- обычная ячейка внутри маршрута имеет ровно `1` входящую и `1` исходящую вычисленную стрелку;
- ячейка, не включенная в маршрут, имеет `0` входящих и `0` исходящих стрелок;
- в рамках одного `PICK_ROUTE_ID` из одной ячейки не может выходить больше одной стрелки и в одну ячейку не может входить больше одной стрелки;
- для обычного физического pick-face действует `UNIQUE(PICK_ROUTE_ID, TOPOLOGY_CELL_ID)` и `UNIQUE(PICK_ROUTE_ID, PICK_SEQUENCE)`;
- для split pick-face порядок может назначаться дочернему slot, тогда уникальность переносится на `UNIQUE(PICK_ROUTE_ID, PICK_FACE_SLOT_ID)` при сохранении того же линейного принципа;
- если в будущем потребуется повторное посещение одной физической ячейки, это должно быть отдельным явно утвержденным расширением, потому что оно нарушает текущий простой линейный инвариант.

Визуальный масштаб:

- расстояние между спинками соседних рядов в карте должно выглядеть малым, потому что в реальности это порядка 20 см;
- рабочий проход внутри аллеи должен восприниматься шире, порядка 3 м;
- иконки ячеек отбора должны быть крупнее, чтобы подписи и направление переходов читались на 2D-плане.
