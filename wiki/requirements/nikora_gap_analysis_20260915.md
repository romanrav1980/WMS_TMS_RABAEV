# NIKORA: глубокий GAP-анализ ТЗ и TMS/WMS

Дата: 15.09.2026. Статус: предложение к согласованию, не акт готовности к production.

Основание: ТЗ 1.3 + XML-профиль 1.1.0, исходный Google Doc, новые материалы Drive и проверенный локальный код. Все ссылки, даты, границы проверки и E1–E16: [[sources/nikora_20260915]].

## Решение в одном абзаце

**Не переписывать WMS и не создавать новую платформу.** Сохранить FastAPI + React/PWA + Oracle, существующие заказы, остатки, отбор, складские волны, ресурсы, рейсы и биллинг. Добавить ограниченный контур межскладской координации: стабильную складскую часть исполнения, универсальный HU и историю преобразований, версионируемую исходящую волну, назначения груза на плечи и надёжный входящий обмен. Нынешних абстракций без расширения недостаточно: связь СТ с одним рейсом и регуляторная агрегация CRPT не выражают требуемый жизненный цикл. Это развитие модульного монолита, не замена складского ядра.

Архитектурное решение: [[architecture/nikora_minimal_extension]]. Отдельные планы: [[roadmap/nikora_architecture_sprints]] и [[roadmap/nikora_functional_sprints]].

## 1. Что изменилось в новой постановке

| Было в исходной задаче | Уточнение рабочего baseline 1.3 | Следствие |
|---|---|---|
| До шести складов | Пилот четырёх потоков: Orkhevi dry, Non Food, Peiqrebi sausage, Samgori fresh без овощей/фруктов; 20–30 магазинов | Четыре потока не обязательно четыре одинаковых адаптера; шестискладская сеть остаётся расширением |
| Консолидация по адресу | Магазин + день обслуживания; несколько заказов одного магазина | Нужны устойчивый destinationGLN и serviceDate, а не сравнение строк адреса |
| Назначение времени консолидации | Ведущий исходящий график основного склада и обратный расчёт всех операций | Нельзя начать с независимых маршрутов складов и затем «склеить» их |
| Подвоз и сборный маршрут | Cross-dock — обязательная схема пилота | Прямой рейс только baseline/согласованное исключение |
| Объединение SSCC | Каждый входящий и родительский HU — один магазин; верхний HU учитывается один раз | Запрет межмагазинной агрегации; коммерческие строки разных заказов сохраняются |
| Корректировки планов | Freeze после RELEASED; WAIT/PARTIAL/NEXT_WAVE как явные решения | Нужен отдельный автомат состояний, а не редактирование поля WAVE |
| XML возможен | Зафиксированы 5 GS1 + 2 собственных типа, XSD, ACK, версии и зависимости | «Есть JSON/API/файловый обмен» не означает совместимость |

«Единая поставка» не означает обязательный один физический HU: температурно несовместимые товары могут требовать разных HU и секций. При отсутствии совместимого автомобиля система должна показать невыполнимость, а не нарушить холодовую цепь ради одного рейса.

## 2. Развести три разных состояния

1. **Локальный продукт TMS/WMS:** код содержит современные складские и транспортные сервисы, но полноценный NIKORA end-to-end не найден.
2. **Действующая сеть NIKORA:** D6/D7 описывают WMS в Orkhevi и ручные/офлайн-процессы на других площадках. Это документарные данные, не наш полевой аудит.
3. **Целевой пилот:** все источники выдают SSCC/состав и принимают задания. Это требование; наличие адаптеров, оборудования, связи и владельцев ещё нужно подтвердить.

Нельзя переносить готовность нашего разработанного wave-модуля на реально установленную WMS NIKORA. Аналогично ответы SAP/Manhattan/SOLVO в матрице — заявления поставщиков, не доказательство готового кода.

## 3. Матрица GAP

Обозначения: «основа» — есть переиспользуемый код; «частично» — есть близкая функция, но не инварианты NIKORA; «нет в проверенном контуре» — не найдено в обследованных путях, не утверждение обо всех внешних системах. P0 — блокирует корректный пилот; P1 — обязателен до его приёмки.

| ID / приоритет | Требование | Фактическая основа и пробел | Решение / проверка |
|---|---|---|---|
| G01 P0 | Устойчивые адрес, заказ, источник | CUSTOMER/STORE_MAP/ORDER есть; нет полного owner+orderId+destinationGLN/version-контракта (E4) | Маппинг внешних ключей, уникальность в своём namespace; ошибки неоднозначности блокируют план |
| G02 P0 | Полнота ожидаемого заказа | Fulfillment содержит legacy-факт, не весь ожидаемый состав (E4) | OrderManifest от назначенного владельца; молчащий источник остаётся missing, не «заказ готов» |
| G03 P0 | Стабильная складская часть | SHIPMENT_PART существует, но генерируется по вместимости и может пересчитываться (E5) | Отделить FulfillmentPart источника от транспортной нарезки; не делать второй коммерческий заказ |
| G04 P0 | PLAN / ACTUAL_ONLY | Паллеты, вес, объём доступны; правил режимов и замещения прогноза нет (E1/E4/E5) | Правила SKU > поток > склад, периоды действия; фактические HU + остаточный прогноз без двойного счёта |
| G05 P0 | XML 1.1.0 | JSON production exchange и outbox есть, по умолчанию mock (E10/E11) | Allowlist, XSD + Context + семантика, сырой payload/hash, inbox, реальные адаптеры |
| G06 P0 | Идемпотентность, версии, ACK | Есть idempotency отдельных операций; нет общей обработки entityVersion/WAITING/APPLIED (E10–E12) | Atomic inbox → доменный эффект → outbox; два уровня ACK; восстановление после сбоя |
| G07 P0 | Один груз на нескольких плечах | ST_NUMBER привязан к единственному TRANSTASK_ID; второй рейс запрещён (E1) | TripStop + CargoAssignment; статус HU по плечу, история подвоз/последняя миля |
| G08 P0 | Исходящая волна/freeze | PICK_WAVE со статусами DRAFT/PREVIEW/LAUNCHED и складскими задачами; не исходящая волна сети (E6) | Отдельное состояние расписания и snapshot состава, связь с локальными pick waves |
| G09 P0 | Календарь и обратный расчёт | Есть транспортные даты/окна, ARM-нормативы; сквозной зависимости складов нет (E2/E6) | Версионируемый календарь и нормативы; дедлайны по каждому источнику; infeasible вместо отрицательного времени |
| G10 P0 | Ворота/маршрутные линии/очередь | DOCK_ID, topology и resource assignments есть (E6/E7/E14), готового gate-slot scheduler нет | Расширить существующее бронирование ресурсами площадки; сериализовать проверку перекрытий |
| G11 P0 | Вес, м³, места, секции, температура, геометрия на каждом участке | Solver использует суммарные паллеты/вес в savings; объём не входит в VrpOrder, секций нет (E3) | Единый hard-validator для ручного и авто-плана; нагрузка после каждой загрузки/выгрузки |
| G12 P0 | Реальные площадки и времена | В solver depot — центр координат заказов, движение через расстояние/условную скорость (E3) | Физические GLN источников/cross-dock, нормативы времени по направлению/смене; quality-флаг оценок |
| G13 P0 | Универсальный HU/SSCC | Legacy PALLETS ориентирован на товар и приход; scanner допускает legacy-коды; CRPT — другой контур (E8/E9/E13) | HU + состав + mapping локальной паллеты; строгое SSCC-правило только на границе профиля NIKORA |
| G14 P0 | Агрегация/разбор/переупаковка | create_aggregation/add_item есть, но не полный товарный баланс, история разрыва, запрет циклов и двойного parent (E8) | Транзакционные операции HU; разделять DISAGGREGATED и REPACK; staged связанные snapshots |
| G15 P0 | Скан физического исполнения | PWA/IndexedDB и ТСД-потоки есть, но не полный cross-dock lifecycle (E7/E13/E15) | READY ≠ LOADED ≠ DEPARTED; скан HU+trip+door/lane, версия, actor, отказ чужому/погруженному HU |
| G16 P0 | Ручное подтверждение и автоматический выпуск | Есть диспетчер/применение плана; нет общей freeze-авторизации/полноты/ACK (E1/E2) | Один command handler и hard-gates для обоих режимов, auto-policy с причиной решения |
| G17 P0 | Безопасный apply/replan | Нет проверки повторного plan_id в apply; create/update/assign имеют отдельные commit (E2/E12) | Idempotent apply, optimistic version + блокировки; всё или ничего для согласованной команды |
| G18 P1 | Исключения/недостача/поздний груз | Частичные picking/shortage есть, но не сквозное решение freeze/OTIF (E6/E7) | WAIT/PARTIAL/NEXT_WAVE, CANCEL_REQUESTED→CANCELLED; разгрузка перед переносом loaded |
| G19 P1 | Магазинная приёмка и возвраты | Рейсы/операции есть; контракта ReceivingAdvice с количественным балансом HU не найдено (E15) | Cross-dock receipt не закрывает магазин; частичная приёмка, отказ, возврат с причинами |
| G20 P1 | Оборотная тара | Ресурсная техника не равна истории наполнений клетки/ролла (E14) | Отдельный постоянный assetId, связи с HU, возврат и вместимость обратного плеча |
| G21 P1 | Экономика полного процесса | Биллинг/транспортные KPI есть, но не совокупная стоимость shuttle+cross-dock+returns | Не менять юридический billing; добавить аналитическую модель одинаковой потребности baseline/pilot |
| G22 P0 | Доказательство готовности | Исторические transport gates не проверяют NIKORA; часть тестов ориентирована на savings и допуски (E16) | Отдельный AT-01…36 набор, fault/replay/concurrency, UI/Oracle/slow-SQL evidence |

## 4. Конкретные дефекты, а не только новая функциональность

| Наблюдение | Доказательство | Что сделать |
|---|---|---|
| Savings не проверяет требуемый тип ТС/жёсткое окно, сообщает tw_violations=0 и duration=0 | Свежая offline-проба + _can_add | P0: перестать трактовать такой результат как безопасный; общий validator, корректная метрика |
| OR-Tools ветка обращается к n_orders вне определения | Статический разбор _solve_ortools; пакет не установлен в проверенном Python | P0 до допуска этого режима: исправить и запустить реальную ветку, тест overweight/type/windows |
| Нулевые координаты исключаются без unassigned | Свежая offline-проба solve | Явное исключение и запрет автоматического «всё запланировано» |
| Повтор apply вызывает повторное создание | Fake-gateway: два create для одного plan_id | Уникальный ключ apply и возврат ранее созданного результата |
| Ошибка назначения возникает после create | Fake-gateway + отдельные commit в gateway | Общая транзакция/команда; не считать выброшенный HTTPException откатом уже созданного рейса |

Это **не утверждение**, что в живой базе сейчас есть потерянные грузы или дубли рейсов. Доказан недостаток кода/оркестрации; реальные последствия не проверялись. Исправления в продукт в рамках анализа не внесены.

## 5. Противоречия и недостающие решения ТЗ

| ID | Вопрос | Рекомендуемая фиксация | Владелец / срок |
|---|---|---|---|
| Q01 | AT-12 разрешает новую версию уже выпущенного плана; AT-33 запрещает менять состав RELEASED | AT-12 отнести к CONFIRMED до RELEASED. Если речь об исключении после freeze — отдельная запись решения, исходный snapshot неизменяем | Логистика + аналитик, A1 |
| Q02 | DISAGGREGATED: валидатор требует один OUTPUT как при AGGREGATED | Развести cardinality: aggregate N→1, seam split 1→N; примеры и отрицательные тесты обновить. Дополнительная проба XSD-valid split сейчас отклоняется валидатором | Владелец XML, A1 |
| Q03 | OrderManifest указан, но XSD/версия/полнота не определены | Назначить владельца заказа/распределения, исходную ревизию, закрытие/отмену, строки/части и контроль полноты | ERP + NIKORA, до F1 |
| Q04 | Actual — одна часть; родительский HU может содержать несколько заказов/частей одного магазина | Зафиксировать owner физического HU, payload нового состава и lineBinding к нескольким частям; не размножать один HU в snapshots каждой части | WMS + XML, A2 до F3 |
| Q05 | План сборки должен содержать outboundWave/trip, но TMS строит план по готовности источников | Определить bootstrap: Manifest → предварительная TMS волна/ID → AssemblyPlan; либо отдельно согласовать initial unassigned forecast. Не внедрять циклическую обязательность молча | TMS + ERP/WMS, A1 |
| Q06 | После RELEASED состав фиксирован, но плановый HU превращается в фактический и выполняется агрегация | Уточнить объект freeze: обязательства заказа/части и их допуски отдельно от физического состава. Физические преобразования только зарегистрированными операциями и версиями, не CHANGE_BY_REFRESH состава волны | Логистика + архитектор, A3 |
| Q07 | ACTUAL_ONLY до факта не получает назначения, но источнику нужен deadline/общая волна | Разделить целевой дедлайн и резерв ресурсов/назначение перевозки. Дедлайн допустим до факта; резервировать перевозку ACTUAL_ONLY нельзя | Логистика, F1/F2 |
| Q08 | FULL reconciliation ≤10 MiB, пагинации нет | Измерить размер активного набора; не обрезать. При превышении — новая версия контракта с согласованными scope/checkpoint/pages | Интеграция, до F7 |
| Q09 | «Без хранения» и физический товар на cross-dock | Это отсутствие обычного доступного запаса, не отсутствие учёта количества/ответственности. Нужен transit/crossdock status и исключения dwell | NIKORA + учёт, A2 |
| Q10 | GLN/GTIN/SSCC, site geometry, режимы, нормы, SLA ещё не утверждены | Паспорта четырёх потоков; реальная этикетка/сканер/связь; интервалы температур и мощности; RPO/RTO в единицах времени | NIKORA + владельцы площадок, до F2/F7 |

До согласования Q01–Q07 допускается разработка независимого основания и тестовых fixtures, но нельзя объявлять промышленный бизнес-контракт завершённым. Изменения профиля должны иметь новую зафиксированную версию, а не скрыто подменять опубликованный v1.1.0.

## 6. Готовность и границы вывода

В существующем коде достаточно основания для инкрементального внедрения; **оснований объявлять готовым NIKORA-пилот нет**. Простой «добавить XML и экран консолидации» не закрывает cardinality, версии, физический баланс и ограничения маршрута.

Не требуются в этой задаче: новая WMS с новым stock ledger, микросервисы, Kafka ради обмена, отдельная графовая БД для HU, универсальный workflow engine, замена Oracle, ML-планировщик как зависимость пилота, переделка MES/регуляторики и бухгалтерии.

Не оценивались как подтверждённые: реальная производительность сентября, текущая схема live Oracle, установленные системы каждого склада, полнота внешних адаптеров, экономический эффект. Эти вопросы включены в gates, а не скрыты за процентом «готовности».
