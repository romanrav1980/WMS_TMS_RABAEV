# NIKORA: диспетчер ричтраков и очередь складской техники

Дата: 15.09.2026. UI-15; уточнение владельца задачи. Реализация F2.7, cross-dock расширение F4.1. Водитель: [[requirements/nikora_ui_reachtruck_tz]]. Общие правила: [[requirements/nikora_ui_workplaces_tz]].

## 1. Назначение и граница роли

Диспетчер управляет очередью ещё не начатых складских задач, их приоритетами и назначением подходящей технике/водителям. Видит выполнение, простои, блокеры и риск не успеть к волне/подаче. Он не подтверждает за водителя фактическое взятие/установку паллеты.

Начальник склада определяет приоритеты смены/волн; координатор консолидации задаёт обязательства по времени; диспетчер ричтраков организует исполнение внутри этих ограничений. Это режим существующего управления warehouse tasks/resources, не отдельный двигатель заданий. Совмещение ролей разрешается правами.

## 2. Варианты экрана

**А — плотная очередь + карточка задачи.** Слева/в центре таблица с закреплёнными порядком, taskId, статусом; справа выбранная задача, груз, техника, зависимость и разрешённые действия. Над таблицей компактная полоса техники: RT-01 занят, RT-02 свободен, RT-03 неисправен. Один экран для назначения и изменения очередности.

Колонки:

- Позиция/приоритет, тип операции, taskId, связанная волна и магазин.
- Источник → назначение; идентификатор паллеты, масса/высота, количество/UoM.
- Нужно начать/закончить к, прогноз начала/конца, риск опоздания, возраст ожидания.
- Назначенные техника/водитель, зона, состояние «готово / назначено / выполняется / груз взят / поставлено / ожидает синхронизации / блокировка».
- Причина блокировки, предшественник, автор/время/причина последней смены приоритета.

Фильтры: площадка, зона, тип задачи, волна, техника, статус, риск deadline. По умолчанию текущая смена и незавершённые задачи, а не вся история. Поиск taskId/HU без отдельной страницы.

**Б — доска по технике.** Колонки RT-01, RT-02, «Не назначено», «Блокировано». Верхняя фиксированная карточка — исполняемое задание, под ней очередь в реальном порядке; карточка показывает источник→цель, срок и причину приоритета. Дополнительный временной вид использует существующие ресурсы/расписание, если нужен при пилоте; не новый проект Ганта ради этой роли.

Оба вида работают с одной версией очереди. Drag-and-drop формирует **предложение**, а не немедленную скрытую команду. Для клавиатуры и touch — «Выше / Ниже / Назначить». Многократные перемещения собираются в один preview и одно подтверждение с причиной. При отсутствии прав просмотр остаётся доступным.

## 3. Очерёдность и допустимость

Базовая политика: только доступные задачи → совместимые техника/зона/допуски → срок и риск простоя downstream → заданный бизнес-приоритет → возраст. Точный алгоритм и нормативы утверждаются на refinement. Нельзя молча повышать долгую очередь так, чтобы нарушить жёсткое окно или зависимость.

Примеры высокого приоритета: пополнение, остановившее сборщика; подача HU к ближайшему подтверждённому выезду; освобождение блокирующих ворот. Приоритет не делает занятую ячейку свободной и не отменяет контроль качества.

Перед подтверждением показать: какие задачи/техника изменятся; старый/новый порядок; прогноз задержек и пропущенных deadlines; несовместимость и заблокированные позиции. Hard conflicts отклоняются. Мягкий риск требует разрешённой причины и автора, сохраняется в журнале.

Назначение не равно старту. До старта задача может быть передана другому совместимому ресурсу с проверкой версии. Если водитель уже начал, действует согласованный протокол отзыва/ACK; нельзя считать отменённой до ответа. **Груз уже на технике — перенос назначения запрещён**, пока не подтверждены безопасная установка/передача и обновление custody. Экран явно показывает запрет.

Новая срочная задача становится следующей допустимой, а не вытесняет незавершённое физическое действие. У водителя появляется одно следующее задание после server ACK предыдущего, без обязательного просмотра изменившейся очереди.

## 4. Исключения, простои, связь

- Неисправна техника: диспетчер переводит ресурс в недоступный, перераспределяет только допустимые ещё не начатые задачи; груз на технике остаётся отдельным инцидентом.
- Ячейка занята/проезд закрыт/нет HU: выбрать альтернативу через проверяемую серверную команду либо запросить разрешение; не закрывать задачу фиктивным исполнением.
- Водитель offline: «последний контакт / подтверждение ожидается», не «свободен». До сверки запрет на новое владение спорным грузом.
- Возраст ожидания не сбрасывается перестановкой очереди. Задача не исчезает из списка при переносе/отмене: есть статус, связь и причина.
- SLA обновления из общего NFR; устаревшая очередь явно помечена. При 409 preview нужно пересчитать, чужая перестановка не перезаписывается.

## 5. Права и интеграция

Предлагаемые права: rt_dispatch_view, rt_queue_prioritize, rt_task_assign, rt_task_recall, rt_resource_unavailable. Server-side scope по площадке и зоне; чтение не даёт права исполнения warehouse_task_execute. Использовать действующие RUSERS/RIGHTS и RESOURCE/WAREHOUSE_TASK; имена прав согласовать с текущим каталогом.

Read model: bounded список задач на смену, порядок/queueVersion, resource/session, deadline, blockers и custody. Команды: preview/confirm reorder, assign, request recall, mark unavailable — на существующих API/командах или узких расширениях. Для queue reorder нужны optimistic queueVersion и транзакционное обновление затронутых назначений. Не заводить второй независимый список физически тех же задач.

Очередь показывает ссылки на ТМС wave/подвоз, но не формирует ERP-статус «в пути» из внутреннего перемещения ричтраком. Полноценный статус ERP относится к соответствующему транспортному плечу и фактическому выезду.

## 6. Приёмка RD-UI / F2.7

1. Из одной таблицы назначить готовую задачу подходящему ресурсу; она появляется следующей у водителя без повторного входа.
2. Поднять ещё не начатую задачу: preview старого/нового порядка, причина, один confirm, очередь обновляется в обоих видах.
3. Два диспетчера одновременно меняют очередь: один commit, другой 409 с понятным пересчётом; задачи не пропадают.
4. Несовместимая техника/зона/высота/масса/зависимость блокируется и в drag-and-drop, и в API.
5. Задача с грузом на технике не переносится. Request recall не выдаётся за confirmed cancel.
6. Неисправность перераспределяет только допустимые задачи; custody незавершённого груза сохраняется.
7. Offline водитель не становится свободным по таймеру; после reconnect нет двойного назначения/исполнения.
8. Очередь устарела — confirm запрещён до сверки. Возраст/исходный deadline сохраняются.
9. Keyboard/touch выполняют reorder без drag; штатное назначение/перестановка без навигации на новую страницу.
10. Реальная нагрузка смены: ограниченное окно, измерены event→UI и время preview/confirm; slow-SQL review по задачам/ресурсам, нет N+1-запроса на карточку.

Дополнительные управленческие метрики: задачи в час по типу, ожидание до старта, блокированный простой и время с грузом; не смешивать их с чистым временем поездки и не сравнивать людей без учёта типа/дистанции задачи.
