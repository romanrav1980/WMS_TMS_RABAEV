# NIKORA: исполнимые срезы раннего кроссдокинга

Дата: 16.09.2026. DRAFT. Приоритет и ограничения: [[roadmap/nikora_crossdock_first]]. Конкретный автор и независимый reviewer каждого CD-ID: [[roadmap/nikora_crossdock_agent_map]]. Обязателен [[requirements/nikora_sprint_contract]]. Ниже отдельные принимаемые результаты, выделенные из 41 родительского ТЗ; родитель не закрывается автоматически.

Для каждого шага три ограниченных tickets: (1) контракт и отрицательный тест; (2) реализация серверного сценария/миграции и минимального UI; (3) независимая проверка и evidence. Архитектурные шаги принимаются через API/Oracle, функциональные — UI + физический факт + сообщение. Точные файлы allowlist выбираются из родителей перед запуском. Никакой отдельной дублирующей архитектуры «MVP».

Назначение агентов по ролям прежнего плана: H — сильный облачный разработчик и независимый проверяющий; X — критическая транзакция/версии с усиленным review; C — ограниченный UI/адаптер по готовому контракту. Модели и тарифы — снимок 15.09.2026, проверяются перед реальным запуском. Local после квалификации выполняет fixtures/изоляционные UI-подзадачи. Если он недоступен, cloud replacement отдельно отражается в фактическом usage; сроки не ждут запуска GPU.

## Общий gate и stop rules

Каждый шаг требует права/site scope, повтор сообщения/команды, version conflict, отказ связи, DB readback, UTF-8 и longest SQL review по применимости. UI обязан показывать pending/failed/HOLD/частичный факт. Автор и reviewer — разные сессии. Не сокращать тесты предыдущих принятых шагов при выдаче новой карточки.

До ACCEPTED_CD предыдущего шага следующий не принимается. Можно заранее готовить контракты/fixtures, но не включать неподтверждённый путь. При отсутствии внешнего endpoint, весового evidence, target-WMS факта или reuse перемещения ставить WAITING_EXTERNAL и выполнить альтернативный обязательный scope из основного плана; не заменять отказ фиктивным PASS.

Новые схемы/поля/сообщения версионируются; имена API проектные. Архитектура данных в раннем и полном выпуске одна. Контракты качества должны предусматривать смену contentVersion и блокировку future repack, даже когда UI преобразования выключен. После CDP принимается решение о расширении состава грузов/источников по измерениям, а не по календарю.
