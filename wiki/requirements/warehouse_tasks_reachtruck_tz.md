# ТЗ: складские задания для водителей ричтраков

## 1. Назначение

Модуль `Складские задания` нужен как единый список работ для водителей ричтраков и складской техники.

Он не заменяет специализированные бизнес-документы MES, Picking или Wave Picking. Это операционный слой исполнения: водитель видит, какой паллет взять, откуда взять, куда поставить и в каком статусе находится задание.

## 2. Основной принцип

- MES, Picking, Wave Picking и другие модули создают свои бизнес-сущности.
- Для физического перемещения паллетов они создают запись в общей таблице `RRL_WAREHOUSE_TASK`.
- Водитель ричтрака работает с `RRL_WAREHOUSE_TASK`.
- Старые остатки WMS не меняются напрямую при создании задания.
- Фактическое изменение остатков выполняется только через подтвержденный процесс и существующий WMS/MES bridge на базе `RRL_EVENTS`.

Архитектурное правило: `RRL_WAREHOUSE_TASK` хранит физическую работу склада, а не отдельный бизнес-процесс. Для водителя это один класс операций: переместить паллет или часть паллета из одной ячейки в другую. Бизнес-контекст задается полями `TASK_SOURCE`, `SOURCE_DOC_TYPE`, `SOURCE_DOC_ID`, `SOURCE_TASK_ID` и `SOURCE_MOVEMENT_ID`.

Типовые контуры:

- пополнение pick face под клиентскую волну комплектации: `TASK_TYPE = REPLENISHMENT`, `TASK_SOURCE = WAVE`, `SOURCE_DOC_TYPE = PICK_WAVE`;
- спуск паллета с хранения в грузовую зону: `TASK_TYPE = PICKING_MOVE`, `TASK_SOURCE = WAVE`, `SOURCE_DOC_TYPE = PICK_WAVE`; волна может быть создана по заказам на отгрузку или производственным заказам, но остается единственным управляющим документом;
- размещение готовой продукции после выпуска: `TASK_TYPE = FG_TO_STORAGE`, `TASK_SOURCE = MES_COMPLETION`;
- пополнение производства: производственная волна использует тот же механизм warehouse tasks; для legacy MES raw supply текущий источник `TASK_SOURCE = MES_RAW_SUPPLY`, а целевая модель может быть `TASK_SOURCE = WAVE`, `SOURCE_DOC_TYPE = PRODUCTION_WAVE`.

## 3. Таблица складских заданий

Целевая таблица: `RRL_WAREHOUSE_TASK`.

Ключевые поля:

- `TASK_ID` - идентификатор задания.
- `TASK_TYPE` - тип задания:
  - `RAW_TO_PRODUCTION` - переместить сырье на склад или ячейку производства.
  - `FG_TO_STORAGE` - переместить выпущенный паллет готовой продукции на склад или ячейку хранения.
  - `REPLENISHMENT` - пополнение ячейки отбора.
  - `PICKING_MOVE` - перемещение в рамках комплектации.
  - `OTHER` - ручное или служебное задание.
- `TASK_SOURCE` - источник:
  - `MES_RAW_SUPPLY`;
  - `MES_COMPLETION`;
  - `PICKING`;
  - `WAVE`;
  - `MANUAL`.
- `SOURCE_TASK_ID` - ссылка на специализированную задачу, например `RRL_MES_RAW_TRANSFER_TASK.TASK_ID`.
- `SOURCE_MOVEMENT_ID` - ссылка на MES movement, например `FG_PALLET_RELEASE`.
- `PRODUCTION_ORDER_ID` - производственный заказ, если применимо.
- `PROD_BATCH_ID` - партия готовой продукции, если применимо.
- `UID_PALLET`, `SSCC` - идентификаторы паллета.
- `RAW_ARTICUL`, `TARGET_ARTICUL` - сырье или готовая продукция.
- `FROM_WARE_ID`, `FROM_CELL` - откуда забрать.
- `TO_WARE_ID`, `TO_CELL` - куда поставить.
- `QTY`, `UNIT_CODE` - количество.
- `QTY_MODE` - способ исполнения количества:
  - `PALLET` - полный паллет;
  - `BOX` - коробки или частичное количество.
- `FACT_QTY` - фактически подтвержденное количество при закрытии.
- `PARENT_TASK_ID` - исходная задача, если текущая задача создана как остаток после частичного выполнения.
- `STATUS` - `PLANNED`, `ASSIGNED`, `IN_PROGRESS`, `DONE`, `CANCELLED`, `ERROR`.
- `ASSIGNED_TO` - водитель или единица техники.

## 4. Сырье в производство

При операции `Передать в производство`:

1. Система рассчитывает потребность по BOM.
2. Создает `SOFT` резерв как потребность.
3. При наличии свободного остатка создает `HARD` резерв на конкретный паллет и ячейку.
4. Создает специализированную задачу `RRL_MES_RAW_TRANSFER_TASK`.
5. Параллельно создает общую складскую задачу:
   - `TASK_TYPE = RAW_TO_PRODUCTION`;
   - `TASK_SOURCE = MES_RAW_SUPPLY`;
   - `SOURCE_TASK_ID = RRL_MES_RAW_TRANSFER_TASK.TASK_ID`;
   - `FROM_CELL = ячейка сырья`;
   - `TO_CELL = ячейка производства`.

Водитель подтверждает физическое перемещение. После подтверждения:

- специализированная MES-задача становится `DONE`;
- складская задача становится `DONE`;
- hard reserve становится `CONSUMED`;
- создается MES movement `RAW_ISSUE_TO_PRODUCTION`;
- старый WMS меняет остатки только при применении WMS bridge.

## 5. Выпуск готовой продукции

При завершении производства:

1. MES создает партию готовой продукции.
2. MES создает паллеты готовой продукции.
3. Для каждого выпущенного паллета создается movement `FG_PALLET_RELEASE`.
4. Для каждого паллета создается складская задача:
   - `TASK_TYPE = FG_TO_STORAGE`;
   - `TASK_SOURCE = MES_COMPLETION`;
   - `SOURCE_MOVEMENT_ID = RRL_MES_MOVEMENT.MOVEMENT_ID`;
   - `FROM_CELL = MES_PRODUCTION`;
   - `TO_CELL = целевая ячейка хранения готовой продукции`.

Целевая ячейка может приходить из API выпуска паллета как `target_cell`. Если она не задана, используется техническая приемочная ячейка `FG_RECEIVE`, после чего оператор склада должен уточнить размещение.

## 6. Работа водителя ричтрака

Минимальный сценарий:

1. Водитель открывает список заданий.
2. Фильтрует задания по статусу `PLANNED` или `ASSIGNED`.
3. Берет задание в работу:
   - система записывает `ASSIGNED_TO`;
   - статус становится `ASSIGNED` или `IN_PROGRESS`.
4. Водитель сканирует паллет.
5. Водитель сканирует ячейку назначения.
6. Система проверяет:
   - паллет совпадает с заданием;
   - ячейка назначения совпадает или разрешена правилами;
   - задание не закрыто и не отменено.
7. После подтверждения статус становится `DONE`.

## 7. Пополнение ячейки отбора под волну

При запуске волны и расчете дефицита pick face пополнение ячейки отбора должно создаваться в общей таблице `RRL_WAREHOUSE_TASK`.

Это та же физическая операция для водителя: переместить паллет или часть паллета из ячейки хранения в ячейку отбора.

Подробное ТЗ для покоробочной комплектации и стратегий `IMMEDIATE` / `MINIMAX` вынесено в [пополнение ячеек отбора под покоробочную комплектацию волны](wave_case_pick_replenishment_tz.md).

Для задач пополнения волны:

- `TASK_TYPE = REPLENISHMENT`;
- `TASK_SOURCE = WAVE`;
- `SOURCE_TASK_ID = RRL_PICK_WAVE_REPLENISH_TASK.PICK_WAVE_REPLENISH_TASK_ID`, если доменная строка пополнения сохранена;
- `SOURCE_DOC_TYPE = PICK_WAVE`;
- `SOURCE_DOC_ID = RRL_PICK_WAVE.PICK_WAVE_ID`;
- `UID_PALLET` и `SSCC` заполняются по паллету-источнику, если известны;
- `FROM_CELL` - ячейка хранения;
- `TO_CELL` - целевая pick face;
- `QTY` - полное или частичное количество для пополнения.

`RRL_PICK_WAVE_REPLENISH_TASK` может оставаться доменной строкой волны и расчетным источником, но водительский список исполнения и статусы физической работы должны идти через `RRL_WAREHOUSE_TASK`.

## 8. Спуск полного паллета в грузовую зону

Подача полного паллета в грузовую зону под отгрузку или дальнейшую операцию также является wave-сценарием, а не самостоятельным `SHIPMENT` источником для ричтрака.

Для строк волны типа `FULL_PALLET` система создает физическую задачу:

- `TASK_TYPE = PICKING_MOVE`;
- `TASK_SOURCE = WAVE`;
- `SOURCE_DOC_TYPE = PICK_WAVE`;
- `SOURCE_DOC_ID = RRL_PICK_WAVE.PICK_WAVE_ID`;
- `SOURCE_TASK_ID = RRL_PICK_WAVE_TASK.PICK_WAVE_TASK_ID`;
- `UID_PALLET` и `SSCC` - идентификатор паллета;
- `FROM_CELL` - ячейка хранения;
- `TO_CELL` - грузовая зона или staging/loading cell;
- `QTY_MODE = PALLET`.

Запуск заданий выполняется через `POST /api/picking/waves/{pick_wave_id}/staging/release` с целевой грузовой зоной `to_cell`.

После подтверждения водителем:

- `RRL_WAREHOUSE_TASK` становится `DONE`;
- domain sync handler закрывает связанную `RRL_PICK_WAVE_TASK`;
- связанная `RRL_PICK_TASK` получает факт и целевую грузовую зону;
- `RRL_PICK_RESERVATION` и `RRL_PICK_WAVE_RESERVATION` переводятся в `CONSUMED`;
- повторный запуск release не создает дублирующие active warehouse tasks для той же строки волны.

## 9. API

Базовые endpoints:

- `GET /api/warehouse-tasks`
- `GET /api/warehouse-tasks/{task_id}`
- `POST /api/warehouse-tasks/{task_id}/assign`
- `POST /api/warehouse-tasks/{task_id}/start`
- `POST /api/warehouse-tasks/{task_id}/complete`
- `POST /api/warehouse-tasks/{task_id}/cancel`
- `POST /api/picking/waves/{pick_wave_id}/staging/release`

Права:

- `warehouse_task_view`;
- `warehouse_task_execute`.
- `pick_wave_launch` для выпуска wave staging-заданий.

## 10. MVP

В MVP обязательно:

- создать таблицу `RRL_WAREHOUSE_TASK`;
- создавать `RAW_TO_PRODUCTION` при передаче сырья в производство;
- создавать `FG_TO_STORAGE` при выпуске паллетов готовой продукции;
- создавать `REPLENISHMENT` при запуске волны, если нужно пополнить pick face;
- создавать `PICKING_MOVE` для полного паллета волны при подаче в грузовую зону;
- дать API списка и смены статусов;
- не менять старые остатки WMS напрямую при создании задания;
- хранить ссылку на исходный MES-документ.

## 11. Следующие расширения

- отдельная мобильная или терминальная страница для водителя;
- сканирование паллета и ячейки;
- назначение заданий на технику;
- приоритеты по маршруту и зонам;
- объединение заданий в рейсы;
- контроль ошибок: неправильный паллет, неправильная ячейка, паллет уже занят другим заданием.

## 12. Отладочный ТСД ричтрака

Для функционального и нагрузочного тестирования нужен компактный экран, который можно открыть на стандартном ТСД.

Текущая raw UI страница:

- `wiki-raw/wms_admin_ui_reference/reachtruck-tsd.html`;
- `wiki-raw/wms_admin_ui_reference/reachtruck-tsd.js`.

Требования к экрану:

- одна колонка, ширина от 320px;
- минимум элементов: водитель, режим, карточка текущего задания, сканы, действия;
- без таблиц и диспетчерских панелей;
- активные задания: `PLANNED`, `ASSIGNED`, `IN_PROGRESS`;
- режимы: `мои + свободные`, `свободные`, `все`;
- действия через `/api/warehouse-tasks`: `assign`, `start`, `complete`, `cancel`;
- при завершении отправляются `scanned_pallet`, `scanned_from_cell`, `scanned_to_cell`, `fact_qty`.

Задача водителя может быть назначена:

- на полный паллет;
- на количество коробок.

Для полного паллета водитель подтверждает выполнение кнопкой `Паллет`, без ручного ввода количества.

Для коробок водитель подтверждает кнопкой `Коробки`:

- если поле факта пустое, считается, что перемещено плановое количество из задания;
- если водитель указал меньшее количество, текущая задача закрывается на фактическое количество, а на остаток создается новая задача `PLANNED`;
- если водитель указал количество больше планового, API должен вернуть бизнес-ошибку и оставить задачу открытой.

Для задачи `QTY_MODE = PALLET` частичное завершение запрещено: водитель подтверждает ее только как полный паллет.

## 13. Ресурсное Планирование Ричтраков И Смен

Следующий архитектурный слой: водитель и техника должны рассматриваться как складские ресурсы.

Подробное ТЗ вынесено в [ресурсы склада, смены водителей, планирование ричтраков и план-фактный Gantt](warehouse_resource_planning_tz.md).

Ключевые правила:

- ричтрак, KIKA, погрузчик и другая техника являются планируемыми ресурсами;
- водитель выходит на смену и регистрируется на конкретной технике;
- после регистрации создается активная resource session;
- ТСД должен выдавать задания только водителю с активной сессией;
- dispatch учитывает тип техники, зону, квалификацию, смену, текущую очередь и приоритеты;
- должен быть плановый Gantt по ресурсам;
- должен быть фактический Gantt по событиям assign/start/complete;
- план-фактный анализ показывает загрузку, простой, отклонения и SLA.
