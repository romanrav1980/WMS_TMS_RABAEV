# NIKORA: быстрый интерфейс водителя ричтрака

Дата: 15.09.2026. Уточнение владельца: простые экраны, минимальные переходы. UI-14, подспринт F2.6; cross-dock расширение F4.1. Связь: [[requirements/nikora_ui_workplaces_tz]], [[roadmap/nikora_ui_subsprints]].

## 1. Основной вариант — одно задание на одном экране

Большими символами: **ОТКУДА A-03-02 → КУДА CD-02**, текущий шаг «Возьмите / Перевезите / Поставьте», идентификатор паллеты, количество/единица, вид операции и предупреждение. Остальное — в раскрытии «Детали», не в обязательном маршруте. Верхняя компактная строка: техника RT-01, исполнитель, связь, очередь. Внизу один активный сканер и кнопка «Проблема». После подтверждённого завершения автоматически показывается следующее назначенное задание.

Первый вход в смену: идентификация сотрудника и техники, действующая сессия и необходимые допуски. Не повторять вход/выбор техники на каждом задании. Смена оператора, выход и неисправность доступны в меню, но не соседствуют с основным действием.

Минимальный штатный цикл:

1. Сервер назначает/резервирует доступное задание с учётом прав, техники, зоны и приоритета. Автоподача только разрешённых задач; нельзя захватить задачу другого водителя.
2. На том же экране сканировать источник, затем идентификатор паллеты. Валидный скан автоматически переводит фокус/шаг без кнопок «Далее». Если политика разрешает источник из однозначного текущего местоположения HU, отдельный скан источника можно убрать только после оценки риска.
3. После фактического безопасного взятия подтвердить «Взял», если физическое событие не подтверждается утверждённым устройством/процессом. Само чтение этикетки не доказывает подъём.
4. Перевезти; после фактической установки сканировать целевую ячейку/линию. В базовом процессе скан назначения является подтверждением «поставил» по инструкции. Если скан приходится делать до установки, требуется отдельная крупная команда «Поставил» — не выдавать ранний скан за факт.
5. Сервер подтверждает завершение, короткий сигнал/надпись «Завершено», следующее назначенное задание появляется на том же экране. При задержке ответа сохраняется «Подтверждается», не следующий груз.

Цель: **0 переходов между страницами на штатное перемещение**, без обязательного открытия списка, без «Взять → Старт → Далее → Завершить» как четырёх формальных кнопок. Число физических подтверждений определяется безопасностью, а не сокращается любой ценой. Не требовать чтения/ввода во время движения; сканирование и взаимодействие только после безопасной остановки согласно локальным правилам.

## 2. Вариант Б — бортовой терминал

Те же данные/команды, но горизонтально: слева источник и «Взять», справа назначение и «Поставить», снизу широкая полоса активного шага. Предназначен для закреплённого планшета; не другая логика. Текст адресов виден с рабочего расстояния, зоны нажатия минимум 48 px, нет мелких иконок и горизонтальной таблицы.

Рекомендация: А для ручного ТСД, Б для бортового устройства. Начальнику склада остаётся список/управление очередью; водителю показывается одна текущая задача и компактно следующая, без принудительной навигации.

## 3. Операции и отклонения

Поддержать перемещение полной паллеты, пополнение зоны отбора, подачу к cross-dock/воротам и возврат разрешённого груза. Отбор коробок — отдельная явно обозначенная операция с фактическим количеством, не случайный альтернативный способ завершить полную паллету.

«Проблема» открывает короткую нижнюю панель: «Нет паллеты», «Ячейка занята», «Повреждено», «Проезд закрыт», «Неисправна техника», «Другой идентификатор». После выбора — фиксированная причина и комментарий/фото, если требуется. Чужая паллета/цель не принимается. Переназначение цели идёт серверной командой с проверкой capacity/допустимости; водитель не вводит произвольную новую ячейку и не отменяет обязательство ТМС.

Пустая очередь — «Заданий нет, ожидание», не ошибка. Потеря связи до взятия блокирует старт; после взятия показывать сохранённое назначение и «Груз на технике, подтверждение ожидается», не потерять custody. Новые задания не выдавать до сверки. При невозможности безопасного продолжения — остановка и связь с диспетчером; offline-факт не равен серверному завершению.

## 4. Приёмка RT-UI

- RT-01: обычное перемещение на одной странице, три требуемых скана и физическое подтверждение взятия; нет обязательных «назад/далее/список».
- RT-02: следующий task появляется только после подтверждения сервера, повтор скана/timeout не удваивает перемещение.
- RT-03: неправильный HU/источник/цель остаётся на том же шаге и показывает ожидаемое значение.
- RT-04: два водителя не получают активное владение одним заданием; смена техники сохраняет историю.
- RT-05: занятая цель формирует исключение, а не «успешное» перемещение.
- RT-06: offline после взятия сохраняет груз/цель/событие; после восстановления выполнена сверка, нет нового груза поверх незавершённого.
- RT-07: перчатки, аппаратный сканер, 360 px и бортовой планшет; адреса читаются, существенное действие не спрятано в меню.
- RT-08: измерить отдельно ручные касания, переходы страниц, время от последнего скана до серверного ответа (предварительная цель P95 ≤1 с в сети склада), повторы и ошибки. Физическое время перемещения учитывать отдельно. Цель уточняется на реальной сети/Oracle, не по макету.

## 5. Переиспользование

Есть [reachtruck-tsd.html](../../wiki-raw/wms_admin_ui_reference/reachtruck-tsd.html) и [reachtruck-tsd.js](../../wiki-raw/wms_admin_ui_reference/reachtruck-tsd.js): сессии сотрудника/техники, задание, источник/назначение, scan fields и API warehouse tasks. Текущий экран содержит «Назад / Дальше / Взять / Старт / Паллет / Коробки / Отмена» и поля входа в основной форме. Для нового UX сгруппировать смену в отдельный вход, оставить одно активное поле и автомат состояний на существующих командах. Это упрощение представления с сохранением серверных проверок, не новый движок складских задач.
