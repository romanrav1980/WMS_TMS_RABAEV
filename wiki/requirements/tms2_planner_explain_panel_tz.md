## 1. Назначение

В планировщике транспорта нужна боковая вылетающая панель, которая объясняет логисту, как был выполнен расчет авто-плана: какие данные вошли в расчет, какой провайдер расстояний использован, какой решатель выбран, какие ограничения применялись, как загружены машины, почему часть заявок могла остаться без рейса и на какие риски нужно обратить внимание перед применением плана.

Панель должна превращать авто-план из "черного ящика" в проверяемое решение. Логист должен видеть не только результат в виде рейсов на карте, но и ход расчета, параметры, метрики качества, предупреждения и источники данных.

## 2. Пользовательский сценарий

1. Логист открывает `Карта + VRP`, выбирает дату СТ, тип ТС и режим решателя.
2. Нажимает `Авто-план`.
3. После старта расчета справа открывается вылетающая панель `Детали расчета`.
4. Во время расчета панель показывает этапы: загрузка заявок, проверка координат, матрица расстояний, подбор машин, оптимизация, сохранение плана.
5. После завершения панель показывает итоговые метрики, загрузку машин, предупреждения и список факторов, которые реально участвовали в расчете.
6. Перед нажатием `Применить план` логист проверяет панель и понимает, почему система предложила именно такой план.

## 3. Размещение и поведение UI

Панель открывается поверх карты справа.

Требования:

- ширина desktop: 420-520 px;
- на узком экране панель занимает 100% ширины;
- карта под панелью не должна ломать масштаб и не должна перекрывать кнопки Leaflet;
- открыть панель можно кнопкой `Детали расчета` рядом с `Авто-план` или кликом по блоку `Метрики плана`;
- после успешного авто-плана панель открывается автоматически;
- закрытие панели не сбрасывает план;
- при новом расчете содержимое панели очищается и заполняется заново;
- при ошибке расчета панель показывает этап, на котором расчет остановился, и техническую причину.

## 4. Структура панели

Панель должна иметь пять разделов: `Обзор`, `Параметры`, `Ход расчета`, `Загрузка автомобилей`, `Предупреждения`.

### 4.1 Обзор

Показывает краткий итог расчета:

| Поле | Описание |
|---|---|
| Дата планирования | `plan_date` |
| Статус | `идет расчет`, `готово`, `ошибка`, `отменено`, `применено` |
| Заявок в расчете | число СТ, переданных в VRP |
| Заявок на карте | число СТ с координатами |
| Рейсов предложено | `routes.length` |
| Без рейса | `unassigned_sts.length` |
| Общий пробег | `total_km` |
| Средняя загрузка парка | `fleet_utilization_pct` |
| Нарушений окон | `tw_violations` |
| Score | итоговая оценка плана |
| Время расчета | `solve_time_ms` |

Если `Без рейса > 0` или `Нарушений окон > 0`, панель должна показывать это как предупреждение, а не как обычную строку.

### 4.2 Параметры расчета

Раздел фиксирует, с какими настройками был выполнен расчет.

| Параметр | Источник |
|---|---|
| Дата СТ | выбранный фильтр UI |
| Тип ТС | выбранный фильтр UI |
| Склады | `ware_ids`, если заданы |
| Решатель | `solver`: auto, OR-Tools, Clarke-Wright, cluster, attention model |
| Провайдер расстояний | `source`: auto, OSRM, Valhalla, Haversine |
| Активный routing provider | `/routing/status.active_provider` |
| Лимит времени | `time_limit_s` |
| Использование кластеров | флаг слоя кластеров |
| Полигон отбора | если применен ручной полигон |
| Источник временных окон | Oracle `ZONE_TIME_PLAN_IN/OUT` или fallback по `ORD` |

Если был fallback, панель должна явно писать: `Временные окна части заявок рассчитаны fallback-правилом по порядку адреса, потому что в Oracle нет ZONE_TIME_PLAN_IN/OUT.`

### 4.3 Ход расчета

Раздел показывает журнал этапов. Это не системный лог для разработчика, а понятный логисту ход работы.

Минимальные этапы:

| Этап | Что показывать |
|---|---|
| Загрузка заявок | сколько СТ найдено на дату, сколько прошло фильтры |
| Проверка координат | сколько адресов с координатами, сколько пропущено |
| Матрица расстояний | провайдер, число пар, был ли fallback |
| Подбор машин | сколько активных машин доступно, какие типы |
| Ограничения | вместимость, вес, временные окна, гидроборт, тип ТС |
| Оптимизация | решатель, лимит времени, факт времени |
| Построение рейсов | сколько рейсов создано в плане |
| Проверка плана | capacity, windows, unassigned, score |
| Сохранение плана | `plan_id` |

Каждый этап имеет статус: `pending`, `running`, `done`, `warning`, `error`, `skipped`.

Пример текста этапов:

```text
Готово: найдено 272 СТ, 272 с координатами
Готово: матрица 121452 пар, провайдер haversine
Готово: построено 97 рейсов, 0 заявок без рейса
Предупреждение: средняя загрузка 93.8%, 4 рейса ниже 60%
```

### 4.4 Загрузка автомобилей

Раздел показывает, как использован автопарк.

По каждой машине:

| Поле | Описание |
|---|---|
| Машина | `vehicle_num` |
| Тип | `vehicle_type` |
| Паллеты | `total_pallets / max_pallets` |
| Вес | `total_kg` |
| Пробег | `total_km` |
| Длительность | `total_duration_min` |
| Загрузка | `utilization_pct` |
| Адресов | `stops.length` |
| Временные окна | число строгих окон и нарушений |

Цвет загрузки:

- зеленый: `>= 85%`;
- желтый: `60-84%`;
- красный: `< 60%`;
- отдельный красный статус: `> 100%`, это ошибка плана.

Нужно показывать агрегаты:

- средняя загрузка;
- минимальная загрузка;
- максимальная загрузка;
- количество машин с загрузкой ниже 60%;
- количество машин выше 100%;
- сколько рейсов в среднем приходится на машину за день;
- соответствует ли текущий план целевому правилу: каждая машина может выполнить минимум 4 рейса в день.

Для правила "минимум 4 рейса в день" панель должна показывать расчет:

```text
Активных машин: 15
Целевой дневной ресурс: 60 рейсов
План требует: 97 рейсов
Оценка: требуется повторное использование машин в течение дня, проверить доступность в Ганте
```

Если есть прогноз доступности из `/vehicles/available` или Ганта, использовать его. Если нет, писать: `Прогноз доступности не проверен`.

### 4.5 Предупреждения и тонкости

Раздел собирает все причины, которые логист должен проверить перед применением.

Обязательные предупреждения:

- есть СТ без координат;
- есть СТ без рейса;
- есть нарушение временного окна;
- часть временных окон взята из fallback;
- provider `auto` упал и был использован Haversine;
- матрица расстояний устарела;
- рейсы ниже минимальной загрузки;
- рейсы выше вместимости;
- машина не подходит по типу ТС;
- нужен гидроборт, а машина без гидроборта;
- часть адресов вручную передвинута drag-and-drop, но `Применить план` создаст исходный backend-план;
- расчет был отменен или завершился timeout;
- план сохранен, но еще не применен в рейсы.

Каждое предупреждение должно иметь краткое действие:

| Предупреждение | Действие |
|---|---|
| Нет координат | открыть список адресов без координат |
| Есть без рейса | показать список СТ |
| Нарушены окна | раскрыть рейсы с нарушениями |
| Haversine fallback | предложить пересчитать матрицу OSRM/Valhalla |
| Низкая загрузка | показать машины ниже 60% |
| Перегруз | заблокировать `Применить план` или требовать явное подтверждение |

### 5.2 Расширение остановок и рейсов

В `VrpRouteStop` дополнительно вернуть:

- `tw_violation_min`;

Если точного arrival/departure пока нет в алгоритме, поле допускается `null`, но UI должен писать `ETA не рассчитано`, а не показывать фиктивные значения.

## 6. Frontend

Компонент: `TransportPlannerExplainDrawer`.

Файлы:

- `admin/wms_admin_frontend/src/components/TransportPlannerPage.tsx`;
- стили только в `admin/wms_admin_frontend/src/styles.css`.

Состояния:

- `closed`;
- `calculating`;
- `ready`;
- `error`;
- `applied`.

Панель не должна заменять текущий правый список рейсов. Она является дополнительным вылетающим слоем объяснения. Текущая правая панель рейсов остается рабочей для просмотра маршрутов и drag-and-drop.

Минимальные элементы:

- заголовок `Детали расчета`;
- статус-чип расчета;
- кнопка закрытия;
- кнопка `Скопировать отчет`;
- раздел `Обзор`;
- раздел `Параметры`;
- раздел `Ход расчета`;
- раздел `Загрузка машин`;
- раздел `Предупреждения`;
- ссылка/кнопка `Открыть план на карте`, которая закрывает drawer и подсвечивает маршруты.

Нельзя использовать browser alert для результата матрицы. Вместо alert результат `Матрица пересчитана: 121452 пар, провайдер haversine` должен попадать в панель и toast.

## 7. Ошибки

Если `/planner/solve` вернул ошибку:

- панель открыта;
- статус `Ошибка`;
- показывается этап, на котором расчет остановился;
- показывается HTTP-код и текст backend;
- если ошибка похожа на CORS/network, UI дополнительно пишет: `Проверьте доступность API 8088 и CORS, браузер мог скрыть backend 500 как Failed to fetch`;
- кнопка `Повторить расчет` остается доступной.

## 8. Права доступа

Панель доступна пользователям с правом `transport_dispatch_view`.

Кнопки действий:

- `Повторить расчет`, `Пересчитать матрицу`, `Применить план` требуют `transport_dispatch_edit`;
- если права нет, панель показывает данные read-only и объясняет, почему действие недоступно.

## 9. Нефункциональные требования

- открытие панели: не более 100 мс после получения плана;
- рендер списка до 150 рейсов без заметного лага;
- длинные списки машин и предупреждений виртуализировать или ограничивать высоту с прокруткой;
- panel state не должен сбрасывать карту и маркеры;
- расчеты и логи не должны запускать дополнительные тяжелые Oracle-запросы при каждом открытии панели;
- все данные панели должны приходить из уже выполненного solve/metrics response или легкого cached endpoint.

## 10. Тестирование и приемка

### 10.1 Functional

Добавить тесты:

- `/planner/solve` возвращает `explain.input`, `explain.routing`, `explain.solver`, `explain.fleet`, `explain.steps`, `explain.warnings`;
- `orders_total == len(planner/orders)` для той же даты;
- `orders_with_coords` совпадает с фактическими координатами;
- `vehicles_used <= vehicles_total`;
- `over_capacity_routes == 0` для принятого seed;
- при `source=auto` и fallback поле `fallback_used=true`;
- при отсутствии временных окон есть warning про fallback.

### 10.2 UI smoke

Playwright должен проверить:

- после клика `Авто-план` открывается `Детали расчета`;
- в панели есть дата, provider, solver, число рейсов, загрузка и ход расчета;
- предупреждения видны, если они есть;
- результат пересчета матрицы не открывает browser alert, а отображается в панели/toast;
- закрытие панели не удаляет план с карты;
- кнопка `Скопировать отчет` кладет текстовый отчет в clipboard.

### 10.3 Wave 3 business-factor trace

Панель должна быть включена в Wave 3 как доказательство участия факторов:

- координаты;
- матрица расстояний;
- вместимость паллет;
- вес;
- временные окна;
- тип ТС;
- гидроборт;
- доступность машины;
- fallback provider;
- unassigned ST.

Тест не должен проверять только наличие ключей. Он должен проверять значения, distinct/non-default, cross-source equality и бизнес-инварианты.

## 11. Acceptance Criteria

Фича считается готовой, когда:

- логист после расчета видит не только маршруты, но и объяснение: входные данные, параметры, provider, solver, шаги, предупреждения;
- нет browser alert для матрицы, все сообщения встроены в UI;
- панель показывает загрузку каждой машины и агрегаты по парку;
- перегруз или нарушение окон нельзя пропустить визуально;
- backend возвращает `explain` contract для solve/metrics;
- Playwright UI smoke прошел;
- functional tests проверяют значения, а не только HTTP 200;
- после приемочного прогона выполнен slow SQL review.
