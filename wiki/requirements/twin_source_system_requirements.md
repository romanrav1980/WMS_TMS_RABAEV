# Требования к головной системе WMS/TMS как источнику цифрового двойника

Дата: 14 октября 2026 года. Основание: live-сверка двойника [[subprojects/wms_twin_3d]] со спецификацией [[requirements/warehouse_operations_digital_twin]] и правилом WMS для топологии (`modules/master_data/infrastructure/topology_coverage.py`).

## Принцип

Структура склада, позиции исполнителей и факты исполнения живут в WMS. Двойник их только читает и не достраивает. Если в WMS чего-то нет, двойник показывает «неизвестно» или «нет на схеме» и не придумывает координаты, движение или занятость. Поэтому полнота картинки определяется требованиями к головной системе, а не к рендеру.

Ниже по каждому требованию: что должно быть, как проверить, состояние dev-стенда на 14.10.2026.

## R1. Структура склада — единственный источник: опубликованная топология

| № | Требование | Проверка | Dev 14.10.2026 |
|---|---|---|---|
| R1.1 | Для каждого рабочего WARE_ID есть ровно одна действующая опубликованная топология. Правило WMS: последняя `PUBLISHED` (max TOPOLOGY_ID); черновики (VALIDATED/DRAFT) рабочими не считаются | Склады с заданиями без опубликованной топологии — 0 | 15 из 16 складов с открытыми заданиями без опубликованной топологии; у склада 1 опубликована тестовая `IDEMP…` на 4 ячейки, а полная `LOAD-1500-2CH-60` только VALIDATED |
| R1.2 | Полное покрытие справочника ячеек: каждая `RRL_CELLS.CELL` склада — ровно одна активная `RRL_TOPOLOGY_CELL` с `LEGACY_CELL_CODE` и классифицированным `CELL_KIND` | `published_cell_coverage(ware).status = PUBLISHED_CATALOG_COMPLETE`; это условие публикации топологии | В `IDEMP…` у 4 ячеек нет `LEGACY_CELL_CODE`; ячейки заданий склада 1 (`QW…`, `QP…`, `QS…`) на схеме не найдены |
| R1.3 | Read-only API покрытия: `GET …/warehouses/{ware_id}/topology-coverage` — результат `published_cell_coverage` (счётчики, образцы непокрытых ячеек) | Ответ совпадает с SQL-проверкой | Функция есть, наружу используется только в shipping register |
| R1.4 | Геометрия в метрах: x, y плоскости, z — фактическая высота уровня, width/depth/height ячейки, angle; единая система координат и происхождение | Нет ячеек с нулевыми размерами; уровни > 1 имеют z > 0 | У `LOAD-1500` все ячейки уровня 1, z=0 |
| R1.5 | Проходы с шириной и допуском техники (picker/reachtruck), направлением; специальные зоны как объекты топологии: приёмка, экспедиция, карантин, зарядка, парковка, контроль | Каждая зона, на которую ссылаются задания, есть в топологии | Ворота/проходы есть только в `LOAD-1500`; спецзон нет |
| R1.6 | Ворота связаны с доками: каждой записи `RRL_TT_DOCK` склада соответствуют ворота топологии (`GATE_CODE`, вид RECEIVING/SHIPPING/BOTH, позиция на фасаде) | Доков без ворот — 0 | Связи нет в схеме (см. [[requirements/twin_live_data_fixes_codex_prompt]], задача 1) |
| R1.7 | Изменение планировки = новая версия публикации; старая версия остаётся для истории и replay | Версия и дата публикации в ответе карты | Поля есть |
| R1.8 | Текстовые поля без порчи кодировки | `scripts/check-encoding.ps1`-маркеры в данных топологий — 0 | `ZONE_NAME` топологии 2 испорчен |

## R2. Позиции людей и техники

| № | Требование | Проверка | Dev |
|---|---|---|---|
| R2.1 | Каждое подтверждающее действие терминала (скан ячейки, паллеты, CASE, ворот) обновляет `last_cell` и `last_position_at` ресурса; код ячейки — из справочника `RRL_CELLS` | Ресурсы с активной сессией без обновления позиции дольше N минут — 0 | `last_cell` есть у 1 ресурса из 2, и она вне топологии |
| R2.2 | Время позиции — с часовым поясом (instant), не локальная строка | Поля `*_instant` или ISO с зоной | Время без зоны |
| R2.3 | Связь человек ↔ техника — через активную сессию (`resource_session`, `equipment_id`), heartbeat сессии | У активной сессии есть heartbeat ≤ 2 мин | 1 активная сессия из 39 |
| R2.4 | Опционально: телеметрия/RTLS техники (x, y, время, источник, точность) отдельным read-only потоком | Нет — пункт для пилота | Нет |

## R3. Факты исполнения заданий

| № | Требование | Проверка | Dev |
|---|---|---|---|
| R3.1 | Журнал переходов каждого задания с временем и operation_id: ASSIGNED, STARTED, SOURCE_CONFIRMED (скан источника), CARRYING (захват), TARGET_CONFIRMED (скан назначения), DONE/PARTIAL, CANCELLED, ERROR | Для DONE-задания есть цепочка событий | Есть только поля started/finished; промежуточные факты не хранятся |
| R3.2 | Лента изменений с курсором (`?since=<cursor>`) вместо опроса списков с `limit=500`; серверный фильтр `ware_id` | Повтор с тем же курсором не даёт дублей; пропусков нет | Только списки с лимитом; 500 строк — не весь склад |
| R3.3 | CASE: `current_cell` обновляется при каждом подтверждении строки; строки хранят ячейку справочника | У CASE IN_PROGRESS есть current_cell | `current_cell` пуст |
| R3.4 | Причина блокировки — структурированный код + текст + блокирующий объект (ячейка, задание, ресурс) | BLOCKED без причины — 0 | Есть `blocking_reason`/`blocking_cell_code` у CASE |

| № | Требование | Проверка | Dev |
|---|---|---|---|

## R5. Транспорт и двор

| № | Требование | Проверка | Dev |
|---|---|---|---|
| R5.1 | Склад рейса — через док (`RRL_TT_DOCK.WARE_ID`) в ответе рейсов | Рейсы с доком без склада — 0 | Нет поля |
| R5.2 | Факты двора с временем: въезд (КПП/геозона), постановка под док, начало/конец погрузки, выезд (`RRL_TT_OPERATIONS` факт, КПП, GPS) | Для отгруженного рейса есть постановка и выезд | Не хранятся в рейсе; фактические операции не подключены |
| R5.3 | Окно дока — явные плановые начало и конец, а не только время отгрузки | Окно есть у спланированных рейсов | Только SHIPMENT_TIME |

## R6. Доступ и эксплуатация

- Отдельная read-only роль двойника с ограничением своим складом (`warehouse_task_view`, `case_pick_view`, `transport_dispatch_view`, `warehouse_topology_view`), без GLOBAL_ADMIN.
- Ограниченные выборки и SLA ответа: структура ≤ 2 с (кэш по версии), лента изменений ≤ 500 мс; долгие SQL — по правилам `AGENTS.md`.
- Гейт перед пилотом: R1.1, R1.2, R1.6, R2.1, R3.2 выполнены для пилотного склада.

## Что это даёт двойнику

| Выполнено | Что начинает показывать двойник |
|---|---|
| R1 | Склад в реальной планировке; все задания и CASE на своих ячейках; ворота рейсов |
| R2 | Люди и техника на последних подтверждённых местах с возрастом наблюдения |
| R3 | Фазы «источник подтверждён → перевозка → назначение» как факт, а не расчётная анимация; live без опроса |
| R4 | Заполненность ячеек и пустые ячейки отбора как факт |
| R5 | Машины во дворе и у ворот; окна дока и опоздания по факту |
