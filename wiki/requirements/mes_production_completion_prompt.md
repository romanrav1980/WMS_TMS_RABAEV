# Prompt: Реализация завершения производства в MES

Статус: prompt для следующего этапа реализации.

## Зачем Нужен Промежуточный Журнал MES-Движений

В старом WMS уже есть таблицы остатков, поддонов, строк поддонов и процедуры, которыми пользуются C# desktop client и `Tserver`. Если новая MES-процедура сразу начнет напрямую менять старые остатки, появляется высокий риск сломать совместимость:

- старый C# клиент может ожидать другой порядок записей, статусов и движений;
- `Tserver` может читать остатки и строки поддонов в старой модели;
- старые процедуры могут сами пересчитывать остатки, создавать события или менять паллеты;
- при ошибке завершения производства будет сложно понять, что уже списано, а что еще нет;
- повторный вызов API может случайно списать сырье второй раз.

Поэтому первый безопасный слой должен быть таким:

1. MES фиксирует намерение и факт движения в отдельном журнале MES-движений.
2. В журнале видно, что произошло: сырье перемещено в производство, сырье потреблено, готовая продукция выпущена, поддон создан.
3. Каждая запись имеет `IDEMPOTENCY_KEY`, статус, ссылку на production order, сырьевую партию, готовую партию, поддон и пользователя.
4. Старые WMS-таблицы обновляются только через отдельный controlled bridge: PL/SQL-процедуру, которая знает старую модель и может быть протестирована отдельно.
5. Если bridge упал, MES-движение остается в статусе `PENDING_WMS_APPLY` или `ERROR`, его можно повторить.
6. Если старый WMS уже обновлен, повторный вызов не дублирует движение, потому что journal/bridge проверяет идемпотентность.

Иными словами, MES journal является буфером между новой бизнес-логикой производства и старым WMS-ядром. Это похоже на outbox, но для внутренних складских движений. Он дает трассируемость, повторяемость, аудит и безопасный переход от legacy-логики к новой.

В MVP не нужно пытаться сразу переписать весь старый учет остатков. Нужно сначала:

- создать MES production order;
- рассчитать плановое сырье по BOM;
- зафиксировать выдачу сырья в производство;
- зафиксировать фактическое потребление сырья;
- зафиксировать выпуск готовой партии и поддонов;
- записать все это в MES movement journal;
- только затем применить изменения к старым WMS-таблицам через контролируемый bridge.

## Prompt Для Исполнения

```text
Ты — senior backend engineer и Oracle PL/SQL developer в проекте WMS/MES RABAEV.

Контекст проекта:
- База Oracle `RABAEV@127.0.0.1:1521/orcl`.
- Backend: Python FastAPI.
- База является основной системой учета.
- Уже есть BOM-блок:
  - `RRL_BOM`
  - `RRL_BOM_LINE`
  - `RRL_BOM_AUDIT`
  - `RRL_BOM_API`
  - API `/api/bom`
- Артикулы в Oracle расширены до 40 символов.
- Уже есть traceability/outbox база:
  - `RRL_TRACE_EVENT`
  - `RRL_TRACE_EDGE`
  - `RRL_EVENT_OUTBOX`
  - `RRL_ADAPTER_REQUEST_LOG`
- Старые C# desktop client и `Tserver` продолжают использовать legacy WMS-таблицы и процедуры.
- Нельзя удалять таблицы, дропать объекты и делать destructive changes без отдельного подтверждения.

Задача:
Проработать и реализовать процедуру завершения производства.

Бизнес-логика:
1. Производственный заказ создается на выпуск готовой продукции по конкретному BOM.
2. До завершения производства сырье уже было перемещено или списано со склада сырья в зону/склад производства.
3. При завершении производства нужно:
   - списать сырье из зоны производства согласно BOM;
   - зафиксировать фактическое потребление сырья;
   - создать партию готовой продукции;
   - выпустить нужное количество поддонов готовой продукции;
   - связать сырьевые партии, производственный заказ, готовую партию и поддоны в traceability genealogy;
   - создать события в outbox для будущих интеграций с Меркурием и Честным Знаком.

Обязательный архитектурный принцип:
Не менять старые WMS-остатки напрямую из новой MES-логики на первом этапе.

Сначала нужно создать отдельный журнал MES-движений и связать его со старым WMS через controlled bridge.

Причина:
- старые остатки и поддоны используются C# клиентом и `Tserver`;
- прямые записи в legacy-таблицы могут сломать старые процедуры;
- завершение производства должно быть идемпотентным;
- при сбое нужно видеть, какое движение уже создано, какое применено к WMS, а какое ожидает повтора;
- нужен аудит и возможность повторного применения без двойного списания.

Требование к MES movement journal:
Добавить таблицу или набор таблиц для внутреннего журнала MES-движений.

Журнал должен хранить:
- `MES_MOVEMENT_ID`;
- `PRODUCTION_ORDER_ID`;
- `MOVEMENT_TYPE`:
  - `RAW_ISSUE_TO_PRODUCTION`;
  - `RAW_CONSUMPTION`;
  - `FG_LOT_RELEASE`;
  - `FG_PALLET_RELEASE`;
- `SOURCE_ENTITY_TYPE`;
- `SOURCE_ENTITY_ID`;
- `TARGET_ENTITY_TYPE`;
- `TARGET_ENTITY_ID`;
- `ARTICUL`;
- `BATCH_NO`;
- `QTY`;
- `UNIT_CODE`;
- `WARE_ID_FROM`;
- `WARE_ID_TO`;
- `PRODUCTION_ZONE`;
- `UID_PALLET`;
- `SSCC`;
- `STATUS`:
  - `DRAFT`;
  - `READY`;
  - `PENDING_WMS_APPLY`;
  - `APPLIED_TO_WMS`;
  - `ERROR`;
  - `CANCELLED`;
- `IDEMPOTENCY_KEY`;
- `ERROR_TEXT`;
- `CREATED_AT`;
- `CREATED_BY`;
- `APPLIED_AT`;
- `APPLIED_BY`;

Controlled bridge:
Нужно реализовать PL/SQL-процедуру или набор процедур, которые применяют записи MES movement journal к старым WMS-таблицам.

Bridge должен:
- брать только движения со статусом `PENDING_WMS_APPLY`;
- проверять `IDEMPOTENCY_KEY`;
- не применять одно движение дважды;
- обновлять legacy WMS-таблицы только через один контролируемый контракт;
- при успехе ставить `APPLIED_TO_WMS`;
- при ошибке писать `ERROR` и `ERROR_TEXT`;
- позволять повторить применение после исправления причины.

Важно:
В MVP допустимо, чтобы часть legacy WMS-обновлений была mock/минимальной, если точная старая процедура еще не подтверждена. Но MES movement journal, traceability и audit должны быть полноценными.

Нужно выполнить анализ текущей схемы:
- найти существующие таблицы остатков, поддонов, строк поддонов, производственных партий;
- понять, какие старые таблицы используются для выпуска поддонов:
  - `RRL_PALLETS`;
  - `RRL_SBORKA_PALLET_ROWS`;
  - `RRL_ORDER_PALLET_ROWS`;
  - `TMP_PALLET_ROWS`;
  - другие связанные таблицы;
- найти существующие процедуры, которые создают паллеты/поддоны;
- проверить, где сейчас списываются остатки и как ведется движение товара.

Сформировать техническое решение:
1. Какие таблицы нужны для MES production order:
   - production order header;
   - production order status;
   - planned BOM snapshot;
   - raw material soft demand, hard reservation, and issue to production;
   - MES movement journal;
   - raw material consumption fact;
   - finished goods lot;
   - finished goods pallets.
2. Какие существующие таблицы можно использовать, а какие лучше добавить новыми.
3. Как связать новую MES-логику со старым WMS, чтобы C# клиент и `Tserver` не сломались.
4. Как учитывать отклонения от BOM:
   - фактический расход больше/меньше планового;
   - замены сырья;
   - потери;
   - брак;
   - частичный выпуск;
   - повторное завершение или отмена завершения.
5. Как обеспечить идемпотентность:
   - нельзя дважды списать одно и то же сырье;
   - нельзя дважды выпустить одни и те же поддоны;
   - нужен `IDEMPOTENCY_KEY` на уровне complete production и на уровне каждого MES movement.
6. Как обеспечить аудит:
   - кто завершил производство;
   - когда;
   - какие партии сырья списаны;
   - какие поддоны выпущены;
   - какие движения применены к legacy WMS;
   - какие ошибки были.
7. Как обеспечить traceability:
   - Raw Material Lot -> Production Order;
   - Production Order -> Finished Goods Lot;
   - Finished Goods Lot -> Pallet / SSCC;
   - Finished Goods Lot -> CRPT codes позже;
   - Mercury VSD -> Raw Material Lot -> Finished Goods Lot.
8. Как работать с Меркурием и Честным Знаком:
   - завершение производства не должно зависеть от доступности внешних систем;
   - события должны попадать в `RRL_EVENT_OUTBOX`;
   - внешние адаптеры обработают их позже;
   - при ошибке должна быть возможность повторить отправку.
```
