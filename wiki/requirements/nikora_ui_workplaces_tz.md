# NIKORA: ТЗ рабочих мест и визуального интерфейса

Дата: 15.09.2026. Статус: проект требований для согласования, не реализованные экраны. Дополняет [[requirements/nikora_gap_analysis_20260915]] и [[architecture/nikora_minimal_extension]]. Детальная приёмка контроля: [[requirements/nikora_ui_quality_tz]]. План поставки: [[roadmap/nikora_ui_subsprints]].

## 1. Границы и решение по интерфейсам

Одна административная оболочка WMS/TMS с рабочими местами по правам; одна терминальная оболочка со сценариями по назначенному заданию. Не создавать отдельное приложение на каждую должность. Роль, площадка и разрешённая операция определяют доступ. Один человек может совмещать роли; это не отменяет разделение полномочий там, где оно требуется.

Внешние WMS сохраняют собственную сборку. Наши экраны сборщика/контроллера реализуются для текущей WMS. Для остальных источников принимаются эквивалентные факты и результаты контроля по согласованному XML-профилю; нельзя обещать замену их ТСД. Если внешняя WMS не умеет двойной контроль, владелец процесса выбирает до пилота: доработка её адаптера/экранов или обязательный контроль на целевой площадке.

Два варианта настольного представления одних данных:

- **А — таблица + детали:** основной вариант для точных решений, поиска и больших списков; закреплены идентификатор и статус, панель выбранного объекта справа.
- **Б — оперативная доска:** карточки по стадии/ресурсу; для маршрута — последовательность остановок, для склада/ворот — временная сетка. Это переключаемый вид, не второй бизнес-процесс и не второй backend.

Рекомендуется А для интеграций, справочников и транспортной консолидации; Б для управления сменой и зоной cross-dock. Мобильный интерфейс — последовательность сканирования, а не уменьшенная настольная таблица.

Макеты: [интерактивная галерея и инструкция](../../wiki-raw/nikora_ui_20260915/README.md). Данные в ней вымышленные; действия локальные, не вызывают API.

## 2. Общие требования ко всем экранам

- Верхняя строка: площадка, рабочая дата, роль, пользователь, состояние соединения, время последнего подтверждённого обновления. Операционное время — Europe/Tbilisi с явной зоной; API хранит UTC/offset. Переключение даты не изменяет события.
- Поиск: заказ, магазин/адрес, рейс, волна, идентификатор паллеты, messageId. Ведущие нули сохраняются. Legacy ID допустим в обычной WMS; валидный SSCC обязателен там, где этого требует профиль NIKORA.
- Общая карточка прослеживаемости: заказ → часть источника → HU/состав/родители → плечо → волна → приёмка; отдельно версия плана и фактическое событие.
- Состояния данных: загрузка, нет данных, нет подходящих результатов, неполный источник, устарело, нет связи, отказ прав, конфликт версии, ошибка сервера. Ноль и отсутствие данных визуально различаются.
- План/факт, сборка/контроль/готовность к отгрузке и HTTP-приём/бизнес-применение сообщения показываются раздельно. Цвет всегда сопровождается текстом и причиной.
- Изменение: preview влияния → подтверждение с версией → серверный результат. При 409 показать различия и обновить просмотр; не молча переписать чужое решение. Нельзя подтвердить устаревший план.
- Pending на устройстве не равно исполнено на сервере. Локальный журнал хранит commandId/scanId, порядок и результат синхронизации. При offline нельзя разрешить погрузку, repack, выпуск или другую операцию, требующую актуальной блокировки. Допустимость offline-сбора согласуется отдельно.
- Запреты hard constraints не обходятся кнопкой администратора. Разрешённые исключения имеют отдельную команду, полномочие, причину, автора и влияние на обязательства.
- Настольный режим: 1440 и 1024 px; планшет 768 px; терминал 360–480 px. На малой ширине детали открываются последовательно, у таблицы допустима локальная горизонтальная прокрутка.
- Сенсорные цели не меньше 44 px, сканирование без мыши, видимый фокус, клавиатура/Enter, ошибки звуком и текстом (звук отключаем). Единицы всегда рядом с количеством; запятая и точка допустимы при вводе массы.
- Подготовить словарь RU/KA и протестировать длинные грузинские строки; перевод утверждает бизнес. Не встраивать названия статусов в формат внешнего API.
- Права проверяются сервером. Использовать RUSERS/RIGHTS и текущую инфраструктуру авторизации, а не отдельную базу пользователей. Новые права ниже — проектируемые, не существующие.
- Общая приёмка: пустое/ошибочное/устаревшее состояние, повтор команды, 409, смена площадки, запрет чужого заказа, keyboard/touch и отсутствие выхода текста за границы. Производительность — по NFR функционального плана, не по скорости макета.

## 4. ТЗ по рабочим местам

### UI-01. Наблюдение XML-интеграции

Компоновка А: фильтры ERP/WMS, направления, типа, площадки, времени и ошибки; таблица messageId, бизнес-ключ, версия, получено, применено, ACK, возраст ожидания, попытки, nextRetry, владелец. Справа — причинная цепочка и обезличенный XML с вкладками «Валидация / Зависимости / Попытки / Сверка». Б: очереди «Ждёт справочник / Конфликт / Технический повтор / Применено» с теми же деталями.

Показывать входящие MasterDataSnapshot/Change и операционный OrderManifest отдельно; исходящие четыре ERP-события — с ссылкой на первичный факт. Транспортный ACK, APPLIED и бизнес-подтверждение получателя не объединять.

Действия: назначить ответственного; открыть отсутствующий справочник; dry-run; повторить техническую доставку неизменного сообщения; запустить ограниченную сверку диапазона с preview. Конфликт данных исправляется владельцем источника новой ревизией, не редактированием XML в очереди. Нельзя «поставить успешно» вручную. Подтверждение массового повтора показывает количество, границы и права.

Права: integration_view; отдельно payload_view, integration_retry, integration_reconcile. Секреты/персональные данные маскируются. Приёмка: дубль не удваивает эффект; timeout после commit восстанавливается; hash-conflict нельзя повтором превратить в успех; неизвестная ссылка сохраняет сообщение в WAITING_DEPENDENCY, а не теряет заказ.

### UI-02. Справочники и маппинг

Таблица ERP key → внутренний key → WMS key; тип «магазин/адрес, артикул, единица, склад/поток»; версия, источник истины, effectiveFrom, активность, полнота транспортных атрибутов. Детали магазина: GLN, точный адрес, окно, зона времени; товара: owner/SKU/GTIN, UoM и разрешённые пересчёты, масса/габариты/температура/stackability.

Перед изменением показать затронутые ожидающие сообщения и будущие заказы. Не переписывать адрес и состав исполненного заказа изменением справочника: используем snapshot/новую ревизию. Б: очередь проблем качества данных. Право md_mapping_edit не даёт права менять ERP-владение. Приёмка: неоднозначный GTIN/адрес блокирует применение, ведущие нули не теряются, catch-weight не пересчитывается постоянным коэффициентом.

### UI-03. Начальник склада сборки

А: волна/магазин, источник, PLAN/ACTUAL_ONLY, к сборке, собрано, закрыто-short, контроль, к подаче, deadline, люди, отставание. Справа — задания, занятость исполнителей, причины дефицита и остаточное время до шаттла. Б: сменная сетка «сборка → два контроля → вес → подача», с назначением на существующие ресурсы.

Действия: расчёт/preview/запуск локальной PICK_WAVE, назначение исполнителя, приоритет до запуска, запрос пополнения, закрытие недосбора с причиной, передача расхождения ответственному. Начальник не сканирует за сборщика и не отмечает отсутствующий товар собранным. ТМС задаёт deadline/приоритет; WMS управляет исполнением.

Приёмка: неподтверждённый факт внешней WMS виден как pending, а не готовность; конфликт ресурса отклоняется; closed-short уменьшает остаточный план и сохраняет причину; контроль не смешан с процентом сборки.

### UI-04. Сборщик

На одном экране: задание/магазин, адрес отбора крупно, артикул/название/партия/срок, количество и UoM, целевой идентификатор паллеты/короба. Последовательность: скан ячейки → товара/партии → целевого HU → подтверждение физического количества. Не дублировать обязательный скан бессмысленным нажатием «ОК».

Один главный переход «Следующий отбор»; вторичные «Недостача», «Повреждение», «Пауза» с причинами. Состояния: назначено/в работе/ожидает пополнение/частично/завершено/ожидает синхронизацию. Ошибочная ячейка/товар/магазин не продвигает задание. Закрытие задания фиксирует assembly fact, но не разрешение отгрузки без контроля. Приёмка: повтор scanId не удваивает, одинаковый GTIN разных единиц считается корректно; другой исполнитель не завершает чужое активное задание без переназначения.

### UI-05 / UI-06. Контроль и вес

Самостоятельное детальное ТЗ: [[requirements/nikora_ui_quality_tz]]. Обязательны два независимых прохода, осмотр, стабильное взвешивание, привязка результата к версии состава и блокировка отгрузки при несоответствии. Результат прошлого прохода не подсказывает второй.

### UI-07. Управление зоной cross-dock

А: прибывающие шаттлы и верхние HU, магазин, исходная часть/SSCC, окно прибытия, план/факт, назначенные ворота/линия/волна, dwell и контроль. Б: сетка ворот и линий по времени с конфликтами и прогнозом выхода. Открытие HU показывает дерево состава, не прибавляет детей к родителю в capacity.

Действия: назначить место по разрешённому расписанию, сформировать порядок выгрузки, отправить задания на ТСД, открыть расхождение, согласовать новую версию до freeze. Объединение — preview состава/баланса/нового ID → подтверждение физического действия; разбор «по шву» отдельно от repack в новые HU. Перетаскивание в доске только формирует предложение, сервер проверяет ресурсы.

Приёмка: неправильный магазин/температура/родитель блокируют объединение; отсутствующая часть не исчезает; dwell отсчитывается от фактической приёмки и не сбрасывается перепаковкой. Cross-dock receipt не является доставкой магазину.

### UI-08. Приёмка и погрузка

ТСД: операция, рейс/плечо/ТС/секция, ворота, позиция в очереди, ожидаемый HU и магазин. Сканировать рейс/ворота и HU; показать «ожидается / принят / проверен / погружен». Несоответствие — красный текст с причиной, без кнопки обхода.

Приёмка cross-dock фиксирует местоположение; погрузка фиксирует LOADED. **Выезд DEPARTED фиксируется отдельно** уполномоченным оператором/источником факта с временем, перечнем реально загруженного и недостающего. Только после него идёт ERP ORDER_IN_TRANSIT. У водителя возможен мобильный режим того же места: подтверждение прибытия/выезда и инцидент, без редактирования состава.

Приёмка: повтор скана безопасен, loaded HU нельзя переназначить без выгрузки; нет связи — событие не обозначается подтверждённым; неверный порядок блокируется или обрабатывается только предусмотренным исключением.

### UI-09. Логист транспортного маршрута

Переиспользовать текущие диспетчер/планировщик/Ганта. А: рейсы и доступные задания, плечо, остановки, окна, ТС/секции, загрузка kg/m³/мест, ETA, отклонения. Справа — объяснение ограничения выбранного назначения. Б: последовательность остановок и временные интервалы; в продукте существующая Leaflet-карта, не новая картографическая подсистема.

Действия: расчёт предложения, ручная корректировка до freeze, проверка, preview изменений, подтверждение версии, сравнение вариантов. Для каждого участка видны остаток вместимости и порядок выгрузки; обратные плечи учитывают тару. Не смешивать входящий шаттл и рейс на магазины.

Приёмка: overweight, окно, температура, геометрия и недоступная секция блокируют ручной и автоматический варианты одинаково; исключённые заказы перечисляются; повтор apply не создаёт рейс заново.

### UI-10. Координатор транспортной консолидации

А: строки магазин+serviceDate, колонки источников с отдельными планом/фактом/контролем; итоговая волна, ворота, время консолидации, ETA подвоза, ACK расписания, режим manual/auto, блокеры. Адрес магазина — группирующий признак с устойчивым destination key, не свободный текст.

Детали: все заказы/части, недостающие источники, ожидаемые HU, график обратного расчёта «выезд из магазина/доставка ← финальная отгрузка ← консолидация ← подвоз ← сборка». Б: календарь волн с карточками магазинов; неполные/опоздавшие видны отдельно.

Действия: создать/изменить график, предварительно проверить, запросить ACK, подтвердить выпуск; назначить whitelist auto; открыть исключение. Перед выпуском — checklist полноты, контроля, вместимости, ворот, ACK, конфликтов и версии. Сохраняется snapshot RELEASED.

Приёмка: PLAN допускает прогнозный подвоз, ACTUAL_ONLY не резервируется до разрешённого факта; auto не обходит контроль и missing-source; нажатие «Выпустить» дважды не создаёт второй рейс.

### UI-11. Приёмщик магазина

Мобильный экран: магазин/адрес, рейс, фактическое прибытие, ожидаемые HU, пломба при использовании. Скан → осмотр/количество → принять полностью/частично/отказать с кодом, фото при разрешении и актом. Итог показывает принято/недостача/повреждено/отказ и подтверждение синхронизации.

Доставлено только по ReceivingAdvice/подтверждённой приёмке, не по геопозиции или закрытию рейса. Частичная приёмка не превращается в полную. Приёмка: повтор безопасен, чужой магазин блокируется, offline draft виден как неотправленный; ERP получает фактические количества и расхождение.

### UI-12. Возвраты и оборотная тара

Реестр transportAssetId с владельцем, типом, текущим custody, состоянием, задолженностью; SSCC очередного наполнения — отдельное поле. Создание возврата товара связано с исходной поставкой и строками; выбор разрешённой площадки и quarantine/disposition. Приёмка: другой допустимый склад принимает тару без потери владельца, возврат не закрывает исходную недостачу.

### UI-13. Отклонения и качество

Очередь: причина, магазин/часть/HU, блокируемая операция, срок решения, владелец, статус, возраст, финансовое/сервисное влияние. Справа история фактов и только допустимые решения с preview. WAIT_WITHIN_BUFFER / PARTIAL_DESPATCH / MOVE_TO_NEXT_WAVE не подменяют качественную приёмку.

Права: exception_view/decide; quality_disposition отдельно. Ранний вариант очереди нужен уже контроллеру в F2.4, общая оркестрация после freeze — F6.1. Приёмка: причина и автор обязательны; исходное обещанное окно не изменяется; отгруженное нельзя «исправить» задним числом.

## 6. Решения перед разработкой

Бизнес/качество утверждают: применение двух проходов по потоку; нужен ли другой оператор; правила веса и измерительное оборудование; допустимость частичного выпуска; нормы dwell; кто фиксирует DEPARTED; подтверждение магазина и обязательность фото. IT утверждает устройства, offline-политику, RU/KA, права и границы внешних WMS. Это открытые параметры реализации, а не повод делать один универсальный неблокирующий checkbox «Проверено».
