# Архитектура решений и бизнес-процессов WMS/TMS — retail / NIKORA

Версия 1.0 · 16.09.2026. Требования заказчика; параметры SLO ниже — предложения на согласование, не измеренные характеристики сети.

Уточнение владельца проекта от 06.10.2026: рабочий цикл начинается с транспортного планирования в 18:00. Логист задаёт сборку по паллетам, рейсам и адресам, ворота и сроки; затем WMS формирует волны и пополнение мини-макс либо под волну. Смена ричтраков начинается и заканчивается на два часа раньше основной смены. Комплектация после 20:00 разрешается только при полном обеспечении волны. Актуальное изложение — [редакция 2 описаний процессов](../nikora_business_processes/README.md). Прежняя таблица процессов сохранена как структура RFP от 16.09.2026; её порядок не определяет очередность исполнения.

## 1. Принцип Оккама

Минимум независимых источников истины и расширений. Не требовать одновременно event sourcing, микросервисы, Kafka и отдельный BPM-движок только ради соответствия рынку. Допустимы модульный монолит, поддерживаемое промышленное приложение или SaaS, если доказаны транзакции, изоляция, производительность, восстановление и переносимость. API-first не означает «всё должно работать через синхронный HTTP».

В текущем проекте сохраняются Oracle/PLSQL-правила, существующие волны, складские задачи, ресурсные сессии, API и ТСД. У коммерческого вендора требуется эквивалентная семантика, а не таблицы RRL или конкретный язык программирования.

## 2. Логические контуры

```text
ERP / MDM / store order
        │ master, orders, corrections
        ▼
Интеграционные адаптеры: inbox → domain transaction → outbox → ACK/reconcile
        │                          │
        ▼                          ▼
WMS источников ← readyBy/plan → головная TMS ← POD → магазин/получатель
        │                           │
        │ physical HU/facts         │ wave/leg/slot/sequence
        ▼                           ▼
WMS консолидации: приёмка → линия → HU/контроль → погрузка
        │
        └── факты + версии → TMS → подтверждённые бизнес-события ERP
```

Схема логическая: адаптеры могут размещаться рядом с продуктами. Одна транзакция БД не охватывает внешние WMS/ERP; сквозная согласованность достигается повторяемыми командами, фактами и сверкой, а не обещанием distributed exactly-once.

## 3. Требования к архитектуре WMS

| ID | Требование и граница | Приёмочное доказательство |
|---|---|---|
| AW01 | Физический ledger/остаток, резерв и доступность разделены; атомарные движения по измерениям owner/SKU/lot/location/HU/UoM. | Конкурентный отбор и повтор операции не создают отрицательный/двойной запас; W11–W15. |
| AW02 | HU имеет внутренний стабильный ключ, namespace/external ID, тип идентификатора, состав и contentVersion. SSCC не единственно допустимый код. | Legacy ID и GS1 SSCC проходят один процесс без подмены стандарта; W27. |
| AW03 | Активная вложенность — дерево/лес без циклов и двух родителей; история repack — отдельный граф происхождения. | Агрегация/разделение/перепаковка сохраняют количество, партии и принадлежность; W29–W31. |
| AW04 | Quality release привязан к версии состава; независимые факты сканов/осмотра/веса с авторами. | Изменение состава лишает прежний допуск применимости; W22–W25. |
| AW05 | Единая модель заданий, ресурсов, claim и domain completion; ТСД не владеет отдельным «истинным» статусом. | ACK выдаётся после durable факта; повтор/конкурентный claim безопасны; W37–W40. |
| AW06 | Версионируемые правила размещения, FEFO, replenishment, wave; опубликованная топология отделена от черновика. | Активная волна воспроизводима с прежней конфигурацией; смена стратегии не портит историю. |
| AW07 | Внешние команды не обходят доменные инварианты; staging/адаптеры отделены от stock core. | Повтор XML и ручная операция дают одинаковые проверки; W41–W43. |
| AW08 | Catch weight хранит независимые фактические меры; единицы и точность согласованы во всех интерфейсах. | Сквозной баланс шт./кг через приёмку, отбор, repack, возврат и ERP; W13. |

Оборотный ролл-кейдж — постоянный актив; его текущая логистическая единица с SSCC — временный состав. Нельзя переносить жизненный цикл маркировочного агрегата CRPT на любой складской HU без анализа различий.

## 4. Требования к архитектуре TMS

| ID | Требование и граница | Приёмочное доказательство |
|---|---|---|
| AT01 | Order и стабильная FulfillmentPart отделены от изменяемого транспортного разбиения; ссылки на исходные строки сохраняются. | Повторный план не создаёт новый физический спрос; T02–T03. |
| AT02 | Network/Leg/Trip/Stop/CargoAssignment описывают многоплечевую перевозку; custody и факт относятся к плечу. | Приёмка hub не превращается в store delivery; T07, T16, T21. |
| AT03 | OutboundWave имеет дату обслуживания, версию, freeze и правила поздних изменений; локальная pick-wave WMS — другой объект. | Конкурентные replan и loaded HU не теряют назначения; T10–T15. |
| AT04 | Solver читает ограниченный снимок, создаёт кандидат; operational commit проходит hard validator, версии и авторизацию. | Неуспешная оптимизация не меняет рабочий план; недопустимый ручной план также запрещён; T06–T10. |
| AT05 | Плановая оценка и факт объёма хранятся отдельно с покрытием forecast фактическими частями. | PLAN=10, fact=8 не становится 18; ACTUAL_ONLY не бронируется преждевременно. |
| AT06 | TMS не меняет stock/HU-состав WMS и не считает свой outbound ACK фактом физической операции. | Зависший target adapter виден, состояние не перескакивает в RECEIVED. |
| AT07 | Плановая ёмкость дока и линии подтверждается WMS/YMS; один authoritative calendar, не два независимых бронирования. | Два логиста не выпускают конфликтующие слоты; T12. |
| AT08 | ERP milestones формируются из явных business facts; биллинг отделён от execution и от оплаты ERP. | Частичная доставка/отказ/оплаченный рейс обрабатываются корректировкой, не переписыванием истории. |

## 5. Обязательная интеграционная матрица

XML — внешний контракт NIKORA, а не требование, чтобы внутренности каждой системы использовали XML. Допустим адаптер XML↔нативное API, если он включён в цену, мониторинг и поддержку. «Интеграция с внешней базой» означает обмен через её прикладной сервис/адаптер; прямые записи в таблицы чужой ERP/WMS запрещаются. Read-only выгрузка или CDC возможны по договору, но не заменяют бизнес-ACK и обратные операции.

Названия ниже — логические семейства сообщений, **не новая редакция wire-schema**. Перед реализацией сопоставить их с NIKORA XML v1.1.0 и оформить недостающие поля как совместимое расширение.

| Поток | Источник → получатель | Содержание / результат |
|---|---|---|
| IX01 Master | ERP/MDM → WMS/TMS | Магазины/адреса/GLN, организации/владельцы, склады, SKU/GTIN/UoM/упаковки, габариты/масса/температура, календари, effectiveFrom/version. |
| IX02 Orders | ERP → WMS/TMS | OrderManifest/строки/количество/шт.+кг/окно/политика частичного исполнения; изменение/отмена, стабильные внешние ключи. |
| IX03 ASN | Поставщик/source WMS → target WMS | План прихода, заказ, HU/состав/лот/партия/срок/документ. TMS получает транспортный срез. |
| IX04 AssemblyPlan | WMS → TMS | План сборки по части/магазину, expectedReadyAt/объём/режим/версия, без фиктивного SSCC факта. |
| IX05 AssemblyActual | WMS → TMS/ERP | Факт по HU и строке, количество, contentVersion, качество отдельно; логическое ORDER_ASSEMBLED. |
| IX06 TransportPlan | TMS → source/target WMS | Плечи/рейсы, readyBy, arrivalBy, wave/gate/line, source loading и target unloading sequence, planVersion/freeze. |
| IX07 MovementPlanned | TMS → ERP | INTERNAL_MOVEMENT_PLANNED, исходный и целевой склад, части/даты/статус/версия. Может появляться до сборки. |
| IX08 Load/Departure | WMS/диспетчер → TMS → ERP | LOADED и DEPARTED отдельно; ORDER_IN_TRANSIT только по выезду с указанием плеча, времени, количества. |
| IX09 HubReceipt | Target WMS → TMS/ERP | Принято/отказано/недостача по HU/строкам; это не доставка магазину. |
| IX10 HU/Quality | WMS → TMS/потребители | Агрегация/разагрегация/repack, lineage, новый состав, quality release/HOLD, связь с перевозкой. |
| IX11 StoreReceipt | Store/POD → TMS → ERP | ORDER_DELIVERED_TO_STORE по подтверждённой приёмке; частичность, отказ/недостача, receivedQty, получатель, подтверждение. |
| IX12 Reconciliation | WMS/TMS ↔ ERP | Приход, расход, внутреннее перемещение, инвентаризация/коррекция, возврат/тара; контроль документов, движений, остатков и застрявших сообщений. |

### Транспортные гарантии

Обязательные envelope-поля: messageId, sourceSystem, schemaVersion, entityId/entityVersion, correlationId, eventType, occurredAt и receivedAt, timezone/UTC, payload hash; в деталях warehouse/owner/order/orderLine/fulfillmentPart/HU/contentVersion/leg и UoM по типу события. Пустое поле не превращать в нулевой факт.

- Transport ACK подтверждает durable получение, business ACK — принятие доменом; HTTP 202 не означает завершение операции.
- Один ID + тот же hash → прежний результат. Один ID + другой hash → конфликт/quarantine.
- Устаревшая версия не откатывает новую; будущая ждёт зависимости либо явно отклоняется по контракту.
- Изменение домена и outbox атомарны. После падения повторная доставка допускается; повторный бизнес-эффект — нет.
- Таймауты, retries с backoff, DLQ, replay с правами/причиной, архив payload по согласованной политике.
- При неизвестном master заказ ожидает исправления; ручной replay не обходит бизнес-валидацию.
- XML parser: отключить DTD/external entities, лимитировать размер/глубину, XSD/семантическая проверка; TLS, авторизация партнёров, секреты вне payload/log.
- Сверка не реже суточного закрытия плюс оперативно перед выпуском волны: missing/duplicate/stale/unmatched и ответственность. Проверять четыре типа складских движений, а не только четыре исходящих ERP milestone.

## 6. Архитектура бизнес-процессов

Уровни: L0 «снабжение магазина» → L1 supply/warehouse/crossdock/transport/returns → L2 процессы ниже → L3 инструкции рабочего места. Для каждого процесса: owner, trigger, входной документ, preconditions, роли, разрешённые переходы, контрольные точки, события, SLA, исключения, компенсация, KPI и evidence. BPMN со swimlanes нужен при формальном проектировании; отдельный BPM-движок необязателен.

| Процесс | Ответственный бизнес-владелец | Триггер → проверяемый результат | Главный контроль / требования |
|---|---|---|---|
| BP01 Master governance | Владелец MDM + коммерция | Новый товар/магазин → опубликованная версия | Упаковка/температура/геокод; W01–05, T01–04 |
| BP02 Store calendar/order | Коммерция + розничная логистика | Потребность → согласованный день/заказ | Не держать свежий товар ради другого дня; T01–03 |
| BP03 Receipt/QA | Начальник приёмки | ASN/машина → принятый либо карантинный запас | Неполный короб/вес/срок; W06–10 |
| BP04 Replenish/pick | Начальник смены | Заказ/deadline → собранная часть/HU | FEFO, резерв, пополнение, недостача; W11–21 |
| BP05 Quality release | Руководитель качества | Сборка → допуск по contentVersion | Два прохода по политике, вес/осмотр; W22–26 |
| BP06 Cross-site planning | Сетевой логист | Заказы + plan/fact → выпущенная транспортная волна | Ёмкость/температура/readyBy/freeze; T06–15 |
| BP07 Source dispatch | Начальник источника + диспетчер | Выпущенный план → loaded/departed HU | Правильные ворота/рейс/очередь; W32–33, T16 |
| BP08 Hub consolidation | Начальник кроссдока | Arrival/ASN → проверенный состав исходящего HU | Линия/магазин/агрегация/срок ожидания; W27–31 |
| BP09 Last-mile execution | Транспортный диспетчер | Выезд → факты стопов/исключений | Окна/ETA/холод/остаточная вместимость; T16–20 |
| BP10 Store receipt | Управляющий магазина | Прибытие → POD/отказ/расхождение | Факт получателя, не GPS/статус водителя; T21 |
| BP11 Returns/assets | Руководитель возвратов | Возврат/тара → решение/ответственность/учёт | Карантин, собственник, assetId; W34–36, T22–23 |
| BP12 Reconcile/settle | Финансы + IT integration owner | Закрытие суток/рейса → согласованный учёт | Документы/остатки/счета/ошибки; W41–42, T26–33 |

Логистика отвечает за правила и приёмку процесса; IT — за реализацию/эксплуатацию; вендор — за договорный компонент; финансы — за учёт. Нельзя передавать всю ответственность за процесс внешнему интегратору.

### Обратное расписание

Для последовательного критического пути: readyBy_source = departure_final − load_final − consolidation − unload_hub − buffer_hub − travel_source_hub − load_source − buffer_source. Отдельно вычисляется assemblyStart = readyBy_source − assemblyDuration. Параллельные операции допускают другой critical path; формула не заменяет ресурсный календарь.

Длительности зависят от объёма, ворот, бригады, погрузчика и окна, а travel time — от направления/времени суток. Если результат в прошлом или пересекает недоступный ресурс — план infeasible, требуется решение логиста, не скрытое нарушение.

### Состояния и компенсации

Товар: EXPECTED → RECEIVED → AVAILABLE/QUALITY_HOLD → RESERVED → PICKED → QA_RELEASED → STAGED → LOADED → DEPARTED. Конкретный поток может пропускать хранение/отбор в crossdock, но не доказательство факта. Состояние качества ортогонально местоположению.

План: DRAFT → VALIDATED → APPROVED/FROZEN → EXECUTING → COMPLETED/PARTIAL/CANCELLED. Повторное планирование создаёт новую версию и сохраняет физические факты. Отмена до pickup освобождает резерв; после pickup требует физического drop/возвратного действия; после departure создаёт новый маршрут/возврат; после финансового закрытия — корректирующий документ.

## 8. Нефункциональные условия для согласования

| Показатель | Предлагаемый стартовый критерий | Что фиксировать в договоре |
|---|---|---|
| ТСД | p95 ≤ 1 сек на подтверждение, p99 ≤ 2 сек при согласованном профиле | Включает Wi-Fi/API/БД; печать и аппаратное измерение отдельно |
| Операторский список | p95 ≤ 2 сек на ограниченную страницу | Фильтры, размер страницы, число конкурентных пользователей |
| XML | 100% принятых durable сообщений прослеживаются до business ACK/ошибки; 0 потерянных бизнес-эффектов | Сеть/партнёр вне SLA обработки; latency p95 и максимальный возраст очереди отдельно |
| Solver | Согласовать лимит, например 5 минут для пилотного набора | Размер задач, time budget, feasible fallback, не обещание optimum |
| Нагрузка | Пик обследованной смены × 1,5 + длительный 12-часовой прогон | SKU, строки/час, сканы/сек, HU, stop count, пользователи, retention; не только среднесуточные паллеты |
| Доступность | Предлагается 99,9% за согласованное окно сервиса | Плановые окна, зависимости, измерение; недостаточно для определения RTO |
| Восстановление | Предлагается RTO ≤ 60 минут; для подтверждённых операций целевой RPO=0 в согласованном классе отказов | Различать отказ процесса/узла и потерю площадки; доказать репликацией/восстановлением, иначе согласовать иной DR RPO |
| Безопасность | Least privilege, SSO/MFA для админов, TLS, защищённые секреты, audit export | Поддержка RU/KA, доступность в Грузии, data residency, хранение/удаление данных по договору |
| Поддержка | Ночные/выходные операции, 24×7 для P1 | Пример P1 response ≤15 мин — предложение; restoration/escalation и ответственность отдельных поставщиков |

После каждого значимого функционального и нагрузочного прогона — анализ самых долгих SQL/SKV. Для текущего решения: RRL_SQL_SLOW_LOG, /api/admin/slow-sql, Oracle top SQL и API audit; для SaaS — эквивалентная vendor telemetry. Каждый долгий запрос заканчивается решением: переписать, ограничить окно, batch/cache, индекс, статистика/план либо backlog с owner и обоснованием.

## 9. Стандарты и локализация

Использовать семантику GS1 для GLN/GTIN/SSCC и событий происхождения; [GS1 Architecture](https://www.gs1.org/standards/gs1-system-architecture-document/current-standard), [EPCIS](https://ref.gs1.org/standards/epcis). EPCIS — возможный стандарт обмена событиями, но не обязательная замена согласованного XML API. Legacy-коды не выдавать за валидные GS1 SSCC; хранить тип/namespace.

RS.GE упомянут в обследовании; конкретный правовой состав документов и обязательства в Грузии требуют подтверждения локальным специалистом и заказчиком. Ни GDPR, ни российские нормы нельзя автоматически объявлять применимыми ко всем данным NIKORA. Доступность лицензий, сопровождения, региона облака и трансграничного доступа — отдельный договорный gate.
