# Текущий проект: организация требований и GAP к retail-стандарту

Версия 1.0 · 16.09.2026. Документарный анализ wiki и результатов обследования; не новый аудит всех исходников/живой БД.

## 1. Три разных «текущих состояния»

1. Физические и информационные процессы NIKORA — по обследованию складов и протоколам.
2. Наш репозиторий TMS/WMS — Oracle + legacy C# + FastAPI/React/PWA, собственные исторические тесты.
3. Целевой NIKORA-контур — требования, 41 ТЗ и 21 crossdock-инкремент.

Их нельзя смешивать. Код волновой сборки в репозитории не означает, что он внедрён в Samgori. Статус функционального теста TMS-2 в мае не доказывает приёмку межскладской NIKORA-цепочки в сентябре. Корневой onramp со «следующим Sprint 1» противоречит более позднему [status 01.06](../../subprojects/tms2_current_status.md); следует проверять timestamp и evidence, а не выбирать удобную формулировку.

## 2. Как организованы требования сейчас

| [GAP G01–G22](../nikora_gap_analysis_20260915.md) | Связь требований и локального кода/пробелов | Маппинг W/T ID и доказательств на level площадки |

| [41 sprint spec](../nikora_sprints/index.md) | Scope, результат, тесты, author/reviewer | Связать каждый принимаемый результат с W/T ID; число спринтов не метрика покрытия |
| [CD00–CDP](../nikora_crossdock_increments.md) | Вертикальные принимаемые срезы раннего crossdock | Разграничить технический пилот и бизнес-готовность полного scope |

Новая единица управления требованиями: stable ID → бизнес-процесс → владелец данных → контракт → реализация/конфигурация → тест → evidence → акт. Каталог настоящего пакета вводит W01–W48, T01–T40, AW/AT, BP и D-ID; он дополняет, не перенумеровывает существующие sprint/GAP/CD-ID.

## 3. Сопоставление организации каталогов вендоров

| Вендор | Как структурирована публичная функциональность | Как нормализовать в наше ТЗ |
|---|---|---|
| [SAP EWM](https://www.sap.com/products/scm/extended-warehouse-management/features.html) | Inbound, storage/internal, outbound, cross-functional; basic/advanced и deployment | Процесс + конкретный scope/лицензия + версия Help + extension fit-gap; TM отдельным продуктом |
| [Infor WMS](https://www.infor.com/en-gb/solutions/scm/warehouse-management-system) | Inventory, receipt/putaway, waves/picking, VAS, 3PL, labor, platform | Разделить ядро/модули/платформу; Nexus TMS не считать включённым в WMS |
| [Manhattan WM](https://www.manh.com/solutions/supply-chain-management-software/warehouse-management) | Unified distribution/planning/execution/automation, общая платформа | Проверять результат конкретного процесса и редакцию, не только слово unified |
| [AXELOT WMS](https://www.axelot.ru/product/axelot-wms-x5/functionality/) | Топология, вход/выход, стратегии, терминальное исполнение и SCM-компоненты | Сопоставить настройку стратегии с invariant/test; отдельно доработки 1С и внешние компоненты |

Сходство терминов не даёт одинаковой семантики: «волна» может означать разные объекты, «консолидация» — объединение заказа, грузомест или рейсов, «crossdock» — как физическую операцию WMS, так и вариант маршрута TMS.

## 4. GAP текущего решения и минимальное действие

| Область / ID | Доказанная документацией база | Неподтверждённое для NIKORA / действие |
|---|---|---|
| W04/W16–20/W37–39 | Есть pick-wave, topology, warehouse tasks/resources и case-pick events | Переиспользовать; проверить политики grocery, конкурентное пополнение и короткий RF на реальной площадке |
| T05–10/T16–19/T26–27 | Диспетчер, карты/VRP, Гант, биллинг TMS-2, исторические gates | Не переписывать базу; проверить сегментную ёмкость, многоплечевой freeze/plan-fact и новый baseline |
| W41–43/T30–33 | HTTP/API audit и отдельные adapters/outbox-подходы | API log не заменяет inbox. Нужны durable dedup/version/hash, бизнес-ACK и атомарный outbox, 4 milestone и сверка 4 типов движений |
| W27–31/T34 | Legacy pallet/SSCC и отдельные regulatory aggregates | Общий HU/content/lineage, legacy namespace, seam split и repack; не переиспользовать CRPT-логику без анализа |
| W22–25 | UI ТЗ двух проходов/веса и предложение Quality evidence | Показать хранение независимых фактов и versioned release, не checkbox «контроль пройден» |
| W13/W26 | Требование catch weight/перефасовки из обследования | Сквозная двойная мера/потери/ERP-сверка ещё требуют отдельной доказательной приёмки |
| T03/T07–15 | Архитектурный план FulfillmentPart/OutboundWave/CargoAssignment | Реализовывать только недостающие семантические объекты; SHIPMENT_PART для capacity split не заменяет stable part |
| W28/W32/T12 | Есть топология/задания и crossdock-plan | Реальный target WMS adapter + подтверждение физической приёмки/ёмкости, а не только UI-статус |
| W34–35/T21–23 | Требования возвратов, тары и store receipt | Постоянный assetId и DeliveryReceipt с частичностью/автором; GPS не POD |
| W45–48/T35–40 | Локальные auth/audit/test/slow-SQL runbooks | Договорные SLO/DR/ночная поддержка, локализация KA, аппаратные тесты и эксплуатационная команда |

Это gap доказательств/архитектуры по доступной документации; «неподтверждено» не означает, что кода нигде нет. Перед программированием провести scoped code/schema inspection по конкретному W/T ID. Нельзя оценивать весь текущий продукт нулём или сравнивать его с рекламным «всё есть».

## 5. Предлагаемое развитие документации

Для каждого W/T ID вести: applicability (площадка/поток), owner, source/version, M/S, gate, интерфейс, модуль/таблица, configuration/custom, sprint/CD, D-test, evidence/date/baseline, итог/открытый дефект. Один requirement может иметь несколько sprint tickets, но закрывается по end-to-end outcome.

Новые таблицы создавать только если существующий объект не сохраняет обязательный факт/историю/инвариант. Архитектурный инкремент принимается отдельным контрактным тестом; функциональный — пользовательским сквозным сценарием. Это соответствует ранее принятому разделению архитектуры и функциональности, не запускает очередную миграцию автоматически.

Предлагаемые следующие действия: утвердить требования/границы и профиль нагрузки; выслать одинаковые опросники; провести D01–D12 с shortlist; параллельно сопоставить актуальный код с теми же ID. Решение «развивать своё / внедрять вендора / гибрид» принимать по одинаковым критериям, поддержке и стоимости полного процесса.
