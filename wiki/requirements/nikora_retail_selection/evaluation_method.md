# Методика выбора, веса и достоверность ответов

Версия 1.0 · 16.09.2026.

## 1. Как читать заполненные опросники

Проведён desk research публичных официальных материалов, а не испытание лицензированных стендов и не официальный ответ поставщиков. Для каждой из 48 WMS- и 40 TMS-строк заполнены клетки девяти продуктов: всего **792 предварительных ответа**.

- **П** — прямо опубликована названная базовая возможность. Это не подтверждение всех подпунктов нашего требования и не PASS теста.
- **Ч** — опубликован только соседний механизм/часть требования; конкретную семантику NIKORA нужно доказать.
- **НД** — в просмотренных источниках достаточных данных нет. Не означает отсутствие функции.
- Ссылка у клетки — основание именно указанной короткой формулировки. Полное описание требований/проверок — в опроснике.
- Поддержку планируемой версии, стоимость модуля, способ реализации и сроки внедрения нельзя вывести из общей страницы продукта.
- Комиссионные баллы пока **не выставлены**. Нельзя считать П=5, Ч=3, НД=0 и объявить победителя: это оценило бы качество публичной документации, а не пригодность системы.

Реестр источников фиксирует дату обращения 16.09.2026. Обновляемые vendor pages могут менять брендинг/редакции; состав коммерческого предложения должен быть зафиксирован отдельно. Gartner используется только для обоснования дополнительных кандидатов, не как доказательство NIKORA-функций.

## 4. Балльная шкала после ответа и испытаний

| Балл | Состояние |
|---:|---|
| 0 | Нет требуемой возможности либо провален обязательный сценарий без принятого решения |
| 1 | Обещание/roadmap, прототип без воспроизводимого выполнения |
| 2 | Частичное выполнение, согласованная существенная доработка ещё не поставлена |
| 3 | Воспроизводимая функция показана, но часть наших критических исключений/параметров не доказана |
| 4 | Требование и согласованные негативные сценарии пройдены на данных NIKORA, ответственный за поддержку определён |
| 5 | Уровень 4 + нагрузка/восстановление/обновление подтверждены в применимой конфигурации, полезный эффект и применимый референс проверены |

Если вопрос составной, комиссия хранит баллы подпунктов; итог строки ограничен самым слабым обязательным подпунктом. Не скрывать критический пробел средним баллом. Штатная и поддерживаемая заказная реализация могут одинаково пройти функциональный тест; их различают стоимость, сопровождение и риск, а не произвольное снижение функции.

Формула итоговой подтверждённой оценки: S = Σ(w_i × s_i / 5), шкала 0–100. Для неизвестных балл остаётся пустым. Дополнительно показывать:
- coverage = сумма весов вопросов с завершённой проверкой / 100;
- нижнюю границу S_low по проверенным баллам;
- верхнюю S_high = S_low + сумма весов непроверенных;
- число непройденных/непроверенных обязательных gates.

Пример только методики: проверено 70% веса и набрано 52 балла → интервал [52;82], а не итог 52/70 для сравнения с полностью проверенным продуктом. Никакому вендору этот пример не приписан.

## 5. Стоп-критерии — независимо от суммы

| Gate | Обязательный результат для полного целевого контура |
|---|---|
| G1 WMS truth | Нет двойного остатка/резерва; catch weight/лот/owner и отзыв прослеживаются |
| G2 Integration | Дубли/переупорядочивание/падение после commit не теряют движение; сверяются четыре типа складских движений и четыре ERP milestone |
| G3 Crossdock | Несколько WMS, реальная target receipt, HU genealogy, шов/repack, store/date/temperature и остаточные части |
| G4 Quality/safety | HOLD/contentVersion соблюдаются, два прохода по политике, вес/температура не обходятся обычным пользователем |
| G5 Transport | Соблюдены вместимость каждого сегмента, окна/совместимость, freeze и сохранение физического факта |
| G6 Store proof | LOADED/DEPARTED/HUB_RECEIVED не подменяют STORE_RECEIVED; partial POD не равен full |
| G7 Operations | Восстановление/ночная поддержка/пиковая нагрузка/права и audit доказаны |
| G8 Deliverability | Поставка/поддержка в Грузии, право использования и выгрузки данных, состав модулей, команда и условия выхода подтверждены договором |

На раннем инженерном пилоте исключённые процессы отключаются физически и в UI, а не считаются прошедшими G3/G4. Запрет использовать repack до его приёмки не равен снятию требования с полного промышленного внедрения.

## 6. Процедура закупки

1. Согласовать приоритеты и веса с логистикой, качеством, розницей, IT и финансами **до** предложений.
2. Разослать одинаковые данные/опросники, потребовать указания конкретной редакции и bill of materials.
3. Получить письменный fit-gap: стандарт/настройка/расширение/партнёр/нет, ответственность и оценка работ по каждой строке.
4. Короткий список по gates и способности выполнить D01–D12. Совместимость пары WMS+TMS проверять отдельно; два высоких отдельных балла не доказывают стык.
5. Выполнить управляемое живое демо с одинаковыми негативными случаями, затем пилот и проверку референсов.
6. Сопоставить доказанную функциональность, сроки/риски и коммерческое предложение раздельно; не придумывать цены лицензий по рекламным страницам.
7. Проверить устойчивость решения при изменении групповых весов ±20% с нормализацией. Если выбор меняется от малой поправки — нужен дополнительный тест, а не точность до сотых.

Предложение для финального многокритериального решения после gates: 55% подтверждённая функциональность/архитектура, 25% полная договорная стоимость внедрения и сопровождения, 20% доказанная способность команды внедрить/поддерживать. Не добавлять эти веса к 100% опросника: это второй уровень модели, подлежащий утверждению.

Поддерживаемость оценивать через обновления, регрессионные сценарии, доступность специалистов и цену изменения. Не требовать закрытых исходников SaaS как единственного способа выхода: обязательны экспорт, документация, API и договорные гарантии; для заказной разработки — дополнительно права на неё.
