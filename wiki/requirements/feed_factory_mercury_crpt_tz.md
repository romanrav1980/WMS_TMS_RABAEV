# Техническое задание: WMS/MES контур фабрики кормов с Меркурием и Честным знаком

## 1. Назначение документа

Документ описывает требования к развитию WMS/TMS `RABAEV` в сторону системы управления складом и производством для фабрики кормов.

Система должна поддерживать:

- выпуск готовой продукции с производственных линий;
- вовлечение сырья в производство;
- приемку готовой продукции на склад в нескольких паллетах;
- прослеживаемость сырье -> производственная партия -> паллеты -> отгрузка клиенту;
- интеграцию с ФГИС `Меркурий` для ветеринарной прослеживаемости;
- интеграцию с системой маркировки `Честный знак` / ГИС МТ для кормов;
- передачу клиенту либо полной поэкземплярной маркировки, либо агрегированных кодов `SSCC`, если клиент принимает агрегацию.

Документ является проектным ТЗ. Он не является миграцией Oracle и не применяет изменения к базе. Любые изменения схемы должны выполняться по [Oracle Change Protocol](../database/oracle_change_protocol.md).

## 2. Контекст проекта

Текущий проект состоит из четырех логических веток:

- Oracle / PL/SQL Core: текущая схема `RABAEV`, процедуры, функции и бизнес-логика.
- C# Desktop Client: legacy WinForms приложение операторов.
- Terminal Contour: `Tserver` и терминальные операции.
- External Integrations: `SUPERMAG`, `Sfera`, будущие контуры `Меркурий` и `Честный знак`.

Текущая Oracle база разработки:

- сервис: `127.0.0.1:1521/orcl`;
- схема: `RABAEV`;
- рабочий принцип: wiki mirror + SQL source + live Oracle verification.

## 3. Нормативно-интеграционные предпосылки

### 3.1. Меркурий

Для производства в Меркурии используется операция оформления производственной партии. По официальному описанию `ProductionOperation` / `RegisterProductionOperation` на вход передаются:

- информация о сырье, из которого произведена партия или несколько партий;
- информация о произведенной партии или нескольких партиях продукции;
- сведения о хозяйствующем субъекте, площадке производства и владельце продукции;
- идентификатор производственной операции для незавершенного производства.

Результатом является списание сырья и оформление производственного ВСД или увеличение объема в уже оформленном производственном документе.

Даты производства и срока годности должны поддерживать точную дату и интервал через модель `GoodsDate`.

### 3.2. Честный знак

Корма для животных относятся к товарной группе, по которой обязательная маркировка вводится по этапам. Для проектирования системы необходимо хранить:

- `GTIN`;
- коды идентификации / DataMatrix по единицам продукции;
- серийные номера;
- статус кодов;
- агрегацию единиц в короб, коробов в паллеты;
- `SSCC` как код транспортной упаковки.

Часть клиентов принимает агрегацию. Для таких клиентов система должна уметь передавать `SSCC` вместо полного списка всех кодов каждой единицы, при условии что состав агрегации зарегистрирован и соответствует фактическому составу паллета.

## 4. Цели системы

1. Создать единый контур прослеживаемости готовой продукции на фабрике кормов.
2. Связать сырье, производственную операцию, готовую партию, паллеты и отгрузку.
3. Исключить ситуацию, когда товар физически принят на склад, но не готов к передаче в Меркурий или Честный знак.
4. Снизить ручной труд при приемке и отгрузке маркированной продукции.
5. Подготовить архитектуру к API-серверу, очередям и Android-терминалам.
6. Сохранить совместимость с существующей WMS-логикой `RRL_PALLETS`, `RRL_REMAINS`, `RRL_SBORKA_PALLETS`.

## 5. Термины

- Производственная партия: партия готовой продукции, выпущенная по производственной операции, смене, линии или заказу.
- Сырьевая партия: входящая партия сырья, имеющая остаток, документы качества и, при необходимости, входящий ВСД.
- Вовлечение сырья: плановая потребность, жесткое резервирование и фактическое списание сырьевых партий в производство.
- Мягкий резерв: плановая потребность без конкретной партии, паллеты и ячейки. Не занимает WMS-остаток.
- Жесткий резерв: WMS-резерв на конкретную партию, паллету, ячейку и количество. Только он исключает остаток из следующих назначений.
- Паллет приемки: физический паллет готовой продукции в `RRL_PALLETS`.
- Паллет сборки/отгрузки: паллет отгрузочного контура в `RRL_SBORKA_PALLETS`.
- CIS: код идентификации маркированной единицы товара.
- DataMatrix: полный код маркировки, нанесенный на единицу.
- SSCC: серийный код транспортной упаковки, используемый для агрегации коробов, паллет или контейнеров.
- ВСД: ветеринарный сопроводительный документ.
- пВСД: производственный ВСД.
- тВСД: транспортный ВСД.

## 6. Целевая процессная модель

### 6.1. Ведение справочников

Система должна хранить настройки по товарам:

- артикул WMS;
- наименование;
- `GTIN`;
- код ТН ВЭД ЕАЭС;
- код ОКПД2;
- признак необходимости Честного знака;
- признак необходимости Меркурия;
- продуктовая категория Меркурия;
- единица измерения Меркурия;
- упаковка;
- срок годности;
- рецептура или маршрут производства.

Система должна хранить настройки по клиентам:

- принимает ли клиент агрегацию Честного знака;
- режим передачи кодов: `ITEM_CODES`, `SSCC`, `MIXED`;
- требует ли клиент полный состав SSCC в электронном виде;
- требует ли клиент транспортный ВСД;
- EDI/API/email канал передачи документов;
- GLN/ИНН/КПП/площадка получателя.

### 6.2. Приемка сырья

Процесс:

1. Получить входящий документ поставщика.
2. Получить или ввести входящий ВСД Меркурия.
3. Принять сырье на склад по партиям.
4. Сопоставить фактические данные с ВСД:
   - артикул;
   - количество;
   - дата выработки;
   - срок годности;
   - производитель;
   - упаковка;
   - номер партии.
5. При расхождении сформировать статус исключения.
6. После успешной приемки создать сырьевую партию и остаток.

Результат:

- сырье доступно для производства;
- партия сырья связана с входящим ВСД и складским остатком;
- система знает, можно ли использовать сырье в производстве.

### 6.3. Производственное задание

Процесс:

1. Создать производственное задание.
2. Указать готовый артикул, плановое количество, линию, смену, дату.
3. Выбрать рецептуру.
4. Рассчитать плановую потребность сырья. На этом этапе создается мягкая потребность, если партия/паллет еще не выбраны.
5. При передаче задания в производство создать жесткий WMS-резерв на конкретные сырьевые партии/паллеты.
6. Разрешить корректировку фактического вовлечения сырья.

Результат:

- создано задание производства;
- сырье зарезервировано жестким резервом только после выбора конкретной партии/паллеты;
- оператор видит, какие партии сырья будут вовлечены.

### 6.4. Вовлечение сырья

Процесс:

1. Оператор или система выбирает сырьевые партии.
2. Терминал или desktop фиксирует фактическое списание.
3. На каждую сырьевую партию создается запись вовлечения.
4. Система проверяет:
   - сырье не заблокировано;
   - срок годности не истек;
   - партия имеет нужные документы;
   - количество не превышает остаток;
   - партия разрешена к производству.
5. После подтверждения сырье списывается в производство.

Результат:

- создана юридическая и складская связь сырье -> производственная операция;
- данные готовы для `Меркурий RegisterProductionOperation`.

### 6.5. Выпуск готовой продукции

Процесс:

1. Производственная линия выпускает готовую продукцию.
2. Система создает производственную партию.
3. Для партии фиксируются:
   - номер партии;
   - артикул;
   - GTIN;
   - дата/интервал выработки;
   - дата/интервал срока годности;
   - количество;
   - упаковка;
   - линия;
   - смена;
   - вовлеченное сырье.
4. Если требуется Меркурий, система готовит производственную операцию.
5. Если требуется Честный знак, система связывает партию с кодами маркировки.

Результат:

- партия готовой продукции создана;
- партия связана с сырьем;
- партия готова к паллетизации и регистрации во внешних системах.

### 6.5.1. Получение данных выпуска из внешней системы по файловому обмену

При определенной настройке системы выпуск готовой продукции может создаваться не вручную в WMS, а на основании данных, поступающих из внешней производственной системы.

Системная настройка:

- `PRODUCTION_BATCH_SOURCE = MANUAL`: партия создается оператором WMS или через терминал.
- `PRODUCTION_BATCH_SOURCE = FILE_EXCHANGE`: партия создается из входящего JSON-файла.
- `PRODUCTION_BATCH_SOURCE = API`: резерв под будущий прямой API-обмен.

Для режима `FILE_EXCHANGE` внешний контур является источником факта выпуска партии, а WMS отвечает за:

- прием файла;
- валидацию структуры и обязательных полей;
- создание или обновление производственной партии;
- создание паллет и остатков;
- постановку задач на Меркурий и Честный знак;
- журналирование результата импорта.

#### Стандарт файлового обмена

Формат обмена: папка + JSON.

Кодировка: `UTF-8` без BOM.

Формат дат: ISO 8601, например `2026-05-17T13:25:00+05:00`.

Десятичные числа: точка как разделитель.

Один файл должен содержать один факт выпуска производственной операции. Внутри операции допускается одна или несколько партий готовой продукции.

Рекомендуемая структура папок:

```text
exchange/
  production_release/
    in/          -- входящие файлы от внешней системы
    processing/  -- файл перемещен сюда на время обработки
    archive/     -- успешно обработанные файлы
    error/       -- файлы с ошибкой структуры или бизнес-валидации
    out/         -- ответы WMS внешней системе
```

Правило атомарной записи:

1. Внешняя система пишет файл с расширением `.tmp`.
2. После завершения записи переименовывает его в `.json`.
3. WMS обрабатывает только файлы `.json`.
4. После захвата файла WMS перемещает его в `processing/`.
5. После обработки файл перемещается в `archive/` или `error/`.

Рекомендуемый шаблон имени:

```text
prod_release_<YYYYMMDDHH24MISS>_<external_operation_id>.json
```

Пример:

```text
prod_release_20260517132500_SHIFT-2026-05-17-01.json
```

Обязательные поля верхнего уровня:

- `schemaVersion`;
- `messageId`;
- `messageType`;
- `createdAt`;
- `sourceSystem`;
- `externalOperationId`;
- `batches`.

Обязательные поля партии:

- `externalBatchId`;
- `batchNo`;
- `articul`;
- `producedDateFrom`;
- `expiryDateFrom`;
- `quantity`;
- `unitCode`;
- `pallets`.

Обязательные поля паллета:

- `externalPalletId`;
- `palletNo`;
- `uidPallet` или правило генерации `UID_PALLET`;
- `quantity`.

Если `mercuryRequired = true`, должны быть переданы сведения о сырье или ссылки на сырьевые партии, достаточные для формирования производственной операции Меркурия.

#### Ответ WMS внешней системе

После обработки WMS должен создать JSON-ответ в папке `out/`.

Шаблон имени:

```text
prod_release_ack_<messageId>.json
```

Пример успешного ответа:

```json
{
  "schemaVersion": "1.0",
  "messageId": "7d1a3e2e-9d5e-4d2d-a65b-9c4f0e9c1d10",
  "status": "ACCEPTED",
  "processedAt": "2026-05-17T13:26:10+05:00",
  "createdProdBatchIds": [10125],
  "warnings": []
}
```

Пример ответа с ошибкой:

```json
{
  "schemaVersion": "1.0",
  "messageId": "7d1a3e2e-9d5e-4d2d-a65b-9c4f0e9c1d10",
  "status": "REJECTED",
  "processedAt": "2026-05-17T13:26:10+05:00",
  "errors": [
    {
      "code": "PALLET_DUPLICATE",
      "message": "UID_PALLET уже существует",
      "field": "batches[0].pallets[0].uidPallet"
    }
  ]
}
```

#### Идемпотентность

Поле `messageId` является ключом идемпотентности. Повторная загрузка файла с тем же `messageId` не должна создавать дубли партий, паллет, остатков или задач интеграции.

Если содержимое повторного файла отличается от ранее принятого файла с тем же `messageId`, WMS должен отклонить файл со статусом `REJECTED` и ошибкой `IDEMPOTENCY_CONFLICT`.

### 6.6. Маркировка Честного знака

Процесс:

1. Получить или импортировать пул кодов маркировки.
2. Связать коды с GTIN и производственной партией.
3. Нанести коды на единицы товара.
4. Проверить читаемость DataMatrix.
5. Заблокировать выпуск партии, если количество валидных кодов меньше фактического количества.
6. Сформировать документы ввода в оборот или иной требуемый документ ГИС МТ.

Результат:

- каждая маркированная единица имеет код и статус;
- партия готова к агрегации.

### 6.7. Агрегация

Процесс:

1. Собрать единицы в короб или сразу на паллет.
2. Назначить `SSCC` транспортной упаковке.
3. Зафиксировать состав:
   - `SSCC -> CIS`;
   - `SSCC паллета -> SSCC коробов`;
   - вложенность уровней.
4. Отправить сведения об агрегации в Честный знак.
5. Получить статус принятия.
6. Запретить отгрузку по агрегации, если статус не подтвержден.

Результат:

- у паллета есть `SSCC`;
- система знает полный состав агрегации;
- можно отгружать клиентам, принимающим `SSCC`.

### 6.8. Приемка готовой продукции на склад в нескольких паллетах

Процесс:

1. Производственная партия раскладывается на несколько паллет.
2. На каждый паллет создается запись в `RRL_PALLETS`.
3. Каждый паллет получает:
   - `UID_PALLET`;
   - `PROD_BATCH_ID`;
   - количество;
   - дату выработки;
   - срок годности;
   - `SSCC`, если есть агрегация;
   - статус качества;
   - статус Меркурия;
   - статус Честного знака.
4. Остатки создаются в `RRL_REMAINS` с привязкой к паллету.

Результат:

- готовая продукция физически находится на складе;
- несколько паллет связаны с одной производственной партией;
- любой паллет можно проследить до сырья и внешних документов.

### 6.9. Отгрузка клиенту

Процесс:

1. Создать заказ клиента.
2. Подобрать паллеты/короба по FEFO, сроку годности, статусам и требованиям клиента.
3. Проверить, принимает ли клиент агрегацию.
4. Если клиент принимает агрегацию:
   - передать `SSCC`;
   - приложить сведения о производственной партии;
   - передать ВСД/идентификаторы Меркурия.
5. Если клиент не принимает агрегацию:
   - развернуть `SSCC` до списка `CIS`;
   - передать полный список кодов по единицам.
6. Сформировать транспортный ВСД, если требуется.
7. Передать документы клиенту через согласованный канал.

Результат:

- отгрузка не нарушает требования Меркурия и Честного знака;
- клиент получает данные в поддерживаемом им режиме.

### 6.10. Разагрегация и пересборка

Система должна поддерживать:

- вскрытие паллета;
- перемещение части коробов или единиц на другой паллет;
- изменение `SSCC` состава;
- отправку разагрегации/переагрегации в Честный знак;
- запрет отгрузки до подтверждения нового состояния.

## 7. Функциональные требования

### 7.1. Требования к производственным партиям

Система должна:

- создавать производственную партию до или во время выпуска;
- поддерживать выпуск одной партии на нескольких паллетах;
- связывать партию с сырьем;
- хранить статус качества;
- хранить статус Меркурия;
- хранить статус Честного знака;
- запрещать отгрузку партии с критическими ошибками интеграции;
- поддерживать корректировку до юридического закрытия операции.

### 7.2. Требования к сырью

Система должна:

- хранить входящие партии сырья;
- хранить ссылки на входящие ВСД;
- учитывать остаток сырья по партии;
- резервировать сырье под производство;
- списывать сырье только в разрешенном статусе;
- обеспечивать трассировку от готовой партии к сырьевым партиям.

### 7.3. Требования к Меркурию

Система должна:

- хранить параметры хозяйствующего субъекта и производственной площадки;
- хранить входящие `stockEntryUuid` сырья;
- формировать производственную операцию;
- хранить `operationId`;
- хранить идентификаторы производственного ВСД;
- хранить статусы отправки и ошибки;
- поддерживать незавершенное производство, если фактическое сырье или выпуск закрывается позже;
- запрещать повторную неконтролируемую отправку операции с тем же идентификатором.

### 7.4. Требования к Честному знаку

Система должна:

- хранить GTIN товара;
- хранить коды маркировки;
- хранить полные DataMatrix с ограниченным доступом;
- фиксировать нанесение и сканирование кодов;
- контролировать дубли;
- формировать агрегацию;
- хранить `SSCC`;
- хранить вложенность `SSCC -> SSCC -> CIS`;
- хранить статус документов ГИС МТ;
- поддерживать клиентов, принимающих и не принимающих агрегацию.

### 7.5. Требования к клиентским режимам передачи

Для клиента должен быть задан режим:

- `ITEM_CODES`: клиент принимает только полный список кодов маркировки.
- `SSCC`: клиент принимает агрегацию по транспортной упаковке.
- `MIXED`: клиент принимает агрегацию по части товаров, но требует полный список по исключениям.

При отгрузке система должна автоматически выбирать формат передачи.

### 7.6. Требования к файловому обмену выпуска партии

Система должна:

- включать или отключать файловый импорт выпуска через настройку;
- принимать JSON-файлы из согласованной входящей папки;
- обрабатывать только полностью записанные файлы `.json`;
- вести журнал каждого файла;
- проверять JSON-схему и обязательные поля;
- проверять идемпотентность по `messageId`;
- не создавать дубли при повторной загрузке;
- создавать производственные партии, паллеты и остатки из файла;
- связывать импортированные партии с внешней производственной операцией;
- формировать ответный JSON-файл для внешней системы;
- перемещать исходный файл в `archive/` или `error/`;
- показывать оператору ошибки импорта в интерфейсе;
- позволять ручной повтор обработки только после исправления причины ошибки.

Файловый импорт не должен обходить проверки Меркурия, Честного знака, качества, дублей паллет и дублей кодов маркировки.

## 9. Статусы

### 9.1. Статусы производственной партии

- `DRAFT`: партия создана.
- `RAW_RESERVED`: сырье зарезервировано.
- `RAW_USED`: сырье вовлечено.
- `PRODUCED`: выпуск завершен.
- `PALLETIZED`: партия разложена на паллеты.
- `QUALITY_HOLD`: партия заблокирована качеством.
- `READY_FOR_SALE`: партия готова к отгрузке.
- `SHIPPED`: партия отгружена.

### 9.2. Статусы Меркурия

- `NOT_REQUIRED`
- `PENDING`
- `SENT`
- `ACCEPTED`
- `REJECTED`
- `ERROR`
- `MANUAL_REVIEW`

### 9.3. Статусы Честного знака

- `NOT_REQUIRED`
- `CODES_RESERVED`
- `APPLIED`
- `INTRO_SENT`
- `INTRO_ACCEPTED`
- `AGG_SENT`
- `AGG_ACCEPTED`
- `AGG_ERROR`
- `TRANSFER_READY`

### 9.4. Статусы файлового обмена

- `RECEIVED`: файл обнаружен во входящей папке.
- `PROCESSING`: файл захвачен обработчиком.
- `ACCEPTED`: файл успешно обработан.
- `REJECTED`: файл отклонен по бизнес-валидации.
- `ERROR`: техническая ошибка обработки.
- `DUPLICATE`: файл с таким `messageId` уже был принят.
- `IDEMPOTENCY_CONFLICT`: повторный файл с тем же `messageId` отличается по содержимому.

## 10. API и очереди

Новые операции должны выполняться через API-сервер, а не напрямую из новых клиентов в Oracle.

Минимальные домены API:

- `ProductionOrders`
- `RawBatches`
- `ProductionBatches`
- `Palletization`
- `MercuryIntegration`
- `CrptIntegration`
- `Shipments`
- `ClientRegulatoryProfiles`
- `ProductionFileExchange`

Каждая мутация должна иметь:

- `operation_id`;
- `idempotency_key`;
- `resource_key`;
- журнал запроса;
- статус выполнения;
- техническую и бизнес-ошибку.

На первом этапе допустима Oracle-backed очередь через `RRL_REGULATORY_OUTBOX`. RabbitMQ или Kafka подключать после подтверждения нагрузки и сценариев повторной доставки.

Файловый обмен должен быть реализован отдельным worker-процессом или задачей API-сервера. Worker не должен выполнять бизнес-логику напрямую в файловой системе: файл только инициирует команду импорта, а результат фиксируется в Oracle-журнале и ответном JSON.

## 11. Требования к интерфейсам

### 11.1. Desktop

Desktop должен получить формы или вкладки:

- производственные задания;
- сырьевые партии;
- вовлечение сырья;
- производственные партии;
- паллеты выпуска;
- статусы Меркурия;
- статусы Честного знака;
- ошибки интеграции;
- профиль клиента по режиму приемки маркировки.
- журнал файлового импорта выпуска партий;
- ручной повтор обработки файла после исправления ошибки.

### 11.2. Терминал / Android

Терминал должен поддерживать:

- сканирование сырья при вовлечении;
- сканирование DataMatrix готовой продукции;
- сканирование SSCC;
- подтверждение паллетизации;
- контроль ошибок агрегации;
- запрет операции при неправильном статусе.

## 12. Контроль отгрузки клиенту

Перед отгрузкой система должна проверить:

- партия не заблокирована качеством;
- срок годности подходит под требования клиента;
- Меркурий оформлен или не требуется;
- Честный знак оформлен или не требуется;
- если клиент принимает агрегацию, `SSCC` подтвержден;
- если клиент не принимает агрегацию, доступен полный список `CIS`;
- фактический состав паллета соответствует электронному составу.

## 13. Исключения и ручное урегулирование

Система должна иметь журнал исключений:

- расхождение фактического сырья с ВСД;
- нехватка кодов маркировки;
- дубль DataMatrix;
- неверный GTIN;
- поврежденный или нечитаемый код;
- ошибка отправки в Меркурий;
- ошибка отправки в Честный знак;
- клиент не принимает формат передачи;
- фактическая разагрегация без подтверждения во внешней системе.

Для каждого исключения должны храниться:

- тип ошибки;
- объект ошибки;
- оператор;
- дата;
- исходный payload;
- ответ внешней системы;
- решение;
- кто подтвердил ручное решение.

## 14. Нефункциональные требования

- Все внешние отправки должны быть идемпотентными.
- Все документы и payload должны храниться для аудита.
- Полные DataMatrix значения должны быть защищены.
- Операции производства и отгрузки должны быть трассируемыми по `operation_id`.
- Для мутирующих операций Oracle нужен тестовый сценарий на snapshot/disposable schema.
- Новые Android-терминалы не должны получать прямой доступ к Oracle.
- Новая логика должна сохранять совместимость с текущими таблицами `RRL_PALLETS`, `RRL_REMAINS`, `RRL_SBORKA_PALLETS`, `RRL_SBORKA_PALLET_ROWS`.

## 15. MVP

### Этап 1. База прослеживаемости

- Создать таблицы производственных партий.
- Добавить связь `RRL_PALLETS -> PROD_BATCH_ID`.
- Добавить `SSCC` на паллет.
- Добавить клиентский признак приема агрегации.
- Добавить outbox.
- Добавить системную настройку источника выпуска партии: `MANUAL` / `FILE_EXCHANGE` / `API`.
- Добавить журнал файлового обмена `RRL_FILE_EXCHANGE_LOG`.

### Этап 2. Производство без внешней отправки

- Создать производственное задание.
- Зарезервировать сырье.
- Зафиксировать фактическое вовлечение сырья.
- Выпустить производственную партию.
- Поддержать выпуск партии из JSON-файла при настройке `PRODUCTION_BATCH_SOURCE = FILE_EXCHANGE`.
- Разложить партию на несколько паллет.

### Этап 3. Честный знак

- Импорт/получение кодов.
- Привязка кодов к партии.
- Сканирование нанесенных кодов.
- Агрегация в `SSCC`.
- Выбор режима передачи клиенту.

### Этап 4. Меркурий

- Хранение входящих ВСД сырья.
- Формирование производственной операции.
- Хранение пВСД.
- Подготовка транспортного ВСД на отгрузку.

### Этап 5. Отгрузка

- Проверка готовности партии.
- Формирование пакета клиенту:
  - `SSCC` для клиентов, принимающих агрегацию;
  - полный список `CIS` для клиентов без агрегации;
  - данные Меркурия.

## 16. Критерии приемки

1. Можно принять сырье с входящим ВСД и связать его со складским остатком.
2. Можно создать производственную партию готового корма.
3. Можно вовлечь несколько партий сырья в одну производственную партию.
4. Можно разложить одну производственную партию на несколько паллет.
5. Каждый паллет знает свою производственную партию и `SSCC`.
6. Можно увидеть всю цепочку: сырье -> производство -> паллет -> отгрузка -> клиент.
7. Можно отгрузить клиенту, принимающему агрегацию, по `SSCC`.
8. Можно отгрузить клиенту, не принимающему агрегацию, с полным списком кодов.
9. Система не разрешает отгрузку при ошибке Меркурия или Честного знака.
10. Все изменения Oracle отражены в wiki mirror и SQL source.
11. При настройке `PRODUCTION_BATCH_SOURCE = FILE_EXCHANGE` можно создать выпуск партии из JSON-файла в папке обмена.
12. Повторная загрузка файла с тем же `messageId` не создает дубли, а конфликт содержимого отклоняется.
