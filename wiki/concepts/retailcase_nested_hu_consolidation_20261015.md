## Важные незакрытые переходы

1. **ASM → зона консолидации → shipping QC.** CASE_CARRIER_MOVE повышает CASE.CONTENT_VERSION и штатный RRL_STOCK_CASE_BIND_MOVE одновременно повышает PICKED_CONTENT_VERSION текущего PICKED fulfilment, не меняя ST identity; повторное произвольное связывание не требуется. HU attach/detach также использует этот owner. Но ASM_FINAL архив остаётся историческим основанием сборки: RRL_WH_FINAL_SCALE_ADMISSION явно отказывает ASM_FINAL_NOT_SHIPPING_QC. Он не переименовывается в shipping scale_qc. Обычный контроль при упаковке отзывается; исключение — собственный действующий SMALL_HU cargo proof, не ASM_FINAL. Нужна предметная приёмка штатного перемещения законченной ASM CASE с CPT, последующего контроля, упаковки и отгрузки. Реальный1136 был компенсирован; такого смешанного положительного случая не выполняли.
2. **Аппаратный GROSS внешнего HU.** Текущий LOAD принимает только MANUAL_CONFIRMED общую массу/габариты. LOAD_BOX_CORE переносит actual warehouse QC малой CASE; обычный BOX пока MANUAL_CONFIRMED. Rack-picked EA/коробка без actual capture не становится измеренной от наличия дерева. Нужен SHIPPING_GROSS существующего внешнего HU с frozen closure/capture-use, см. [предложение](../../docs/integrations/shipping-gross-proposed.md).
3. **Масса дерева.** Планируемый паспорт хранит observed GROSS отдельно от расчётного expected GROSS. Расчёт только по непосредственным детям: сумма их GROSS + собственная тара/упаковка текущего узла; вложенные gross/tare повторно не суммируются. Если у хотя бы одного ребёнка нет actual основания, результат unknown/estimated с явным источником, не measured. Нынешний LOAD_BOX_CORE защищает exact coverage/от двойного nested-box подсчёта и проверяет нижнюю границу outer≥boxes+outertare; это не новый полноценный рекурсивный паспорт и не доказательство равенства внешнего GROSS.
4. **Температура до консолидации.** Текущий HU_ATTACH/MOVE не содержит продуктового температурного/санитарного допуска консолидации. LOAD_THERMAL пересекает настроенные SKU диапазоны и capability машины, отказывает конфликту и сохраняет ручное подтверждение/версию; sensor/cold-chain этим не доказаны. Неизвестные SKU считаются unconfirmed; когда известных правил0, без confirmation путь возвращает null. Следовательно fail-closed для неизвестной совместимости овощей с охлаждёнными колбасой/сыром/молочкой сейчас НЕ гарантирован. Нужен явный native допуск product/storage zone + сочетание пищевых групп/упаковки и временной выдержки; отсутствие настройки не означает ambient/совместимость. Модель одного пространства машины не заменяет независимые отсеки.
5. **Несколько магазинов на одном внешнем месте.** LOAD может объединять ST одного рейса с разными destination. Но STORE_RECEIPT_READ требует frozen single destination: все active member ST должны относиться к текущему магазину. Приёмка целого внешнего SSCC для route-pallet нескольких магазинов сейчас отказывается; приёмка собственного child-subtree с отделением/версией/пломбой и сохранением остальных магазинов не реализована этим контрактом. Нельзя сравнить полный outer GROSS с частичной выдачей. Нужен native scoped subtree handover/unload/custody/receipt и отдельный исходящий вес фактически выдаваемого child-HU либо иная стратегия приёмки.

## Следующий объём в существующих спринтах

**AK06-F (F1–F6):** reuse HU snapshot/link/version и прежний quantity writer; паспорт массы узла с provenance/basis/domain/capture/measurement-version и отдельными observed/expected/unknown; аппаратный SHIPPING_GROSS внешнего места; сохранение независимых child proofs после допустимого перемещения, действующий shipping-QC переход для ASM без подмены домена. Native температурная/санитарная совместимость и staging-zone admission должны быть проверены до необратимого смешивания, а не только у машины.

**AK06-E:** задания консолидации существующего HU и дочерних потоков в рабочем месте старшего смены/Ганте. Показать недостающих детей, ресурс/зону/док/рейс, unfinished QC, unknown weight, несовместимость, сроки и риск готовности. Статусы берутся у существующих native owners; UI не конструирует складской остаток.

**AK08 mixed acceptance:** один TOP с несколькими вложенными SSCC/internal UID: один ASM CASE, одна rack-picked коробка/EA, два уровня вложенности; move детей→attach→whole-HU task до финальной зоны→актуальный QC детей→outer weighing→load→depart→магазин. Отдельно один магазин против route-pallet нескольких магазинов/child delivery. Проверить cycle/duplicate/leaf-once, изменение версии/распаковку/потерянный proof, unknown mass без fake measurement, direct-child sum без двойной тары, несовместимость/unknown температуры, late/revoked capture, exact retry/restart/concurrent moves, полную rollback/каноническую компенсацию. Новый mixed quantity-case выполняется на изолированной TEST-фикстуре после готовности native переходов, с предварительной проверкой отката и канонической компенсацией.

## Ограничения доказательств и SQL

Это аудит кода и ранее сохранённых случаев, не новая runtime/физическая приёмка. Live native тела сохранены read-only в отчёте; прикладные SELECT к USER_SOURCE ограничены перечисленными пакетами. Нового бизнес-SQL workload не было. Для следующего mixed case владелец inventory должен измерить bounded closure≤200/16, member ST≤200, thermal SKU≤1000, LOAD_BOX_CORE и STORE source snapshot на реальном плане; до измерения не добавлять индекс и не заявлять industrial capacity.

## Уточнение: контроль после упаковки не требует цикла распаковки

Текущий RRL_STOCK_PALLET_QC_CMD принимает **идентификатор существующей СТ**, а не произвольный outer HU. Для PLAN/SCAN/WEIGHT он вызывает SHIPPING_CORE.compile_shipment с p_skip_qc=true, затем записывает текущий результат и CASE CONTROLLED/READY_TO_SHIP. Проверка nested не запрещает QC: она выставляет whole_hu_shipment_required и запрещает автоматическую отдельную отгрузку. Сам запрет SHIPMENT_WHOLE_HU_REQUIRED находится в shipping execute_resolved для root, отличного от HU_SHIP. Это согласуется с прежним software случаем nested CASE12+8 и независимым PLAN/SCAN/WEIGHT из [[../database/retailcase_ni051_case_control_20261010]].

Поэтому уже предусмотрена нециклическая последовательность: **штатное перемещение в допустимую общую ячейку → окончательная упаковка/ATTACH → текущий контроль каждой дочерней СТ без DETACH → целая HU_SHIP/LOAD**. Контроль не меняет состав/CONTENT_VERSION, поэтому сам себя не отзывает. Дальнейшее изменение упаковки/состава требует нового актуального допуска. Новый mixed ASM hardware случай по этой последовательности ещё не выполнялся.

Но consolidated-parent QC, который одним внешним GROSS подтверждает все ST внутри, в данном owner отсутствует: запрос QC сначала ищет RRL_SBORKA_PALLETS.PALLET_UID. Нельзя подставлять outer массу как массу каждой ST либо считать один агрегированный вес доказательством артикула/количества. Когда дочерняя политика требует hardware proof, нужен собственный допустимый proof ребёнка либо отдельно реализованная политика проверки всего frozen closure с распределением **допуска**, а не выдуманной массы. ASM_FINAL и legacy SMALL_HU shipping-QC остаются разными доменами; прямой outer observed capture и его контроль будут отдельным SHIPPING_GROSS инкрементом.

## Уточнение: план консолидации, склады и области прав

Планируемый manifest/dependency graph консолидации может заранее перечислять ожидаемых детей из разных зон/складов. Это **не активное физическое HU дерево**: текущий HU_ATTACH требует общего фактического CELL/WARE, а HU_TASK целого места требует одинаковый FROM/TO WARE. До фактического прибытия нельзя создавать активные связи, менять WARE поля или выдавать будущего ребёнка за находящийся на паллете.

Если «склад овощей» и «склад охлаждённой продукции» — разные зоны одного WARE, нужен native допуск всех товаров и зоны назначения, после реального перемещения — физическая упаковка. Если это разные WARE_ID, нужен существующий canonical межскладской handover/receipt/putaway к общему складу с сохранением origin chain и прав обоих направлений; затем ATTACH. Уже есть bounded межскладская приёмка CONTAINER-only матрёшки с одним STOCK листом (RRL_IW_HU_SOURCE/RRL_IW_HU_REC_CORE; [[../database/retailcase_ni061_nested_receiving_20261012]]) и последующая multi-ST консолидация ([[../database/retailcase_ni061_ordinary_consolidation_20261012]]). Это не доказательство произвольной передачи закрытой ASM CASE с текущим ST/fulfilment: точный интеграционный переход остаётся AK06-F/AK08.

Новые scoped ordinary TASK actor/executor намеренно возвращают0 при HU_CONTENT_VERSION not null, то есть не распространяются автоматически на целое HU. HU_CMD/HU_TASK сейчас проверяют legacy warehouse_task_execute, HU_SHIP — прежние shipping права; HTTP HU endpoints также требуют прежние permissions. Scoped HU/whole-HU-task требует явного owner-bound AK03/F authorizer: current physical warehouse/source+destination, actor/assignee/resource/closure и ревизия прав под native locks. Не обходить native denial Python fallback или GLOBAL/legacy трактовкой.

Для паспорта независимый actual outer GROSS остаётся измеренным даже при неизвестной массе одного ребёнка. В таком случае expected total/reconciliation — UNKNOWN, а не MATCHED и не причина переписать actual. Расчётная версия зависит от непосредственного набора детей, их оснований/версий, собственной тары/упаковки, basis/domain/time; изменение потомка инвалидирует вычисления предков, сохраняя старые наблюдения неизменяемыми. Для нескольких магазинов exact receipt identity должна включать frozen departure + конкретный subtree/handover; outer identifier сам по себе недостаточен.

Дополнительный текущий interWARE аудит уточнил запрет: RRL_IW_HU_SOURCE.stock_uid требует ROOT_CASE_TASK_ID IS NULL и отказывает CASE узлам INTERWARE_STOCK_CONTAINER_ONLY_SOURCE; RRL_STOCK_INTERWARE_REC также отказывает CASE. RRL_IW_HU_REC_CORE восстанавливает CONTAINER metadata/links, не является мостом assembled CASE. Проверка UNIT_SOURCE.assert_case_archive доказывает историческое происхождение, а не перенос currentWARE/fulfilment/тары. Для ASM CASE разных складов AK06-F2 должен расширить существующий межскладской owner с сохранением CASE/ST/tare/origin, а не просто вызвать уже работающий STOCK-only путь. Независимые read-only источники: [interWARE audit](../../reports/retailcase/2026-10-15/nested-hu-audit/).
