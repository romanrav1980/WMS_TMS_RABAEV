# Роли, KPI и восстановление команд — предложение

14.10.2026. Статус: обсуждение с владельцем; это не утверждённый контракт и не выполненная миграция. Основа: [[components/retailcase_roles_initial_review_20261014]], auth.py, main.py, transport_kpi.py, терминальный localJournal и ТЗ ядра проводки.

## Доступ

Сохранить RUSERS/USER_GROUP/RIGHTS и семантику GLOBAL_ADMIN для совместимости. Добавить версионированные роли, связи роль→право, назначения пользователь→роль→область→срок, аудит назначения/отзыва. Должность и подчинение остаются организационными данными, ресурс/квалификация/смена — допуском к исполнению.

Право проверяется в контексте объекта и конкретного назначения. Нельзя независимо объединять права и области разных назначений. Область SELF выводится из проверенной привязки пользователя к исполнителю, а не из client actor. REGION/NETWORK используют явный состав с управляемым изменением; они не следуют автоматически из подчинения. Администратор назначений не может делегировать права/области сверх своего мандата или изменять состав роли. Выбор рабочего места не повышает права.

Целевой владелец политики — модуль platform и согласованный Oracle-контракт. Для критических команд окончательные проверки доступа, автора и версии выполняются внутри транзакционной границы; API и UI используют ту же политику. Legacy-группа сохраняется явным источником совместимости; новая ограниченная роль сама по себе не отнимает старые широкие права. Переход требует mapping фактических полномочий и отдельных решений об отзыве, без автоматической миграции всех пользователей.

В просмотренных /fleet и /summary transport_kpi.py SQL не содержит фильтра по складу пользователя. Это противоречит обобщению исследования Claude о складской области всех KPI; новые сетевые сводки нельзя строить на этом допущении.

## Структурные изменения

1. Каталог бизнес-возможностей: действие, объект, HTTP-команда, эффективное право, область, правила состояния, ключ повтора и результат. Имена legacy-прав сопоставляются явно, без дублирования бизнес-движка.
2. Ролевые рабочие места собираются из этого каталога и существующих функций; директор получает исключения и drill-down, исполнитель — свою очередь и следующее действие.
3. Разделение обязанностей проверяется по совокупным назначениям и автору конкретного объекта. Правила задаются для конкретных процессов, не для любых execute/approve вообще.
4. KPI имеют версии определения, область, период, поля/события источника, правила качества и агрегации. Read model/кэш вводятся по фактической стоимости SQL, не сканированием всех карточек браузером.

## Предлагаемые KPI первой очереди

Общий контракт: период [начало,конец) в timezone площадки/магазина; отдельно деловой день и смена. Итог сети = сумма числителей / сумма знаменателей, не среднее процентов. Ноль знаменателя = «не применимо», неизвестный факт = «нет подтверждения». Для каждого KPI показываются числитель, знаменатель, покрытие достоверными данными, время актуальности и список исходных объектов. План фиксируется версией на согласованном рубеже; поздний перенос/отмена не переписывает историю.

- Готовность склада к отгрузке: число плановых отправок, у которых весь состав прошёл обязательный контроль и готов к погрузке не позже зафиксированного cutoff / все плановые отправки периода. Cutoff из плана рейса с явной нормой погрузки. Только реальные события готовности/контроля; недостающий исторический снимок — GAP.
- Выезд вовремя: фактические выезды не позже утверждённого планового времени плюс согласованный допуск / все отправки, назначенные к выезду в периоде. Неуехавшие после срока остаются в знаменателе. При нулевом допуске ранний выезд отдельно проверяется допустимым earliest departure.
- Доставка вовремя: остановки планового периода с началом разгрузки внутри утверждённого окна / все обязательные остановки с окном периода. Несколько окон — объединение интервалов без склейки перерыва. Отсутствующий факт не считается успехом; показываются отдельно подтверждённые опоздания и неподтверждённые. Выбор основного события ожидает согласования владельца.
- Историческое предложение «доставка полностью» (заменено решением15.10 о стратегии магазина): остановки, где магазин подтвердил каждую строку в базовой единице не меньше согласованного количества / все обязательные остановки периода. Нет компенсации дефицита одного SKU излишком другого; отмены/допуски только с основанием и временем. Временная незавершённая приёмка отдельно, итог после установленного рубежа закрытия.
- OTIF: остановки, одновременно выполнившие условия вовремя и полностью / те же обязательные остановки. Это пересечение фактов, не произведение двух процентов.
- Качество сборки с первого предъявления: CASE с завершённым первым обязательным контролем без несоответствий / CASE с завершённым первым контролем. Не проверенные по политике не считаются проверенными; исправленный CASE не становится успешным первым предъявлением. Отдельно покрытие контроля.
- Точность запаса: ключи SKU/партия/владелец/ячейка/физическая доля с совпадением зафиксированного учётного и подтверждённого пересчитанного количества / завершённые ключи пересчёта. Движения между снимком и пересчётом согласуются протоколом. Порог — профиль измерения товара. Отклонения по SKU показываются в базовых единицах без взаимопогашения и сложения разнородных единиц; денежная оценка только при согласованной стоимости.
- Выработка: решение владельца15.10 — подобранные строки/час и коробки/час, отдельно. Нормо-минуты не выбраны. [[concepts/retailcase_store_app_and_kpi_owner_20261015]] фиксирует также стратегию приёмки и точное плановое окно.
- Затраты доставки: подтверждённая относимая стоимость / подтверждённая доставленная масса, отдельно ₽/остановку. Валюты отдельно без согласованного курса; поздние корректировки имеют период и версию. Нулевой объём не превращается в нулевую себестоимость.

Точные физические поля, доступность истории, рубежи закрытия и стоимость SQL проверяются отдельно перед подключением каждого показателя. Описанные формулы — целевой контракт, не утверждение, что все источники уже реализованы.

## Надёжные команды

Существующий operation_id сохраняется. Перед первой отправкой атомарно сохранить локально ключ, неизменный payload, версию контракта, автора, область и hash. Сервер сам вычисляет канонический hash; клиентский не является доказательством. Повтор одного ключа с иным содержимым отклоняется. Проводка и сохранённый результат фиксируются одной транзакцией.

Состояния клиента: черновик → ожидает отправки → отправлено/результат неизвестен → подтверждено или достоверно отклонено. Принятие HTTP-запроса не означает проводку. После timeout/reload сначала восстановить исход по ключу; отсутствие видимой записи не доказывает отсутствие выполняющегося запроса. Допустим повтор только исходного содержимого под тем же ключом, с ограниченной задержкой и разбросом интервалов. Несколько вкладок координируются, но серверная уникальность остаётся последним барьером.

Изменение expected_version, количества, назначения или другого содержимого — новая команда после определения исхода прежней. Offline-действия показываются как ожидание, не как состоявшийся приход/отбор. Актуальные права, запас и версии проверяет сервер при исполнении; отзыв доступа не обходится локальной очередью. Сохранённый результат читается с отдельной проверкой доступа. Для внешних сообщений/печати необходимы свои квитанции и идентичность попытки; локальная проводка не доказывает внешний эффект.

Не создавать второй количественный writer или универсальную параллельную очередь проводки. Унифицировать восстановление поверх существующих предметных журналов. Хранить минимальную идентичность операции и после архивирования результата; ограниченный TTL не должен разрешать повтор старой команды.

## Предлагаемый порядок

Сначала матрица совместимости и серверный доступ; затем одна роль диспетчера end-to-end; далее единый контракт восстановления для комплектовщика/водителя; KPI подключать по одному с доказанными источниками. Вопросы владельцу: основной момент своевременности доставки, строгость полноты по строкам, знаменатель выработки. Назначения, runtime и Oracle до согласования в этом шаге не менялись.
