# Принципы цифрового двойника склада и транспорта

Дата: 14 октября 2026 года. Статус: принято как рабочая основа для подпроекта [[subprojects/wms_twin_3d]]. Дополняет [[concepts/warehouse_digital_twin_codex_spec]] (визуальная спецификация смены склада) и не заменяет её.

## Что это

Цифровой двойник — живая модель площадки и связанных рейсов. Она показывает, **что происходит**, **почему** и **чем это грозит**: склад (ячейки, задания, люди, техника, ворота) и транспорт (рейсы, окна доков, путь до магазинов) — как одна цепочка.

Ориентиры, на которых проверен подход: WareTrack (React Three Fiber, единый стор и `tick()`), NuriTrack (сеть площадок, «путь одной посылки», ИИ с запасными правилами), WareTwin (единый контракт состояния, FULL+PATCH по WebSocket, локальный запасной движок). Стандарты данных: GS1 EPCIS 2.0 (события цепи поставок), VDA 5050 (флот AGV/AMR), OPC UA (оборудование), ISO 23247 / Asset Administration Shell (рамка двойника), glTF/OpenUSD (3D-ассеты).

## Принципы

### 1. Двойник — проекция, а не второй источник истины

Единственный источник товарного остатка, резервов, состава грузовых мест, рейсов и подтверждённых операций — Oracle и владельцы данных ([[architecture/retailcase_modular_development_contract]]). Двойник читает и отображает. Он не пишет товарные факты и не реализует собственную версию бизнес-правила. Будущие команды из двойника (назначить ворота, приоритет пополнения) идут только через существующие API владельца, с правами и аудитом.

### 2. Состояние отдельно от отображения

Один контракт `TwinState` (типизированный, версионированный). Источник → стор → представления (3D-сцена, панели, таблицы, 2D-карта). Сцена ничего не вычисляет о бизнесе: KPI и статусы считаются из того же состояния, поэтому 3D и панели не расходятся. 3D — одно из представлений, интерфейс можно менять без изменения модели данных.

### 3. Событийная модель: что, где, когда, почему, кто

Каждое изменение — событие с идентификатором, временем, объектом, местом, причиной, исполнителем и источником (в духе EPCIS: what/where/when/why). Состояние = свёртка событий. Live, повтор смены (replay) и «что если» используют один механизм, различается только источник событий.

### 4. Фиксированный такт модели, плавный кадр

Модель шагает с фиксированной частотой (10 Гц, шаг модельного времени ограничен), кадр рисуется на 60 Гц с интерполяцией. Высокая скорость проигрывания не «перепрыгивает» события. Симуляция детерминирована (seed): один seed — одинаковый прогон, это основа воспроизводимых проверок и сравнения сценариев.

### 5. Сквозная идентичность с WMS/TMS

Объекты двойника носят те же идентификаторы, что в системе: ячейка `A01-S023-L1`, СТ (`ST_NUMBER`), рейс (`RRL_TRANSPORT_TASK`), ворота, ТС и госномер, паллета/HU (идентификатор паллеты — не только SSCC). Клик в 3D = переход к реальному документу; поиск работает по тем же ключам.

### 6. Склад и транспорт — одна цепочка

Заказ → волна → СТ → отбор → контроль → выставка к воротам → погрузка → рейс → магазин; обратная ветка: поставка → выгрузка → приёмка → размещение → пополнение. Стык склада и транспорта — **ворота и окно дока**: рейс бронирует окно при планировании, физически занимает ворота при постановке. Риск окна виден заранее (очередь, СТ не готовы), а не после опоздания.

### 7. Объяснимость: причина и цена

Двойник показывает не только статус, но и коллизию с корневой причиной, затронутыми объектами и потерянными минутами: пустая ячейка отбора, затор в проходе, очередь ричтраков, очередь к воротам, машина ждёт СТ, опоздание рейса, низкий заряд. Каждая коллизия видна на сцене, в панели и в журнале событий одновременно.

### 8. Режимы явно маркированы

`LIVE` (данные системы), `SIM` (мок-модель по реальным шагам процесса), `REPLAY` (прошедшая смена), `WHAT-IF` (клон состояния с изменёнными параметрами). Режим всегда виден в интерфейсе; симулированные данные никогда не выдаются за реальные.

### 9. Заменяемые адаптеры и запасной режим

Источник — адаптер с одним интерфейсом: мок-симуляция, WMS/TMS API ТМС, GPS, оборудование (VDA 5050 / OPC UA). Недоступность внешнего источника не ломает интерфейс: показывается статус подключения и последний известный снимок либо симуляция с явной пометкой.

### 10. Бережная нагрузка на Oracle

Двойник не опрашивает операционные таблицы на каждый кадр. Нужна выделенная read model или ограниченные выборки, пакет «полный снимок + изменения», кэш справочников. Новые запросы проходят обычную проверку долгих SQL (`RRL_SQL_SLOW_LOG`, `/api/admin/slow-sql`) с явным решением.

### 11. Производительность сцены

Одинаковые объекты (стойки, ячейки, груз) — InstancedMesh; текст — HTML-оверлеи, а не 3D-шрифт; процедурная low-poly геометрия; качество снижается на слабых GPU. Склад на тысячи ячеек и десятки единиц техники должен работать на офисном ноутбуке.

### 12. Права и аудит

Видимость по складу и роли берётся из действующей модели прав ([[concepts/legacy_rights_model]]). Действия из двойника — только с существующими правами владельца и в журнале аудита.

### 13. ИИ — помощник с запасными правилами

LLM может читать неструктурированный текст (сообщения водителей, заметки контроля, причины возврата) и объяснять ситуацию, но у каждой функции есть путь без ИИ — правила. Ответ ИИ ссылается только на объекты из текущего снимка. Без ключа система полностью работоспособна.

### 14. Доказательность

Ключевые состояния фиксируются скриншотами и отчётами (Playwright), прогоны воспроизводимы по seed. Красивая картинка без связи с данными не считается результатом.

## Что можно менять безопасно

Визуальный стиль, раскладку панелей, набор слоёв, параметры симуляции, новые адаптеры при сохранении `TwinState`.

## Что нельзя ломать

Принцип единственного владельца данных; запрет записи товарных фактов из двойника; сквозные идентификаторы WMS/TMS; явную маркировку режима SIM/LIVE.
