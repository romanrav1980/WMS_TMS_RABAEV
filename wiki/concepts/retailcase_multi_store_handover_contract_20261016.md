# Передача поддерева маршрутной паллеты магазину

Статус **CANCELLED_BY_OWNER, 16.10.2026**. Владелец прямо исключил выдачу частей одной паллеты разным магазинам как управленчески неприменимый сценарий. Не реализовывать handover/custody overlay и UI из этой страницы; не считать их незавершённым спринтом. Ниже сохранён исторический проект контракта, а не действующее требование. Вложенные грузовые места и смешанные способы отбора для одного магазина остаются в объёме; действующий одноадресный поток сохраняется.

## Установленный разрыв

Действующие STORE_RECEIPT, unloading и custody ориентированы на целую LOAD_OPERATION_ID. Native проверяет единый DESTINATION_ADDR; уникальности квитанции/старта/освобождения custody не описывают несколько независимых получателей одной погрузки. Read-only departure_subtree — проекция архива, не передача физического владения. Нельзя закрыть F2 фильтрацией JSON, обходом проверки адреса или заменой уникального индекса без изменения всех владельцев процесса.

Evidence: `reports/retailcase/2026-10-16/route-subtree/before/` —8 источников, mapping/constraints. Native nested manifest уже поддерживает CASE→BOX→PALLET и массу без двойного счёта; это отдельная законченная часть F2, [[../database/retailcase_nested_box_manifest_20261016]].

## Единица передачи

Единица handover — целое физически идентифицируемое поддерево замороженной погрузки. Поле «Идентификатор паллеты» принимает SSCC и внутренний номер. Технический CASE/task ID не заменяет сканируемую метку.

Связь получателя определяется frozen shipments/legs → исходная СТ → DESTINATION_ADDR, а не сегодняшним справочником или введённым оператором адресом. Все листья выдаваемого поддерева должны принадлежать этому магазину. Если внутри узла два получателя, целый узел не выдаётся; выбираются чистые дочерние места. Разделение одного физического листа/коробки требует отдельной физической переупаковки и новых меток; виртуальное распределение одного UID не доказывает такой раздел.

Подтверждение магазина связывается с load + store + handover unit + версией состава. Departure snapshot неизменяем. Текущее владение на машине представляется отдельным overlay/journal; отгруженное дерево не редактируется как складской HU с живым остатком.

## Native владельцы и транзакция

- Добавить immutable handover command/receipt и версию остатка custody погрузки. Одна единица/лист замороженного состава не может принадлежать двум handover; запрет должен учитывать пересечение предок–потомок и frozen allocation identity, а не один текст UID.
- Перед новой командой и cached replay проверять текущего получателя/магазин; shared REV, прежние OP/LOAD/CUSTODY fences и блокировка версии custody. На первом этапе сериализация всей погрузки существующим load fence предпочтительнее нового независимого протокола конкуренции.
- Атомарно фиксировать выбранный состав, переход владения, native store receipt, квитанцию и outbox. Количество уже списано при LOAD: повторного складского SHIP или расхода при handover/приёмке быть не должно.
- Не использовать прежний whole-load receipt owner с подменённым snapshot. Выделить общий механизм записи проверенных строк и использовать его из whole-load и нового handover owner; проверить все consumers до переключения.
- Финальный whole-load custody release возможен только после разрешения всех единиц. Приёмка одного магазина оставляет другие поддеревья и custody на машине. Отказы/повреждения/возвраты требуют явного дальнейшего владельца, а не автоматического освобождения всего груза.

Новая операция имеет собственный operation_id, immutable body и expected custody/handover version. Потерянный ответ повторяется неизменно; изменённый состав под прежним ключом — конфликт. Тайм-аут не разрешает создать вторую передачу или удалить durable intent.

## Вес и приложение магазина

Весовая приёмка использует frozen измерение именно выдаваемой CASE/BOX либо новый подтверждённый замер единицы передачи. Брутто внешней паллеты не сравнивается с частью груза. Если подходящего измерения нет, система требует взвешивания/разрешённой стратегии, а не вычисляет «фактический вес» из нормы. Manual origin и электронный capture различаются; существующий шлюз сохраняется.

Магазин сканирует внешний или свой дочерний идентификатор. Ответ показывает только его единицы, строки и разрешённые действия; чужие адреса/состав не попадают в preview, ошибки или локальный журнал. Поэтапно: найти поставку → выбрать/сканировать своё место → разгрузка → вес/пересчёт/сканирование → подтверждение и квитанция. Остаток других магазинов не изображается уже принятым.

KPI доставки агрегируется по load + store: FULL только после подтверждения всех ожидаемых этому магазину единиц без расхождений. Частичная приёмка одной коробки не даёт FULL всей поставке. Плановое окно/прибытие уже имеют адрес магазина; receipt aggregation нужно перевести на тот же ключ без дублирования знаменателя.

## Порядок реализации и gate

1. Схема handover/custody overlay и frozen leaf/store mapping; миграция с точными guards и совместимостью старых whole-load receipts.
2. Native prepare/confirm/replay/revoke и отрицательные проверки пересечения поддеревьев; одновременно новые scoped reads магазина и обход всех consumers: unloading, receipt, custody, returns, KPI, audit/replay.
3. UI после API READY, с прежним сканированием/ручным весом/durable intent и обычной URL-справкой. Не публиковать статьи через API без отдельного основания.
4. Свежая паллета минимум двух магазинов, ASM + BOX/EA, два уровня. Первый магазин принимает только свой child; второй остаётся на машине. Затем второй принимает остаток. Итоги равны frozen количеству, повторного списания нет, whole custody закрывается в конце.
5. Гонки outer-vs-child и два подтверждения одной ветви; rollback, exact retry после потери ответа, revoke до replay, чужой магазин, несовместимый вес/состав. По каждому meaningful кейсу — slow SQL decision и source readback. TEST evidence не является аппаратным пилотом.
