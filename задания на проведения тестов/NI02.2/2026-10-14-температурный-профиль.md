# NI02.2 — температурный профиль и совместимость
Исполнитель: локальная Qwen. Авторские проверки не заменяют независимый результат. Исходники: wiki/database/nicora_ni022_vehicle_temperature_20261014.md; report34; план55.

1. Проверить V2 укладку: диапазоны2…4 и15…20 разделены;2…4 и3…6 смешиваются с итогом3…4; известный/неизвестный разделены; min>max отказ. Точные количества/коробки/масса/объём сохранены.
2. Проверить старый1118 savedV1 повтор/resolve без перерасчёта и без новых ST/FF. Не запускать case1118 заново.
3. На собственной отдельной машине проверить профиль: оба предела, отрицательные/дробные числа, min≤max; один предел/null/число вместо строки/NaN/лишнее поле отклоняются. Старый10-полевой запрос не приобретает температур по умолчанию.
4. Два отправителя одного запроса создают одну версию. Изменённое тело того же ID отказ; staleversion/base отказ; outerrollback возвращает прежний head. Нельзя удалять историю. Не пересоздавать fixture1152/10100.
5. Preflight: возможности−20.125…6.25 и товар2…8 дают2…6.25; товар10…20 несовместим; неизвестный SKU/профиль/BASE_CHANGED не подтверждают температуру. Measurement и operational admission остаются false.
6. UI: desktop/mobile, сохранение доPOST, неизвестный результат и точный повтор; другой пользователь/вкладка не удаляет чужой новый запрос. Текущий GET содержит реальную версию и основание.
7. Не выдать эту часть за физическое измерение, сенсорный контроль или завершённый NI02.2. Погрузка/выезд с температурой остаются следующим изменением.

Перед записью использовать отдельные идентификаторы и выделенный dev RABAEV; protected987 P20/H20 и сохранённые кейсы не менять. Отчёт/скриншоты — reports/nicora/2026-10-13, с фактической датой14Oct. Долгие SQL требуют решения по ограничению/переписыванию/индексу либо обоснованного backlog; массовые нагрузки не нужны.
