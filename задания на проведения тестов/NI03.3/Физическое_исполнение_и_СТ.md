# Qwen: фактическое исполнение заказа и подготовленная СТ
Независимое задание; исполнение не заявлено. RABAEV/orcl, только собственные документы/запас. Сохранить журналы; очистить свои P/H через root.

1. Подготовить СТ существующим механизмом: PLANNED и physical progress0. Назначение рейса не означает PICKED.
2. Подтвердить CASE в root, закрыть носитель: /execution показывает точный BASE факт; bind к существующей совпадающей ST → PICKED с составом, версией, автором/временем.
3. Exact replay → одно SHIPMENT_BOUND; иная версия/носитель/СТ отвергнуты. Несовпадающая укладка или чужой заказ не получают PICKED.
4. Состав нескольких SKU с одинаковой BASE единицей может иметь общий scalar; разные BASE единицы сохраняются отдельно, без суммы штуки+кг.
5. CASE_CARRIER_RETURN: current fulfillment снова PLANNED, current progress0, physical movement и historical SHIPMENT_BOUND сохраняются. Отгружённый носитель нельзя таким возвратом вернуть.
6. Частичный CASE, approved shortage и cancelled task: фактические количества/причины/remaining корректны. Не вычитать HARD дважды; несколько маркировочных профилей одной physical unit не увеличивают факт.
7. FULL_PALLET partial task family: использовать суммарный BASE physical movement; prepared ST и голый legacy FACT без physical evidence не засчитывать.
8. Нет точной конверсии UOM, округление, слишком большой заказ: явный отказ/REQUIRES_UOM, без угаданной единицы/числа.
Проверить operator UI и API rights, связать IDs/evidence с выводом. После meaningful cases записать longest SQL и конкретное решение; не запускать массовую нагрузку автоматически.
